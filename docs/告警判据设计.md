# 排放超标告警 · 判据设计方案

> **分支**：`feat/cems-12points-hj212`
> **日期**：2026-10-01　**状态**：**方案，未实现**（等决策后再动手）
> **范围**：本文只定"判什么、判多久、事件怎么起止、结果存哪、怎么通知、怎么验证"。
> ⚠️ **不含实现代码**；**不改** `src/common/points.py` 契约字段，**不改**接入层既有拒收逻辑，**不新建**折算列。
> **依赖事实**：`src/common/points.py`（契约）、`src/platform/subscriber_to_td.py`（折算出口）、
> `src/device/simulator.py`（尖峰演练源）、TDengine `3.3.6.13`（实测）。

---

## 1. 要解决什么

**现在链路能造出"超限值"，但没有任何一处去判定它、记录它、通知它。**
数据只做到"入库"：超限的数值混在正常曲线里，没人知道它发生过、持续多久、峰值多少、恢复没有。

这不是假设问题，是**已在库里发生、可复现**的事实（2026-10-01 实测，最近 60 分钟 685 条样本，5 秒轮询）：

| 测点 | 折算值均值（限值） | 折算值最大 | 瞬时越限条数 | 连续 ≥3 条(15s) 的段 | 连续 ≥12 条(60s) 的段 | 最长连续段 |
|---|---|---|---|---|---|---|
| 颗粒物 dust | 3.21（5） | **5.00**（正好等于限值） | 0 条 | 0 | 0 | 0 |
| SO2 | 21.17（35） | 32.86 | 0 条 | 0 | 0 | 0 |
| NOx | 36.01（50） | **55.13** | **62 条（9.1%）** | **6** | **2** | **14 条（70 秒）** |

同一小时的口径差异也已经在库里：历史某个小时 NOx **标干均值 40.02（< 50，按标干判达标）**，
而**折算均值 59.61（> 50，按折算判超标）**——这是"判折算"的直接证据（§3.1）。

结论：**链路已具备触发条件，缺的是判据、事件记录与通知。** 本文给方案。

---

## 2. 候选方案

三条路线：**甲** 库侧流式计算、**乙** 接入层逐条判（推荐）、**丙** 接入层只算折算 + 独立告警服务。
甲、乙为必答路线，丙作为演进方向一并列出。

### 2.1 方案甲：库侧流式计算（TDengine `CREATE STREAM`）

**实测结论先摆出来**：本机 `3.3.6.13` 上 `CREATE STREAM` **能建成、也真的算了**
（`INTERVAL(10s)` + `TRIGGER AT_ONCE`，70 秒内目标表产出 7 行窗口结果），
但它有 4 个**实测/文档层面的硬约束**，直接决定这个方案的代价：
目标必须是超级表、流名不能带库名、本环境**没有 snode（无检查点）**、官方文档把流式计算标为**企业版**。

#### 1) 怎么做

```
数据流：cems.cems_data（超级表，已有 9 个物理量列）
          │  （由 TDengine 内部的流计算引擎在写入时触发，不需要任何外部进程）
          ▼
      STREAM：窗口聚合 + 表达式判定（折算公式必须写进 SQL）
          │
          ▼
      告警结果超级表 cems_alarm_result（窗口级结论：越限样本数 / 折算均值 / 折算最大值）
          │
          ├─ 通知：流只会"写表"，不会发消息 → 必须另有一个通知器轮询这张表
          └─ 事件状态机（开始/结束/去重）：流表达不了 → 仍然要在表外做折叠
```

建流语句（实测可用的形式，`USE` 必须在前，**流名不能带库名前缀**）：

```sql
USE cems;
CREATE STREAM alarm_nox_1m TRIGGER AT_ONCE INTO cems_alarm_result AS
SELECT _wstart,
       COUNT(*)                                              AS n,
       SUM(CASE WHEN nox * (21-6)/(21-o2) > 50 THEN 1 ELSE 0 END) AS over_n,
       AVG(nox * (21-6)/(21-o2))                             AS conv_mean,
       MAX(nox * (21-6)/(21-o2))                             AS conv_max
FROM cems_data INTERVAL(1m);
```

#### 2) 优点与代价

| 维度 | 评价 |
|---|---|
| 延迟 | 低。`TRIGGER AT_ONCE` 写入即算（实测 10s 窗口、70 秒出 7 行）；默认 `WINDOW_CLOSE` 要等窗口关闭 |
| 复杂度 | **高**。判定逻辑变成 SQL 文本；公式与契约分离；窗口语义（`INTERVAL/SLIDING/WATERMARK/TRIGGER`）需要额外知识 |
| 可观测性 | 好。`SHOW STREAMS`（返回 `stream_name/status/message`）+ `information_schema.ins_streams`（含 `status/trigger/checkpoint_backup/message`，实测 `status=ready`） |
| 对现有链路的影响 | **低但脆弱**：不碰接入层，不加进程；但**目标必须是超级表**，且 DDL 不能带库名（见下） |
| 部署依赖 | ⚠️ **`SHOW SNODES` = 0 行**，`taos.cfg` 里没有 `snodeAddress` / `checkpointBackupDir`；官方文档要求 3.3.2.1 起必须创建 snode 才能生成 checkpoint，否则"可能导致后续的计算结果产生错误" → **当前环境是"无检查点"跑流计算** |
| 版本可用性 | ⚠️ 官方 3.3.3 中文文档把"流式计算"标注为 **TDengine 企业版**；当前是 Docker 社区镜像。实测能建能算，但**特性可用性没有任何版本承诺**，换镜像/升级就可能失效 |

**已实测的两个语法约束（做这个方案前必须先知道）**：

```sql
-- ✗ 流名带库名 → 语法错误（实测）
CREATE STREAM cems.s1 INTO cems_alarm_result AS SELECT ...;
--   DB error: syntax error near ".s1 into cems_alarm_result as select ..." [0x80002600]

-- ✗ 目标表是普通表 → 报错（实测）
--   DB error: Stream can only be written to super table [0x80002645]

-- ✓ 正确：先 USE，再建；目标必须是超级表
USE cems; CREATE STREAM s1 INTO cems_alarm_result AS SELECT ...;
```

⚠️ 影响实现的连带问题：接入层现有 `TdWriter` 的写法是"每条 SQL 显式带库名前缀"
（REST 无状态、`USE` 不生效），而 `CREATE STREAM` **恰恰不能带库名**。
从 Python 建流只能改走 taosAdapter 的库级 REST 路径 `POST /rest/sql/<db>`（**本项目未验证**），
或落到运维脚本/CLI 建流、应用只读结果表。**这一点必须先定，否则接入层改不动。**

#### 3) 失败模式

| 类型 | 怎么产生 | 怎么防 |
|---|---|---|
| **漏报** | ① 数据流中断 → 事件时间不推进 → 窗口永不关闭 → 该窗口的结论永远不产出（官方文档明示）② 流任务自身出错后**只把状态写进 `status/message`，不会告警**，外部不知道它停了 ③ 无 snode、无 checkpoint → 重启/恢复后结果可能出错 ④ `IGNORE EXPIRED 1`（默认）会**直接丢弃**迟到数据 ⑤ 新建的流默认**不处理建流前的历史数据**（要 `FILL_HISTORY 1`） | 窗口判定一律用 `TRIGGER MAX_DELAY` 或 `AT_ONCE` 而不是默认 `WINDOW_CLOSE`；把 `SHOW STREAMS` 的 `status/message` 纳入巡检（非 `ready` 即告警）；补 `snode`；迟到数据要么容忍（`IGNORE EXPIRED 0`）要么明确接受丢；历史数据不追（见 §3.3 起算边界） |
| **误报** | ① **折算公式在 SQL 里重写**，与 `points.py` 会漂 ② SQL 没有 `nan` 语义：`o2 >= 21` 时分母 ≤ 0，算式给出的是**负数**而不是"无效"，负数进 `SUM/AVG` 直接把统计带偏（实测：库里 56 条 `o2>=21` 的样本；某个历史小时 NOx 折算均值因此算成 **-50.65**）③ 单点瞬时越限直接产告警 → 尖峰一次能产几十条 | 折算**必须**在 SQL 里显式复刻 `o2 >= 21` 的无效判定（`CASE WHEN o2 >= 21 THEN NULL ELSE ... END`）并保证聚合忽略 NULL；判定用"滑窗计数"而不是单点（见 §3.2）；`points.py` 改公式时必须同步改流 SQL——这一条靠流程保证，**是永久性负债** |
| **重复告警** | ① `AT_ONCE` 会在窗口关闭前**反复重算同一窗口**并重复写同一 `_wstart` 行（实测同一 `_wstart` 多次出现）② 下游通知器轮询结果表，每次都会看到"仍然越限"的那一行 | 结果表按窗口起点 `_wstart` 建子表/行（同 ts 覆盖，天然幂等）；通知器必须**按窗口起点去重**，并只对"首次出现"或"级别变化"发通知 |

#### 4) 需要新增的表/字段/环境变量

| 项 | 内容 |
|---|---|
| 新超级表 | `cems.cems_alarm_result(ts TIMESTAMP, point NCHAR(16), n INT, over_n INT, conv_mean FLOAT, conv_max FLOAT, limit_value FLOAT, verdict NCHAR(12)) TAGS(plant, device, judge_type)` — 目标必须是超级表（实测约束） |
| 环境变量 | `ALARM_STREAM_ENABLE`、`ALARM_STREAM_TRIGGER`（`AT_ONCE`/`MAX_DELAY`）、`ALARM_STREAM_INTERVAL`；建流语句本身需要**固化进运维脚本**（因为不能带库名，无法沿用接入层的 SQL 拼法） |
| 运维依赖 | snode 配置（`snodeAddress`、`checkpointBackupDir`、容器内 `rsync` 已存在）+ `CREATE SNODE ON DNODE 1`；以及流任务状态巡检 |

#### 5) 怎么验证它真的工作（可复现）

```powershell
# 0) 前置：确认数据在流
docker exec tdengine taos -s "SELECT COUNT(*) FROM cems.cems_data"      # 两次间隔 30s，应增长约 6

# 1) 建探针库与流（TRIGGER AT_ONCE 才能几十秒内看到结果）
docker exec tdengine taos -s "CREATE DATABASE IF NOT EXISTS cems_alarm_probe"
docker exec tdengine taos -s "USE cems_alarm_probe; CREATE STREAM p1 TRIGGER AT_ONCE INTO probe_st AS SELECT _wstart, COUNT(*), AVG(nox*(21-6)/(21-o2)) FROM cems.cems_data INTERVAL(10s);"
#   期望：Create OK, 0 row(s) affected

# 2) 看流状态
docker exec tdengine taos -s "SELECT status, message, checkpoint_backup FROM information_schema.ins_streams"
#   实测：status=ready, checkpoint_backup=none  ← none 就是"无检查点"的证据

# 3) 等 70 秒，看目标表是否真的被写入
Start-Sleep -Seconds 70
docker exec tdengine taos -s "SELECT COUNT(*) FROM cems_alarm_probe.probe_st"
#   实测：7 行（10s 窗口 + 5s 采样 → 每窗 1~2 条）；0 行 = 流没算，按失败处理
docker exec tdengine taos -s "SELECT * FROM cems_alarm_probe.probe_st LIMIT 5"
#   实测列：_wstart / count(*) / avg(nox*(21-6)/(21-o2)) / group_id

# 4) 反向用例（必须能复现这些报错，否则说明环境变了，方案要重新评估）
docker exec tdengine taos -s "CREATE STREAM cems_alarm_probe.p2 INTO cems_alarm_probe.probe_st AS SELECT ..."
#   期望：syntax error（流名不能带库名）
# 目标为普通表 → 期望：Stream can only be written to super table

# 5) 断流验证（证明 WINDOW_CLOSE 会漏）
docker compose stop gateway
docker exec tdengine taos -s "SELECT COUNT(*) FROM cems_alarm_probe.probe_st"   # WINDOW_CLOSE 下应停止增长
docker compose start gateway

# 6) 清理（必须做，别留探针库/流）
docker exec tdengine taos -s "USE cems_alarm_probe; DROP STREAM IF EXISTS p1;"
docker exec tdengine taos -s "DROP DATABASE IF EXISTS cems_alarm_probe"
docker exec tdengine taos -s "SHOW STREAMS"    # 期望 0 row(s)
```

#### 6) 评价

**不推荐作为一期方案。** 它能跑，但要接受三个长期负债：
**公式在 SQL 里重写**（与契约漂移）、**无 snode/无检查点**（结果可靠性无保障）、
**企业版特性归属**（可用性无承诺）；并且它**根本表达不了"一个事件只告警一次"**——
窗口聚合只是素材，事件状态机仍然要在表外实现。既然状态机无论如何都要写，把判定也放在应用侧反而更省。

### 2.2 方案乙：接入层逐条判（**推荐**）

#### 1) 怎么做

```
MQTT 报文（含 9 个测点 + 同一时间戳）
   ▼
on_message → parse_payload()（既有：拒收逻辑不动）
   ▼
writer.write()（既有：入库）
   ▼  ★ 仅当入库成功后
record_reference(ts, values)  ← 既有函数，返回本条的折算值（dust/so2/nox）
   ▼  ★ 新增一处调用：把"已经算好的折算值"喂给判据（不重算、不再调公式）
alarm_judge.on_sample(ts, values, references)
   ├─ 滑窗判定（越限计数）→ 事件状态机（START / REMIND / END）
   ├─ 无效样本判定（o2 >= 21 或折算为 nan）→ "数据无效"事件
   ├─ 落库：append-only 写入 cems.cems_alarm_event（按 (point, judge_type) 子表）
   └─ 通知：结构化日志（一期）+ 可选 MQTT 主题 cems/plant1/alarm（QoS1）
   ▼
小时结算（独立定时任务，每小时跑一次）
   └─ 读 cems_data 该小时的原始行 → 用 points.to_reference_o2() 逐条重算 → 覆盖率判定 → 写 cems.cems_hourly_verdict
```

**为什么必须判折算、且只能这样判**：折算值在接入层**按报文算一次**就已经存在（`reference_values()`），
它与该条的 O2 **同帧同时刻**，"同一时刻的 O2"这个问题天然不成立——不需要任何时间对齐。
判定直接吃这份 `references`，全链路折算调用点仍然只有一处。

#### 2) 优点与代价

| 维度 | 评价 |
|---|---|
| 延迟 | = 一个报文（≤5s，与轮询同周期）。比流计算慢不到一个窗口 |
| 复杂度 | **低**。新增 1 个判据模块 + 1 次调用；判定是普通 Python，可单测、可离线回放 |
| 可观测性 | 好。事件表可查、日志有 `event_id/point/phase/折算值/限值`、可加计数（本次会话已判/已发/无效样本数） |
| 对现有链路的影响 | 小且可控：只在 `writer.write()` 成功后追加一次调用；**不改**拒收逻辑、**不改**契约、**不加**服务、**不加**依赖 |
| 公式唯一真源 | ✅ 直接复用 `reference_values()` / `to_reference_o2()`，**不存在第二份公式**；`o2>=21 → nan` 的契约语义天然生效 |
| 代价 | ① 进程内状态（滑窗/OPEN 事件）重启会丢 → 必须落库并可恢复 ② 小时均值要另做结算任务（因为折算值不落库，必须用**同一个契约函数**重算，不能在 SQL 里重写） |

#### 3) 失败模式

| 类型 | 怎么产生 | 怎么防 |
|---|---|---|
| **漏报** | ① 判据用"严格连续 N 条"：网关/订阅端一重启就断链，连续段被打断 → 事件被判没了（本项目 5s 一条，重启窗口实测约 5 秒，直接断一条就是断一段）② 只判"小时均值"：实测反证——最近一小时 NOx 瞬时越限 62 条、最长连续 70 秒，但**折算均值 36.01 < 50**，只判小时均值这一小时**一条告警都不会有** ③ 判据只覆盖入库成功的数据：写入失败的那几条不会被判（可接受，但要在报告里说明"未入库即未判定"）④ 订阅端离线期间靠 EMQX 持久会话补投，若会话过期（默认 24h）则这段数据永久缺失 → 那段时间无判定也无"数据不足"事件 | 判据用**滑窗计数**而不是严格连续（窗口 M 条里至少 N 条越限，允许中间缺样本，见 §3.2）；**瞬时事件与小时均值事件两条判据并行**，互不替代；把"上游静默"单独作为"数据不足"事件（§3.4）而不是当成达标；会话过期风险沿用现有 `MQTT_CLEAN_SESSION=0` + 24h 会话配置，并把"补投了多少条/是否恢复旧会话"记进日志 |
| **误报** | ① 单点瞬时越限就发 → 实测 NOx 一小时 62 条，直接变成告警风暴（等于没有告警）② 尖峰是**仿真造出来的真实形状**（三角包络 ±2 分钟），判定阈值定得太低就会把正常波动当事故事件 ③ 边界取值：实测 dust 折算最大值**正好 5.00**，用 `>=` 会把"正好达标"判成超标 | 用滑窗 N/M 参数把事件率压到"每小时个位数"（实测 N=3/M=6 时 NOx 一小时 6 个事件段）；**统一用 `points.over_limit()`（`>` 语义）**，把"正好等于限值"判为达标，并在文档里写死这条口径；阈值全部走环境变量，便于用 `SIM_SPIKE_ENABLE=0/1` 做 A/B 对照 |
| **重复告警** | ① **MQTT 持久会话会补投**：QoS1 + `MQTT_CLEAN_SESSION=0` + 24h 会话 → 订阅端重连时 broker 会把离线期间的报文**重投一遍**，同一时间戳的样本会被判两次 ② 通知器重试/重启后重复发 ③ 事件仍然 OPEN 期间每来一条越限样本就再发一次 | 写入用 **`(子表, ts)` 天然覆盖语义**做幂等：子表名 = `plant_device_point_judgetype`，START 记录的 `ts` = 该事件首次越限样本的时间戳 → **重投同一报文只会覆盖同一行，不会新增事件**；状态机保证"同一 `(point, judge_type)` 同时只允许一个 OPEN 事件"；通知按 `event_id + phase` 幂等键，重复通知由下游按 `event_id` 去重（选择 **at-least-once**：宁可重复通知，不可漏报） |

#### 4) 需要新增的表/字段/环境变量

| 项 | 内容 |
|---|---|
| 新超级表 `cems.cems_alarm_event` | 列：`ts`（事件/阶段时间）、`event_id`、`phase`（`start`/`remind`/`end`/`invalid`）、`converted`（**判定当时的折算值快照**）、`raw_value`（标干值）、`o2`、`limit_value`、`o2_reference`、`over_samples`、`window_seconds`、`judge_version`；TAGS：`plant`、`device`、`point`、`judge_type`（`instant`/`hourly`）。子表名 `plant_device_point_judgetype`（最多 3×2=6 张） |
| 新超级表 `cems.cems_hourly_verdict` | 列：`ts`（小时起点）、`n_total`、`n_valid`、`n_invalid`、`coverage`、`conv_mean`、`conv_max`、`limit_value`、`verdict`（`ok`/`over`/`insufficient`/`invalid`）；TAGS：`plant`、`device`、`point`。重复结算写同一 `ts` → 覆盖，可安全重算 |
| 环境变量 | `ALARM_ENABLE=1`、`ALARM_WINDOW_SAMPLES=6`、`ALARM_MIN_OVER_SAMPLES=3`、`ALARM_RECOVER_RATIO=0.95`、`ALARM_RECOVER_SAMPLES=6`、`ALARM_REMIND_SECONDS=1800`、`ALARM_HOURLY_ENABLE=1`、`ALARM_COVERAGE_MIN=0.75`、`ALARM_INVALID_RATIO_MAX=0.10`、`ALARM_TOPIC=cems/plant1/alarm`（是否发 MQTT 由开关控制）、`ALARM_EVENT_STABLE=cems_alarm_event` |
| 明确**不加** | 不改 `points.py`；不给 `cems_data` 加折算列；不改拒收逻辑；不引入新依赖 |
| 一个必须表态的取舍 | 事件表里的 `converted` 是"判定当时的快照"。它与"折算不落库"不冲突（`cems_data` 仍然只有 9 个物理量列），但**它是导出量的历史副本**。若要彻底不存，替代做法是只存 `raw_value/o2/limit_value/o2_reference`，由下游用同一函数重算——代价是"当时判了什么"不可直接审计。**建议存快照**（并带 `judge_version`、`o2_reference`，公式变更后仍能解释历史结论） |

#### 5) 怎么验证它真的工作（可复现）

```
V1 离线回放（不需要 Docker，最先做）
   把一段固定样本序列喂给判据函数，序列必须包含 5 个边界用例：
     (a) 折算值 = 限值（应判达标）        → 断言 0 个事件
     (b) 折算值 > 限值 连续 3 条           → 断言 恰好 1 个 START
     (c) 越限后恢复 < 限值×0.95 连续 6 条  → 断言 恰好 1 个 END，且 duration 正确
     (d) 同一批样本重放两次（模拟重投）    → 断言事件表行数不变、无第二个 START
     (e) o2 = 21 / 25                      → 断言不产"超标"事件，产 1 条 invalid 事件

V2 线上触发（造事件）
   docker compose up -d device 后，临时把尖峰概率调高：
     $env:SIM_SPIKE_PROB="0.02"; docker compose up -d device     # 期望：NOx 折算越限明显变密
   等待 ≥10 分钟，然后：
     docker exec tdengine taos -s "SELECT ts, point, phase, converted, limit_value FROM cems.cems_alarm_event ORDER BY ts DESC LIMIT 20"
   期望：出现 phase=start 的行，且 converted > limit_value；start/end 成对出现
   对照实验：SIM_SPIKE_ENABLE=0 重启设备 → 同样时长内 start 行数应为 0

V3 去重（重投）
   用同一个 MQTT client 把**同一条报文**（同时间戳）重发 3 次：
     mosquitto_pub -t cems/plant1/data -q 1 -m "<原样报文>"   （或用项目内的 paho 单行脚本）
   期望：cems_alarm_event 里对应 (子表, ts) 仍然只有 1 行

V4 重启恢复
   事件 OPEN 期间 `docker restart cems-subscriber`：
   期望：重启后不产生第二个 START；该事件最终仍能正常 END（状态从库里折叠恢复）

V5 样本不足的小时
   造一个低覆盖小时（例如停网关 50 分钟）：
   期望：cems_hourly_verdict 里该小时 verdict=insufficient，且**不出现** verdict=ok

V6 时间基准断言
   docker exec tdengine taos -s "SELECT NOW"        # CLI 基准
   REST: POST /rest/sql  {"SELECT NOW"}             # REST 基准（与上面差 8 小时，见 §3.6）
   期望：事件表里的 ts、日志里的 ts、REST 查询里的 ts 三者同基准；跨基准比较必须显式换算
```

#### 6) 评价

**推荐。** 理由三条：
1. **公式只有一份**：判定直接吃 `reference_values()` 已有的结果，`o2>=21 → nan` 的契约语义天然生效，
   不会出现"SQL 里算 −50.65"这种事；
2. **延迟与成本最优**：判定成本是每帧 3 次乘除，落库一次写；不新增服务、不依赖企业版特性；
3. **失败模式可测**：判定是纯函数式的一段 Python，可以离线回放、可以注入重投、可以断言事件数——
   这正是"告警这件事必须能被验证"的前提。

代价是"进程内状态要落库恢复"和"小时结算要单独跑"，这两件都在 §2.2.4/§2.2.5 里给了做法。

### 2.3 方案丙：接入层只算折算 + 独立告警服务（演进方向）

#### 1) 怎么做
接入层在算完折算值后，把**判定输入**再发一条 MQTT 消息（新主题 `cems/plant1/judge`，
内容 = ts + 折算值 + 标干值 + O2 + 限值），由一个**独立告警服务**订阅、判定、去重、通知、落库。

#### 2) 优点与代价
| 维度 | 评价 |
|---|---|
| 优点 | 判定与入库彻底解耦：告警服务可独立重启/升级/回放；接入层保持"只管入库"的单一职责；将来通知渠道变多、或要多实例部署时更顺 |
| 代价 | 多一个进程 + 一个新主题 + 一整套投递语义（QoS1 重复、乱序、积压）；判定输入本身也可能丢（EMQX 保留期 24h，超出了就永久缺）；调试链路变长（一条报文要跨两个服务才能追完） |

#### 3) 失败模式
| 类型 | 怎么产生 | 怎么防 |
|---|---|---|
| 漏报 | 判定输入主题丢消息/积压到会话过期 | 与 V3 相同的幂等键 + 积压深度监控；一旦积压，告警延迟无上界 |
| 误报 | 与乙相同（判据一样），另加"乱序"：晚到的判定输入可能把已 END 的事件又推回 OPEN | 事件状态机带时间单调性检查：`ts` 早于当前事件 `end_ts` 的样本只做幂等覆盖，不改状态 |
| 重复告警 | QoS1 重投 + 消费进度回退（at-least-once） | `(event_id, phase)` 幂等键；事件表 `(子表, ts)` 覆盖 |

#### 4) 新增表/字段/环境变量
同方案乙（事件表、小时结论表、`ALARM_*`），另加 `ALARM_JUDGE_TOPIC`、`ALARM_JUDGE_QOS`、
告警服务的 `MQTT_CLIENT_ID`（必须固定，否则持久会话失效）。

#### 5) 怎么验证
在方案乙的 V1–V6 基础上加三条：**重复投递同一条判定输入 → 事件数不变**；
**判定输入乱序注入（把旧 ts 的样本晚发）→ 不产生第二个事件**；
**重启告警服务 → 消费进度从 broker/表恢复，不丢不改状态**。

#### 6) 评价
方向是对的（判定会越来越重，值得独立），但**一期不值得**：现在判定只有 3 个测点 × 2 条判据，
放在接入层是"多一次函数调用"，拆成服务要多维护一条投递链路和它的重复/乱序语义。
**建议：接口按丙设计（判据模块不依赖 MQTT 回调上下文），部署先按乙落。**

## 3. 必须先定的口径问题

这一节是设计的核心。**判据参数可以调，口径不能含糊。**

### 3.1 判标干还是折算？——**判折算**，且判据必须拿到同一时刻的 O2

* **口径**：污染物达标判定用**折算值**，不是标干值。
  理由在库里就能看到反例：同一小时 NOx **标干均值 40.02（<50 达标）**、**折算均值 59.61（>50 超标）**——
  两种判法结论相反；另有点名反例：SO2 标干 30.0 达标，O2=9% 时折算 37.5 超标。
* **"判折算"的连带要求**：折算需要一个 O2，**必须是同一时刻的 O2**。本项目天然满足：
  一个 MQTT 报文里同时含 9 个测点、共用一个时间戳，`reference_values(values)` 从**同一条报文**里取 O2
  → "同一时刻"是结构保证的，不需要插值/最近邻对齐。
* ⚠️ **明令禁止**的做法：用"最近的 O2"或"小时平均 O2"去折算另一时刻的浓度。
  那会把"某一刻的高浓度"配到"另一刻的 O2"上，判定结果不可复现（而且是**静默**的不可复现）。
* **判定集合必须显式声明**，不能靠阈值猜：契约里已有 `ZS_TARGETS = ("dust","so2","nox")`
  和 `LIMITS`，直接用。⚠️ 不要写成"遍历所有测点、`limit` 存在就判"——
  `Flow/Velocity/Temp/Humidity/Pressure/O2` 的 `limit` 等于量程上限，那样会把"量程上限"当排放限值用。

### 3.2 持续多久算一次告警？——三种语义完全不同

| 语义 | 定义 | 实测表现（最近 60 分钟） | 误报 | 漏报 |
|---|---|---|---|---|
| **A 单点瞬时** | 任意一条样本折算值 > 限值即告警 | NOx **62 条/小时** | **极高**：一次尖峰几十条，一小时 62 条 → 告警风暴 | 低 |
| **B 连续 N 周期** | 连续 N 条样本越限才告警 | NOx：N=3 → 6 次；N=12 → 2 次；N=60(5min) → **0 次** | 低（可调） | 中：N 越大漏得越多；**且"连续"要求样本不缺**，网关一重启就断段 |
| **C 小时均值** | 该小时折算均值 > 限值才算超标 | NOx 小时折算均值 **36.01 < 50 → 达标** | 低 | **高**：这一小时 62 条瞬时越限、最长连续 70 秒，却**一条告警都不会有** |

**结论与推荐**：
1. **不要用 A**（风暴）；**不要只用 C**（实测漏掉整小时的短时超标，而 C 恰好是报表口径，容易给人"已经判过了"的错觉）；
2. **B 采用滑窗计数形式**，不要用严格连续：`最近 M 条样本里至少 N 条越限`（默认 **M=6、N=3**，
   即 5s 采样下的 30 秒窗口里至少 15 秒越限）。这样对"网关重启断一条样本"有容忍度，
   实测能把 NOx 事件率压到 **6 次/小时**（严格连续的语义在断链时会静默失效）；
3. **C 作为独立判据并行跑**（小时结算任务），产出"小时均值超标/达标/数据不足"的**报表口径结论**；
   A/B/C 三条口径的结论**分别记录、分别通知，互不替代**——因为它们的业务含义不同：
   B 是"排放异常事件"，C 是"达标考核结论"。
4. 阈值参数化（`ALARM_WINDOW_SAMPLES` / `ALARM_MIN_OVER_SAMPLES`），用 `SIM_SPIKE_ENABLE=0/1` 做 A/B 对照标定。

### 3.3 一个"超标事件"怎么定义开始与结束？

**状态机（每个 `(point, judge_type)` 一个实例）：**

```
                滑窗内越限样本数 >= N
   IDLE ───────────────────────────────────► OPEN
     ▲                                        │  ├─ 每来一条越限样本：更新 peak / over_samples
     │                                        │  └─ 距上次通知 >= ALARM_REMIND_SECONDS：写一条 remind
     │   连续 K 条折算值 <= 限值 × 恢复系数      │
     └────────────────────────────────────────┘
                      写 END
```

| 项 | 定义 |
|---|---|
| **开始** | 触发条件成立的那一刻。事件表的 `start` 记录里，`ts` = **该事件首个越限样本的时间戳**（不是触发时刻），并记 `trigger_ts` 供追溯；`event_id = point + judge_type + start_ts`（可复现、无随机数） |
| **结束** | 恢复条件成立：**连续 K 条**（默认 6 条 = 30s）折算值 ≤ 限值 × `恢复系数`（默认 **0.95**）。用 0.95 而不是 1.0 是为了**滞回**：贴限值波动时不会 begin/end 反复抖 |
| **去重** | 同一 `(point, judge_type)` **同时只允许一个 OPEN 事件**；OPEN 期间不再产生新的 START（只更新峰值/计数、或按 `ALARM_REMIND_SECONDS` 产 `remind`）。所有重复通知都靠 `event_id` 收敛到同一个事件 |
| **幂等** | 事件记录 append-only；写入用 `(子表名 = plant_device_point_judgetype, ts)` → **同 ts 覆盖**。报文重投/重放只会覆盖同一行，不会新增事件（这是本项目在 TDengine 上最省事的幂等手段） |
| **落库形态** | `start` / `remind` / `end` 都是同一张事件表里的行，`phase` 区分；事件"当前是否 OPEN"= 该事件最后一条 phase（**不要依赖原地更新状态**） |
| ⚠️ 已实测的约束 | 本机 `UPDATE <table> SET col=val`（带/不带 ts 条件、带/不带库名）**均报语法错误** → **不能靠 UPDATE 原地改事件状态**，只能 append-only + 折叠恢复。⚠️ 社区文章描述了"带 ts 条件即可 UPDATE"的语义（见附录），**与本次实测不符**，实现前需在目标表上再验一次 |
| 重启恢复 | 订阅端启动时，从事件表折叠出各 `(point, judge_type)` 的最后 phase；若为 `start` → 该事件视为仍 OPEN，继续累计，不重发 START |

### 3.4 样本不足的小时怎么算？——**判"数据不足"，绝不判达标**

* **应有样本数** = 3600 / 轮询周期 = 3600/5 = **720 条/小时**。
* **有效样本** = 该小时内、折算值非 nan 的样本（即 `o2 < 21`）。
* **覆盖率** = 有效样本 / 720；默认门限 `ALARM_COVERAGE_MIN = 0.75`（≈45 分钟）。
  ⚠️ **"每小时至少 45 分钟有效数据"是行业通行做法，本项目未取到一手条文**
  （与 `points.py` 里折算公式出处的处置一致：先按可配置阈值实现，出处待补充）。
* **判定规则（三态，不是两态）**：
  | 条件 | 结论 | 处理 |
  |---|---|---|
  | 覆盖率 ≥ 门限 且 折算均值 ≤ 限值 | `ok` | 记结论，不通知 |
  | 覆盖率 ≥ 门限 且 折算均值 > 限值 | `over` | **超标事件**（judge_type=hourly），按 §3.3 通知 |
  | 覆盖率 < 门限 | `insufficient` | **不判达标也不判超标**；同时产"数据不足"事件（缺数据本身是故障，最危险的漏报形态是"缺数据被当成达标"） |
* **实测备注**：当前库里**未复现**到"24 条/小时"这种极低覆盖的小时（最近的 4 个小时窗口分别 369/689/687/297 条，
  其中 369 与 297 是启动/截断造成的不完整小时，完整小时接近 720）。因此该门限**按参数实现**，
  不要写死成"当前数据总是够"。
* **小时边界**：见 §3.6（时区/基准问题），窗口起点必须显式声明。

### 3.5 O2 ≥ 21% 时折算为 nan：判不判？判什么？

**判，但判的不是"达标/超标"，而是"数据无效"。**

* `points.to_reference_o2()` 在 `o2 >= 21` 时返回 `nan`（分母 ≤ 0，折算无物理意义）。**不许绕过、不许当 0、不许当达标。**
* 该样本：**不参与任何达标判定**（既不计入越限，也不计入达标），单独计为**无效样本**。
* 该样本必须产生 **`phase=invalid`** 的事件记录（记 `raw_value`、`o2`、时间戳）：
  O2 ≥ 21% 在真实工况里通常意味着样气/仪表/工况异常，**"折算算不出来"本身就是要报的事**；
  如果只是静默跳过，这条数据就永远没人看。
* 若一小时无效样本占比 > `ALARM_INVALID_RATIO_MAX`（默认 0.10）→ 该小时判 `insufficient`（§3.4）。
* ⚠️ 库侧方案（甲）**必须手工复刻这条语义**：SQL 的 `nox*(21-6)/(21-o2)` 在 `o2>21` 时给的是**负数**，
  实测库里已有 56 条 `o2>=21` 的样本，某个历史小时的 NOx"折算均值"因此算成 **−50.65**。
  负数会同时污染 `AVG/MAX/SUM`，这是甲方案最容易被忽略的坑。

### 3.6 时间基准（复核结论：两条读路径一致，无需换算）

**⚠️ 本节初稿曾记录"REST 呈现 UTC、比 CLI 慢 8 小时"，该结论在 2026-10-01 03:35 复核时被证伪，故改写。**

**复核证据（同一时刻，三条路径 + 同一行数据一起比）：**

| 核对项 | 结果 |
|---|---|
| 宿主机 `Get-Date` | `2026-10-01 03:35:14` |
| `tdengine` 容器 `date` | `2026-10-01 03:35:14` |
| `cems-web` 容器 `date` | `2026-10-01 03:35:14` |
| 原生 CLI `SELECT ts ... LIMIT 1` | `2026-10-01 03:35:05.000` |
| REST（`taosrest`）同一行 | `datetime(2026, 10, 1, 3, 35, 5)` |

**⇒ 容器时钟、原生 CLI、REST 三者一致，同一行的 `ts` 在两条路径上显示相同，不存在 8 小时偏移。**
`docker-compose.yml` 里各服务统一注入 `TZ: Asia/Shanghai`，TDengine 容器同样，所以读出来的时间就是北京时间。

**⚠️ 初稿为什么会出现那个现象**：初稿测量时**正在 `--force-recreate` 重启容器**（当时 web 容器刚重建），
读到的是重启窗口期的暂态值。**教训：核对时间基准必须"同一时刻、多条路径、并且比对同一行数据"，
单独看一次 `SELECT NOW` 会被重启窗口骗到。**

**对实现的结论：**
* 聚合窗口就是**北京时间的小时**（00:00、01:00…），与环保口径一致，**不需要 `INTERVAL(1h, 8h)` 偏移**；
* 仍建议验证脚本与人工核查**用同一条读路径**（都用 CLI 或都用 REST），避免混用造成误判；
* 若将来在别的机器上部署发现偏移，先按上面那张表核一遍**再**决定要不要换算，
  不要默认"REST 就是 UTC"。

## 4. 与项目已完成部分怎么衔接

**原则：能用现成的就绝不重写；折算只调用契约函数，绝不出现第二份公式。**

| 已有资产 | 位置 | 判据怎么用 |
|---|---|---|
| `to_reference_o2(value, o2)` | `src/common/points.py` | **唯一的折算公式实现**。判定与小时结算都调它（或复用其调用点），不在 SQL/脚本里重抄公式 |
| `reference_values(values)` | `src/platform/subscriber_to_td.py` | 接入层判定**直接吃它的返回值**：写入成功后已经算好，判定不再算第二遍。它是全仓库 `to_reference_o2()` 的唯一调用点 |
| `record_reference()` / `latest_reference_values()` | 同上 | `record_reference` 已维护"最近一条折算值"快照，可用于探活与自检（判据不要依赖这个快照做判定，判定必须按条） |
| `ZS_TARGETS = ("dust","so2","nox")` | `points.py` | **判定集合的显式声明**：只判这三列，不靠"有没有 limit"去猜 |
| `LIMITS` / `Point.limit` | `points.py` | 限值来源（颗粒物 5 / SO2 35 / NOx 50，mg/m3，标干、基准氧 6%） |
| `over_limit(name, value)` | `points.py` | 判定函数（`>` 语义：**正好等于限值算达标**）。调用方负责传入**折算值** |
| `O2_REFERENCE = 6.0` | `points.py` | 基准氧。写入事件表的 `o2_reference`，将来换行业/换燃料时历史记录仍可解释 |
| `RANGES` / 拒收逻辑 | `subscriber_to_td.parse_payload` | **不动**。量程拒收（超量程=表坏）与限值告警（超限值=排超标）是两件事 |
| `POINTS` / `COLUMNS` / `COLUMN_TO_NAME` | `points.py` / `subscriber_to_td.py` | 列名↔测点名映射已有（`COLUMN_TO_NAME`），小时结算从库里读列名后用它还原测点名，**不需要改契约** |
| `SIM_SPIKE_PROB` / `SIM_SPIKE_ENABLE` / `SIM_SPIKE_WIDTH_STEPS` | `src/device/simulator.py` | 告警演练与标定的**事件源**：默认开（越限时间占比约 1%~10%），`=0` 时污染物恒定达标，正好做 A/B 对照 |
| 六服务与编排 | `docker-compose.yml` | 判定若新增环境变量，按现有样式注入 subscriber；**不改端口/主题/QoS/client_id** |
| Web 展示层 | `src/web/*`（已押后） | 事件表与小时结论表是 Web 的天然数据源。展示层仍按既定顺序押到最后，判据先落库 |

**明确不做的事**（与既有决定一致）：
1. 不给 `cems.cems_data` 加折算列，不加折算寄存器；
2. 不修改 `points.py` 的量程/限值/列名，不重构契约；
3. 不改接入层的拒收逻辑与拒收口径；
4. 不引入新依赖（判定用标准库；通知优先复用既有 EMQX）。

## 5. 一期实现清单（供决策后执行）

4. 小时结算任务（每小时触发，读原始行 + `to_reference_o2()` 重算 + 覆盖率门限）；
5. 通知：结构化日志（必做）+ MQTT `cems/plant1/alarm`（可选，`ALARM_*` 开关控制）；
6. 离线回放验收脚本（覆盖 §2.2.5 的 V1 五个边界用例，退出码 0/1，与既有 `scripts/verify_*.py` 风格一致）。

**验收判据（可量化）**：
* `SIM_SPIKE_ENABLE=0` 跑 1 小时 → 事件表新增 `start` 行数 = 0；
* `SIM_SPIKE_PROB=0.02` 跑 1 小时 → 出现 `start/end` 成对记录，且**小时事件数 ≤ 12 个/测点**（不出现风暴）；
* 同一条报文重发 3 次 → 事件表行数不变；
* 停网关 50 分钟 → 该小时 `verdict=insufficient`，且**没有** `ok`；
* 事件表里任取一个 `start` 行，用 `raw_value/o2/o2_reference` 手工代入公式，
  与行内 `converted` **逐位一致**（折算可复核）。

```

```

**A5 时间基准（⚠️ 初稿结论已被证伪，见 §3.6；下面是复核证据）**

```
初稿（重启窗口期测得，**不可采信**）:
  REST  POST /rest/sql {"SELECT NOW"} → 2026/9/30 19:31:23
  CLI   SELECT NOW                    → 2026-10-01 03:31:23（当时被解读为 8 小时差）

复核（2026-10-01 03:35，同一时刻三条路径 + 同一行数据）:
  host / tdengine / cems-web 的 date  : 2026-10-01 03:35:14（三者逐秒一致）
```

**A6 与本设计无关但影响验证方法的一点**

```
UPDATE <表> SET col=val                      → syntax error [0x80002600]
UPDATE <表> SET col=val WHERE ts > '...'     → syntax error [0x80002600]
UPDATE <库>.<表> SET col=val WHERE col='...' → syntax error [0x80002600]
DELETE FROM <表>                             → OK
→ 事件表按 append-only 设计；不要指望原地更新状态。
```
