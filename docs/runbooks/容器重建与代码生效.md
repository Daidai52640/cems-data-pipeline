# 改代码后怎么让容器真的生效（含一个必踩的坑）

> **什么时候看这份**：改完 `src/` 下的代码、重建了容器，但行为**看起来没变**。
> **最后更新**：2026-10-02

---

## ⚠️ 坑：`--build` 加在错误的 service 上 = 空操作

下面这条命令**不会重建镜像**：

```powershell
docker compose up -d --build --force-recreate subscriber   # ❌ 空操作
```

**原因**：`docker-compose.yml` 里**只有 `device` 服务**声明了 `build:`（全项目唯一构建入口），
其余应用服务（`gateway` / `subscriber` / `web`）都是：

```yaml
image: cems-pipeline:latest
pull_policy: never          # 只在本机构建、不上 registry
```

`subscriber` 自己没有 `build:` 段，所以 `--build` **无处可建** ——
compose 只会拿**已有的旧镜像**重建容器，改动根本没进去。

**实测症状**：`docker compose up -d --build --force-recreate subscriber` 输出一切正常
（`Container cems-subscriber Recreated / Started`），但容器里的代码是旧的。

---

## ✅ 正确姿势

```powershell
# 1) 用真正的构建入口重建镜像
docker compose build device

# 2) 重建要用新镜像的服务
docker compose up -d --force-recreate device gateway subscriber web

# 3) 检查是否已经重建（增量构建时缓存命中会很快）
docker images cems-pipeline:latest --format "{{.CreatedSince}}"
```

---

## ✅ 验证改动真的生效（**这一步不能省**）

**光看容器 healthy 不够** —— 旧代码也能 healthy。要比对容器内文件与工作区的哈希：

```powershell
# 在容器内算哈希
docker exec cems-subscriber md5sum /app/src/platform/subscriber_to_td.py

# 在工作区算哈希
(Get-FileHash src\platform\subscriber_to_td.py -Algorithm MD5).Hash.ToLower()

# 两者一致才算生效
```

**更直接的判据**：grep 新加的函数名/字符串：

```powershell
docker exec cems-subscriber sh -c "grep -c '_post_webhook' /app/src/platform/subscriber_to_td.py"
# 期望 >= 1；返回 0 说明容器里还是旧代码
```

---

## 为什么会有这个坑（设计上的取舍）

只有一个镜像、多个服务共用，是为了**四个 Python 服务共用一套依赖**（Dockerfile 只装一次）。
代价就是"构建入口只有一个"，从别的 service 名去 build 会静默失败。

**`pull_policy: never` 是故意的**：镜像只在本机存在，不设这个的话新机器 `up` 会先白等一次
registry 拉取超时（404）才回落到 build。
