## 故障 1 · 拔线（网络中断）

- **时间**：2026-10-01 ~21:24:15 ~ ~21:27:17（约 3 分钟；原计划 5 分钟，中途插回）
- **操作**：`docker network disconnect cems-net cems-gateway`（只断网关链条，等价拔网线；操作**全部在 PowerShell 端**，不需要进容器）
- **现象**：
  - 网关容器**仍然 healthy**（`Up 4 hours`）——⚠️ **容器状态骗人**
  - 日志：`连不上 Modbus 设备 device:5020（Temporary failure in name resolution）`，每 5 秒重试
  - 随后：`Modbus 已连接` → 立刻连续 6 条 `[缓存] 断网，数据已入本地队列`
  - 恢复：`MQTT 已连接: emqx:1883` → `[补传] 开始补传 6 条` → `[补传完成] broker 已确认 6 条`
  - 库内：**21:26 整分钟无数据**（断档），21:24/21:25/21:27 条数明显偏低
- **排查命令**：
  ```powershell
  docker compose ps                                # 网关仍 healthy（第一眼会以为没事）
  docker logs cems-gateway --tail 25               # 看 Modbus/MQTT 报错与恢复
  docker exec tdengine taos -s "SELECT _wstart, COUNT(*) FROM cems.cems_data \
      WHERE ts >= '2026-10-01 21:20:00' INTERVAL(1m) ORDER BY _wstart;"   # 逐分钟看断档
  ```
- **⭐ 根因（本条最大收获）："拔线"其实有两种，后果完全不同**

  | 断在哪 | 代码路径 | 结果 |
  |---|---|---|
  | **网关 ↔ 设备**（Modbus） | `read_device()` 返回 None → `本轮采集失败` → `continue` | ⚠️ **压根没采到 → 没有任何数据可缓存 → 真丢，补不回来** |
  | **网关 ↔ Broker**（MQTT） | 读成功、`publish` 失败 → `save_to_cache(reason="断网")` | ✅ **数据已在手 → 落缓存 → 恢复后补传，一条不丢** |

  **本次演练在几分钟内把两种都演示了**：先是设备侧断（读不到），插回后 MQTT 还没连上（21:27:17~21:27:42），
  那 6 条走的是"断网"入队路径，最后**补传全部成功**。

- **修复**：`docker network connect cems-net cems-gateway` → 恢复耗时约 **26 秒**（21:27:17 Modbus 通 → 21:27:43 MQTT 通并补传完）
  - ⚠️ 其中 **MQTT 重连占大头**（实测 paho 重连退避最坏 84 秒；本次 26 秒）
- **数据影响（对账）**：
  | 项 | 值 |
  |---|---|
  | 基线（拔线前） | **7870** 条 |
  | 断档窗口 | **21:25:20 → 21:27:17（117 秒 ≈ 23 条）** |
  | 恢复后总数 | **7932** 条（+62） |
  | 若无故障应有 | ≈ **96 条**（8 分钟 × 12 条/分钟） |
  | **净损失** | ⚠️ **≈ 34 条**（其中 **6 条被缓存补传救回**，其余 ~28 条因"设备侧断"永久丢失） |
  | 补传成功率 | **6/6 = 100%** |
  | 缓存残留 | **0 行**（演练后回纯直发） |
- **⭐ 我学到的一条**：
  > **"断网续传"保护的是"已经采到的数据"，保护不了"压根没采到的数据"。**
  > 设备侧断链 = 数据源头消失，缓存再大也救不回来；只有"网关↔Broker"这一段断了，缓存才有意义。
  > **所以对账时必须先问"断在哪一段"，否则会得出错误结论。**

- **⚠️ 遗留待做**：项目负责人忘了记"插回的准确时刻"，本次用日志时间反推。
  下次演练**拔/插两个时刻都要立刻记**（`Get-Date -Format "HH:mm:ss"`）。

- **⚠️ 本次暴露的卡点**：执行卡原写"拔线 5 分钟"未区分断在哪一段 → **已修正执行卡**（区分甲/乙两种断法）。

## 故障 2 · 停 EMQX（Broker 侧断）

- **操作**：`docker stop emqx`（项目负责人亲手执行）→ 观察 → `docker start emqx`
- **现象**：
  - 网关容器**仍 healthy**，且**仍在正常读设备**（与故障 1 的关键区别）
  - 日志每 5 秒一条：`[缓存] 断网，数据已入本地队列: …`（**入队原因是"断网"**）
  - 缓存文件**持续增长**：22:17:21 → 68 行、22:19:01 → 88 行、22:20:41 → 108 行
    （≈ **12 行/分钟 = 5 秒一条**，与采集周期一致）
  - 恢复：`MQTT 已连接: emqx:1883` → `[补传] 开始补传 128 条，在途窗口 100 条`
    → `[补传完成] broker 已确认 128 条`
- **排查命令**：
  ```powershell
  docker compose ps --format "{{.Name}}`t{{.Status}}"      # 网关仍 healthy（容器状态骗人）
  docker logs cems-gateway --tail 12                        # 看入队原因：应为"断网"
  (Get-Content data\cache.jsonl | Measure-Object -Line).Lines   # 缓存增长
  docker exec tdengine taos -s 'SELECT COUNT(*) AS n FROM cems.cems_data;'   # 库内停止增长
  ```
- **根因**：断的是**网关 ↔ Broker** 这一跳。数据**已经进入网关**（读设备成功），
  只是 `publish` 发不出去 → 走 `save_to_cache(reason="断网")` → 恢复后按序补传。
- **修复**：`docker start emqx` → 重连并自动补传，**无需人工干预**
- **数据影响（对账）**：
  | 项 | 值 |
  |---|---|
  | 基线（停 EMQX 前） | **8417** 条 |
  | 断链时长 | 约 **11 分钟** |
  | 缓存峰值 / 补传条数 | **128 行**（`[补传完成] broker 已确认 128 条`） |
  | 缓存残留 | **0 行**（排空） |
  | 恢复后库内 | **8603** 条（+186 = **128 缓存补传** + 58 断链前在途/恢复后直发） |
  | ⭐ **数据缺口** | **0 分钟** —— 22:10~22:25 逐分钟全部 12 条（仅 22:19 为 11 条） |
  | **净损失** | ⭐ **0 条** |
- **⭐ 我学到的一条**：
  > **"断网续传"保护的是"已经进入网关的数据"。**
  > 断在**下游（Broker）→ 一条不丢**；断在**上游（设备）→ 真丢**（见故障 1）。
  > **对账前必须先问"断在哪一段"，否则会得出完全错误的结论。**
- **⚠️ 补充发现（两套缓存的分工）**：
  本次数据是**卡在网关本地缓存**里等恢复的（日志显示是网关自己补的 128 条），
  **不是**靠 EMQX 离线队列。→ 两者分工：
  - **网关本地缓存**（`data/cache.jsonl`）管 **网关 ↔ Broker** 这一段
  - **EMQX 离线队列**（`MAX_MQUEUE_LEN=20000`）管 **Broker ↔ 订阅端** 这一段

  - 日志：`网关启动: 设备 device:5020 → MQTT emqx:1884`（**错值就在启动横幅第一行**）
  - 日志每 5 秒：`[缓存] 断网，数据已入本地队列`（**与"停 EMQX"同一句话**）
  - 缓存持续增长；库内条数基本停滞

  ```powershell
  docker compose ps                                  # ⚠️ 全都 healthy -> 一无所获

  ```
  **→ 对比两个容器：gateway 是 `MQTT_PORT=1884`、subscriber 是 `MQTT_PORT=1883`。**
- **根因**：配置写错一个字符。**链路本身没问题、所有服务都在跑、没有任何进程崩溃。**
- **修复**：把 `MQTT_PORT` 改回 `"1883"` → 重建网关
  - 恢复：`MQTT 已连接: emqx:1883` → `[补传] 开始补传 46 条` → `[补传完成] broker 已确认 46 条`
- **数据影响（对账）**：
  | 项 | 值 |
  |---|---|
  | 基线 | 8701 条 |
  | 补传条数 | **46 条（46/46 全部确认）** |
  | 缓存残留 | 1 行（补传期间新采的，属正常） |
  | 恢复后 | 8760 条（+59 = 46 补传 + 13 直发） |
  | **数据缺口** | ⭐ **0** —— 14:17~14:22 逐分钟 11~12 条 |

- **⭐ 我学到的一条**：
  > **所有服务都 `healthy` ≠ 配置是对的。**
  > 运行状态（进程活着/心跳在刷）和配置正确性（能不能连通）是**两件独立的事**。
  > 数据不进库时，**别只看"谁停了"**——没有东西停的时候，要去看**配置本身**（启动横幅、`docker inspect` 的实际环境变量）。

- **⚠️ 本次额外踩到的工具坑（不是演练故障，但是真坑，值得记）**：
  用 PowerShell 改这个 YAML 文件时踩了两次：
  1. **`Set-Content -Encoding utf8` 会写入 UTF-8 BOM**（PS7 行为）→ `docker compose` 的 YAML 解析器**不接受 BOM**：
     `go-yaml load error in parser (while parsing a block mapping) at L12.C1-L16.C3: did not find expected key`
     → 修法：`[IO.File]::WriteAllText($p, $text, [Text.UTF8Encoding]::new($false))`（显式无 BOM）
  2. **`Set-Content` 会把行尾由 LF 改成 CRLF** → 本来只改 1 行，`git diff` 却显示 **77 insertions / 151 deletions**（全文件都"变了"）
     → 修法：显式用 LF 写回；诊断时先 `git diff --stat` 看改动量对不对
  **⭐ 教训：改配置文件后，先看 `git diff --stat` 的改动量是否符合预期。** 只改 1 行却显示上百行改动 = 行尾/编码被动过。

## 故障 4 · 磁盘写满 / 日志爆盘

- **时间**：2026-10-02 14:25~14:35
- **⭐ 处置方式（有意偏离"把磁盘写满"的原计划）**：
  **只做「诊断层」+「代码层修复」，不真把磁盘写满，也不真写满宿主机。**
  | 层 | 做没做 | 说明 |
  |---|---|---|
  | A 诊断层（`df -h` / `du -sh` / `ls -lh`） | ✅ **做了** | 量出真实占用与增长速率 |
  | B 安全复现 ENOSPC | ⚠️ **失败**（容器无 `CAP_SYS_ADMIN`，`mount` 被拒） | 见下方"附带事实" |
  | C 真写满 | ❌ **不做** | 理由见下 |
- **⭐ 为什么不做 C（这是本条最该学的判断）**：
  **容器里 `df` 看到的就是宿主机的 Docker 盘**：
  ```
  overlay        1007G  4.7G  951G   1% /
  /dev/sdd       1007G  4.7G  951G   1% /var/lib/taos   <- 同一块
  /dev/sdd       1007G  4.7G  951G   1% /var/log/taos   <- 同一块
  ```
  → 要"把磁盘写满"就得真写 ~951 GB，**那是写用户自己的电脑**；
  且删的时候可能连 Docker 一起搞坏。**用一个已知答案的现象去冒这个风险，收益远小于代价。**
- **诊断层实测结论**：
  | 项 | 值 |
  |---|---|
  | `/var/log/taos` | **658 MB**（其中 `taoslog1.0` 单文件 **449 MB**） |
  | `/var/lib/taos` | 91 MB（业务库只占约 2 MB，其余是内置 `log` 库） |
  | 日志/数据比 | **7.2 倍** |
  | **增长速率** | 40 秒 +186,705 字节 → **约 384 MB/天** |
  | 按速率算何时写满 | 从 4.7G 到 951G 需 **约 2,500 天** |
  | taosAdapter 日志文件数 | **57 个**，**最早日期到 3 周前** |
  | 配置 `logKeepDays` | **`0`**（= 不自动删） |
- **⭐ 我学到的一条**：
  > **"658 MB 日志 vs 91 MB 数据（7.2 倍）"看着吓人，但算速率只有 384 MB/天。**
  > **先算速率，再下结论** —— 否则会对一个 2500 天后才会发生的问题做出过激反应。
  > 而**真正的风险不是"涨得快"，是"从不清理"**（57 个文件、最老 3 周前、`logKeepDays=0`）。
- **修复（代码层，已提交 `98c0228`）**：
  | 层 | 措施 |
  |---|---|
  | **容器 stdout 日志** | `docker-compose.yml` 加 `logging`（`json-file` + `max-size=10m` + `max-file=3`）→ **上限 30 MB/容器**<br>⚠️ YAML 合并键是**逐 key 浅合并**，所以非 `*app` 的 emqx/tdengine/redis/nginx 各自**显式**加一份 |
  | **TDengine 自带日志** | 新增 `deploy/tdengine/gen-log-limits-config.ps1`：**从镜像取原配置 + 就地补丁**（不是手抄副本，避免镜像升级后悄悄过期），compose **只读**挂进 `/etc/taos/`<br>`taos.cfg`：`numOfLogLines=2000000` / `minimalLogDirGB=1.0` / `logKeepDays=7`（三层一起限）<br>`taosadapter.toml`：补丁 `[log]` 段内 `rotationCount=10` / `rotationSize=100MB` / **`keepDays=7`** |
  | **验收** | `docker inspect` **八个容器 LogConfig 全部含 `max-size`/`max-file`**；容器内 `/etc/taos/*` 为**只读**（`RW=false`） |
- **⚠️ 修复过程中踩到的三个真坑（都值得记）**：
  1. **`taosadapter.toml` 已有 `[log]` 段**（含 `rotationCount`/`rotationSize`）→ 在**根级追加重名键 = TOML 重复键 → adapter 起不来**。必须**就地补丁段内值**。
  2. **该镜像里真正的保留期键名是 `keepDays`，不是 `logKeepDays`** —— 我第一版加了 `logKeepDays`，镜像根本不认（会被忽略，配置看着"加上了"其实没生效）。
     **⭐ 教训：配置项名字必须去镜像原文件里核对，不能凭记忆或文档印象写。**
  3. **`.cmd` 脚本里写中文注释会崩**：cmd.exe 按 ANSI/GBK 解码 → **命令行被截断** → 脚本报一堆 `'...' is not recognized`。
     本机约定（`~/.dsh/AGENTS.md`）明确写了 `.ps1`/`.bat` **必须纯 ASCII**，中文放数据文件。改用 `.ps1` 后正常。
- **代价（如实记录）**：应用容器 `logging` 需要**重建容器**（`docker update` 不支持改日志配置，实测 `unknown flag: --log-driver`）→ 本次重建约 **10 秒**，采集出现约 **70 秒断档（约 14 条仿真读数）**，属计划内维护窗口。
- **⚠️ 附带事实（安全复现 ENOSPC 的尝试失败）**：
  容器内 `mount -t tmpfs` 与 `mount -o loop` 均被拒（`Operation not permitted`）
  → **容器没有 `CAP_SYS_ADMIN`**。**"在容器里"不等于"可以为所欲为"**，
  这条本身也是容器安全边界的一个实测点。
  ⚠️ 而且**"mount 失败"不等于"我保护了宿主机"**——纯粹是权限不够。
  **凡是会真写宿主机的实验，动手前必须先说清：最多写多少、写在哪、怎么回收。**

## 故障 5 · 容器时区错 / 时钟漂移

- **时间**：2026-10-02 14:35:07 ~ 14:36:02（注入约 1 分钟）
- **故障注入**：把**网关**的 `TZ` 由 `Asia/Shanghai` 改为 `UTC`（**只改网关**，因为**时间戳是网关打的**；其余 8 处 TZ 不动）→ 重建网关
- **现象**：
  - 网关容器时间立刻差 8 小时：`host 14:35:32` vs `cems-gateway 06:35:32 UTC`（tdengine 仍是 CST）
  - ⚠️ **没有报错、没有异常、数据照常入库** —— 这是**隐蔽型故障**
  - 网关日志时间戳也变成 `06:35:07`（日志时间本身也错）
  - **库里出现 8 小时错位的行**：`06:35:07 ~ 06:36:02` 共 **12~14 行**，
    so2=19.9 / nox=32.3（**与 14:34 那批数值连续** → 证明是同一批数据被贴错了时间）
  - 14:35 那一分钟只剩 2 条（数据被"搬"到了 8 小时前）
- **排查命令**：
  ```powershell
  docker exec cems-gateway date "+%Y-%m-%d %H:%M:%S %Z"     # ⭐ 一眼看出 UTC
  docker exec tdengine    date "+%Y-%m-%d %H:%M:%S %Z"      # 对比：CST
  docker exec cems-gateway sh -c 'echo $TZ'                  # UTC
  git diff docker-compose.yml                                # 看到 TZ 那一行被改过
  # 查库：按小时分桶会看到"当前小时 + 8 小时前的孤立桶"
  docker exec tdengine taos -s "SELECT _wstart, COUNT(*) FROM cems.cems_data \
      WHERE ts >= '<今天>' INTERVAL(1h) ORDER BY _wstart DESC LIMIT 4;"
  ```
- **根因**：容器时区与数据时间戳的语义不匹配。**设备层不产生时间**（Modbus 只是数值），
  所以**整条链路的时间由网关一家决定** → 网关错，全错，且下游无从察觉。
- **修复**：`TZ` 改回 `Asia/Shanghai` → 重建网关。恢复后：网关回到 CST、新数据回到当前时刻。
- **数据影响（对账）**：
  | 项 | 值 |
  |---|---|
  | 错位行数 | **12~14 行**（`06:35:07~06:36:02`，本应在 `14:35:07~14:36:02`） |
  | 当前时刻的缺口 | 14:35 只剩 **2 条**（正常 12 条） |
  | 这些行能修吗 | ⚠️ **TDengine 主键就是 ts，改时间戳要先删再插**；且这些行本身**数值完整**，只是时间错 |
  | 长期影响 | 当天日报的 14:35 窗口缺数据；06:35 窗口多出 12 行"幽灵数据" |

- **⭐ 我学到的一条（本条最有价值）**：
  > **覆盖率只能发现"缺数据"，发现不了"数据时间是错的"。**
  > 用刚上线的覆盖率接口实测：错位数据落在 `06:35` 那一分钟，
  > **n=11 / coverage=0.917 / insufficient=False** —— **判定合格**，
  > 从报表上**完全看不出这 11 行本该属于 14:35**。
  > 而真正的断档（14:35 只剩 2 条）**被准确标成 coverage=0.167 / insufficient=true**。
  > **→ 「时间错位」必须靠另一类检查**（时间戳合理性、跨层时间一致性对账），**覆盖率补不了这个洞**。

- **⚠️ 一个容易忽略的点**：**为什么只改网关的 TZ 就够**？
  因为**设备层不产生时间**（Modbus 寄存器只有数值），**全链路时间由网关一家决定**。
  所以"时间对不对"的**单点故障**就在网关——这也是为什么 `TZ` 必须与 TDengine 容器一致
  （compose 里那行注释写的就是这个）。

## 故障 6 · 备份恢复后计数对不上

- **时间**：2026-10-02 14:37~14:39
- **用到的现成工具**（上一轮"数据可靠性"任务留下的基础设施）：
  `scripts/backup_tdengine.py`（备份）、`scripts/restore_drill_tdengine.py`（恢复+六项校验）。
- **⚠️ 第一步就撞上了本条的核心现象 —— "对不上"其实是【在线备份的固有 RPO】，不是备份坏了**：
  备份脚本自己在日志里把三个数都打了出来：
  ```
  dump 前基线：8924 条（ts 到 14:37:01）
  taosdump 自报：8924 条
  dump 后基线：8925 条（ts 到 14:37:06）   <- 备份期间源端又写了 1 条
  ```
  **→ 备份里是 8924，而源端"现在"是 8925（之后还在涨）。**
  **这不是数据丢失**：备份是**某一时刻的快照**，源端是**活的**。
  ⚠️ **如果拿"恢复后的条数"去比"源端现在的条数"，永远会差一截，而且差多少取决于备份跑了多久。**

- **真恢复一次（不碰现网库）**：
  | 项 | 值 |
  |---|---|
  | 恢复模式 | `rename`（导入成 `cems_drill_restore`，用完自动 DROP） |
  | 条数 | 源 **8924** / 恢复 **8924** → **一致** |
  | 按小时分段 | 16 桶 vs 16 桶，**逐桶全等 True** |
  | 按天分段 | 2 桶 vs 2 桶，**逐桶全等 True** |
  | 库属性 | 差异无（预期差异只有 `name`） |
  | 表结构 | 12 列逐行一致 |
  | 子表标签 | `[['plant1','device1']]` 一致 |
  | **RTO** | **6.693 s**（就绪 0.306 + 传入 0.145 + 入库 1.576 + 校验 4.665） |
  | 残留 | 无 |
  留档：`docs/evidence/drill/tdengine_restore_drill_fault6.json`

- **⭐ 对账的关键：口径必须先对齐（本条最该学的一条）**：
  > **"计数对不上"不是一个结论，是一个症状。**
  > 必须先回答：**比的是哪两个数？它们可比吗？**
  >
  > | 比法 | 结论是否有效 |
  > |---|---|
  > | 备份快照条数 **vs** 源端**当下**条数 | ❌ **无效**（差的是 RPO，不是丢失） |
  > | 备份快照条数 **vs** 该备份自身的 dump 前基线 | ✅ **有效**（相等才是备份完整） |
  > | 恢复后条数 **vs** 备份自报条数（同一窗口） | ✅ **有效**（这才是"恢复完整性"） |
  > | 恢复后条数 **vs** 该窗口内源端条数 | ✅ **有效**（分段比对，见下） |
  >
  > 本项目 `restore_drill_tdengine.py` 的做法正确：**窗口取自备份 manifest 的 dump 前基线**
  > （`win_lo = 2026-10-01 00:28:11`、`win_hi = 2026-10-02 14:37:01`），
  > 而不是拿"现在几点"当窗口——所以它能判定一致。

- **⭐ 附加验证：证明"对账/分段校验"不是摆设**（否则整个演练就是自证自话）
  手动恢复一份副本到 `cems_drill_verify`，先校验一次（应一致），**再故意删掉它 2026-10-02 全天数据（280 行）**，再校验一次：
  | 校验 | 结果 |
  |---|---|
  | 第 1 次（副本完整） | **ok = True**（证明校验函数不是"永远报错"） |
  | 第 2 次（删了一天） | **ok = False** |
  | 条数 | `src 8924 / dst 8644` → 不一致 |
  | 按小时分段 | **16 桶 vs 14 桶** → 不一致 |
  | **⭐ 仅源端有的桶** | **`['2026-10-02 06:00:00', '2026-10-02 14:00:00']`** → **直接指出缺在哪两个桶** |
  | 按天分段 | 2 桶 vs 1 桶 → 不一致 |

  **⭐ 结论**：
  > **"总数对不上"只告诉你"有问题"；"分段对比"才告诉你"缺在哪"。**
  > 只比总数会在"丢了 A 段、多了 B 段"时**总数一样而完全看不出问题**——
  > 这就是校验必须**分段**（按小时 + 按天）而不能只比总数的原因。

- **修复/善后**：演练副本已 `DROP DATABASE`、临时目录已删、源库未受影响；
  `SHOW DATABASES` 回到 5 个库；八服务 healthy。

- **⚠️ 本次踩到的工具坑**：
  手动复现恢复时我执行了 `rm -rf /tmp/vfy-in/taosdump.*`，**结果把数据目录删了**——
  备份结构是 `taosdump.<id>/data0-<hash>/*.avro`，**数据在那个 `taosdump.*` 目录里面**，
  删掉它后 `taosdump -i` 报 `OK: 0 row(s) dumped in!`（**返回码是 0、还打印 OK，最容易误判成"恢复成功但库里没数据"**）。
  ⭐ **教训：`taosdump -i` 的"OK"不能当恢复成功的判据，必须回库查条数。**
  （脚本 `restore_drill_tdengine.py` 里就有这道防线：导入后 `ensure_db_after_restore()` 查库确认。）

## 故障 7 · 多设备（双实例）共因断网

- **时间**：2026-10-02 20:58:54 → 21:00:10（断 75 秒）
- **对象**：第二台设备接入后的两套实例（从站 1/2 → `device1`/`device2`，两套网关 + 两套接入）
- **操作**：
  ```powershell
  docker network disconnect cems-net emqx    # 断 broker 与链路的连接（EMQX 进程不重启）
  # 等 75 秒
  docker network connect    cems-net emqx
  ```
- **现象**：
  - 两套网关**各自**进入缓存模式（`[缓存] 断网，数据已入本地队列`），缓存分别落在宿主
    `data/`（device1）与 `data/plant2/`（device2）—— **没有一条写进对方的目录**
  - 断网期间的补传尝试 → `[补传未完成] N 条未确认，已放回缓存队首等待重试`（PUBACK 等不到）
  - 链路恢复后 → `MQTT 已连接` → `[补传] 开始补传 N 条` → `[补传完成] broker 已确认 N 条`
- **排查命令**：
  ```powershell
  docker logs cems-gateway        --since 5m | Select-String "开始补传|补传完成|补传未完成"
  docker logs cems-gateway-plant2 --since 5m | Select-String "开始补传|补传完成|补传未完成"
  (Get-Content data\cache.jsonl).Count           # 第一台待发条数
  (Get-Content data\plant2\cache.jsonl).Count    # 第二台待发条数（各自独立）
  ```
- **数据影响（对账）**：

  | 项 | device1（`cems-gateway`） | device2（`cems-gateway-plant2`） |
  |---|---|---|
  | 断网期间入本地队列 | **10 条** | **10 条** |
  | 补传确认条数 | **10 条**（8+2 两批） | **10 条**（6+4 两批） |
  | 逐条对账（缓存的每个时间戳在库里有没有） | **无缺失** | **无缺失** |
  | 补传后缓存残留 | 0（含在途段） | 0（含在途段） |

  ⚠️ 断网窗口内**轮询周期由 5 秒被拉长到约 10 秒**：等 PUBACK 白等 5 秒 + `sleep(5)`，
  所以断网窗口条数约为常态的一半。这是既有设计（"等不到 PUBACK 才落盘"）的固有代价，
  不是本轮引入；恢复后立刻回到 5 秒节拍。
- **⭐ 根因与两条收获**：
  1. **`broker 已确认` ≠ "下游已入库"**。网关的补传确认是 **broker 级 PUBACK**。
     另一次"停 EMQX 容器"（重启 broker）的演练实测到：EMQX 的会话是**内存态**
     （`emqx ctl conf show durable_sessions` → `enable = false`），重启后两个订阅端的
     `session_present` 都是 `False`，离线队列随之消失；两台各补传 29 条，device1 全部落库、
     device2 那 29 条因"订阅端尚未重订阅 + 会话未持久化"被 broker 丢弃。
     **要扛 broker 重启，必须开 EMQX `durable_sessions`（或让订阅端先于网关恢复）。**
  2. **缓存目录必须每实例一份**。缓存/续传状态都是目录内的固定文件名：段号由目录内文件名推导、
     补传是"整目录接手"（`inflight-*.jsonl` glob）、心跳文件同名 —— 两个网关共用目录时，
     A 会把 B 缓存的报文**发到自己的主题上**（数据张冠李戴，且两边都以为发成功）。
     所以第二套实例显式给 `GATEWAY_DATA_DIR`（见 `adr/0008-多设备多实例路线.md` §5）。
- **修复/善后**：链路恢复即自动重连补传，无需人工干预；两套缓存均排空，十容器 healthy。
- **原始输出**：`docs/evidence/drill/multi_device_two_instances_20261002.txt`
