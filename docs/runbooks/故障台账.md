## 故障 1 · 拔线（网络中断）

- **时间**：2026-10-01 ~21:24:15 ~ ~21:27:17（约 3 分钟；原计划 5 分钟，中途插回）
- **操作**：`docker network disconnect cems-net cems-gateway`（只断网关链条，等价拔网线；操作**全部在 PowerShell 端**，不需要进容器）
- **现象**：
  - 网关容器**仍然 healthy**（`Up 4 hours`）——⚠️ **容器状态骗人**
  - 日志：`连不上 Modbus 设备 device:5020（Temporary failure in name resolution）`，每 5 秒重试
  - 随后：`Modbus 已连接` → 立刻连续 6 条 `[缓存] 断网，数据已入本地队列`
  - 恢复：`MQTT 已连接: emqx:1883` → `[补传] 开始补传 6 条` → `[补传完成] broker 已确认 6 条`
  - 库内：**21:26 整分钟无数据**（断档），21:24/21:25/21:27 条数明显偏低
- **排查命令**：
  ```powershell
  docker compose ps                                # 网关仍 healthy（第一眼会以为没事）
  docker logs cems-gateway --tail 25               # 看 Modbus/MQTT 报错与恢复
  docker exec tdengine taos -s "SELECT _wstart, COUNT(*) FROM cems.cems_data \
      WHERE ts >= '2026-10-01 21:20:00' INTERVAL(1m) ORDER BY _wstart;"   # 逐分钟看断档
  ```
- **⭐ 根因（本条最大收获）："拔线"其实有两种，后果完全不同**

  | 断在哪 | 代码路径 | 结果 |
  |---|---|---|
  | **网关 ↔ 设备**（Modbus） | `read_device()` 返回 None → `本轮采集失败` → `continue` | ⚠️ **压根没采到 → 没有任何数据可缓存 → 真丢，补不回来** |
  | **网关 ↔ Broker**（MQTT） | 读成功、`publish` 失败 → `save_to_cache(reason="断网")` | ✅ **数据已在手 → 落缓存 → 恢复后补传，一条不丢** |

  **本次演练在几分钟内把两种都演示了**：先是设备侧断（读不到），插回后 MQTT 还没连上（21:27:17~21:27:42），
  那 6 条走的是"断网"入队路径，最后**补传全部成功**。

- **修复**：`docker network connect cems-net cems-gateway` → 恢复耗时约 **26 秒**（21:27:17 Modbus 通 → 21:27:43 MQTT 通并补传完）
  - ⚠️ 其中 **MQTT 重连占大头**（实测 paho 重连退避最坏 84 秒；本次 26 秒）
- **数据影响（对账）**：
  | 项 | 值 |
  |---|---|
  | 基线（拔线前） | **7870** 条 |
  | 断档窗口 | **21:25:20 → 21:27:17（117 秒 ≈ 23 条）** |
  | 恢复后总数 | **7932** 条（+62） |
  | 若无故障应有 | ≈ **96 条**（8 分钟 × 12 条/分钟） |
  | **净损失** | ⚠️ **≈ 34 条**（其中 **6 条被缓存补传救回**，其余 ~28 条因"设备侧断"永久丢失） |
  | 补传成功率 | **6/6 = 100%** |
  | 缓存残留 | **0 行**（演练后回纯直发） |
- **⭐ 我学到的一条**：
  > **"断网续传"保护的是"已经采到的数据"，保护不了"压根没采到的数据"。**
  > 设备侧断链 = 数据源头消失，缓存再大也救不回来；只有"网关↔Broker"这一段断了，缓存才有意义。
  > **所以对账时必须先问"断在哪一段"，否则会得出错误结论。**

- **⚠️ 遗留待做**：库主忘了记"插回的准确时刻"，本次用日志时间反推。
  下次演练**拔/插两个时刻都要立刻记**（`Get-Date -Format "HH:mm:ss"`）。

- **⚠️ 本次暴露的卡点**：执行卡原写"拔线 5 分钟"未区分断在哪一段 → **已修正执行卡**（区分甲/乙两种断法）。

## 故障 2 · 停 EMQX（Broker 侧断）

- **时间**：2026-10-01 22:11:18 ~ 22:22:24（约 11 分钟）
- **操作**：`docker stop emqx`（库主亲手执行）→ 观察 → `docker start emqx`
- **现象**：
  - 网关容器**仍 healthy**，且**仍在正常读设备**（与故障 1 的关键区别）
  - 日志每 5 秒一条：`[缓存] 断网，数据已入本地队列: …`（**入队原因是"断网"**）
  - 缓存文件**持续增长**：22:17:21 → 68 行、22:19:01 → 88 行、22:20:41 → 108 行
    （≈ **12 行/分钟 = 5 秒一条**，与采集周期一致）
  - 恢复：`MQTT 已连接: emqx:1883` → `[补传] 开始补传 128 条，在途窗口 100 条`
    → `[补传完成] broker 已确认 128 条`
- **排查命令**：
  ```powershell
  docker compose ps --format "{{.Name}}`t{{.Status}}"      # 网关仍 healthy（容器状态骗人）
  docker logs cems-gateway --tail 12                        # 看入队原因：应为"断网"
  (Get-Content data\cache.jsonl | Measure-Object -Line).Lines   # 缓存增长
  docker exec tdengine taos -s 'SELECT COUNT(*) AS n FROM cems.cems_data;'   # 库内停止增长
  ```
- **根因**：断的是**网关 ↔ Broker** 这一跳。数据**已经进入网关**（读设备成功），
  只是 `publish` 发不出去 → 走 `save_to_cache(reason="断网")` → 恢复后按序补传。
- **修复**：`docker start emqx` → 重连并自动补传，**无需人工干预**
- **数据影响（对账）**：
  | 项 | 值 |
  |---|---|
  | 基线（停 EMQX 前） | **8417** 条 |
  | 断链时长 | 约 **11 分钟** |
  | 缓存峰值 / 补传条数 | **128 行**（`[补传完成] broker 已确认 128 条`） |
  | 缓存残留 | **0 行**（排空） |
  | 恢复后库内 | **8603** 条（+186 = **128 缓存补传** + 58 断链前在途/恢复后直发） |
  | ⭐ **数据缺口** | **0 分钟** —— 22:10~22:25 逐分钟全部 12 条（仅 22:19 为 11 条） |
  | **净损失** | ⭐ **0 条** |
- **⭐ 我学到的一条**：
  > **"断网续传"保护的是"已经进入网关的数据"。**
  > 断在**下游（Broker）→ 一条不丢**；断在**上游（设备）→ 真丢**（见故障 1）。
  > **对账前必须先问"断在哪一段"，否则会得出完全错误的结论。**
- **⚠️ 补充发现（两套缓存的分工）**：
  本次数据是**卡在网关本地缓存**里等恢复的（日志显示是网关自己补的 128 条），
  **不是**靠 EMQX 离线队列。→ 两者分工：
  - **网关本地缓存**（`data/cache.jsonl`）管 **网关 ↔ Broker** 这一段
  - **EMQX 离线队列**（`MAX_MQUEUE_LEN=20000`）管 **Broker ↔ 订阅端** 这一段
- **⚠️ 与故障 1 的对照（两条合起来才是完整边界）**：
  | | 故障 1 · 拔线（设备侧） | **故障 2 · 停 EMQX（Broker 侧）** |
  |---|---|---|
  | 日志入队原因 | `连不上 Modbus 设备` | **`[缓存] 断网`** |
  | 缓存 | ❌ 0 行（无数据可存） | ✅ 128 行 |
  | 数据缺口 | ⚠️ 21:26 整分钟消失 | ✅ **0 分钟** |
  | 净损失 | ≈ 34 条 | **0 条** |

## 故障 3 · 改错端口（配置类故障）

- **时间**：2026-10-02 14:19 前后（注入约 3 分钟）
- **故障注入**：把网关的 `MQTT_PORT` 由 `"1883"` 改为 `"1884"`（⚠️ **只改网关那一处**，订阅端仍是 1883）→ `docker compose up -d --force-recreate gateway`
- **现象**：
  - ⚠️ **`cems-gateway` 仍然 `healthy`** —— 端口错着也 healthy（健康检查只看心跳文件是否新鲜，与 broker 是否可达无关）
  - 其余服务（emqx / subscriber）**全部 healthy** —— **没有任何东西是"停的"**
  - 日志：`网关启动: 设备 device:5020 → MQTT emqx:1884`（**错值就在启动横幅第一行**）
  - 日志每 5 秒：`[缓存] 断网，数据已入本地队列`（**与"停 EMQX"同一句话**）
  - 缓存持续增长；库内条数基本停滞
- **排查命令（⭐ 本条的核心）**：
  ```powershell
  docker compose ps                                  # ⚠️ 全都 healthy -> 一无所获
  docker logs cems-gateway --tail 10                 # 看到"[缓存] 断网" -> 会把人骗向"网络问题"
  docker logs cems-gateway | Select-String "网关启动" # ⭐ 启动横幅直接写着 emqx:1884
  docker inspect cems-gateway --format "{{range .Config.Env}}{{println .}}{{end}}" | Select-String MQTT_PORT
  docker inspect cems-subscriber --format "{{range .Config.Env}}{{println .}}{{end}}" | Select-String MQTT_PORT
  ```
  **→ 对比两个容器：gateway 是 `MQTT_PORT=1884`、subscriber 是 `MQTT_PORT=1883`。**
- **根因**：配置写错一个字符。**链路本身没问题、所有服务都在跑、没有任何进程崩溃。**
- **修复**：把 `MQTT_PORT` 改回 `"1883"` → 重建网关
  - 恢复：`MQTT 已连接: emqx:1883` → `[补传] 开始补传 46 条` → `[补传完成] broker 已确认 46 条`
- **数据影响（对账）**：
  | 项 | 值 |
  |---|---|
  | 基线 | 8701 条 |
  | 补传条数 | **46 条（46/46 全部确认）** |
  | 缓存残留 | 1 行（补传期间新采的，属正常） |
  | 恢复后 | 8760 条（+59 = 46 补传 + 13 直发） |
  | **数据缺口** | ⭐ **0** —— 14:17~14:22 逐分钟 11~12 条 |
  | **净损失** | **0 条** |
- **⭐ 我学到的一条**：
  > **所有服务都 `healthy` ≠ 配置是对的。**
  > 运行状态（进程活着/心跳在刷）和配置正确性（能不能连通）是**两件独立的事**。
  > 数据不进库时，**别只看"谁停了"**——没有东西停的时候，要去看**配置本身**（启动横幅、`docker inspect` 的实际环境变量）。
  > ⚠️ 且 `[缓存] 断网` 这个日志措辞会把人骗向"网络故障"，**但本条根因是配置写错一个字符**。

- **⚠️ 本次额外踩到的工具坑（不是演练故障，但是真坑，值得记）**：
  用 PowerShell 改这个 YAML 文件时踩了两次：
  1. **`Set-Content -Encoding utf8` 会写入 UTF-8 BOM**（PS7 行为）→ `docker compose` 的 YAML 解析器**不接受 BOM**：
     `go-yaml load error in parser (while parsing a block mapping) at L12.C1-L16.C3: did not find expected key`
     → 修法：`[IO.File]::WriteAllText($p, $text, [Text.UTF8Encoding]::new($false))`（显式无 BOM）
  2. **`Set-Content` 会把行尾由 LF 改成 CRLF** → 本来只改 1 行，`git diff` 却显示 **77 insertions / 151 deletions**（全文件都"变了"）
     → 修法：显式用 LF 写回；诊断时先 `git diff --stat` 看改动量对不对
  **⭐ 教训：改配置文件后，先看 `git diff --stat` 的改动量是否符合预期。** 只改 1 行却显示上百行改动 = 行尾/编码被动过。
