> 这一步要解决的是本项目最大的一条边界——「没有真实现场联调」
> （见 `docs/reference/已知边界汇总.md` §1 第 1 条：合成数据 + 合成负载 + 未接真实仪表）。
>
> 目标：把"合成数据"换成一条真实 RS-485 链路，并顺手补上"串口（RTU）"这条
> 项目 1 完全没有的代码路径（项目 1 只有 Modbus TCP）。
>
> 止损线：到货后最多 2 天。读不通就回退到虚拟串口继续，不要陷进去。

## 2. 接线

```
【变送器】                    【USB 转 485】              【DC 电源】
 1  485-A  ─────────────────  A
 2  485-B  ─────────────────  B
 3  电源正  ──────────────────────────────────────────  正极
 4  电源负  ────────────┬─────────────────────────────  负极
                        └────  G（共地）
                                   TR  → 先不接
```

三条硬要求（每条都是现场最常见的通信故障）：

| # | 要求 | 后果 |
|---|---|---|
| 1 | A 接 A、B 接 B | 反了读不到任何数据 |
| 2 | 供电别忘（且电压在范围内） | 不供电 = 静默 |
| 3 | 共地（变送器电源负极 ↔ 转换器 `G`） | 不共地是常见的"时通时不通"原因 |

桌面短线（几十厘米）不需要：终端电阻、屏蔽、阻抗匹配——别把这件事想复杂。

## 3. 步骤（每步有独立通过标准，不要跳步）

### S1 · 装驱动，确认出现 COM 口

| 项 | 内容 |
|---|---|
| 做 | 装 CH340 驱动 → 插上转换器 → 设备管理器看端口 |
| 通过标准 | 出现一个新的 `COMx`（记住编号，后面要用） |
| 不通 | 换 USB 口 / 换线；确认不是"USB转TTL"错型号 |

### S2 · 串口助手手动发帧（先不写任何代码）

| 项 | 内容 |
|---|---|
| 做 | 打开串口助手（SSCOM / 友善串口助手等），参数设 `COMx / 4800 / 8 / N / 1`，十六进制发送：<br>`01 03 00 00 00 02 C4 0B` |
| 通过标准 | 收到 9 字节：`01 03 04 [湿Hi] [湿Lo] [温Hi] [温Lo] [CRClo] [CRChi]`<br>（地址1 + 功能码1 + 字节数1 + 数据4 + CRC2 = 9）。本文件初稿误写"8 字节"，2026-10-07 实测后修正 |
| 最大的坑 | 默认波特率是 4800，不是 9600——填错一个字都收不到 |
| 第二步坑 | 手册写"初始/结束结构 ≥4 字节的时间"（比标准的 3.5 字符更保守）→ 你的切帧逻辑留的静默间隔要大于 3.5 字符 |

为什么先做 S2：先把硬件和参数确认掉，再写代码。
否则一旦读不通，你分不清是接线错、参数错、还是代码错。

### S3 · 对着寄存器表解析（用刚加的契约字段）

| 寄存器地址 | PLC/组态地址 | 内容 | 类型 | 换算 | 操作 |
|---|---|---|---|---|---|
| `0000H` | `40001` | 湿度 | `uint16` | ÷10 → %RH | 只读 |
| `0001H` | `40002` | 温度 | `int16`（有符号） | ÷10 → degC | 只读 |

手册原例（可直接对照）：
- 问询：`01 03 00 00 00 02 C4 0B`
- 应答：`01 03 04 01 E6 FF 9F 1B A0`
  - 湿度 `0x01E6` = 486 → 48.6 %RH
  - 温度 `0xFF9F` = -97（补码）→ -9.7 degC
- 手册明写："16bits 数据高字节在前" → `endian = AB`

> 这是本轮新增的 `dtype` / `endian` 字段的第一个真实用例：
> 温度必须声明为 `int16`（不是 `uint16`）——否则 `-9.7℃` 会读成 `6543.9℃`。
> 契约里已实现并测过这个例子（`tests/common/test_point_wire_format.py`）。

通过标准：读出的温湿度与独立来源（体温计 / 手机天气 / 空调显示）一致（±0.5℃ 内）。
这条叫"用第二个独立来源验证读数"：单一来源的读数不可信，必须有第二个来源交叉验证。

### S4 · 6 种异常实验（这一步才真正练到"现场排障"）

| # | 故意发什么 | 期望设备反应 | 练到什么 |
|---|---|---|---|
| 1 | 功能码 `06`（写寄存器）：`01 06 00 00 00 01 ...` | 回 `01 86 01 ...`（功能码 `06\|0x80`，异常码 `0x01` 非法功能码） | 异常响应格式 + `0x01` |
| 2 | 读不存在的寄存器（起始 `0x0010`，长度 2） | 回 `01 83 02 ...`（异常码 `0x02` 非法数据地址） | 地址校验 + `0x02` |
| 3 | 故意算错 CRC（改最后一个字节） | 完全不回（静默） | 超时处理 |
| 4 | 发错从站地址（`02` 替代 `01`） | 静默 | 超时 + 从站地址概念 |
| 5 | 波特率填错（9600 而不是 4800） | 乱码 / 静默 | 参数不匹配的典型现象 |
| 6 | A/B 反接 | 静默 | 现场第一号故障 |

第 3、4、5、6 条现象一模一样（都收不到回包）——区分它们靠排查顺序：

```
① 物理层：接线（A→A、B→B）、供电、共地
② 参数层：波特率 / 数据位 / 校验 / 停止位 / 从站地址（五个都要对）
③ 帧层  ：CRC 算对没、地址对不对、功能码对不对
④ 时序层：静默间隔够不够、超时设太短没
⑤ 设备层：这个地址的寄存器真的存在吗？设备真支持这个功能码吗？
```

异常响应格式（记住）：`[地址码] [功能码 | 0x80] [异常码] [CRC低] [CRC高]`

通过标准：6 条全部实测并记录（贴原始收发字节），且能说清每条"现象 → 归因"。

### S4 完成——两条实测与手册不符，且这两条最有价值

| 实验 | 手册/预期 | 实测 | 一致? |
|---|---|---|---|
| EXP1 发功能码 `06`（写单个寄存器） | `01 86 01`（异常码 `0x01` 非法功能码） | 原样回显 `01 06 00 00 00 01 48 0A` | 不符 |
| EXP2 读不存在的地址 `0x0010` | `01 83 02`（异常码 `0x02` 非法数据地址） | 正常应答，值全 0 `01 03 04 00 00 00 00 FA 33` | 不符 |
| EXP3 故意错 CRC | 静默 | 静默（0 字节） | 一致 |
| EXP4 错从站地址 `0x02` | 静默 | 静默 | 一致 |
| EXP5 错波特率（`9600`） | 乱码 / 静默 | 静默 | 一致 |
| REF 回到 `4800` 正常读 | 正常 | `01 03 04 02 30 01 12 7A 19` → 56.0 %RH / 27.4 degC | 一致 |

#### 发现 1：读错地址不报错，返回 0（静默的假数据）

设备对不存在的寄存器地址不返回"非法数据地址"异常，而是返回全 0。

后果：上位机寄存器地址配错时，会读到 `0 %RH / 0 degC` 而不是收到错误。

而且更麻烦：`0 %RH` / `0 degC` 都落在量程内（湿度 0~100、温度 -40~125）→
单靠量程白名单拦不住，必须加跳变检测 / 合理性判断（温度不可能 1 秒内从 27 degC 掉到 0）。

→ 与 `docs/reference/已知边界汇总.md` 里那条「缺数不能判达标」是同一类问题：
设备/链路的"沉默"不等于"数据可用"。

#### 发现 2：功能码 06 被回显，但值没真正改变

手册明写「本变送器只用到功能码 0x03」，实测发 `06` 会收到正常回显；
但随后读回湿度仍是 56.0 %RH（不是写入的 0.1）→ 写入没有真正生效。

后果："回显"会让人误以为写成功了——连"设备到底支不支持写"都判断不出来。

→ 印证本项目既有纪律：「收到 PUBACK ≠ 入库成功」；
写的响应是原样回显，不能证明写入生效——必须回读验证。

#### 两条串起来的结论

> 设备会用「假数据（0）」代替「报错」，用「回显」代替「真正的确认」。
> 所以「设备说成功」不等于成功——上位机必须自己校验、自己回读。

这是本项目「数据可靠性」设计在真实硬件上的第一次印证，且有原始字节支撑。

### S5 / S6 进行中（2026-10-11 起）

#### 关键架构发现：Docker 容器访问不到 Windows 的 COM 口

真机挂在 `COM3` 上，而项目 1 的网关跑在容器里——容器拿不到宿主的串口。
所以真机不能直接被容器读。

#### 解法 = 串口服务器模式（现场本来就这么接 485 设备）

```
[温湿度变送器] --RS485/Modbus RTU--> COM3
                                        |
                        scripts/serial_bridge.py（跑在 Windows 宿主）
                                        |
                                Modbus TCP 127.0.0.1:5021
                                        |
                    [项目 1 的网关容器]  MODBUS_HOST=host.docker.internal
```

这样不需要给网关加 RTU 支持——这正是真实 CEMS 现场把 485 设备接入网络的标准做法。
而"亲手接 485 线、跑 RTU 帧、做异常实验"这件事，由上面的 S2/S4 承证（有原始字节）。

#### 已实测通过

| 步 | 结果 |
|---|---|
| 桥在宿主启动、轮询 `COM3` | 日志每秒刷新：`湿度 57.4→57.6 %RH ｜ 温度 26.4 degC` |
| 宿主侧读桥（TCP `5021`） | `regs [575, 264, 0, 0]` → 57.5 %RH / 26.4 degC，桥状态 `0`（新鲜） |
| 容器内读桥（`host.docker.internal:5021`） | `regs [578, 263, 0, 0]` → 57.8 %RH / 26.3 degC |
| 负向对照：读不存在的从站 | `isError: True`——`single=False` 生效，没有静默返回别的从站数据 |

#### 桥的两个设计取舍

1. 对外多暴露两个寄存器：`0x0002` 桥状态（`0` 新鲜 / `1` 陈旧）、`0x0003` 累计读失败次数。
   理由：实测发现真机读错地址会沉默返回 0（见上面 S4 发现 1），
   桥故意不重复这个错误——读失败时保留上次好值 + 置状态位，
   让下游能看见"这份数陈旧了"，而不是把 0 当真实湿度。
2. `single=False`（照 `src/device/modbus_server.py` 的既有结论）——
   否则"请求不存在的从站"会静默返回数据（本项目已经踩过一次的坑）。

##### 两条必须守住的边界

1. 语义边界（已在代码与 compose 注释里写明）：
   `Temp`/`Humidity` 两列在环保口径上是烟气参数，真机测的是环境温湿度——
   两个不同的物理量。启用本开关的部署只作数据链路演示，不作环保口径依据。
2. 读不到真机时不回落到仿真值或 0——机制分三层，任何一层都不许静默：

   | 时机 | 行为 | 为什么 |
   |---|---|---|
   | 启动时读不到 | 设备层**降级启动**（不退出）：日志打 CRITICAL，Temp/Humidity 写越界值，其余 7 点照常 | 与运行期用同一条规则（读不到就写越界值）。硬退出会让整层起不来——部署到没有真机的机器上时，一个可选外设能把整条链路全灭；而降级启动的可见性更好（日志 + 断档 + 覆盖率 + 事件表留痕），硬退出只有一个"起不来" |
   | 运行中变送器掉线（桥活着） | 设备层读桥的状态位 `0x0002` → 写越界值 | 桥会保留上次好值，只有状态位能说明"这个值不新鲜了" |
   | 运行中桥本身掉线 | 连续失败 ≥ `REAL_DEVICE_STALE_AFTER_FAILURES`（默认 3）→ 把保留值标记为陈旧 → 同样写越界值 | 桥死了就读不到状态位——所以"连不上"本身必须升级成"陈旧" |
   | 桥重新上线 | 轮询线程下一次读成功即自动恢复，**不需要重启容器** | 降级态与正常态走同一条读路径，区别只在于桥在不在 |

   降级启动的判定点在 `main()`；写越界值在 `overlay_real_values()`。
   注意 `overlay_real_values()` 里有个必须的分支：**从没读到过**（`snapshot()` 为 `None`）
   也要写越界值——那种情况下寄存器里躺着的是仿真读数，直接原样返回就等于把仿真温湿度
   当真实值发出去。这个分支以前被"启动预检直接退出"挡住了，改成降级启动后必须显式处理。

   越界值怎么来：`量程上限 + 1` × scale（`Temp` → 301.0 degC、`Humidity` → 101.0 %），
   由契约导入期算出来，不写魔数。
   不用 0：`0` 落在量程内（`Temp [0,300]`、`Humidity [0,100]` 都含 0），
   会被当成真实读数一路入库——那正是真机教我们的坑（S4 发现 1）。

   下游效果：接入层按既有"超量程"规则拒收整条报文 → 日志有明确原因 + 原始报文、
   库里出现断档、覆盖率下降。三级都可查，一眼能看出"真机死了"。

##### 掉线/恢复实测（2026-10-11，故意 kill 掉桥）

| 阶段 | 观测 |
|---|---|
| 断开后 14 s | 设备层 `reg6=3010 (301.0 degC)`、`reg7=1010 (101.0 %)`——两个都超量程；其余 7 点照常仿真 |
| | 设备层日志 `[ERROR] 读真机失败（连续第 7…10 次）…` |
| | 接入层日志 `[WARNING] 报文已拒收（累计 N 条）: 测点 Temp 超出量程 [0.0, 300.0]: 301.0 \| 原始报文: … Temp=301.0 Humidity=101.0 …` |
| | 库里最后一行停在 `14:36:36`——不再前进 |
| 恢复后 18 s | `reg6=268 (26.8 degC)`、`reg7=593 (59.3 %)`——回到量程内 |
| | 设备层日志 `[WARNING] 真机恢复读取（此前连续失败 13 次）` |
| | 库里从 `14:36:36` 直接跳到 `14:37:06`——中间那 ~30 s 是断档，一条假数据都没补 |

那个断档就是证据：证明系统宁可缺数，也不编数——与项目既有的「缺数不能判达标」是同一套纪律。

##### 第二次故障注入：桥写越界值（修掉"路径 B 有洞"）

背景（评审发现）：`POINT_SET=transmitter` 的网关（路径 B）只读 2 个寄存器、看不到桥的状态位——
所以"桥活着、变送器死"时，路径 B 会把陈旧值当新鲜写进 `transmitter_data`。
也就是说：只把洞从路径 A 挪到了路径 B。

修法（一处改动，两条路径同时修好）：桥在陈旧时不返回旧值，改返回越界值
（`Humidity → 101.0 %`、`Temp → 301.0 degC`——同时超出 CEMS 与变送器两套契约的量程，
导入期有自检 `_check_stale_sentinels()` 防止有人放宽量程后哨兵失效）。
把"无效"做进值本身，任何消费者都无法误用；状态位 `0x0002` 保留给诊断。

| 层 | 现象 |
|---|---|
| 桥 `:5021` | `[1010, 3010, 1, 15]`；日志 `could not open port 'COM3': PermissionError(13, '拒绝访问')`，每秒重试不放弃 |
| 设备层 `:5020` | `[…, 3010, 1010, …]`——真机 2 点越界，其余 7 点照常仿真 |
| 路径 A 接入层 | `报文已拒收: 测点 Temp 超出量程 [0.0, 300.0]: 301.0` |
| 路径 B 接入层 | `报文已拒收: 测点 AirHumidity 超出量程 [0.0, 100.0]: 101.0 \| 原始报文: AirHumidity=101.0 AirTemp=301.0` |
| 两张表 | `transmitter_tx01` 停在 `14:50:11`；`plant1_device1` 断档 `14:50:17 → 14:51:57` |
| 释放后 | 桥 `[611, 261, 0, 86]`（状态位回 0）；两条链路各自自动续上，无需人工干预 |

注入方式：用另一个进程独占 `COM3` 90 秒——同时覆盖"串口被别的程序占用"这个真实场景
（与串口助手互斥是同一种故障）。

##### 已知设计边界（报告必须写明，不要含糊）

真机那 2 个点混在 9 点报文里，而接入层是"一处不合格 → 整条报文拒收"——
所以真机故障会让其余 7 个仿真测点一起断档。这是项目原有的、刻意的设计
（见 `subscriber_to_td.py` 的 `parse_payload` docstring：`NaN`/`inf` 会让 TDengine 报语法错误）。

但它在工业口径上是个缺陷，名字叫「故障不隔离 / 单点故障扩散」：
成熟体系（HJ 212 的逐参数 `Flag`、OPC UA 的 `StatusCode`、SCADA 的质量位）都是逐点质量位——
"一个点坏"与"整条不可信"是两件事，项目用一条规则处理了。

根因：项目本项目的 `Flag` 是整条一个（`gateway.py` 的 `build_payload` 硬编码 `Flag=N`），
而 HJ 212 里 `Flag` 是每参数一个；`points.py` 也明确写"本项目不是 HJ 212 报文"，
ADR-0007 把"数据标记的判定源（本项目无仪表状态源）"登记为南向扩项。
仿真器里从没有"某一点可能是坏的"这个需求——真机接进来才第一次产生它。

现状取舍（两条路并存）：

| 路径 | 定位 | 隔离性 |
|---|---|---|
| A. 设备层混流（`REAL_DEVICE_ENABLE=1`） | 故障注错工装：耦合让"全链路如何响应设备故障"最可见，正是报告要的效果 | 2 点故障 → 9 点断档 |
| B. 点集分离（`--profile transmitter`） | 真机日常数据的推荐路径 | 只影响 `transmitter_data` |

改进方向（需 ADR，本期未做）：给报文与表加逐点质量位，把接入层从"整条拒收"改为"逐点标注"。

##### 开关三个状态下的行为（回答"不接真机时是什么"）

| `REAL_DEVICE_ENABLE` | 真机状态 | `Temp`/`Humidity` 的值 |
|---|---|---|
| `0`（默认） | — | 纯仿真值（~199 degC / ~46 %）。本开关关闭时的语义就是"纯仿真设备"，这是设计意图，不是缺陷 |
| `1` | 启动时读不到 | **降级启动**：越界值 301.0 degC / 101.0 % → 接入层拒收 → 可见断档；其余 7 点照常。桥上线后自动恢复，不用重启容器 |
| `1` | 运行中读不到 | 越界值 301.0 degC / 101.0 % → 接入层拒收 → 可见断档 |

> 说明：本表原写"启动时读不到 → 设备层拒绝启动"，2026-10-12 改为降级启动。
> 理由见上面"机制分三层"那张表；实测见本文 §降级启动实测。

##### 途中抓到的 4 个"静默类"缺陷（都已修）

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | 桥读取器 `read_once()` 只读不落状态 | 预检通过后到轮询首次成功之间会对外发布仿真值 |
| 2 | 接入层最初写 `getattr(点集,"EMISSION_LIMIT_APPLICABLE",False)` | `points.py` 无此常量 ⇒ cems 告警与小时结算整体静默消失 |
| 3 | 派生表列按线格式建 `SMALLINT` | TDengine 静默取整 `57.8→58`、`-9.7→-10` |
| 4 | 镜像"半旧" | 并发场景下 `docker build` 抓到了改到一半的源码（缺 `main()` 的真机块）。`docker build` 不受文件版本守卫保护——用宿主 vs 容器文件哈希才确认（`8a4f4254` vs `2879a6b5`），重建后一致 |

##### 怎么开关

```powershell
# 开（.env 里已写好；改完重建 device 容器）
REAL_DEVICE_ENABLE=1
REAL_DEVICE_HOST=host.docker.internal
REAL_DEVICE_PORT=5021
docker compose up -d --build device

# 关（回到纯仿真）
REAL_DEVICE_ENABLE=0 ; docker compose up -d device
```

桥必须先在宿主上跑：`python scripts/serial_bridge.py --port COM3`（它占着 COM3）。
桥先起不是硬要求——不起也能跑，设备层会降级（见下）；但先起就没有那段降级窗口。

##### 降级启动实测（2026-10-12）

三个场景都在本机实测过，用的是设备层直跑（不经容器）+ 一个假桥（同 4 寄存器布局）：

| 场景 | 做法 | 实测结果 |
|---|---|---|
| **桥不在** | `REAL_DEVICE_ENABLE=1`，桥端口无人监听 | 进程**不退出**（`alive after 8s: True`）；`Temp_raw=3010 / Humidity_raw=1010`（越界值）；其余 6 个测点照常变化；日志出现 CRITICAL 降级说明与 `[从站1] 真机尚无有效读数…写越界值` |
| **桥上线** | 起假桥（湿度 623 / 温度 254 / 状态 0） | **+2 秒即恢复** `Temp_raw=254 / Humidity_raw=623`，**没有重启容器**；日志出现"真机恢复读取" |
| **纯仿真** | `REAL_DEVICE_ENABLE=0` | 行为完全不变（走未启用分支，逐位不动） |

场景 1 的关键判据不是"进程活着"，而是**寄存器里是越界值而不是仿真值**——
如果只是不退出而让仿真值流出去，那就从"起不来"变成了"静默假数据"，比原来更糟。
代码上这一点由 `overlay_real_values()` 的 `snapshot() is None` 分支保证。
