# 边缘节点下板：树莓派 2B（ARMv7）跑 device + 网关

> 目的：把链路**南向两层**（device + gateway）搬到一块 ARM 边缘节点上，用 systemd 托管，
> 并把"真机直读 / 断网补传 / 崩溃自愈 / 重启自启"四条在真实硬件上验一遍。
> 取证日期：2026-10-22 · 证据见 `docs/evidence/edge-arm-20261022/`

---

## 一、为什么是这两层，不是全栈

| 层 | 跑在哪 | 理由 |
|---|---|---|
| device（:5020，真机直读） | **边缘节点** | 串口在这块板子上；容器拿不到宿主串口 |
| gateway（采集 / 断网缓存 / 补传） | **边缘节点** | 断网自治的载体，必须在现场 |
| EMQX / TDengine / 接入层 / web / nginx | **平台侧**（x86 宿主） | 按时序库、broker、展示的定义属平台侧；1 GB 内存的 2B 也跑不动 |

拓扑：

```
[温湿度变送器] --RS485--> [树莓派 2B · cems-edge]
                            cems-device      :5020  （直读 /dev/ttyUSB0，1 号炉 2 个点）
                            cems-gateway-plant1      从站 1 → MQTT
                            cems-gateway-plant2      从站 2（纯仿真）→ MQTT
                                  | MQTT 1883（百兆网口）
                                  v
                            [x86 宿主 192.168.31.18]
                            EMQX → 接入层 → TDengine → web / nginx
```

## 四、服务托管（systemd）

单元文件在 `deploy/systemd/`，三个服务：`cems-device` / `cems-gateway-plant1` / `cems-gateway-plant2`，
全部 `Restart=always`（进程退出即拉起）+ `Type=notify` / `WatchdogSec=60`（采集循环每圈发 `WATCHDOG=1`，
超时未发 = 活着但不出数，systemd 杀掉重启）、日志走 journald。

心跳实现在 `src/common/sd_notify.py`：没有 `NOTIFY_SOCKET` 时是 **no-op**，所以普通
`python -m src.device.modbus_server`、容器、单元测试都不受影响，不需要开关。

```bash
sudo bash deploy/systemd/install.sh --repo /home/ddf/cems --user ddf --platform-host 192.168.31.18
systemctl is-enabled cems-device cems-gateway-plant1 cems-gateway-plant2
```

> ⚠️ **Modbus `:5020` 只绑回环**（`SERVER_HOST=127.0.0.1`）：网关就在同一台板子上读它，
> Modbus 本身无认证，没必要对局域网开放。实测从 Windows 探测 `192.168.31.236:5020` 为 closed。
>
> ⚠️ **设备层日志已节流**（2026-10-22）：稳态读数逐条 DEBUG，每 `SERIAL_INFO_SUMMARY_SECONDS`（默认 60 s）
> 一条 INFO 汇总；串口失败在状态变化时打 WARNING、之后每 `SERIAL_FAILURE_REMIND_SECONDS`（默认 300 s）
> 提醒一次。实测 70 s 窗口只有 **1 行**日志（此前约 35 行），量级从 ~10.7 MB/天 降到 ~1 MB/天。
>
> ⚠️ 平台侧 broker 必须能从板子访问。本次在 x86 宿主上把 EMQX 的 1883 绑到 `0.0.0.0`；
> **其余端口（TDengine / nginx / web / 管理台）应保持 `127.0.0.1`**，见 `README.md` §端口暴露 / 安全。

> ⚠️ **平台侧不要再起仿真设备层**：2026-10-22 起 `docker-compose.yml` 的 `device` / `gateway` 两个服务
> 放在 `profiles: ["sim"]` 下。边缘部署时平台侧 `docker compose up -d` **不要带** `--profile sim`，
> 否则会在这台机器上另起一个仿真从站 1，与树莓派的真机数据混写进同一张子表（`plant1/device1`），
> 事后无法区分哪段是真、哪段是假。全本机演示才用 `--profile sim`。

## 四·五、冻结状态（2026-10-22）

**冻结范围**：树莓派上的 `cems-device` + `cems-gateway-plant1/2` 三个服务、`deploy/systemd/` 单元、
`/etc/cems/edge.env`、`/dev/ttyUSB0` 的接线方式、485 参数（4800/8/N/1、从站 1）。

**冻结基线**（本次核过）：
- 三个服务 `active`、`enabled`、`NRestarts=0`，单元文件与仓库 `deploy/systemd/` 逐字节一致；
- 真机读数新鲜（湿度 58.2 %RH / 温度 26.0 degC，状态位 0），心跳 `south_ok=true` / `mqtt_ok=true` / `backlog_bytes=0`；
- 前端 health `healthy:true`、`rows_last_1min=12`；磁盘 16%、journal 4.5 MB、`systemctl --failed` 为 0；
- 时区 `Asia/Shanghai`、NTP 已同步。

**解冻记录**：① 2026-10-22 19:29 为验证 `sensor_ok` 告警做过一次受控解冻（改 drop-in 指向不存在的串口
→ 重启设备层 → 验证告警与恢复 → 删除 drop-in → 再重启）。复核结果：三服务 `active`、`NRestarts=0`、
真机读数恢复（58.5 %RH / 26.0 degC）、`/api/health` 的 `sensor_ok=true`，已重新冻结。

**冻结纪律**：
1. 冻结期内**不改 Pi 上的配置、不重启 `cems-device`**（重启要重新观察 10 分钟）；
2. 任何改动（含 5020 改绑回环、日志降级）都算"解冻"，改完必须重跑 §五 的第 1/3/4/7/8 项；
3. 平台侧改动不受冻结限制，但平台侧**不要带** `--profile sim`（见上一条）；
4. 硬件层面的已知问题不随冻结消失：供电欠压 `0x50005`（不长期跑则接受）、硬断电未测、无 RTC 靠 NTP。

## 五、实测结果（2026-10-22）

| # | 项 | 结果 | 证据 |
|---|---|---|---|
| 1 | **真机直读** | 每 2 s 采一次：湿度 **56.6~56.7 %RH**、温度 **25.6 degC**、状态位 0；无一次读失败。（2026-10-22 起日志改为每 60 s 一条汇总，逐条走 DEBUG） | `02-serial-read.txt`（日志段）、`07-e2e-tdengine.txt` |
| 2 | **端到端入库** | TDengine `device1` 的 `temp`/`humidity` 是环境真值（25.6 / 56.8~57.3），真机在线期间非空行 **840** 条；同库 `device2` 仍是烟气仿真值（207 / 44） | `07-e2e-tdengine.txt` |
| 3 | **重启自启** | `reboot` 后三个服务无人工介入自动 active；三个 unit `enabled`。（只验了正常 `reboot`，**硬断电未测**） | `04-boot-autostart.txt`、`03-systemd-units.txt` |
| 4 | **崩溃自愈** | `kill -9` 主进程 → systemd 拉起（PID 433→790，`NRestarts=1`），另外两个服务不受影响，重启后自动补传 1 条 | `05-crash-recovery.txt` |
| 5 | **断网补传** | 停 broker 90 s：网关缓存 **25 条**；broker 恢复后 `[补传完成] broker 已确认 25 条`，`cache.jsonl` 归零；`device2` 近 6 分钟 **71 行**（期望 72，差 1 行为窗口边界） | `06-broker-outage-resend.txt` |
| 6 | **资源足迹** | 常驻 RSS：device **19.2 MB**、网关各 **21.4 MB**；CPU 合计 **< 2.5%** | `09-resources.txt` |
| 7 | **真机失效与自动恢复** | 拔掉 485（USB 断开 16 分钟，连续失败 **186** 次）：状态位=1、对外写越界值、**不回落到仿真**；库里 `device1` 的 `temp`/`humidity` 变成 **NULL**（不是 0、不是假数据）。插回后**同一进程**（PID 未变、`NRestarts=0`）自动恢复：57.2 %RH / 26.1 degC，库里恢复真值 | `12-485-absent-stale.txt`、`16-485-replug-recovery.txt`、`07-e2e-tdengine.txt` |
| 8 | **应用级看门狗** | `Type=notify` + `WatchdogSec=60`，采集循环每圈发 `WATCHDOG=1`。`kill -STOP` 冻结主进程（模拟"进程活着但循环卡住"）→ 60 s 后 `Watchdog timeout (limit 1min)!` → `SIGABRT` → 自动重启（PID 883→905，`NRestarts=1`），重启后继续出数 | `13-watchdog-sigstop.txt` |
| 9 | **真机失效告警** | drop-in 把串口指向不存在的端口（等价拔 485）：`sensor_ok=false`、`invalid_points_last_window=38`、WARNING 在越过阈值时打出；恢复后 `sensor_ok` 回 `true` 并打 INFO。`healthy` 全程为 `true`（链路在流） | `18-p2-hardening.txt` | P2 四项：5020 回环、日志节流（70 s 1 行）、web2 进 compose、空 inflight 清理 + 冻结复核 |
| 10 | **加固四项**（P2） | ① Modbus :5020 只绑回环（Windows 侧不可达）；② 设备层日志节流（70 s 仅 1 行）；③ 二号炉大屏 `web2` 进 compose（project=cems、service=web2、healthy）；④ 0 字节 `inflight-*.jsonl` 清空（11 → 0） | `18-p2-hardening.txt` |
| `17-health-sensor-alarm.txt` |

> 第 4、5 条是验收时现场做的：kill 是 `kill -9` 主 PID；断网是停掉平台侧 EMQX 容器 90 s
> （等价于"broker 不可达"，比拔网线少一个变量），恢复后按缓存条数逐条对账。

## 六、边界（本次**没有**覆盖的）

| # | 边界 | 说明 |
|---|---|---|
| 1 | ⚠️ **看门狗只覆盖"采集循环卡死"** | `Type=notify` + `WatchdogSec=60`。但 device 的心跳在 `refresh_once` **之前**无条件发，刷新失败也照发（`refresh_once` 按从站吞异常），所以：真机失效、串口线程假死、刷新全失败，**都不会**触发重启。它抓的只是"线程完全不转了"。数据真伪靠越界值 + 接入层拒收兜底，见第 9 条 |
| 2 | ⚠️ **MQTT 已开认证、但仍是明文** | 2026-10-22 起 broker 用 `password_based` + `built_in_database`：匿名连接被拒（CONNACK 135）、带凭据成功；凭据在 `/etc/cems/edge.env`（600）。**无 TLS**，只适合可信内网 |
| 3 | ⚠️ **供电欠压** | `vcgencmd get_throttled = 0x50005`：换线后仍报欠压+降频，长期跑有随机卡死与 SD 损坏风险，需换 5V 2.5 A 电源 |
| 4 | ⚠️ **SD 卡写寿命** | 网关缓存文件落在 SD 卡上（正常运行时 `cache.jsonl` 为空，只在断网时写）；未做写放大测量 |
| 5 | ⚠️ **ARM 上只跑了南向两层** | web / 接入层 / 时序库仍在 x86；"整栈上 ARM"未验证 |
| 6 | ⚠️ **无 RTC** | 2B 没有硬时钟，首次启动时间来自 fake-hwclock，联网后由 NTP 校正（`last` 里会看到假的旧日期） |
| 7 | ⚠️ **只测一组串口参数** | 4800/8/N/1、从站 1；其它波特率/校验组合未测 |
| 8 | ⚠️ **单串口单设备** | 一条 485 总线只挂了一台变送器；多从站真实直读未测 |
| 9 | ⭐ **真机失效告警**（已补） | `/api/health` 新增 `sensor_ok`：最近 300 s 无效测点数 ≥ 12 即 `false` 并打 WARNING，持续 5 分钟升 CRITICAL。⚠️ `healthy` 仍为 `true`（链路在流）——两者分开是有意的，真机坏了不该让 nginx 的 `depends_on=web healthy` 起不来。受控注入实测见 `17-health-sensor-alarm.txt`；恢复延迟上界 = 300 s 窗口 |

## 七、复现命令（从拿到板子到跑通）

```bash
# 0) 板子上：依赖
sudo apt-get update && sudo apt-get install -y python3-venv python3-pip
python3 -m venv ~/cems/.venv
cp requirements-edge.txt ~/cems/
~/cems/.venv/bin/pip install -r ~/cems/requirements-edge.txt

# 1) 同步代码（仓库在该机上不是 git 仓库时）
#    Windows: tar -C <repo> -czf - src deploy requirements-edge.txt | ssh ddf@cems-edge.local "tar -C ~/cems -xzf -"

# 2) 冒烟：只读探针（不占 TCP 端口）
cd ~/cems && .venv/bin/python -m src.device.rtu_master --port /dev/ttyUSB0 --count 5

# 3) 装 systemd 单元
sudo bash deploy/systemd/install.sh --repo /home/ddf/cems --user ddf --platform-host <平台侧 IP>

# 4) 自检
systemctl is-active cems-device cems-gateway-plant1 cems-gateway-plant2
journalctl -u cems-device -n 20 --no-pager        # 应有"串口直读：湿度 x %RH ｜ 温度 y degC ｜ 状态位=0"
```

**预期**：三个服务 active；device 日志每 2 s 一条真机读数；平台侧 TDengine 里 `device1` 的
`temp`/`humidity` 是环境值，`device2` 仍是仿真值。
