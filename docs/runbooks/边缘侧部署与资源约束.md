# 边缘侧部署与资源约束

> **这份文档补的是一条"定位证据"**：项目对外说自己是**"工业数据采集 + 边缘计算"**，
> 链路设计上确实是边缘形态（本地采集 → 本地清洗/校验 → 本地缓存/断网自治 → 本地时序库 → 本地告警，北向才上云），
> 但仓库里**一直没有任何"跑在资源受限的机器上"的痕迹** ——
> 全仓搜 `边缘|edge|ARM|systemd` 零命中，612 行 `docker-compose.yml` **零个资源上限**，
> 实际跑法是 12 个容器 + Docker Desktop + WSL2（一台 20 vCPU / 15.9 GiB 的机器）。
>
> **本文只补这一条，并且只补能实测的那部分**：给边缘侧服务封顶 + 长时间采证实际占用 +
> 把"断了北向会不会丢数""进程崩了会不会自己回来"这两件事真跑一遍。
> 它**不改架构**（架构本来就是边缘的），也**不新增 ADR**（没有新的架构决策）。
>
> ⚠️ **本文所有数字都来自实跑**，原始输出在 `docs/evidence/edge/`。
> ⚠️ **局限单列在 §6**，包括"哪些没做到"。

## 一、边缘侧是哪几个服务，为什么是它们

| 层次 | 容器 | 是否"边缘侧" | 理由 |
|---|---|---|---|
| 数采 | `cems-device` | ✅ | 它扮演现场的数采仪/PLC：读从站寄存器、聚合成一个寄存器块。现场部署时它就在机柜里 |
| 网关 | `cems-gateway` / `cems-gateway-plant2` | ✅ | 本地清洗/校验/打时间戳/**本地缓存+补传**（断网自治的载体），北向才发给 broker |
| 平台 | `tdengine` / `emqx` / `cems-redis` / `cems-nginx` / `cems-web` | ❌ | 按定义属于**中心侧**（时序库、broker、缓存、展示）。本机为省事把它们和边缘侧挤在一台机器上，但**不把它们算进边缘资源额度** |
| 接入 | `cems-subscriber` / `cems-subscriber-plant2` | ❌（口径说明） | 它订阅 broker 写库，逻辑上属于**平台侧接入层**。部署上若和边缘盒子同机，资源要另算；本文按"平台侧"处理 |

> 本文资源采证只记**数采 + 两个网关**，共 3 个容器。
> 把平台侧混进来的话，"边缘占用"这个数字会被 TDengine 这类重件稀释掉，失去意义。

## 二、资源约束怎么写的（含"哪种写法真生效"的实测）

### 2.1 事实先行：**两种写法在本机都生效**

这是要先实测的项，因为 `deploy.resources.limits` 是 **swarm 口径**的字段，
在 `docker compose`（非 swarm）下"到底吃不吃"随版本变，**不能照抄**。

实测方法：写一个一次性 compose 文件，两个服务分别只用一种写法，起来后读 `HostConfig`。

```
# probe-deploy.yml（一次性的，跑完即删）
services:
  probe-deploy:                      # 只写 swarm 口径
    deploy:
      resources:
        limits: { memory: 512m, cpus: "1.0" }
  probe-service:                     # 只写 service 级字段
    mem_limit: 512m
    cpus: 1.0
```

```
$ docker inspect edgeprobe-probe-deploy-1 --format 'Memory={{.HostConfig.Memory}} NanoCpus={{.HostConfig.NanoCpus}}'
Memory=536870912 NanoCpus=1000000000          <-- 生效
$ docker inspect edgeprobe-probe-service-1 --format 'Memory={{.HostConfig.Memory}} NanoCpus={{.HostConfig.NanoCpus}}'
Memory=536870912 NanoCpus=1000000000          <-- 生效，且逐位相同
```

环境：Docker **29.7.2**、Docker Compose **v5.5.1**（本机 `docker version` / `docker compose version`）。

### 2.2 本仓库的选择：**两种都写**

`docker-compose.yml` 里新增锚点 `x-edge-limits`（`device` / `gateway` / `gateway2` 三处合并）：

```yaml
x-edge-limits: &edge-limits
  mem_limit: 512m            # compose 原生字段：语义最确定，不依赖 swarm 口径
  cpus: 1.0
  deploy:                    # 让这份编排在 swarm / 其它入口下也带着同样的约束
    resources:
      limits:
        memory: 512m
        cpus: "1.0"
```

**为什么两种都写而不是只写一种**：`mem_limit`/`cpus` 是"本机这条路径确定生效"的那一份；
`deploy.resources.limits` 是"换入口也不至于悄悄变成无上限"的那一份。
两者取值**故意保持一致**，免得将来有人只改一处、两个入口给出不同额度。

⚠️ 合并键用的是**列表形式** `<<: [*app, *edge-limits]`：YAML 合并是逐 key 的**浅合并**，
两个锚点各有各的键，列表形式合并后 `image`/`restart`/`logging` 与 `mem_limit`/`cpus` 都在。
（实测：`docker compose config` 渲染出的 `mem_limit` / `cpus` / `deploy.resources.limits` 三项齐全。）

### 2.3 生效验证（现场命令与原始输出）

```
$ for c in cems-device cems-gateway cems-gateway-plant2; do
    docker inspect $c --format '{{.HostConfig.Memory}} {{.HostConfig.NanoCpus}}'; done
  加之前: 0 0        <- 全仓零限制的现状：两个都是 0
  加之后: 536870912 1000000000    （512 MiB / 1.0 vCPU）
```

重建只动了三个边缘侧容器（`docker compose --profile plant2 up -d device gateway gateway2`），
其余 7 个容器**没被重建**（`Up 12~15 minutes` 未变），真机链路不受影响。

### 2.4 取值理由：512 MiB / 1 vCPU 够不够

- **量级**：512 MiB / 1 vCPU ≈ 一台 **2 核 2 GB 边缘盒子**给单个服务留的额度。
- **实际占用**（§3 采证）：三容器常驻 **22~27 MiB**、CPU 峰值 **< 8%**，
  即内存用了上限的 **~5%**、CPU 用了 1 vCPU 的 **< 8%** —— **额度是有余量的顶，不是贴着用**。
- ⚠️ **没有出现 OOM / 重启**：10 个容器在加限后全部 healthy（§4 验收 4）。
  采证 CSV 里 `mem_used_bytes = 0` 的行只出现在网关**被 kill 的那段时间**（容器没在跑，`docker stats` 给 0）。

### 2.5 ⚠️ 实测反例：**自动重启会丢掉这个额度**

见 §5.2 的崩溃实验：`docker kill` 之后容器一度被外部（Docker Desktop 侧）拉起，
**同一容器、未重建，`HostConfig.Memory` 从 512 MiB 变成 1 GiB** —— 额度没被保住。
**用 `docker compose up -d <svc>` 恢复则能拿回 512 MiB**（实测 `恢复后 mem_limit=536870912 B`）。
⇒ **结论：资源额度在"容器重建"这条路径上是可靠的，在"容器被外部拉起"这条路径上不可靠**。
生产上要真保证，应让编排器（或用 `docker compose up` 的巡检脚本）负责重启，而不是靠 Docker 自动重启。

**⚠️ 为什么要分成"入库快照 + 长跑追加段"两份**：采证脚本一跑就是 24 h，每个采样点都在追加 ——
如果它直接写**被 git 跟踪**的那份 CSV，`git status` 会在提交后**立刻又变脏**，
评审看到的是"改了却没提交"。所以约定：
`resource-24h.csv` 是**入库的、提交那一刻的冻结快照**，
继续采的那部分写 `resource-24h.append-live.csv`（`.gitignore` 排除，用 `--append-file` 或直接把 `--out` 指过去）。
24 h 跑完后把追加段并入 `resource-24h.csv` 再提交一次，就得到"一份完整、且入库时工作区干净"的证据。

**⚠️ 时长如实交代**：采证脚本是**真的按 24 小时设计并在跑**（`--duration-hours 24`，
心跳文件里 `duration_hours: 24.0`），但本文写作时它才跑了几十分钟，
**所以本文里的汇总数字是"约 25 分钟窗口"的，不是 24 小时的**。
24 小时跑完后，用同一条命令重算汇总即可（无需重跑采证）：

## 四、断链自治实验

### 4.1 ⚠️ 选了哪种断法，以及**为什么另外两种被实测否掉**

任务是"**断上行**，不要拔网线"。候选有三种，全部**没有碰宿主网络**（没拔网线 / 没 `netsh` / 没禁网卡），
宿主上的 `scripts/serial_bridge.py`（占 COM3 的真机桥）**全程在跑**。

| 候选 | 结果 | 实测证据 |
|---|---|---|
| (a) `docker network disconnect cems-net cems-gateway` | ❌ **失败** | 网关只挂在 `cems-net` 一张网上，断掉它 = **连 Modbus 的设备层也一起断**：网关日志 `Connection to (device, 5020) failed: [Errno -3] Temporary failure in name resolution`。结果是**采不到数**：60 s 内积压 **0 行**，"没丢数据"变成了"本来就没产生数据" —— 自治这件事**根本没被验证到**（原始输出留档：`docs/evidence/edge/edge_autonomy_linkcut_20261011T183650.txt`） |
| (b) 把 broker 名字改指黑洞（容器内 `/etc/hosts` 加 `127.0.0.1 emqx`） | ❌ **失败** | paho **已建好的 TCP 会话不会因为改 hosts 而断开**（hosts 只在下一次重连解析时生效），`is_connected()` 一直是 True → 网关继续"发得成功"。持续观察 **2 分钟无断开、无积压** |
| (c) **`docker stop emqx`（采用）** | ✅ **有效** | 立刻关掉 TCP → 网关 `on_disconnect` **当轮触发**、立刻转本地缓存。**17 s 内就积压 3 行**，60 s 积压 12 行 = 理论值 `60/5.0` |

**选择理由（对外口径）**：边缘计算的典型故障是"**边缘盒子与云之间的北向断了，但现场仪表照常转**"。
(c) 制造的正是"北向出口整体不可用"这件事，而且**是三种做法里唯一能在 60 秒窗口内真正造出积压的**。
**代价如实记**：它打掉的是**两台网关**（plant1 + plant2）的北向，不是"单台边缘节点失联"；
对账仍按 `--device` 分设备做，两台各算各的。

## 五、崩溃自愈实验

### 5.1 做法与原始输出（`docs/evidence/edge/edge_autonomy_crash_20261011T185122.txt` 节选）

```
=== [1] 崩溃：docker kill cems-gateway（SIGKILL，不给优雅退出机会）===
  前置完成: status=running health=healthy
  已 kill @ 2026-10-11 18:51:28 → status=exited health=unhealthy
  +    3s ... +   46s status=exited    health=unhealthy
  等待 45 s 的自动重启结果: 未自动重启
=== [1b] 显式恢复：docker compose up -d gateway ===
  显式恢复: healthy=True 用时 7.1 s，StartedAt=2026-10-11T10:52:15.481053431Z
  恢复结论: 由「docker compose up -d」恢复，总停机 53.2 s，RestartCount=0，恢复后 mem_limit=536870912 B
=== [2] 数据是否继续入库（连续两次 COUNT 必须递增）===
  COUNT(*) = 26259 @ 2026-10-11 18:52:22
  COUNT(*) = 26261 @ 2026-10-11 18:52:34
=== [3] 时间戳连续性（断档 > 3×POLL_INTERVAL 才列出）===
  最大间隔 48 s（POLL_INTERVAL=5 s）
  · 停机期间断档   48 s : 2026-10-11 18:51:27 → 2026-10-11 18:52:15（崩溃的直接后果，非自愈问题）
  库内 26255 → 26261（+6），MAX(ts) 2026-10-11 18:45:47 → 2026-10-11 18:52:31
  判定: {"saw_down": true, "recovered": true, "data_continues": true, "no_gap_after_recovery": true}
```

### 5.2 ⭐ 最值钱的一条：**`restart: unless-stopped` 没有把被 `kill` 的容器拉回来**

实测（2026-10-11，前后做了 3 次，最长观察 **180 s**）：

| 操作 | 观察结果 |
|---|---|
| `docker kill cems-gateway` | 状态 `exited`，**45 s / 60 s / 180 s 都没有自己回来**；`RestartCount` 恒为 **0** |
| 容器被外部拉起后（未重建） | `HostConfig.Memory` 变成 **1073741824（1 GiB）**，不是编排里的 512 MiB |
| `docker compose up -d gateway` | ✅ 7.1 s 回到 healthy，`HostConfig.Memory` = **536870912（512 MiB）** |

**根因（可核对的解释）**：Docker 文档口径 —— `on-failure` 才覆盖"非零退出"，
而 `unless-stopped`/`always` 对**外部显式停止**（`docker stop` / `docker kill`）**不会**重新拉起，
这是设计行为、不是 bug。所以：
- **`docker kill` 演练测不出"进程自己崩掉会不会自愈"** —— 它测的是"被运维停掉之后会不会自己回来"，
  答案是**不会**（这也是对的：运维停的容器不该自己弹回来）。
- 真正会触发 `restart` 策略的是**容器内主进程非零退出**。本容器里 PID 1 就是 `python src/gateway/gateway.py`，
  而 `docker exec` 拿不到它的信号控制（实测 `os.kill(1, SIGKILL)` 后容器进程存活），
  所以"进程级崩溃自愈"这条**本轮没能在不改 `src/` 的前提下做出来** —— 如实记为局限（§6）。

**结论口径**：可以说的是「**崩溃后按运维流程恢复，7.1 s 回到 healthy，数据在新时间戳上继续，恢复后无断档**」；
**不能**说的是「容器崩了会自己起来」—— 实测不支持。

## 六、⚠️ 局限与没做到的（单列，不粉饰）

1. **采证时长不是 24 小时**：本文中的汇总是 **~25 分钟**窗口。脚本按 24 h 设计并在跑，
   跑满后用同一条汇总命令重算即可；**本文没有拿 25 分钟的数字冒充 24 小时**。
2. **不是真的 ARM/边缘盒子**：资源上限是**声明**在编排里、**实测**占用很低，
   但**没有在 2 核 2 GB 的真盒子（或 ARM）上跑过**。平台侧 5 个容器仍与边缘侧同机。
3. **断链只断到"broker 不可用"这一层**：没做"出口被限速/半连接/只断 DNS"等更细的故障形态；
   `docker network disconnect`（单节点隔离）**实测不成立**（会一起断掉设备侧）。
4. **进程级崩溃自愈未验证**：见 §5.2；`restart` 策略在"外部 kill"路径上**实测不生效**。
5. **没有 systemd / 开机自启**：本仓库的启停仍是 `scripts/up.ps1`（**刻意不做开机自启**，
   理由见 `scripts/README.md` 的 `up.ps1` 条目：设备没插时不该有东西在跑）。
   所以"边缘盒子断电重启后自动恢复整条链路"这条**没有验证**。
6. **资源采证的 `docker stats` 是采样值**：`--no-stream` 每次是一次瞬时读数，
   峰值若发生在两次采样之间**会被漏掉**；30 s 间隔对"秒级毛刺"不可见。
7. **`cems-subscriber` 的归属**：本文按"平台侧"处理（不采它的资源）。
   若某天把它和边缘盒子放同一台机器上，**512m/1.0 这套额度不能直接套用**。

## 七、复现命令

```powershell
# 0) 前置：10 个容器在跑
docker ps --format '{{.Names}}|{{.Status}}'

# 1) 资源限制生效验证（非 0 即为生效）
foreach ($c in 'cems-device','cems-gateway','cems-gateway-plant2') {
  docker inspect $c --format "$c Memory={{.HostConfig.Memory}} NanoCpus={{.HostConfig.NanoCpus}}"
}

# 2) 采证（脱离会话；父进程会退出，脚本继续跑 24 h）
#    ⚠️ 长跑段写"追加文件"（.gitignore 排除），让入库的 resource-24h.csv 保持冻结快照，
#       否则每个采样点都会把工作区弄脏、提交完立刻又变脏。
$py = 'C:\Users\Administrator\AppData\Local\Programs\Python\Python312\python.exe'
Start-Process -FilePath $py -WindowStyle Hidden -PassThru -ArgumentList `
  'scripts\measure_edge_resources.py',
  '--out','docs\evidence\edge\resource-24h.append-live.csv',
  '--status-file','docs\evidence\edge\resource-24h.status.append-live.json',
  '--interval','30','--duration-hours','24'
# 汇总（可随时重跑，不打扰采证；跑满 24 h 后把追加段并入 resource-24h.csv 再汇总）
python scripts\measure_edge_resource_summary.py --ceiling-ratio 0.40

# 3) 断链自治（停 broker 60 s → 恢复 → 逐条对账）
python scripts\drill_edge_autonomy.py --mode linkcut --outage 60

# 4) 崩溃自愈（kill → 观察 45 s 是否自愈 → 显式恢复 → 验数据连续）
python scripts\drill_edge_autonomy.py --mode crash --auto-wait 45
```

验收口径：`drill_edge_autonomy.py` 退出码 `0` = 演练完成且对账通过；`2` = 完成但对账不通过；`1` = 前置/异常。
证据落点：`docs/evidence/edge/`（`.txt` 是原始输出、`.json` 是机读结果、`.csv` 是采证原始数据）。
