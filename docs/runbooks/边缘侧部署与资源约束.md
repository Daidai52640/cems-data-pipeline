# 边缘侧部署与资源约束

> 这份文档补的是一条"定位证据"：项目对外说自己是"工业数据采集 + 边缘计算"，
> 链路设计上确实是边缘形态（本地采集 → 本地清洗/校验 → 本地缓存/断网自治 → 本地时序库 → 本地告警，北向才上云），
> 但仓库里一直没有任何"跑在资源受限的机器上"的痕迹——
> 全仓搜 `边缘|edge|ARM|systemd` 零命中，612 行 `docker-compose.yml` 零个资源上限，
> 实际跑法是 12 个容器 + Docker Desktop + WSL2（一台 20 vCPU / 15.9 GiB 的机器）。
>
> 本文只补这一条，并且只补能实测的那部分：给边缘侧服务封顶 + 长时间采证实际占用 +
> 把"断了北向会不会丢数""进程崩了会不会自己回来"这两件事真跑一遍。
> 它不改架构（架构本来就是边缘的），也不新增 ADR（没有新的架构决策）。
>
> 本文所有数字都来自实跑，原始输出在 `docs/evidence/edge/`。
> 局限单列在 §6，包括"哪些没做到"。

## 一、边缘侧是哪几个服务，为什么是它们

| 层次 | 容器 | 是否"边缘侧" | 理由 |
|---|---|---|---|
| 数采 | `cems-device` | 是 | 它扮演现场的数采仪/PLC：读从站寄存器、聚合成一个寄存器块。现场部署时它就在机柜里 |
| 网关 | `cems-gateway` / `cems-gateway-plant2` | 是 | 本地清洗/校验/打时间戳/本地缓存+补传（断网自治的载体），北向才发给 broker |
| 平台 | `tdengine` / `emqx` / `cems-redis` / `cems-nginx` / `cems-web` | 否 | 按定义属于中心侧（时序库、broker、缓存、展示）。本机为省事把它们和边缘侧挤在一台机器上，但不把它们算进边缘资源额度 |
| 接入 | `cems-subscriber` / `cems-subscriber-plant2` | 否（口径说明） | 它订阅 broker 写库，逻辑上属于平台侧接入层。部署上若和边缘盒子同机，资源要另算；本文按"平台侧"处理 |

> 本文资源采证只记数采 + 两个网关，共 3 个容器。
> 把平台侧混进来的话，"边缘占用"这个数字会被 TDengine 这类重件稀释掉，失去意义。

## 二、资源约束怎么写的（含"哪种写法真生效"的实测）

### 2.1 事实先行：两种写法在本机都生效

这是要先实测的项，因为 `deploy.resources.limits` 是 swarm 口径的字段，
在 `docker compose`（非 swarm）下"到底吃不吃"随版本变，不能照抄。

实测方法：写一个一次性 compose 文件，两个服务分别只用一种写法，起来后读 `HostConfig`。

```
# probe-deploy.yml（一次性的，跑完即删）
services:
  probe-deploy:                      # 只写 swarm 口径
    deploy:
      resources:
        limits: { memory: 512m, cpus: "1.0" }
  probe-service:                     # 只写 service 级字段
    mem_limit: 512m
    cpus: 1.0
```

```
$ docker inspect edgeprobe-probe-deploy-1 --format 'Memory={{.HostConfig.Memory}} NanoCpus={{.HostConfig.NanoCpus}}'
Memory=536870912 NanoCpus=1000000000          <-- 生效
$ docker inspect edgeprobe-probe-service-1 --format 'Memory={{.HostConfig.Memory}} NanoCpus={{.HostConfig.NanoCpus}}'
Memory=536870912 NanoCpus=1000000000          <-- 生效，且逐位相同
```

环境：Docker 29.7.2、Docker Compose v5.5.1（本机 `docker version` / `docker compose version`）。

### 2.2 本仓库的选择：两种都写

`docker-compose.yml` 里新增锚点 `x-edge-limits`（`device` / `gateway` / `gateway2` 三处合并）：

```yaml
x-edge-limits: &edge-limits
  mem_limit: 128m            # compose 原生字段：语义最确定，不依赖 swarm 口径
  cpus: 1.0
  deploy:                    # 让这份编排在 swarm / 其它入口下也带着同样的约束
    resources:
      limits:
        memory: 128m
        cpus: "1.0"
```

> 取值不是一开始就写 128m 的：先落的是 `512m`，随后按实测收紧到 `128m`（理由见 §2.4）。

为什么两种都写而不是只写一种：`mem_limit`/`cpus` 是"本机这条路径确定生效"的那一份；
`deploy.resources.limits` 是"换入口也不至于悄悄变成无上限"的那一份。
两者取值保持一致，免得将来有人只改一处、两个入口给出不同额度。

合并键用的是列表形式 `<<: [*app, *edge-limits]`：YAML 合并是逐 key 的浅合并，
两个锚点各有各的键，列表形式合并后 `image`/`restart`/`logging` 与 `mem_limit`/`cpus` 都在。
（实测：`docker compose config` 渲染出的 `mem_limit` / `cpus` / `deploy.resources.limits` 三项齐全。）

### 2.3 生效验证（现场命令与原始输出）

```
$ for c in cems-device cems-gateway cems-gateway-plant2; do
    docker inspect $c --format '{{.HostConfig.Memory}} {{.HostConfig.NanoCpus}}'; done
  加之前: 0 0                      <- 全仓零限制的现状：两个都是 0
  加之后: 536870912 1000000000     <- 当时的 512 MiB
  收紧后: 134217728 1000000000     <- 现行 128 MiB（见 §2.4 的取值理由）
```

重建只动了三个边缘侧容器（`docker compose --profile plant2 up -d device gateway gateway2`），
其余 7 个容器没被重建（`Up 12~15 minutes` 未变），真机链路不受影响。

### 2.4 取值理由：为什么最终是 128 MiB / 1 vCPU（不是 512 MiB）

先落 512 MiB——随后按实测收紧到 128 MiB。这不是拍脑袋，是三件事叠出来的：

| # | 依据 | 数字 |
|---|---|---|
| 1 | 实测常驻（§3 采证，三个容器） | 内存 22~27 MiB、CPU 峰值 < 8% |
| 2 | 512 MiB 太松、证明不了什么 | 占用只有上限的 ~5% ⇒ 10 倍余量，等于没约束 |
| 3 | 对标真实工业边缘网关 | 例：GW101（在售产品）= 512 MiB RAM + 单核 800 MHz + 4 GB 存储 + 1.8 W——那 512 MiB 还要分给 OS 与协议栈，留给单个应用的只有百来 MiB |

128 MiB 的安全性论证（最坏情况）：
```
运行期常驻          ~25 MiB
+ 断网缓存上限       64 MiB   （CACHE_MAX_BYTES，网关最长的一根内存增长线）
= 最坏 ≈ 89 MiB   <  128 MiB   ⇒ 仍留 ~39 MiB 余量
```
CPU 同理：1 vCPU 对 < 8% 的峰值是极宽松的（真正贴边的是内存，不是 CPU）。

结论：`128 MiB` 才是"边缘级内存足迹"的有效证明——
它同时满足"贴着真实小盒子能给单服务的额度"和"容得下最坏情况"。
（参考：<https://wiki.i2som.com/cn/gw101manualdoccn/gw101manualdoccn-1gfdmp1u9kna2>）

没有出现 OOM / 重启：10 个容器在加限后全部 healthy（§4 验收 4）。
采证 CSV 里 `mem_used_bytes = 0` 的行只出现在网关被 kill 的那段时间（容器没在跑，`docker stats` 给 0）。

### 2.5 实测反例：运行期额度可以被绕过编排地改掉

（2026-10-11）处置一次网关"停住"时用了 `docker update --memory 1g` 临时放宽 + `docker start` 拉起：
同一容器、未重建，`HostConfig.Memory` 从 512 MiB 变成 1 GiB（`恢复后 mem_limit=1073741824 B`）。

> ⚠️ 归因更正：那次 1 GiB 是人为 `docker update` 造成的（急救时的临时操作），
> 不是 Docker 自己改的——但它证明了一件真事：
> `HostConfig` 的运行期额度可以被"绕过编排"地改掉，
> 所以"额度生效"这条判据必须以 `docker compose up -d` 之后的 `docker inspect` 为准，
> 不能拿"容器里看着对"当数。
> 生产上要真保证额度，应让编排器（或用巡检脚本）负责重启，而不是靠 `docker update` 或 Docker 自动重启。

## 三、资源占用采证（长跑）

| 项 | 值 |
|---|---|
| 脚本 | `scripts/measure_edge_resources.py`（采证）+ `scripts/measure_edge_resource_summary.py`（汇总） |
| 采样 | 每 30 s 一次 `docker stats --no-stream --format json`，只采边缘侧 3 个容器 |
| 落点 | `docs/evidence/edge/resource-24h.csv`（入库的冻结快照）+ `resource-24h.append-live.csv`（长跑追加段，`.gitignore` 排除；每行带 `run_id` / `sample_no`，每行 `flush + fsync`） |
| 汇总 | `docs/evidence/edge/resource-summary.json`（逐容器 CPU/内存 min/avg/max + 触顶 + 缺采） |
| 脱离会话 | 用 `Start-Process -WindowStyle Hidden -PassThru` 起，父进程已退出（见 §4 验收 7） |
| 目标时长 | 24 小时 |
| 实际时长 | 本轮报告时只跑到了约 25 分钟（见下） |

为什么要分成"入库快照 + 长跑追加段"两份：采证脚本一跑就是 24 h，每个采样点都在追加——
如果它直接写被 git 跟踪的那份 CSV，`git status` 会在提交后立刻又变脏，
评审看到的是"改了却没提交"。所以约定：
`resource-24h.csv` 是入库的、提交那一刻的冻结快照，
继续采的那部分写 `resource-24h.append-live.csv`（`.gitignore` 排除，用 `--append-file` 或直接把 `--out` 指过去）。
24 h 跑完后把追加段并入 `resource-24h.csv` 再提交一次，就得到"一份完整、且入库时工作区干净"的证据。

时长如实交代：采证脚本是真的按 24 小时设计并在跑（`--duration-hours 24`，
心跳文件里 `duration_hours: 24.0`），但本文写作时它才跑了几十分钟，
所以本文里的汇总数字是"约 25 分钟窗口"的，不是 24 小时的。
24 小时跑完后，用同一条命令重算汇总即可（无需重跑采证）：

```
python scripts/measure_edge_resource_summary.py --ceiling-ratio 0.40
```

汇总快照（窗口 2026-10-11 18:28:01 ~ 18:55:24，约 0.46 h，2 个 run_id，159 行采样）：

| 容器 | 样本 | 缺采 | CPU min/avg/max (%) | 内存 min/avg/max | 内存上限 | 峰值占上限 | 触顶次数(cpu/mem) |
|---|---|---|---|---|---|---|---|
| `cems-device` | 53 | 0 | 0.00 / 0.85 / 7.08 | 22.5 / 23.7 / 25.1 MiB | 512 MiB | 4.91% | 0 / 0 |
| `cems-gateway` | 53 | 0 | 0.00 / 0.31 / 7.90 | 0.0 / 15.6 / 26.5 MiB | 512 MiB | 5.18% | 0 / 0 |
| `cems-gateway-plant2` | 53 | 0 | 0.00 / 0.49 / 7.97 | 24.2 / 25.0 / 26.0 MiB | 512 MiB | 5.07% | 0 / 0 |

本表的限定：这 53 个采样点的上限是当时的 512 MiB，所以 `占用%` 列是 512 口径。
收紧到 128 MiB 后，同口径占用约 17~21%——仍有余量，但不再是"可有可无"的约束（§2.4）。

> 触顶判据：CPU 顶 = `cpu >= 100%`（= 1 vCPU 用满）；内存顶 = `mem >= 上限 × 0.40`
> （收得比 0.90 严得多，"没触顶"这句话才有力）。
> `cems-gateway` 的 `min=0.0B` 来自它被 kill 的那两段采样（容器没在跑）。
> 上表是某一时刻的汇总快照；`resource-24h.csv` 是长跑追加的，跑满 24 h 后重跑汇总命令，
> 数字会比较这张表更大（窗口更长），这张表的窗口以它自己标的时间为准。

## 四、断链自治实验

### 4.1 选了哪种断法，以及为什么另外两种被实测否掉

任务是"断上行，不要拔网线"。候选有三种，全部没有碰宿主网络（没拔网线 / 没 `netsh` / 没禁网卡），
宿主上的 `scripts/serial_bridge.py`（占 COM3 的真机桥）全程在跑。

| 候选 | 结果 | 实测证据 |
|---|---|---|
| (a) `docker network disconnect cems-net cems-gateway` | 失败 | 网关只挂在 `cems-net` 一张网上，断掉它 = 连 Modbus 的设备层也一起断：网关日志 `Connection to (device, 5020) failed: [Errno -3] Temporary failure in name resolution`。结果是采不到数：60 s 内积压 0 行，"没丢数据"变成了"本来就没产生数据"——自治这件事根本没被验证到（原始输出留档：`docs/evidence/edge/edge_autonomy_linkcut_20261011T183650.txt`） |
| (b) 把 broker 名字改指黑洞（容器内 `/etc/hosts` 加 `127.0.0.1 emqx`） | 失败 | paho 已建好的 TCP 会话不会因为改 hosts 而断开（hosts 只在下一次重连解析时生效），`is_connected()` 一直是 True → 网关继续"发得成功"。持续观察 2 分钟无断开、无积压 |
| (c) `docker stop emqx`（采用） | 有效 | 立刻关掉 TCP → 网关 `on_disconnect` 当轮触发、立刻转本地缓存。17 s 内就积压 3 行，60 s 积压 12 行 = 理论值 `60/5.0` |

选择理由（对外口径）：边缘计算的典型故障是"边缘盒子与云之间的北向断了，但现场仪表照常转"。
(c) 制造的正是"北向出口整体不可用"这件事，而且是三种做法里唯一能在 60 秒窗口内真正造出积压的。
代价如实记：它打掉的是两台网关（plant1 + plant2）的北向，不是"单台边缘节点失联"；
对账仍按 `--device` 分设备做，两台各算各的。

### 5.2 最值钱的一条：`restart: unless-stopped` 没有把被 `kill` 的容器拉回来

实测（2026-10-11，前后做了 3 次，最长观察 180 s）：

| 操作 | 观察结果 |
|---|---|
| `docker kill cems-gateway` | 状态 `exited`，45 s / 60 s / 180 s 都没有自己回来；`RestartCount` 恒为 0 |
| 容器被外部拉起后（未重建） | `HostConfig.Memory` 变成 1073741824（1 GiB）——那是人为 `docker update` 临时放宽造成的（见 §2.5 的归因更正），不是编排里的值 |
| `docker compose up -d gateway` | 7.1 s 回到 healthy，`HostConfig.Memory` 回到编排里的值 |

根因（可核对的解释）：Docker 文档口径——`on-failure` 才覆盖"非零退出"，
而 `unless-stopped`/`always` 对外部显式停止（`docker stop` / `docker kill`）不会重新拉起，
这是设计行为、不是 bug。所以：
- `docker kill` 演练测不出"进程自己崩掉会不会自愈"——它测的是"被运维停掉之后会不会自己回来"，
  答案是不会（这也是对的：运维停的容器不该自己弹回来）。
- 真正会触发 `restart` 策略的是容器内主进程非零退出。本容器里 PID 1 就是 `python src/gateway/gateway.py`，
  而 `docker exec` 拿不到它的信号控制（实测 `os.kill(1, SIGKILL)` 后容器进程存活），
  所以"进程级崩溃自愈"这条本轮没能在不改 `src/` 的前提下做出来——如实记为局限（§6）。

结论口径：可以说的是「崩溃后按运维流程恢复，7.1 s 回到 healthy，数据在新时间戳上继续，恢复后无断档」；
不能说的是「容器崩了会自己起来」——实测不支持。

---

## 六、局限与没做到的（单列，不粉饰）

1. 采证时长不是 24 小时：本文中的汇总是 ~25 分钟窗口。脚本按 24 h 设计并在跑，
   跑满后用同一条汇总命令重算即可；本文没有拿 25 分钟的数字冒充 24 小时。
2. 不是真的 ARM/边缘盒子：资源上限是声明在编排里、实测占用很低，
   但没有在 2 核 2 GB 的真盒子（或 ARM）上跑过。平台侧 5 个容器仍与边缘侧同机。
3. 断链只断到"broker 不可用"这一层：没做"出口被限速/半连接/只断 DNS"等更细的故障形态；
   `docker network disconnect`（单节点隔离）实测不成立（会一起断掉设备侧）。
4. 进程级崩溃自愈未验证：见 §5.2；`restart` 策略在"外部 kill"路径上实测不生效。
5. 没有 systemd / 开机自启：本仓库的启停仍是 `scripts/up.ps1`（不做开机自启，
   理由见 `scripts/README.md` 的 `up.ps1` 条目：设备没插时不该有东西在跑）。
   所以"边缘盒子断电重启后自动恢复整条链路"这条没有验证。
6. 资源采证的 `docker stats` 是采样值：`--no-stream` 每次是一次瞬时读数，
   峰值若发生在两次采样之间会被漏掉；30 s 间隔对"秒级毛刺"不可见。
7. `cems-subscriber` 的归属：本文按"平台侧"处理（不采它的资源）。
   若某天把它和边缘盒子放同一台机器上，128m/1.0 这套额度不能直接套用。

## 七、复现命令

```powershell
# 0) 前置：10 个容器在跑
docker ps --format '{{.Names}}|{{.Status}}'

# 1) 资源限制生效验证（非 0 即为生效）
foreach ($c in 'cems-device','cems-gateway','cems-gateway-plant2') {
  docker inspect $c --format "$c Memory={{.HostConfig.Memory}} NanoCpus={{.HostConfig.NanoCpus}}"
}

# 2) 采证（脱离会话；父进程会退出，脚本继续跑 24 h）
#    长跑段写"追加文件"（.gitignore 排除），让入库的 resource-24h.csv 保持冻结快照，
#    否则每个采样点都会把工作区弄脏、提交完立刻又变脏。
$py = 'C:\Users\Administrator\AppData\Local\Programs\Python\Python312\python.exe'
Start-Process -FilePath $py -WindowStyle Hidden -PassThru -ArgumentList `
  'scripts\measure_edge_resources.py',
  '--out','docs\evidence\edge\resource-24h.append-live.csv',
  '--status-file','docs\evidence\edge\resource-24h.status.append-live.json',
  '--interval','30','--duration-hours','24'
# 汇总（可随时重跑，不打扰采证；跑满 24 h 后把追加段并入 resource-24h.csv 再汇总）
python scripts\measure_edge_resource_summary.py --ceiling-ratio 0.40

# 3) 断链自治（停 broker 60 s → 恢复 → 逐条对账）
python scripts\drill_edge_autonomy.py --mode linkcut --outage 60

# 4) 崩溃自愈（kill → 观察 45 s 是否自愈 → 显式恢复 → 验数据连续）
python scripts\drill_edge_autonomy.py --mode crash --auto-wait 45
```

验收口径：`drill_edge_autonomy.py` 退出码 `0` = 演练完成且对账通过；`2` = 完成但对账不通过；`1` = 前置/异常。
证据落点：`docs/evidence/edge/`（`.txt` 是原始输出、`.json` 是机读结果、`.csv` 是采证原始数据）。
