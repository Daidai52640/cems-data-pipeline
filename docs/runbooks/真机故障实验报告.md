# 真机故障实验报告 —— 全链路在真实设备故障下的行为

> 一句话结论：
> 设备层给什么，全链路就如实体现什么；设备层给"无"，链路就体现"无"；
> 链路不把它自作主张变成 0 或别的值。
> ——一台设备的 2 个测点故障，不再拖垮其余 7 个测点。

- 实验日期：2026-10-11
- 基线：`real-device-baseline-2`（见 `真机接入-基线冻结v2.md`）
- 被注错设备：RS-485 温湿度变送器（真机，接在 1 号炉）

---

## 1. 判据：不看"故障叫什么名字"，只看"数据该长什么样"

本报告不按故障类型分类，而是按"设备层注入什么数据形态 → 链路必须体现成什么"来组织。

理由：我们不声称知道每种物理故障的确切表现（现实中"掉线"可能表现为无数据、也可能表现为上次值或垃圾值）。
只保证一件事：不管设备层给什么，链路都如实传递、不编造。

| 注入的形态 | 链路必须满足的性质 |
|---|---|
| 超量程 / NaN（物理上不可能） | 该点不入库，且事件表留痕；其余测点全部入库 |
| 跳变 / 冻结（可疑但可能真实） | 照常入库 + 事件表留痕——丢了会掩盖真实工况突变 |
| 无数据（设备不可达） | 该点不入库，其余测点正常；恢复后自动续上 |
| 整条语法坏 | 整条拒收（噪声/NaN 会让 TDengine 报语法错） |

唯一红线：不把"无"变成 `0`——`0` 落在量程内，会被当成真实读数一路入库（这正是真机教我们的坑，见 §2）。

## 2. 故障实验清单与实测结果

| # | 注入方式 | 走哪条代码路径 | 结果 |
|---|---|---|---|
| E1 | 杀掉桥进程（`kill`） | 设备层失败门限（3 次 ≈ 6 s） | 设备层写越界值 → 接入层拒收 → 库断档 → 重启桥即自愈 |
| E2 | 独占 COM3（模拟串口被别的程序占用） | 桥失败门限（立即） | 桥写越界值 → 路径 A 与路径 B 都拒收（见 §4） |
| E3 | 拔掉变送器电源 | 桥状态位（立即）——与 E1/E2 不同路径 | 见 §3，本轮主角 |
| E4 | 断开上行 60 s（`docker stop emqx`） | 网关缓存 + 补传 | 12/12 条补传，100%，逐条对账恒等式成立，排空 21.0 s |
| E5 | `docker kill` 网关 | 容器重启策略 | 不自愈（Docker 对"外部显式停止"的设计行为）→ `docker compose up -d` 7.1 s 恢复 |
| E6 | 端子线被碰掉（间歇性接触不良，非计划、真实发生） | 桥状态位 | 见 §6.5：两段断线 + 中间恢复过，系统逐段留痕（26 条 = 13 点 × 2），没被中间的恢复骗出假的"已结束" |
| F1 | 注入单点超量程 | 逐点质量位 | 该点 `NULL`，其余 8 点非空列计数 = 8 |
| F2 | 注入单点阶跃 / 持续不变 | 合理性判据 | 照常入库 + 事件 `kind=jump/frozen, stored=1` |

## 3. E3 全过程（拔掉真机电源 → 插回），端到端 ~7 秒

```
 t(s) | 桥(hum,temp,status,fails) | 设备层 reg6/reg7 | 主表 temp/hum | 新增无效点事件
    0 | 648,251,0,0                | 251/648          | 25.1 / 64.8   | 0
   25 | 648,251,0,0                | 251/648          | 25.1 / 64.8   | 0     <- 拔电源
   29 | 1010,3010,1,1              | 251/649          | 25.1 / 64.9   | 0     <- 桥 4s 发现
   33 | 1010,3010,1,2              | 3010/1010        | 25.1 / 64.9   | 0     <- 设备层 4s 跟上
   36 | 1010,3010,1,3              | 3010/1010        | NULL / NULL   | 2     <- 接入层判定 + 留痕
   95 | 1010,3010,1,22             | 3010/1010        | NULL / NULL   | 4
```

插回后（同一套采样脚本）：

```
桥      [1010,3010,1,22]  ->  [649,251,0,31]      <- status 回 0（累计失败 31 是历史计数，不清零）
设备层  3010/1010          ->  251/649  = 25.1 degC / 64.9 %
主表    NULL / NULL        ->  19:00:18 | 25.1 | 64.9
事件表  持续新增            ->  停在 36 条
```

事件表 36 条 = 掉线 90 秒 ÷ 5 秒 × 2 个测点——不多不少，正好对上。

### 3.1 这 36 条 + 其余 7 点，一起说明了什么

| | 改造前（整条拒收） | 现在（逐点隔离） |
|---|---|---|
| 1 号炉温湿度掉线 | 9 个测点全部不入库 | 只丢这 2 点，其余 7 点照常入库 |
| 大屏 | 全断 | 7 条曲线正常，只有 2 条断 |
| 可追溯 | 分不清"缺数"还是"判无效" | 事件表留 `kind=invalid / stored=0` |
| 数据新鲜度 | 可能标红 | 仍 `fresh`（还有数据在流） |

改造的依据：`docs/adr/0009-接入层逐点质量位.md`。
根因：原实现把"语法坏（NaN/inf 写不进库，必须整条拦）"与"语义坏（单点超量程，数值合法但不可信）"
用一条规则处理——工业口径上这叫「故障不隔离 / 单点故障扩散」。

## 4. E2 的额外价值：两条真机路径同时被保护

真机数据有两条并存的接入路径，E2 证明一次改动同时修好了两条：

| 路径 | 桥给越界值后 |
|---|---|
| 路径 A（设备层混流，`REAL_DEVICE_ENABLE=1`） | 透传越界 → 接入层按"超量程"拒收 |
| 路径 B（点集分离，`POINT_SET=transmitter`，在独立分支） | 该网关只读 2 个寄存器、看不到桥的状态位 → 靠值本身越界（`AirTemp` 量程 `[-40,125]`）拒收 |

这是"把'无效'做进值本身"而不是"只置状态位"的理由——只置状态位会把洞留给下一个消费者。

---

## 5. 三条"不编造"的具体设计

| 设计 | 做法 | 为什么不能省 |
|---|---|---|
| 不用 `0` 当无效标记 | 用 `量程上限 + 1` 的越界值（`301.0 degC / 101.0 %`） | `0` 落在量程内，会被当成真实读数入库——真机实测过它读错地址就沉默返回 `0` |
| "无效"与"缺失"可区分 | 事件表加 `kind`（`invalid` / `missing`） | 都写成 `NULL` 会让"网络断"、"设备死"、"被判无效"分不清；最严重的是超标数据被当"超量程"丢掉 = 把超标藏起来 |
| "可疑"与"无效"可区分 | 事件表加 `stored`（`1`=已入库 / `0`=被丢弃） | 跳变可能是真实工况突变，丢掉等于掩盖真实事件 |

## 6. 恢复能力（两条链路各自的证据）

| 场景 | 恢复方式 | 实测 |
|---|---|---|
| 真机掉线 | 自动（桥状态位回 0） | 插回即恢复，无需人工干预 |
| 断上行 60 s | 自动（网关缓存 → 补传） | `N=12 → M=12`，成功率 100%，排空 21.0 s，逐条对账恒等式成立 |
| 网关 `docker kill` | 不自动（Docker 设计：外部显式停止不会被 `unless-stopped` 拉起） | `docker compose up -d` 7.1 s 回 healthy |

## 6.5 E6：端子线被碰掉——间歇性接触不良（2026-10-12 01:35，非计划、真实发生）

这条比 E1~E5 都更有价值：它不是"干净地断一次"，而是接触不良——
线松了，通一下断一下。系统必须能处理"反复横跳"，而不能被它骗出一个假的"已恢复"。

实测时间线（原始记录）：

| 时刻 | 现象 |
|---|---|
| `01:35:29` | 第一段断线开始——主表 `temp` 变 `NULL`，事件表开始留痕 |
| `01:35:29 ~ 01:36:15` | 持续 ~47 s（9 个采样点） |
| `01:36:20 ~ 01:36:30` | 中间恢复过（`temp` 重新有值）——这就是"接触不良"的签名 |
| `01:36:36 ~ 01:36:46` | 第二段断线（3 个采样点，~15 s） |
| `01:36:46` 之后 | 稳定（用户重新压紧端子） |

统计：

```
主表 temp IS NULL 的时刻：01:35:29/34/39/44/49/55, 01:36:00/05/10/15, 01:36:36/41/46   共 13 个采样点
事件表 cems_point_invalid：FIRST=01:35:29  LAST=01:36:46  COUNT=26
26 = 13 个采样点 × 2 个测点（Temp + Humidity）—— 不多不少，正好对上
```

恢复验证（用户接回后 40 秒连采 8 次桥寄存器）：

```
t+ 0s [hum=623 temp=254 status=0 fails=54]
t+ 5s [hum=623 temp=254 status=0 fails=54]  (稳定)
...
t+30s [hum=624 temp=253 status=0 fails=54]  (稳定)   <- 读数在轻微变化 = 传感器在工作，不是卡住的假值
t+35s [hum=623 temp=254 status=0 fails=54]  (稳定)
```

判据是"累计失败数 `fails` 一次没涨"（全程 54）——它若还在涨，说明线仍是松的。
这比"看主表有没有值"更灵敏：接触不良可能"碰巧读到一次"而让主表有值。

这一条证明了什么：

| 性质 | 结论 |
|---|---|
| 不带状态记忆的误判 | 没有——中间那次恢复没有被当成"故障结束"，第二段照常留痕 |
| 故障隔离 | 全程 `so2/nox/dust/...` 其余 7 个测点正常入库（`temp=NULL` 的同时 `so2=19.6 nox=32.2 dust=3.14`） |
| 停流告警是否误报 | 0 条 CRITICAL——正确：单段最长 47 s < 300 s 阈值，且还有 7 个测点在流（根本没停流） |
| 可追溯 | 26 条事件留痕可按时刻逐条核对 |

局限：这次断线的物理原因（端子松动）由人工判断，系统侧无法区分
"端子松"与"变送器故障"与"A/B 线被老鼠咬"——它只能如实报告"读不到"。
这正是 §1 那条判据的设计前提：不问故障叫什么，只保证如实体现。

## 7. 局限（单列，不绕开）

- 只覆盖通信类与数据类故障：传感器缓慢漂移（硬件腐蚀）、超量程的真实物理量、
  MQTT 伪造报文、时钟错乱均未覆盖。其中"漂移"是最难的一条——它是渐变，
  量程、跳变、冻结都抓不到，需要趋势检测或独立参照。
- 缺第三方参照：`真机接入.md` 的 S3 判据"与独立来源对照 ±0.5 degC"未做——
  现有验证全部自证（桥/网关/库同源）。
- "冻结"判据的检测延迟约 100 分钟（`N=1200` @5s）——这是零误报的代价；
  阈值由 10 天全量 25093 个样本标定（最长自然平台期 404），跨季节仍未验证。
- 路径 A 下 2 个测点故障仍会拖累整条报文（因为设备层混流后，那 2 个点与其余 7 点同一张表、
  同一列布局——逐点隔离解决的是"入库"，不是"同一台设备内的物理隔离"）。
  真要物理隔离应用路径 B（点集分离，已在独立分支）。
- E4 的断链手法不是"单节点失联"：`docker network disconnect` 实测会连 Modbus 一起断
  （网关只挂一张网），最终用的是 `docker stop emqx`——它打掉的是两台网关的北向。
- 崩溃自愈未做到进程级：容器 PID 1 就是 gateway，`docker exec` 拿不到其信号控制。
- 真机只接 1 号炉；`Temp`/`Humidity` 承载的是环境温湿度，不是烟气参数。

## 8. 复现

```powershell
# 基线
git checkout real-device-baseline-2
pwsh -NoProfile -File scripts/up.ps1          # 起桥（宿主）+ 起全栈

# E3：拔掉变送器电源 → 等 40 s → 插回；期间观察三级证据
docker exec tdengine taos -d cems -s "SELECT ts,temp,humidity FROM cems.plant1_device1 ORDER BY ts DESC LIMIT 3;"
docker exec tdengine taos -d cems -s "SELECT ts,point,kind,stored FROM cems.cems_point_invalid ORDER BY ts DESC LIMIT 5;"

# E4/E5：断链与崩溃自愈（脚本自带证据落盘）
python scripts/drill_edge_autonomy.py --mode linkcut --outage 60
```
