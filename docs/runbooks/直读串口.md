# 直读串口：device 进程内的 Modbus RTU 主站

> 本文对应两项已有边界的收窄：
> - `docs/runbooks/跨平台部署.md` §六 边界 2「485 真机不在链路里」
> - [README.md](../../README.md) §已知边界 第 6 条「串口侧是宿主脚本 `scripts/serial_bridge.py`」
>
> 结论一句话：**device 进程现在可以自己打开串口、按 Modbus RTU(FC03) 直读变送器**，
> 对外仍然只是一个 9 寄存器的 Modbus TCP 从站（`:5020`），其中 1 号炉的 Temp/Humidity
> 两个点由真机供给、其余 7 点仍是仿真。
> ⚠️ 真机实测在 **Linux Mint 宿主 + /dev/ttyUSB0** 上完成（2026-10-18）；Windows 侧
> 因 USB-485 已不在那台机器上，真机路径**未验证**（见 §七）。

## 一、为什么做这件事

改造前真机走的是「外挂串口服务器」形态：

```
[温湿度变送器] --RS485/Modbus RTU--> COM3 / ttyUSB0
                                        |
                                scripts/serial_bridge.py（独立进程，跑在宿主）
                                        |
                                Modbus TCP :5021
                                        |
                                device 进程（RealDeviceReader 按 TCP 读）
```

现场确实大量存在这种形态（数采仪 / 串口服务器把 RS485 转成 TCP，上位机按 TCP 读），
所以 `scripts/serial_bridge.py` **保留**，`docs/runbooks/真机接入.md`、
`docs/runbooks/物理层取证.md` 与基线冻结文档里的一手证据仍然以它为准。

但 device 进程与串口在**同一台宿主**时（数采一体机的常见形态），中间那一跳可以省掉：
device 进程自己就是 RTU 主站。两种形态是**并存可选**，不是替代关系。

### 两种形态的取舍

| 形态 | 适用场景 | 代价 |
|---|---|---|
| `scripts/serial_bridge.py`（外挂，默认 `REAL_DEVICE_SOURCE=tcp`） | 一个串口要给多个消费者；device 跑在容器里、串口只在宿主上；需要保留原有证据链 | 多一个进程、多一跳 TCP、多一份要维护的配置 |
| `src/device/rtu_master.py`（进程内直读，`REAL_DEVICE_SOURCE=serial`） | device 进程与串口在同一宿主；想少一跳、少一个进程 | device 进程必须能自己打开串口（容器拿不到宿主 COM/ttyUSB，**不适用**）；宿主需装 pyserial |

**默认值仍是 `tcp`**：不显式写 `REAL_DEVICE_SOURCE=serial` 时，行为与改造前逐字节一致。
容器部署仍应使用 `tcp` 形态 —— 这是直读形态明确的适用边界，不是遗漏。

## 二、设备事实（实测）

| 项 | 值 |
|---|---|
| 设备 | RS485 温湿度变送器 |
| 通讯参数 | **4800 / 8 / N / 1**，从站 **0x01**，功能码 **03**（只读） |
| 湿度 | 寄存器 `0x0000`，`uint16`，÷10，单位 %RH |
| 温度 | 寄存器 `0x0001`，**`int16`**，÷10，单位 degC |
| 字节序 | **AB**（高字节在前） |

这些事实的唯一真源是 `src/common/points_transmitter.py`；`rtu_master.py` 不抄第二份，
直接引用它的 `BAUD_RATE` / `DATA_BITS` / `PARITY` / `STOP_BITS` / `SLAVE_ADDRESS` /
`READ_FUNCTION_CODE` / `FRAME_GAP_MIN_BYTES` / `REG_BASE` / `REG_COUNT` /
`EXPECTED_RESPONSE_BYTES` / `POINTS`，字节序解码复用 `points.decode_register`。

本次在 Mint 上抓到的原始帧（`docs/evidence/serial-20261018/ev_02_probe.txt`）：

```
请求帧=01 03 00 00 00 02 c4 0b
应答帧=01 03 04 02 44 00 f3 fb db   -> 湿度 0x0244=580 -> 58.0 %RH；温度 0x00f3=243 -> 24.3 degC
```

请求帧与 `docs/runbooks/物理层取证.md` 里逻辑分析仪抓到的真机帧**逐字节相同**
（`01 03 00 00 00 02 C4 0B`），CRC 已由独立实现复算一致。

## 三、代码结构与语义

### 3.1 新增模块 `src/device/rtu_master.py`

| 组成 | 作用 |
|---|---|
| `crc16_modbus` / `append_crc` / `crc_ok` | 标准 Modbus CRC16（0xA001 反射、初值 0xFFFF、低字节先发） |
| `build_read_request` / `parse_read_response` | FC03 请求帧拼装；应答定长解析（长度 / CRC / 从站 / 功能码 / 字节数逐项校验，异常响应单独报） |
| `decode_data_segment` | 数据段 → 两个寄存器原始整数（温度保留 int16 补码位型），契约字段来自 `points_transmitter` |
| `SerialTransport` 协议 + `transport_factory` | 串口能力子集（write/read/reset_input_buffer/close），**单测注入假串口即不需要硬件** |
| `RtuMaster` | 轮询、失败计数、新鲜/陈旧状态、`snapshot()` / `status()` / `status_registers()`，接口与 `RealDeviceReader` 一致 |
| `python -m src.device.rtu_master` | 只读取证探针：打印原始帧、两个原始寄存器、状态位、累计失败数（不占 TCP 端口） |

`RtuMaster` 的对外接口（`read_once` / `snapshot` / `poll_forever`）与原有
`RealDeviceReader` 一致，所以 device 层只换"真机值从哪来"，混流逻辑一行没动。

### 3.2 `src/device/modbus_server.py` 的变化（最小侵入）

新增一个显式开关，默认行为不变：

| 环境变量 | 默认 | 说明 |
|---|---|---|
| `REAL_DEVICE_SOURCE` | `tcp` | `tcp` = 读宿主上的 `scripts/serial_bridge.py`（改造前行为）；`serial` = 本进程直读串口 |
| `REAL_DEVICE_SERIAL_PORT` | `COM3` | 直读形态的串口名（Linux 上写 `/dev/ttyUSB0`） |
| `REAL_DEVICE_SERIAL_BAUD` | `4800` | 默认取设备契约里的波特率 |
| `REAL_DEVICE_SERIAL_TIMEOUT` | `1.0` | 单帧读超时（秒） |

- `REAL_DEVICE_SOURCE` 非法值在启动阶段抛 `ValueError`（不静默回落到默认来源）。
- `serial` 模块是**延迟导入**的：容器里没有 pyserial，纯仿真 / `tcp` 形态的 device
  进程不能因为一个可选外设的依赖起不来。这条承诺由
  `tests/device/test_real_device_source.py::test_modbus_server_still_imports_and_simulates_without_pyserial`
  钉住（子进程里 `sys.modules["serial"]=None`，验证导入与纯仿真照常、只有真去开串口才失败且被吞成"陈旧"）。
- 原有混流逻辑（`overlay_real_values`）、降级启动、语义边界告警全部复用，未改判据。

### 3.3 读失败时的语义（与 `serial_bridge.py` 一致，不得回退）

读失败（串口打不开 / 读超时 / CRC 错 / 坏帧 / 异常响应）时：

1. **状态位 = 1（陈旧）**；连续失败清零后自动回 0（新鲜）。
2. 对外寄存器写**越界值** `101.0 %` / `301.0 degC`（原始整数 1010 / 3010），
   **不是**上一次好值 —— 只保留在 `snapshot()` 里并打陈旧标记，device 层 overlay 据此写越界值。
3. 进程**绝不因为读失败退出**。
4. 恢复后下一次成功读取即回新鲜，不需要重启。

⭐ **为什么不用 0 表示无效**：实测这台变送器读不存在的地址会沉默返回全 0 而不报异常
（`docs/runbooks/真机接入.md` S4 发现 1），而 0 落在 CEMS 与变送器两套契约的量程内 ——
会被当成真实读数一路入库。把"无效"做进**值本身**，任何不读状态位的消费者也无法误用；
只置状态位是不够的，那只是把洞留给下一个人。

⚠️ **直读形态没有新增对外状态寄存器**：`:5020` 仍是 9 个测点的既有布局（不改契约、
不改网关）。状态位通过探针的 `status_registers()` 与进程日志可见；下游能看到的"无效"
仍然是**越界值本身**。这是本形态的一条明确边界（见 §七）。

### 3.4 与量程 / 单位的关系

- device 寄存器存的是 `物理值 × point.scale`，Temp/Humidity 的 scale 都是 10；
  直读给出的也是 `×10` 的原始整数，直接赋值，不需要二次换算。
- 负温（环境温度 < 0 degC）走 int16 补码位型（如 `FF 9F` → 65439）；写进无符号寄存器后
  接入层会按 `Temp` 超量程拒收 —— **宁可拒收，也不要一个看起来合理的错数**。
- 语义边界照旧：Temp/Humidity 两列装的是**环境**温湿度，不是烟气参数；本部署只用于
  数据链路演示，不作环保口径依据（启动日志有一条 WARNING 明确写出）。

## 四、怎么开

### 4.1 Linux 宿主（本次实测形态）

```bash
cd /home/ddf/cems-data-pipeline
REAL_DEVICE_ENABLE=1 \
REAL_DEVICE_SOURCE=serial \
REAL_DEVICE_SERIAL_PORT=/dev/ttyUSB0 \
REAL_DEVICE_UNIT=1 \
REAL_DEVICE_SLAVE=1 \
REAL_DEVICE_POLL_INTERVAL=2.0 \
.venv/bin/python -m src.device.modbus_server
```

- `/dev/ttyUSB0` 属 `root:dialout`、权限 `crw-rw-rw-`；操作者在 `dialout` 组即可，**不需要 sudo**。
- `REAL_DEVICE_UNIT` = 变送器的 RTU 从站号；`REAL_DEVICE_SLAVE` = 被覆盖的是 5020 的哪台设备（1 号炉）。
- 启动时读不到真机**不拒绝启动**：降级为 `Temp/Humidity` 持续写越界值，日志有 CRITICAL
  与按来源区分的排查顺序；串口恢复后自动回新鲜（与改造前 TCP 形态同一条规则）。

### 4.2 Windows 宿主

Windows 上同样可写 `REAL_DEVICE_SERIAL_PORT=COM3`（USB-485 的 CH340 通常给 COM3）。
⚠️ 本次**没有**在 Windows 上验证直读路径：取证时该 USB-485 已不在 Windows 机器上
（设备管理里是 Code 45 phantom、COM3 不存在），真机读数改在 Mint 上取。

### 4.3 容器

容器拿不到宿主串口，**不要在容器里开 `serial` 形态**。容器部署保持 `tcp` 形态 +
宿主上的 `scripts/serial_bridge.py`（现场即有这种形态）。

### 4.4 只读探针（排障 / 取证）

```bash
# 与 device 进程抢同一个串口：取证时先停 device 实例，或换一个物理口
python -m src.device.rtu_master --port /dev/ttyUSB0 --count 5 --interval 1
```

## 五、实测结果（2026-10-18，Linux Mint 22.3 x86_64）

宿主：`Linux 6.14.0-37-generic x86_64`、Python 3.12.3、pyserial 3.5、pymodbus 3.8.6；
`/dev/ttyUSB0` = CH340（`lsusb`：`1a86:7523`）。环境原始输出见
`docs/evidence/serial-20261018/ev_01_env.txt`。

### 5.1 真机直读（最硬的一条）

- 5 次连读：**5/5 成功**，湿度 580→581（**58.0~58.1 %RH**）、温度 243（**24.3 degC**），
  状态位 0，单次耗时 45~62 ms，原始帧见上。
  证据：`docs/evidence/serial-20261018/ev_02_probe.txt`
- 20 次连读：**20/20 成功**，湿度 576~577（**57.6~57.7 %RH**）、温度 241（**24.1 degC**），
  单次 ~45 ms。
  证据：`docs/evidence/serial-20261018/ev_07_success_rate.txt`

### 5.2 混流：2 真 + 7 仿真同时从 Modbus TCP 可读

在**独立端口 15021**（未占 5020/5000/80）起直读实例，两次读回（相隔 4 s）：

| 测点 | 读 1（原始） | 读 2（原始） | 判读 |
|---|---|---|---|
| Temp | 242 | 242 | **24.2 degC，真机** |
| Humidity | 573 | 575 | **57.3 / 57.5 %RH，真机** |
| Flow | 29744 | 29862 | 仿真波形（在变） |
| SO2 | 299 | 294 | 仿真波形（在变） |
| O2 | 50 | 51 | 仿真波形（在变） |

其余 Dust/NOx/Velocity/Pressure 也在量程内波动。同一秒的 device 日志写着
`串口直读：湿度 57.3 %RH ｜ 温度 24.2 degC ｜ 状态位=0`，与 5020 读回值对得上。
证据：`docs/evidence/serial-20261018/ev_04_mixed_flow.txt`（读回）、
`ev_06_device_log.txt`（同秒日志）。

### 5.3 故障语义（**真机链路干扰注入**）

真实硬件无法用软件拔线，所以用同一宿主上的第二个进程按 4800/8/N/1 向**同一个**
`/dev/ttyUSB0` 连续写噪声字节（帧碰撞/总线干扰，不写任何寄存器）。效果：

- 设备层连续 5 次读失败（`RtuTimeout: 应答超时：只收到 0/3 字节帧头`），
  状态位 1、对外 `Temp=3010 (301.0 degC)`、`Humidity=1010 (101.0 %)`，
  两个值都被判 `OUT_OF_RANGE`；
- 噪声停止后**同一进程自动恢复**：`串口直读恢复（此前连续失败 5 次）`，
  状态位回 0，读回真机值 `24.2 degC / 58.0 %RH`；
- 全程 device 进程存活（`ps` 有 PID），没有重启。
  证据：`docs/evidence/serial-20261018/ev_05_fault_recovery.txt`、
  `ev_03_probe_fault_status.txt`（探针口径：噪声中 4/4 失败、状态=1、越界值；
  噪声停后 3/3 成功、状态=0）、`ev_06_device_log.txt`（故障到恢复的全部日志行）。

### 5.4 故障语义（**模拟对端，不是真机**）

真机不能拔线，另用 pty 模拟一个 RTU 从站，验证"串口链路消失/恢复"这一类故障。
⚠️ 这一组证据的对端是**模拟对端（Python pty）**，不是真机：

- 模拟从站应答 `01 03 04 02 31 01 11 6b d8` → 5020 读回 `27.3 degC / 56.1 %RH`，
  其余 7 点仍是仿真；
- `SIGUSR1` 暂停应答（读超时）→ `301.0 degC / 101.0 %`、进程存活；
- `SIGUSR2` 恢复应答 → 自动回 `27.3 degC / 56.1 %RH`；
- 直接杀掉模拟从站（`/tmp/ttyV0` 悬空、串口打不开）→ 仍是越界值；
  重建模拟从站（新 pty）→ device 自动重连恢复，不需要重启。
  证据：`docs/evidence/serial-20261018/ev_09_pty_fault_recovery.txt`、
  `ev_09_pty_device_log.txt`、`ev_08_peer_log.txt`；模拟从站脚本
  `docs/evidence/serial-20261018/sim_peer_rtu_slave.py`。

## 七、边界（未验证 / 本形态不做什么）

1. ⚠️ **Windows 侧真机未验证**：取证时 USB-485 已不在 Windows 机器上（设备管理器里是
   Code 45 phantom），COM3 不存在；真机读数是在 Linux Mint 宿主上测的。
2. ⚠️ **拔线 / 断电故障未验证**：真实硬件上的故障注入是"同宿主第二进程向同一 485 总线
   写噪声"（链路干扰），不是物理断开；拔线与断电恢复曲线需要现场动手才能取证。
3. ⚠️ **容器内直读未做，也不建议做**：容器拿不到宿主串口。直读形态只适用于
   device 进程与串口同宿主的部署；容器部署继续用 `serial_bridge.py` + `tcp` 形态。
4. ⚠️ **状态位没有独立对外寄存器**：`:5020` 仍是 9 测点布局（不改契约），陈旧语义体现在
   值上（101.0 % / 301.0 degC）；状态位本身通过探针 `status_registers()` 与进程日志观察。
5. ⚠️ **负温实机未验证**：本次环境温度 23~24 degC；`-9.7 degC`（`FF 9F`）的补码解析只有
   单测覆盖。
6. ⚠️ **只在 Mint 22.3 / x86_64 验证**：其他 Linux 发行版、ARM、USB-485 型号未验证。
7. ⚠️ **只覆盖 1 号炉的 2 个测点**：一条串口只有一台变送器；`REAL_DEVICE_SLAVE=2` 的多从站
   直读没有硬件可验，仍是纯仿真。
8. ⚠️ **只测了 4800/8/N/1**：波特率/校验填错的表现（完全静默 → 读超时 → 越界值）是同一套
   超时语义，但没有逐项复测。
9. ⚠️ **端到端只验证了 `device → gateway → EMQX → 接入层 → TDengine → Web` 这一条**；
   告警、报表、回调等其它消费者没有逐一复验（它们读的是同一条入库数据）。
10. ℹ️ 切换后接入层会记录一条 `Temp 跳变可疑` 事件（175.1 → 23.8）：这是**语义边界**
    （环境量 vs 烟气量）被跳变检测如实记录下来，不是故障。
