# 离线部署验证（换机 / 断网可跑）

> **这份文档解决什么**：面试高频题 ——
> **"给你一台干净机器，还没网，你怎么把整套系统跑起来？"**
>
> 它记录的是**真做过的验证**，不是设计意图。每一步都注明"验到哪一步、哪一步没验"。
>
> 环境：Windows + Docker Desktop 29.7.2 ｜ 验证日期：2026-10-03 ｜ 结论：**机制已实测通过**

---

## 0. 一句话结论

镜像搬运的**机制**（导出 → 校验 → 导入 → 起链路）已在单机上**逐环节实测通过**；
**"换一台物理机器"这一步没有设备，未做** —— 见 §6，那一节可以直接当面试口径用。

---

## 1. ⚠️ 核心发现：按 digest 导出 = 离线部署当场死掉

这是本次验证最值钱的一条，**不实测绝对想不到**。

### 1.1 实测对照

| 实验 | `docker save` 出的 tar 里 `RepoTags` | 结果 |
|---|---|---|
| `docker save nginx@sha256:df221db8…`（**按 digest**） | **`null`** | ❌ 包**不带任何名字** |
| `docker save nginx:1.31.6-alpine`（**按 tag**） | `["nginx:1.31.6-alpine"]` | ✅ 名字在包里 |

### 1.2 按 digest 导出的包，导进去之后会怎样

```
$ docker load -i nginx.tar
Loaded image ID: sha256:df221db836e1…          ← 注意：只有 ID，没有 Loaded image: 名字

$ docker image inspect df221db836e1 --format '{{.RepoTags}} {{.RepoDigests}}'
[]  []                                          ← 名字和 digest 一个都没有

$ docker create nginx@sha256:df221db8…
Unable to find image 'nginx@sha256:df221db8…' locally
docker.io/library/nginx@sha256:df221db8…: Pulling from library/nginx   ← 转去联网拉！
```

**有网的机器上它"看起来成功了"（其实是偷偷下载了一遍）；断网机器上就是硬失败。**

### 1.3 这条发现推翻了什么

本项目原先为"可复现性"把四个基础设施镜像**按 digest 钉死**（见 commit `b61d874`）。
但 digest 与离线搬运**互斥**：

> `docker save <image>@sha256:...` 无法保留仓库名，而 digest 引用的解析**依赖仓库名**。

**所以 compose 里改回"具体版本 tag"**（`6.3.0` / `3.3.6.13` / `7.4.11-alpine` / `1.31.6-alpine`），
digest 降级为 `.env.example` 里的台账。

**取舍说清楚**：

| 方案 | 可复现性 | 离线可搬运 | 结论 |
|---|---|---|---|
| `:latest` / `:alpine` | ❌ 重建会漂到大版本 | ✅ | 不用 |
| `@sha256:...` | ✅ 最强 | ❌ **包不带名字** | 单机可以，**本项目不行** |
| **具体版本 tag** | ✅ 够用（tag 名即版本） | ✅ | **采用** |

换 tag 前**逐个实测拉取**过，并核对"拉下来的 digest 与当时在跑的容器逐位相等" —— 同构建、零行为变化：

| 镜像 | digest（前 12 位） | 与运行中容器 |
|---|---|---|
| `emqx/emqx:6.3.0` | `3b6d9c0c4199` | ✅ 一致 |
| `tdengine/tdengine:3.3.6.13` | `79d32ce8a42f` | ✅ 一致 |
| `redis:7.4.11-alpine` | `858f009f9709` | ✅ 一致 |
| `nginx:1.31.6-alpine` | `df221db836e1` | ✅ 一致 |

## 2. 完整步骤（三步）

### 2.1 源机：打包

```powershell
pwsh -NoProfile -File scripts\export_images.ps1
```

做的事：构建应用镜像 → 确认四个基础镜像在位（缺则 `docker pull`）→
**按 tag** 导出成一个 tar → 写 sha256 → **自检 tar 里 `RepoTags` 不为 null**（为 null 直接报错退出）。

产物：

```
dist\cems-images-<时间戳>.tar          # 5 个镜像（4 基础 + 1 应用）
dist\cems-images-<时间戳>.sha256       # 校验和
```

### 2.2 搬运

`dist\*.tar` + `dist\*.sha256` + 仓库代码 → U 盘 / 内网共享 / 任何能过的方式。

### 2.3 目标机（干净、无外网）：导入并起链路

```powershell
pwsh -NoProfile -File scripts\import_images.ps1 -From D:\dist
docker compose up -d --build
docker compose ps                       # 期望：全部 healthy
```

`import_images.ps1` 做的事：校验 sha256 → **读 tar 里的 `manifest.json` 取镜像名**（不信任参数）
→ 与 compose 需要的镜像清单比对（缺了会明说）→ `docker load` → 逐个 `docker image inspect` 确认能解析。

> **为什么 `--build` 在断网下也能用**：应用镜像的 Dockerfile 基础层（`python:3.12`）与
> 依赖包都已打在导出的应用镜像里/或已在本地层缓存中，构建不需要访问外网。
> ⚠️ 这一点**未在真正断网的机器上验证过**（见 §6）。

## 3. 💥 最容易漏的一条：`docker save` 导出的是**镜像**，不是数据

**镜像搬过去 ≠ 系统能跑。** 这些东西**不在镜像里**，换机必须单独带：

| 不在镜像里的东西 | 后果 | 怎么带 |
|---|---|---|
| `.env` 真实配置（口令、端口、BIND_ADDR） | 容器起来但连不上库/broker | 单独拷（**别提交进 git**） |
| `data/` 卷（TDengine 历史数据、网关缓存、落盘队列） | 起来是**空库**，历史数据没了 | `docker run --rm -v` tar 打包，或走备份恢复流程 |
| 宿主机时区 | 时间戳整体偏 8 小时 | 目标机 `TZ` 与源机一致 |
| Modbus 从站地址 / 端口占用 | 设备层连不上 | 见 `.env` 与 `docker-compose.yml` 的 ports |
| 四个基础镜像之外的东西（如将来加的 DB） | 某服务起不来 | 加进 `export_images.ps1` 的 `$infraImages` |

> 计划文档里 P4「新机部署验收清单」曾被判定为"Docker 一键起已覆盖"而取消。
> **实测证明它没被完全覆盖** —— 上表这几项就是清单该有的内容，只是不另立文件，写在这里。

## 4. 实测记录（本次真跑出来的输出）

| 环节 | 命令 | 结果 |
|---|---|---|
| 导出 | `export_images.ps1 -SkipBuild` | `cems-images-20261003-182329.tar` **661.8 MB**，自检 `RepoTags:["nginx:1.31.6-alpine"]` ✅ |
| 校验和 | 脚本自动 | `sha256=279c65848b275833…` 写入 `.sha256` ✅ |
| **负向对照** | 故意放入一个**按 digest 导出**的坏包，跑 import | **被拒绝**：`bad-digest-export.tar carries an image with RepoTags=null -- it was exported BY DIGEST`，退出码 1 ✅ |
| 模拟干净机器 | `docker rmi nginx:1.31.6-alpine` | `docker image inspect` 返回 `[]`，确认本地已无该引用 ✅ |
| 导入 | `import_images.ps1 -From dist` | `Loaded image: nginx:1.31.6-alpine` ×5，逐个 inspect 全部解析 ✅ |
| 起链路 | `docker compose --profile plant2 up -d` | **10/10 healthy** ✅ |
| 回归 | `acceptance_min.py` / `pytest` / `verify_data_lineage.py` | 全通过（见验收报告） ✅ |

**负向对照这一条最关键**：它证明校验器**真的会拦住**那个错误做法，而不是"看起来写了校验"。

## 5. 排障：如果目标机上 compose 还是想联网

| 症状 | 原因 | 处理 |
|---|---|---|
| `Unable to find image 'X' locally` + `Pulling from` | 包里的镜像**不带名字**（按 digest 导出过） | 回到源机用 `export_images.ps1` 重导 |
| 某个服务报镜像不存在 | 该镜像**没进包**（脚本漏列） | 加进 `$infraImages` 后重导 |
| `docker load` 报 tar 损坏 | 搬运过程截断 | 用 `.sha256` 核对；重新拷 |
| 起来了但连不上库/broker | `.env` 没带过去 | 见 §3 上表 |
| 起来是空库 | `data/` 卷没搬 | 见 §3 上表；不搬就是"新系统"，不是"恢复" |

## 6. ⚠️ 没验到的部分（面试时必须主动说）

**"换一台物理机器"这一步没有第二台设备，未做。** 所以下面这些是**推导**，不是实测：

1. **真正断网的构建**：本次 `--build` 是在有网机器上跑的。断网下构建是否完全不需要外网，未实测。
2. **目标机 Docker 版本差异**：镜像格式对 Docker 版本有要求（本机 29.7.2），老版本 Docker 能否 `load` 未验。
3. **跨平台**：只在 Windows + Docker Desktop 上做过，Linux 宿主未验。
4. **`data/` 卷搬迁**：本次没搬（目标就是验证"镜像搬运"这一环），搬卷流程走的是备份恢复那套（有独立演练记录）。
5. **`.env` 缺失的失败表现**：没真跑过"故意不给 .env"的场景。

### 建议的补验方式（成本从低到高）

| 方式 | 能补上什么 | 成本 |
|---|---|---|
| **VirtualBox / VMware 装一台最小 Ubuntu** | §6 全部 5 条，最接近真实换机 | 半天（本机 F 盘余量 215 GB，够） |
| Windows 沙盒 / 另一台分区 | 部分（同一内核，隔离性弱） | 1 小时 |
| 本机 `docker` 换个受限用户 + 断网 | 只能验导入那半段 | 半小时 |

## 7. 面试口径（可直接背，但每句都有上面的事实支撑）

> **问**："给你一台干净机器，还没网，你怎么跑起来？"
>
> **答**：
> "分三步：源机按 tag 把镜像导成 tar，连代码和配置一起搬过去，目标机 load 完直接 compose up。
>
> 这里面有一个坑我实测踩过：**导出必须按 tag，不能按 digest**。
> `docker save` 一个 digest 引用的镜像，出来的 tar 里 `RepoTags` 是 null，包里一点名字都没有；
> `docker load` 回去之后 compose 解析不了那个 digest，会改去联网拉 —— 断网机器上就是硬失败。
> 我就是因为先按 digest 钉了版本，才发现这条路被堵死了，后来改成版本 tag，digest 留台账。
>
> 另外要分清：**镜像搬过去不等于系统能跑**。`.env`、`data/` 卷、宿主机时区都不在镜像里，
> 少一样就是"起来了但数据是空的"。
>
> **我没做到的是**：我只有一台机器，所以"换到另一台物理机"这一步没实测过 ——
> 我验的是打包、校验、导入这三个环节，都在本机真跑通了，还专门放了个错包验证校验器会拦。
> 要补的话，装个虚拟机半天就能补上。"

**这段回答为什么强**：它同时给出了①做法②踩过的坑③边界。**主动说没做的那一句，比多说三个工具更值钱。**
