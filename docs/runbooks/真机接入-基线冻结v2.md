## 5. 数据链路与**数据新鲜度指示**

### 5.1 两条并存的取值路径

```
[温湿度变送器] --RS485--> COM3
                             |
              scripts/serial_bridge.py（宿主，Modbus TCP :5021）
                             |
    路径 A：设备层混流（REAL_DEVICE_ENABLE=1，本基线走这条）
    地址 6=Temp / 7=Humidity ← 真机，其余 7 点仿真，只作用于从站 1
        |
    cems/plant1/data → cems-subscriber → cems_data(plant1/device1)
        |
        └──────► 大屏（:80 / :5001）
```

> v1 里还有一条"路径 B：点集分离（`gateway-transmitter` → `cems/transmitter/data`）"，
> 它随 `--profile transmitter` 一起移出了主线。**本基线只有路径 A。**

### 5.2 数据新鲜度指示（v2 新增 · "治全绿零数据"的最小方案）

**问题**：容器全绿（`healthy`）而**数据已经停了** —— 大屏照样显示最后一张图、状态栏写着
"实时模式"，人看不出来。这是本项目记录在案的第 7 条边界（"网关心跳在读设备之前刷新 ⇒ 全绿零数据"）。

**做法（刻意保持最小）**：

| 项 | 取值 |
|---|---|
| 显示位置 | **首页（`/`，监测数据表）** 与曲线页（`/chart`）的标题旁，同一条胶囊指示 |
| 文案 | `数据新鲜度：最后一条数据：N 秒前` |
| 取数 | **已有的** `GET /api/health`（它内部用**已有的** `query_recent()` 查 TDengine 最新 `ts`） |
| 判据 | **仅** 走"数据年龄"这一个数：`data_age_seconds > FRESHNESS_WARN_SECONDS` ⇒ 红 |
| 阈值 | `FRESHNESS_WARN_SECONDS`，**默认 30 秒**，env 可覆盖 |
| 刷新 | 与页面既有刷新机制同一节拍（首页固定 5 秒轮询；曲线页挂在实时轮询的 `finally` 上） |
| **不引入** | ❌ 不加 Prometheus、❌ 不加容器、❌ 不加依赖、❌ 不新造查询路径 |

**实现位置**：`src/web/web_dashboard.py` 的配置区（`FRESHNESS_WARN_SECONDS`）、
`_render_page()`（注入 `__FRESHNESS_WARN__`）与两页脚本里的 `loadFreshness()` / `setFreshness()`。

⚠️ **为什么展示层阈值（30 s）不等于健康判据阈值（15 s）**：`/api/health` 的
`stale_after_seconds` 是**编排层**判据（超了要让容器 unhealthy，必须敏感）；
页面上那条是**给人看**的。真机链路上偶发一次补传滞后（实测最大 32.1 s，
见 `docs/reference/性能与可靠性指标.md` §4.2）就会让 15 s 的判据闪红 ——
人被训练成"红色=正常抖动"之后，真正停流时反而没人看。所以展示层更宽。

**实测证据（两种状态都做过，截图 + `rendered.txt` 见提交时的验收记录）**：

| 状态 | 怎么造 | 实测输出 |
|---|---|---|
| **正常态** | 默认阈值 30 s，数据在流 | `/api/health` → `{"data_age_seconds":3.225,"ok":true,"reason":"fresh",…}`；页面注入 `FRESHNESS_WARN=30.0`；渲染 `class="fresh ok"` / `数据新鲜度：最后一条数据：4 秒前`（**绿色胶囊**） |
| **超时态** | `$env:FRESHNESS_WARN_SECONDS='1'` + `up -d --force-recreate web`（容器内实测 `w.FRESHNESS_WARN_SECONDS = 1.0`） | `/api/health` → `data_age_seconds=2.365`；页面注入 `FRESHNESS_WARN=1.0`；渲染 `class="fresh bad"` / `数据新鲜度：最后一条数据：5.5 秒前（已超过 1 秒，疑似停流）`（**红色加粗**） |

⚠️ **为什么用"调阈值"而不是"停 subscriber"造超时**：停订阅端会顺带造出真实断档（污染这次
基线冻结的数据），而调阈值**只影响上色、不影响 healthcheck 与入库**，可逆且无副作用。
两种造法的结论一样（都是"年龄 > 阈值 ⇒ 红"），取副作用更小的那个。

## 6. 统一镜像 / 清悬空（**复现基线时必须做的一步**）

⚠️ **`up -d --build subscriber` 不会重建镜像** —— compose 里**只有 `device` 声明了 `build:`**，
其余服务只是引用 `cems-pipeline:latest`。这正是"改了代码、容器 healthy、跑的还是旧代码"那个坑
（见 `docs/runbooks/容器重建与代码生效.md`）。**构建入口只有一条**：

```powershell
$env:DOCKER_BUILDKIT=0            # 经典构建器：中间层命名可读，便于对照 dangling
docker compose build device       # 全项目唯一构建入口 → cems-pipeline:latest
docker compose --profile plant2 up -d --force-recreate
docker image prune -f             # 清悬空
```

**实测结果（2026-10-11 冻结时刻）**：

- `docker image prune -f` → **`Total reclaimed space: 171.4MB`**，
  被删的悬空镜像里**包含 v1 记的那一个**：
  `untagged: sha256:44a7034083a7a25854b499d195c55b745737e7534177484138f2490203e0f34c`
- 应用镜像唯一性：`docker ps --format "{{.Image}}" | Sort-Object -Unique` →
  `cems-pipeline:latest` **只出现一次**（另外 4 项是基础设施镜像）
- 悬空镜像：**35 → 3**（清悬空这一步连做了两轮：`up -d --force-recreate` 会把上一版镜像
  变成悬空，所以顺序必须是 **build → up → prune**，最后再确认一次）

⚠️ **残留的 3 个悬空镜像是有意留下的**（`docker image prune -f` 报 `Total reclaimed space: 0B`，
说明它们**不可回收**）：

| ID | 大小 | 它是什么 |
|---|---|---|
| `858f009f9709` | 57.8 MB | 基础设施镜像的**同层副本**（`redis:7.4.11-alpine` 与 `redis:7-alpine` 指向同一 ID `858f009f9709`；层文件只有一份，删它等于删镜像本身） |
| `3b6d9c0c4199` | 484 MB | 同上（`emqx/emqx:6.3.0` / `emqx/emqx:latest`） |
| `79d32ce8a42f` | 1.47 GB | 同上（`tdengine/tdengine:3.3.6.13` / `tdengine/tdengine:latest`） |

即：**悬空计数无法降到 0**，下限就是这 3 个（每个 = 一个基础设施镜像的第二个 tag 指向）。
验收条件按"**0~2 个悬空应用镜像**"口径满足（**应用镜像悬空数 = 0**）。

## 7. 复现 / 回到本基线

```powershell
# 1. 回到本基线的代码
git checkout real-device-baseline-2

# 2. 起桥（宿主，必须先起 —— 设备层要读它；⚠️ 它独占 COM3）
python scripts/serial_bridge.py --port COM3 --interval 1.0

# 3. 统一镜像 + 起全栈（★ 注意：没有 transmitter profile）
$env:DOCKER_BUILDKIT=0
docker compose build device
docker compose --profile plant2 up -d --force-recreate
docker image prune -f

# 4. 验证（六条必须全过）
python -m pytest -q                 # 542 passed
python check_doc_links.py           # 退出码 0
docker ps --format "{{.Image}}" | Sort-Object -Unique   # cems-pipeline:latest 只出现一次
docker images -f "dangling=true" -q | Measure-Object    # Count = 3（下限，见 §6）
docker exec tdengine taos -d cems -s "SELECT LAST_ROW(ts), LAST_ROW(temp), LAST_ROW(humidity) FROM cems.plant1_device1;"
(Invoke-WebRequest -Uri 'http://127.0.0.1:5001/api/health' -UseBasicParsing).Content
#   → {"data_age_seconds":<小的数>,"healthy":true,"ok":true,"reason":"fresh","stale_after_seconds":15.0,...}
#   → 浏览器打开 http://localhost 应看到**绿色**胶囊"数据新鲜度：最后一条数据：N 秒前"

# 5.（可选）复现"超时变红"：把展示层阈值压到 1 秒，只重建 web
$env:FRESHNESS_WARN_SECONDS='1'
docker compose --profile plant2 up -d --force-recreate web
#   → 等 30 秒以上（让最后一条数据的年龄超过 1 秒），页面胶囊变**红色加粗**：
#     "数据新鲜度：最后一条数据：N 秒前（已超过 1 秒，疑似停流）"
#   → 恢复：Remove-Item Env:FRESHNESS_WARN_SECONDS; docker compose --profile plant2 up -d --force-recreate web
```

⚠️ **控制台是 GBK**：上面第 4 步最后一条是 PowerShell 命令，`taos` 那条是容器内命令
（**必须带 `-d cems`**，TDengine 容器里没有默认库）。

⚠️ **`host.docker.internal` 是 Docker Desktop 的特性**；Linux 下需在 compose 里加
`extra_hosts: ["host.docker.internal:host-gateway"]`，否则容器读不到桥。

## 9. 明确不在本基线范围内的（报告要写清）

- **传感器漂移失准**、**超量程的真实物理量**、**MQTT 伪造报文**、**时钟错乱** —— 均未覆盖
- **逐点质量位**的"整条一个 Flag"问题 —— 已在 ADR-0009 拆成"语法坏整条拒收 / 语义坏逐点处理"，
  但**真机链路上的逐点质量位**未做专门实验
- **跳变/冻结判据的真机标定** —— 已有 ADR-0010 的 10 天全量标定（`N=1200 / 容差 1e-4`），
  但**未在真机故障注入下逐条验证**
- **路径 B（点集分离）** —— 已随 `--profile transmitter` 移出主线，
  只在 `feat/point-set-config` 分支上，**本基线不使用、也不保证它还能跑**
- **第三方仪器对照** —— 仍然没有（全部验证仍是自证）
