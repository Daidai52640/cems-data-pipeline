### 1.4 在线备份的"窗口"问题，以及自检为什么这么写

备份时 tdengine **不停机**（它还在被写入），所以一次备份不是一个瞬间，是一个**窗口**。
如果恢复校验拿"库内当前全部数据"当基准，就会把"备份之后新写入的行"算成"恢复丢的数据"，得出假失败。

处理方式（两端都做）：

1. **备份侧**：manifest 记 `pre_count / pre_min / pre_max`（dump **前**）与 `post_*`（dump **后**）；
2. **恢复侧**：**校验窗口取 `[pre_min_ms, pre_max_ms]`**。
   这个区间在 dump 开始前就已全部落库，**必然完整落在备份里**；
   源端在 dump 期间/之后新增的行被窗口切掉，不参与比较。
3. **两个自检，判据强度不同**：

   | 模式 | 判据 | 强度 |
   |---|---|---|
   | 全量 | `pre_count ≤ dumped_rows ≤ post_count` | 只能判区间（dump 覆盖的是窗口内某一瞬间） |
   | 时间窗差量 | `dumped_rows == COUNT(*) WHERE ts ∈ [since, until]` | **精确相等**（窗口两端都是已封口的历史，源端继续写不影响它） |

   ⚠️ 实测踩到：`taosdump` 把 `OK: N row(s) dumped out!` 这行写在 **stderr**（进度条在 stdout），
   只 grep stdout 会得到 `None`，于是自检永远判失败。见 §1.5。

### 1.5 备份/恢复实现里踩到的坑（都已修，记下来避免重犯）

| # | 坑 | 现象 | 处理 |
|---|---|---|---|
| 1 | **`taosdump` 的行数写在 stderr** | 只读 stdout → `dumped_rows = None` → 自检 `dumped_rows_unparsed`，但备份其实成功 | 两路输出合并后再正则匹配 |
| 2 | **`taos -s` 对 0 行结果不打表头与分隔行** | 解析器找不到 `====` 行，对"不存在的库"抛异常，把"查不到"变成"脚本崩" | `parse_taos_table` 把"无分隔行 + `Query OK, 0 row(s)`"判成**空结果集**（不是失败） |
| 3 | **DDL 回的是 `Create OK` / `Drop OK`，不是 `Query OK`** | 实例预热判据写 `"Query OK" in out` → 空转 180 s / 47 次仍判失败 | 判据改成"无 `DB error` 且含 `OK,`" |
| 4 | **`MAX(ts)` / `MIN(ts)` 在 3.3.6 不可用** | `Invalid data type: max` / `Invalid parameter data type : min`。分段查询里用 `MIN(ts)` 做桶边界直接报错 | 首末用 `ORDER BY ts LIMIT 1`；桶内首末用 `FIRST(ts)/LAST(ts)`（INTERVAL 查询里它们就是桶的首末，已实测核对） |
| 5 | **`TO_UNIXTIMESTAMP()` 不可用** | `Invalid parameter data type : to_unixtimestamp` | 统一用 `CAST(ts AS BIGINT)` / `CAST(_wstart AS BIGINT)` 取纪元毫秒，顺带绕开时区与 UTC 陷阱 |
| 6 | ⭐ **全新实例的首次 DDL 会失败** | `wait_taos_ready`（`SHOW DATABASES` 成功）之后立刻 `taosdump -i`，出现过**返回码 0、但目标库里根本没有 `cems`**；taosd 日志里是成串的 `Stable already exists` / `Stable not exists` 重试。**实测这个窗口约 2.6 s（3 次尝试）** | 恢复前先跑一遍与 taosdump 同形状的 `CREATE DATABASE / CREATE STABLE / DROP` **预热**（判据见 §1.5 第 4 条），并把这段耗时**单独计入 RTO**（§2.3）；恢复后**必须真的查到库**（最多等 20 s），否则判失败 |
| 7 | **taosAdapter REST 的 `ts` 是 UTC** | 项目在 [ADR-0004 引入 nginx 与 redis 缓存](../adr/0004-引入nginx与redis缓存.md) §8.2 第 10 条记过一次由此造成的真实数据错位 | 本方案的取数**一律走容器内 `taos` CLI**，且时间字段全部取纪元毫秒，不经过 ISO 字符串 |

⚠️ 第 6 条是本次最有价值的一条：**"命令返回 0"不等于"恢复成功"**。
如果只信返回码，就会把一次假成功写进验收报告。所以恢复脚本的判据是
"**库里真的查得到，且条数与分段逐桶一致**"。

### 1.6 备份自检的行数口径：整库 vs 主表（双设备复验时暴露并已定性）

双设备复验的第一份备份（`cems_full_20261003_002857`）在备份脚本里被判
**`rows_out_of_range`** 并以退出码 5 结束：

```
dump 前基线：18570 条  →  taosdump 完成：自报 19100 条  →  dump 后基线：18570 条
⚠️ 自检未通过：rows_out_of_range（pre=18570 dumped=19100 post=18570）
```

**这不是备份失败，是自检把两个不同口径的数放在一起比了**：

| 量 | 值 | 取法 |
|---|---|---|
| `dumped_rows`（`taosdump` 自报） | **19 100** | **整库**：`cems` 下**全部 4 张超级表**的行数总和 |
| `pre_count` / `post_count` | **18 570** | **主表**：`SELECT COUNT(*) FROM cems.cems_data`（多设备共用 super table） |

差额 **530 条**恰好是**另外 3 张历史表**在 dump 时刻的行数（复核脚本
`scripts/verify_backup_selfcheck_scope.py`，证据
[backup_selfcheck_scope_dual_dev_20261003.json](../evidence/backup/backup_selfcheck_scope_dual_dev_20261003.json)）：

| 表 | dump 后同一时刻（`ts <= 2026-10-03 00:29:01`） | 复核时（01:00 后） |
|---|---|---|
| `cems_hourly_verdict` | 42 | 42 |
| `cems_alarm_event` | 244 | 247 |
| `cems_alarm_push` | 244 | 247 |
| **小计** | **530** | 536 |
| **重建 = 主表 dump 前 18 570 + 530** | **19 100 = `reported_rows`** ✅ 差 0 | — |

即：**备份本身是完整的**（taosdump 确实把整库都导了，`OK: 19100 row(s) dumped out!`），
`rows_out_of_range` 是**判据的取数口径不一致**造成的假告警 —— 自检拿"整库条数"去比"主表条数"。
留下的两条确定性结论：

1. **`taosdump` 导出的是整个 `cems` 库**，不止 `cems_data` ⇒ 恢复出来的库里
   告警事件、小时结论、推送记录**同样被备份/恢复**（本次演练只校验 `cems_data` 的保真度，
   另外 3 张表**未逐条对账**，见 §7 第 16 条）；
2. 引用 `manifest.dump.self_check` 时**必须先看 `reported_rows` 与主表条数是不是同一口径**；
   在"库里有 4 张超级表"的现状下，全量模式的 `self_check == "ok"` 需要按 §1.4 的窗口判据
   单独看主表，不能只看这个字段的字符串。

> ⚠️ 该告警**不代表可以忽略自检**：本节的结论来自"530 能被 3 张表逐表对上、且差 0"的
> 实测重建，不是"解释一下就过去了"。若差额对不上任何一张已知表，仍按备份失败处理。

## 2. 恢复演练：真恢复 + RTO

### 2.1 RTO 的定义（先说清口径，数字才有意义）

```
t0  = 发出「开始恢复」的那一刻（time.perf_counter，宿主机单调时钟）
t_up     = 恢复目标实例可以执行查询（不是容器 healthy）
t_data   = 数据导入完成 / 卷解包完成且实例可查
t_count  = 窗口内条数校验通过
t_seg    = 按小时 + 按天分段校验通过

RTO = t_seg − t0      ← 本文口径：「数据可查且计数正确」
```

- 同时报 `t_data − t0`（**数据真正可查**的时刻）作为下界参考：
  它与 RTO 的差就是**校验工装的自身开销**。
- ⚠️ 校验工装的固定成本不小：每次判定要 `docker exec <容器> taos -s ...`，
  单次约 0.6 s，六项校验合计 **约 4.6 s**。
  也就是说 **RTO 里 4.6 s 是"我们在验证"，不是"系统在恢复"** —— 这个分解必须一起给，
  否则 9.80 s 的 RTO 会被误读成"恢复很慢"。

### 2.2 三条恢复路径（都真跑过，不是设计文档）

| 路径 | 做什么 | 碰不碰现网数据 | 适用场景 |
|---|---|---|---|
| **`--mode instance`** | 另起容器 `cems-tdengine-drill` + 独立卷 `cems-tdengine-drill-data`，把备份 `taosdump -i` 进去 | **完全不碰**（演练实例故意不接 `cems-net`，默认 bridge 是另一个二层域，不会与现网 dnode 互相发现） | 最接近真实灾难：整实例丢失后从备份重建 |
| **`--mode rename`** | 在现网实例内 `taosdump -i -W cems=cems_drill_restore` 恢复成**独立库名** | 在现网实例里**新建一个库**，不碰 `cems`；结束后 `DROP DATABASE` 并二次核对 | 想在同机快速取证/比对某个历史点 |
| **`--mode physical`** | 把备份里的 `var_lib_taos.tar.gz` 解包进独立卷，起独立实例 | 不碰现网（tar 是只读挂载现网卷做出来的） | 逻辑备份不可用时的应急路径 |

**清理方式（每个模式都有，且脚本自动执行 + 二次核对）**：

```powershell
# instance / physical
docker rm -f cems-tdengine-drill
docker volume rm cems-tdengine-drill-data
# rename（脚本在 finally 里做，出问题可手工）
docker exec tdengine taos -s "DROP DATABASE IF EXISTS cems_drill_restore;"
docker exec tdengine sh -c "rm -rf /tmp/drill-restore-in"
```

每次演练结束脚本都会打印 `清理完成，残留：无`；8 次演练的 `cleanup.leftovers` 全为 `[]`。

### 2.4 恢复保真度校验：为什么必须分段（只比总数会掩盖问题）

**校验六项**（全部通过才算成功，任一项不过 → 脚本退出码 4，不写"成功"）：

| # | 项 | 判据 | 为什么不能省 |
|---|---|---|---|
| ① | **窗口内条数** | 源 `COUNT(*)` == 恢复 `COUNT(*)`（窗口 `[pre_min, pre_max]`，精确相等） | 最基本，但**单独比它会被骗**：丢了 A 段、多了 B 段，总数可能一样 |
| ② | **恢复库全局首末 ts** | 信息项，用于看备份是否含窗口之后的行 | 定位"备份比窗口新/旧" |
| ③ | **按小时分段（`INTERVAL(1h)`）** | 逐桶比 `n` + 逐列 `SUM` + 桶内首末 ts，**全部相等** | ⭐ 这是"丢了 A 段多了 B 段"的唯一有效判据 |
| ④ | **按天分段（`INTERVAL(1d)`）** | 同上 | 小时桶之间的错位在大桶上也可能被掩盖，两个粒度互证 |
| ⑤ | **表结构** | `DESCRIBE` 逐行相等（12 列，含 ENCODE/COMPRESS/LEVEL） | 列存了但编码/压缩变了，属静默的保真度下降 |
| ⑥ | **子表标签** | `SELECT DISTINCT plant, device` 相等（`[['plant1','device1']]`） | 数据搬到别的 tag 下，条数照样对 |

**逐桶比较的容差**：`SUM` 用相对容差 `1e-6`。
理由：同一批值聚合，正常应当逐位相等；留容差只是不把"聚合顺序差异"误报成"数据不一致"。
**实测 8/8 次都是逐位相等**（`windows_with_sum_diff = []`）。

**实测覆盖的分段规模**：**13 个按小时桶**（含 04:00–13:25 整栈停机造成的空档，所以不是 21 个连续桶）
+ **1 个按天桶**（数据只跨 1 天）。⚠️ **1 个天桶说明"按天分段"这一项目前几乎无鉴别力** ——
数据长到跨多天后才真正起作用，见 §7 第 4 条。

> **双设备复验已把这两项规模都推大**（§2.7）：按小时桶 **26 个**（`device1`）+ **5 个**（`device2`），
> 按天桶 **3 个** + **2 个**（数据跨 2026-10-01 ~ 10-03）。按天分段的鉴别力因此**首次真正被用到**
> （`device2` 的第 2 个天桶只有 346 行，与第 1 个桶的 2 234 行相差 6.5 倍，逐桶比对仍然全等）。

### 2.7 双设备复验（2026-10-03，现行口径）

§2.3 的结论建立在**一台设备**上：整表级校验只比"`cems_data` 全表"，而两台设备的数据
在**同一个超级表**里（TAG = `plant`/`device`），所以"两台设备互相串台""其中一台整段丢失"
这两种故障在整表级校验里**只看得到总数变化**，定位不到是哪一台。本节把对账**下沉到设备**。

**做法**（`scripts/restore_drill_dual_device.py`，RTO 口径与 §2.1 完全一致）：

1. 备份：`backup_tdengine.py --tier manual --physical` → `cems_full_20261003_002857`；
2. 破坏/隔离：**不碰现网**。恢复目标是**另起独立实例**
   （`cems-tdengine-drill` + 独立卷 `cems-tdengine-drill-data`，故意不接 `cems-net`），
   源库只有 SELECT；这与 §2.2 的 `--mode instance` 同一套隔离手法；
3. 恢复：`taosdump -i` 把整库导进独立实例；
4. **逐设备对账**（恢复端与源端各自独立取数，不做库间对拷）：

| # | 项 | 判据 |
|---|---|---|
| ① | 逐设备条数 | `COUNT(*) WHERE plant=… AND device=… AND ts ∈ 窗口` 精确相等 |
| ② | 逐设备首末 ts | `ORDER BY ts LIMIT 1` / `DESC LIMIT 1` 精确相等 |
| ③ | 逐设备逐列 SUM | 9 个测点列 `SUM()`，相对容差 `1e-6` |
| ④ | 逐设备 × 小时桶 | `INTERVAL(1h)`：逐桶条数 + 逐列 SUM + 桶内 `FIRST/LAST(ts)` |
| ⑤ | 逐设备 × 天桶 | `INTERVAL(1d)`：同上 |
| ⑥ | 标签集合 | `SELECT DISTINCT plant, device` 源端 == 恢复端，**且恰为两台** |
| ⑦ | 合计闭合 | 窗口内恢复端总条数 == 两台之和 == 源端总条数 |

**结果（三次独立运行，逐项一致）**：

| 设备 | 源端条数 | 恢复端条数 | 小时桶 | 天桶 | 逐列 SUM | 首末 ts | 判定 |
|---|---|---|---|---|---|---|---|
| `plant1/device1` | **15 990** | **15 990** | 26 | 3 | 9/9 全等 | 相等 | ✅ |
| `plant2/device2` | **2 580** | **2 580** | 5 | 2 | 9/9 全等 | 相等 | ✅ |
| **窗口合计** | **18 570** | **18 570** | 26 | 3 | — | — | ✅ |

- 校验窗口：`2026-10-01 00:28:11 → 2026-10-03 00:28:57`（manifest `window.pre_*`，口径同 §1.4）；
- 标签集合：源 `[['plant1','device1'], ['plant2','device2']]` == 恢复端，**且恰为两台** ——
  这同时排除了"漏恢复一台设备"与"多出一台/标签错位"；
- 三次运行的 `cleanup.leftovers` 全为 `[]`（容器与卷均不存在）；

## 4. 时区错误演练（TZ=UTC）与日周期复验

> 本节回答两个问题：① **容器时区配错时，故障能不能被发现**（还是被"正常"掩盖）；
> ② **仿真器的日周期刚从"UTC 小时"改成"容器本地时区"，峰值到底落在几点**。
> 两者都只碰隔离实例，不碰生产链路。

### 4.1 为什么要专门练这一项

本项目有**一条硬口径**（[容器时钟漂移](../reference/容器时钟漂移.md) + `docker-compose.yml` 注释）：

> 容器时区必须与 TDengine 一致（都是 `Asia/Shanghai`），否则库里时间戳会整体偏移 8 小时；
> taosAdapter REST 返回的 `ts` 是 **UTC**，项目因此出过一次真实的数据错位。

而"时区配错"的可怕之处不在报错，在于**可能什么都不报**：数据照收、条数照涨、
容器照样 healthy，只是**每条数据都挂在一个错的时刻上**。所以这一项要实测的是
**判据的反应**，不是"会不会报错"。

### 4.2 做法（隔离，不碰生产）

| 项 | 值 |
|---|---|
| 注入的故障 | 网关容器 `TZ=UTC`（其余一切与生产逐字相同：同镜像、同真设备 `cems-device:5020` 从站 1、`POLL_INTERVAL=5.0`） |
| 对照 | 接入层 `TZ=Asia/Shanghai`、TDengine `TZ=Asia/Shanghai`、宿主 `+08:00` —— 与生产一致 |
| 隔离 | 主题 `cems/tzdrill/data`、独立 `client_id`、独立缓存目录、入库标签 `plant=tzdrill`（子表 `tzdrill_device1`） |
| 时长 | 75 s（等子表出现后再采满） |
| 清理 | 两个容器 `docker rm -f`；演练子表 `DROP TABLE` 后复核 |

脚本：`scripts/drill_timezone_misconfig.py`。判据用的是**同一份生产代码**
（`src/web/web_dashboard.py::api_health` 的两条判据），只是把
`TD_PLANT/TD_DEVICE` 指向演练标签 —— 这样测到的就是"生产判据会不会发现"，而不是另写一个判据。

### 4.3 实测结果

**① 容器墙上时钟（同一时刻）**

| 容器 | `date` 输出 |
|---|---|
| `cems-tzdrill-gw`（注入 `TZ=UTC`） | `2026-10-02 16:37:46 UTC +0000` |
| `cems-tzdrill-sub`（`Asia/Shanghai`） | `2026-10-03 00:37:46 CST +0800` |

**② 数据落在哪个时刻**（`plant=tzdrill` 子表，20 条）

| 项 | 值 |
|---|---|
| 入库 ts 范围 | `2026-10-02 16:36:45` → `2026-10-02 16:38:21` |
| 宿主墙上时钟（同一时刻） | `2026-10-03 00:39:02` |
| **库内最新一条相对当地时刻的偏移** | **−28 841.27 s = −8.011 h** |

现象与成因：网关的报文时间戳是 `time.strftime()`（**容器本地时区**）产生的字符串，
接入层 `datetime.strptime()` 按**本地时区**解析后原样入库；于是"网关的 UTC 钟点"
被当成"当地钟点"存进库 —— 每条数据的时刻**整体前移 8 小时**。
数据本身（9 个测点值）**没有错**，错的只有时刻。

**③ 覆盖率/新鲜度判据的反应（这是本节要的结论）**

`GET /api/health`（`TD_PLANT=tzdrill, TD_DEVICE=device1`，同一份生产代码）：

```json
HTTP 503
{"ok": false, "healthy": false, "reason": "no_rows_last_1min",
 "td": "up", "rows_last_1min": 0, "data_age_seconds": null, "stale_after_seconds": 15.0}
```

| 判据 | 阈值 | 演练标签实测 | 判定 |
|---|---|---|---|
| ① 最近 1 分钟条数 | `> 0` | **0**（库内最新一条是 8 小时前） | **判不健康（503）** |
| ② 最近一条样本距今 | ≤ 15.0 s | **28 841.27 s** | **判不健康** |
| ③ 容器/服务存活 | healthy | 网关与接入层**都活着**（进程正常、日志无错） | —— |

⭐ **结论：时区配错**不会**被掩盖成"正常"** —— 它会被**新鲜度判据以最直接的方式抓到**
（`503 + no_rows_last_1min`，日志里也有 `健康检查不通过：reason=no_rows_last_1min`）。
原因是这套判据是**基于"数据时刻 vs 现在"**的，而时区错位恰好把数据时刻推到 8 小时前，
判据必然翻红。**这与既有结论一致**（[性能与可靠性指标](../reference/性能与可靠性指标.md)
与 `web_dashboard` 头部的"数据新鲜度才是健康判据"一条），本次是**在真实注入下复现**。

**同时必须说清的三条边界**（否则容易过度解读这条结论）：

1. **判据能发现"整体错时区"，但给不出"错的是时区"这个诊断**：`reason` 只会说
   `no_rows_last_1min` / `stale_data`，与"网关挂了""链路断了""设备不出了"**表现完全相同**。
   要定位到"时区"，还得人工比对容器 `date` 与库内 ts（本节表①与表②就是这么做的）。
2. **只有"错得足够大"才会被发现**：阈值是 `POLL_INTERVAL × 3 = 15 s`。若偏移小于 15 s
   （例如容器虚拟时钟几百毫秒的漂移），新鲜度判据**不会**报警 —— 那也是本项目
   "容器虚拟时钟 823 ms 级锯齿"被明确排除在判据之外的原因。
3. **"最新一条"口径的局限**：如果错时区的那一路是我方**唯一**的数据源，判据会一直 503（安全侧）；
   但若同一子表里**混着**正确与错误两种时刻的行（本次演练用独立标签避开了这种混合），
   `rows_last_1min > 0` 会由正确的那些行满足，判据就可能**看着是绿的**。
   即：**判据抓的是"这个设备最近有没有新鲜数据"，不是"这个设备的数据时刻对不对"。**

> 补充说明：本次演练的演练标签与生产标签共用 `cems.cems_data` 超级表，
> 但 `/api/health` 的查询**按 `plant`/`device` tag 过滤**（`web_dashboard.query_recent`），
> 所以演练行不会把生产标签的判定带绿，反之亦然。清理后 `tzdrill_device1` 已 `DROP`
> （`cleanup.child_table_dropped = true`、`cleanup.containers = []`）。
> 原始证据：[tz_misconfig_drill_tz_utc_run1.json](../evidence/backup/tz_misconfig_drill_tz_utc_run1.json)。

| **应自动备份到"非系统磁盘"** | HJ 75-2017 H.4 | 落点 `F:\cems-backup`，`F:` 是 **Disk 0**、系统盘 `C:` 是 **Disk 1**（两块不同物理 NVMe） | **满足** | 本机还满足"不同物理盘"这一更强的条件 |

## 7. 没做到 / 测不准的部分（诚实清单）

1. **没有落地定时调度**。脚本与退出码已就位（非 `ok` 返回 5），但**没有挂 Windows 计划任务 /
   cron**，所以"应自动备份"这条目前靠人跑。这一条是**当前最大的缺口** ——
   备份策略再好，没人跑就等于没有。
2. **"基线全量 + 差量链"的合并恢复没做过**。差量本身已验证（359 行精确相等、可独立恢复成库），
   但**"全量 + 一串差量按序叠加，恢复出某个时间点"这条链没有端到端演练**，
   也没有链完整性台账。所以 ADR-0005 §1.2 的切换判据一旦被触发，**还需要先补这套工具**。
3. **RTO 与数据量/网络的关系完全没测**。全部数字来自 7 500 行 / 184 KiB / 同机。
   `taosdump -i` 在 736 MiB 时要多久、跨机传 736 MiB 要多久，**本文给不出任何外推**。
4. **按天分段目前几乎没有鉴别力**。数据只跨 1 天，`INTERVAL(1d)` 只有 1 个桶。
   两个粒度互证的机制写好了，但"按天能发现问题"这件事**要等数据跨多天后才有证据**。
5. **物理副本的可靠性没有被证明**。两次演练都启动成功且窗口内一致，
   但那是**崩溃一致性副本没赶上撕裂**，不是"保证一致"。
   "停 taosd 后做卷拷贝"这条真正一致的做法**没测**（会中断链路，本轮没做）。
6. **多副本 / 仲裁者 / snode 全部未实测**。[ADR-0005 §5.4](../adr/0005-备份策略与保留期.md#54-本项目实际已有的局部冗余别把没有多副本读成零冗余) 里关于 `REPLICA 2`、arbitrator、
   读写分离的具体行为，只有 schema 与文档层面的依据（`with_arbitrator=0`、`SHOW SNODES` 0 行），
   **没有跑过任何一次多副本部署**。结论是"按成本收益不做"，不是"验证过不需要"。
7. **TDengine 的分级存储（local + S3）完全没碰**。
   `ins_databases` 里有 `s3_chunkpages / s3_keeplocal / s3_compact` 这些列，
   它是"把老数据下沉到对象存储"的正路，但本轮**一个字都没验证**。
8. **对账口径没有用旁听探针独立复算**。§3.2 说的是"源端计数最可靠的做法是 MQTT 旁听探针"，
   但本文引用的 task-7 台账用的是**缓存文件快照**口径。两种口径的一致性**未验证**。
9. **没有做定时对账**。§3.4 建议的"每日按小时桶核对源端与库内"没有实现，
   也就意味着**静默丢行在下一次人工对账前不会被发现**。
10. **恢复只验到库查询层**。Web/报表/告警指向新实例后的端到端可用性、以及
    恢复后 Redis 缓存水位如何重建，**都没验**。
11. **备份的 SHA-256 只做记录，没做定期校验**。`manifest.json` 里有逐文件哈希，
    但**没有"定期回读全部备份并核对哈希"的巡检任务**，也没有模拟过"备份文件被截断/损坏"时能否被发现。
12. **HJ 75-2017 H.4 与 HJ 76-2017 B.5.2(3) 的条文原文未取证**（与
    [性能与可靠性指标](../reference/性能与可靠性指标.md) §8 同一处理）。
13. **演练实例与现网实例共处同一 Docker 环境**。本方案靠"不接同一个网络"规避 dnode 互相发现，
    但**真实割接**（新实例替换旧实例、或新旧并存）的集群身份处理**没有验证**。
14. **备份脚本自身没有单元测试**。验证方式是"真跑 13 次备份 + 8 次恢复演练"，
    解析逻辑（`parse_taos_table`、`parse_dump_rows`）靠实测覆盖，**没有构造畸形输入用例**。
15. ⭐ **RTO 的第一版数字被工装缺陷污染过，已修正但过程要留档**。
    第一版 `warmup_instance` 的重试间隔固定 `sleep 2 s`，而它发生在 `t_up` 之后、
    又被计进了"备份传入目标"这一项 —— 于是 **`docker cp` 被报成 4.2 s**
    （实际 **0.14 s**，差 30 倍），instance 模式的 RTO 被报成 **11.2 ~ 11.6 s**。
    修正两处后（退避改成 0.1/0.2/0.4… 上限 1 s；预热单独成项）重跑 3 次，
    RTO = **9.754 / 9.799 / 9.857 s**，`docker cp` = 0.139 ~ 0.142 s。
    **本文所有 RTO 数字都是修正后重跑的**。留这条是因为"测量工装本身出错"比"系统慢"更常见，
    也更难被发现 —— 当时 8 次演练的"校验结果全部一致"，没有一个能发现这个错。

**双设备复验（2026-10-03）新增的诚实条目：**

16. **另外 3 张超级表没有逐条对账**。§1.6 证实 `taosdump` 把整个 `cems` 库（4 张超级表）都备份/恢复了，
    但**保真度校验只覆盖了 `cems_data`**：`cems_hourly_verdict`（42 行）、
    `cems_alarm_event`（244 行）、`cems_alarm_push`（244 行）**没有做逐条/分段比对**。
    所以"告警与小时结论也能被正确恢复"这件事，目前只有"条数口径对得上"的间接证据（§1.6），
    **没有独立校验**。
17. **`manifest.dump.self_check` 的全量模式判据目前会把成功报成失败**（§1.6 实测：
    整库 19 100 vs 主表 18 570 ⇒ 假告警 `rows_out_of_range`）。本轮的处置是**定性 + 记录**，
    把口径写进文档并给了复核脚本；**判据本身没有改**（验收不改源码）。
    在"库里有多张超级表"的现状下，全量备份的退出码 5 **不能直接当作备份失败**。
18. **双设备只跨 3 个自然日**（2026-10-01 ~ 10-03）。按天分段的桶数从 1 个涨到 3 个，
    但"按天的鉴别力"仍然只有 3 个桶 —— 第 4 条的限制只是**缓解**，没有解除。
19. **双设备演练的 `rename` / `physical` 路径只有 1 ~ 2 次**，只够给区间，给不出分位数；
    `instance` 路径 n=3 同样只够 min/P50/max。**三种路径都只在同一台机器上测过**，
    跨机传输（"备份传到目标"那 0.60 ~ 0.72 s 是**本机 `docker cp`**）没有真实网络参与。
20. **时区演练只覆盖"整机时区错"这一种形态**。混合时刻（同子表里既有正确行也有错误行）、
    小于 15 s 阈值的偏移、以及"接入层与网关时区**不一致**"这三种形态**都没有测**（§4.3 的边界 1~3）。
21. **时区演练期间观测到 EMQX 反复重启**（00:31:56 / 00:38:25 / 00:42:00 / 00:50:40 各一次
    `received_terminate_signal`），其中 00:31:56 发生在本次演练开始（00:33:10）**之前**；
    重启后出现 `ds_*` durable session 分片 `shard_replica_not_ready` / `replica_offline` 报错，
    并伴随"TCP 1883 在监听但无法建立会话"的窗口。**这 4 次终止不是本次验收发出的**
    （只发过 `docker start emqx` 用于恢复，见 §2.6 的环境复核），触发方不在本次验收的控制范围内，
    **根因未定位**（见 [并发与负载指标](../reference/并发与负载指标.md) §10.6）。
    这条**不影响 §4 的时区结论**（演练数据在 00:36:45–00:38:21 成功入库并被判不健康），
    但它意味着**"演练期间链路可用性"这次不是干净基线**。
