### 2.2 三步时序：③ 为什么"必然"看到在途线程

一个迭代内的真实顺序（同一线程）：

```
L523  has_backlog() 为真 ──► trigger_if_due() 启动补传线程 W
                              W: 抢 CACHE_LOCK → 读 .sending → os.replace(cache.jsonl,.sending)
                                 → 再读 .sending → _write_lines(.sending) → 发布 + 等 PUBACK
L531  read_device()          ← 主线程只花 0.08 ms
L544  读 RESEND_WORKER.running ← 主线程到这里的时刻是"触发后 ~0.08 ms"
                              而 W 至少还要活 10 ms 才可能退出循环
L553  于是走"补传中"入队
```

关键量不是"谁先谁后"的直觉，而是**两个耗时差多少**。用容器内只读探针实测（探针源码见附录 A，全程不改网关文件、不写 `cache.jsonl`、用完删除）：

| 事件 | n | min | **p50** | max |
|---|---|---|---|---|
| 主循环预算：`read_device()`（触发后到判定点要花的全部时间） | 30 | 0.08 ms | **0.08 ms** | 0.35 ms |
| 补传线程下界：`Thread.start()` → `_take_over_pending()` 返回 | 25 | 6.33 ms | **10.45 ms** | 14.74 ms |
| 其中 `Thread.start()` 自身返回耗时 | 25 | 0.12 ms | 0.13 ms | 0.18 ms |
| 单条 QoS 1 `publish → PUBACK`（同 broker、独立 client_id/主题） | 25 | 0.11 ms | **0.17 ms** | 0.45 ms |

**裕度 = 10.45 ms ÷ 0.08 ms ≈ 130 倍**（且 10.45 ms 里不含已完成的发布等待，只是下界）。
所以 ③ 处 `running` 为真不是"通常如此"，而是**在 6.33 ms 的最坏情况下也成立**：判定点必然落在 W 的存活窗口内。

> 为什么 W 的 prologue 要 ~10 ms：`data/` 是**宿主机 bind mount**（`docker-compose.yml`: `./data:/app/data`），
> `_take_over_pending()` 在那上面做了 4 次文件系统操作（2 读 + 1 写 + 1 次 `os.replace`），
> 而 `read_device()` 只是容器网络内一次 Modbus TCP 往返。这就是 130 倍差距的来源。

### 2.3 正反馈：入队本身让下一轮必然再触发

把 §2.2 的结果代进循环：

1. 第 N 轮（距上次触发 ≥30 s）：`has_backlog()` 真 → 触发 W → ③ 入队 1 条 → 队列回到 1 行；
2. 第 N+1 ~ N+5 轮：队列非空但 `trigger_if_due` 被 30 s 节流挡住 → 不触发；这 5 条走直发（**注意：它们越过了队列里那条更旧的样本**）；
3. 第 N+6 轮：`time.monotonic() - _last_trigger ≥ 30` → 再触发 → ③ 又入队 1 条 → 回到第 1 步。

触发周期 = `ceil(30 / 5.146) = 6` 个轮询 = **30.9 s**，与实测 `间隔 p50 31 s`、`滞后 p50 31 s` 完全对上；
每个周期恰好入队 1 条 → **慢路径占比 = 1/6 = 16.7 %**，与实测 16.6 % / 16.8 % 一致。

**队列非空 → 触发继续；触发继续 → 队列继续非空。这是一个正反馈闭环**，只要初始队列里有一行，就不会自己停下来。

### 2.4 进入 / 维持 / 退出：它其实是**双稳态**

上一条只解释了"怎么维持"，没解释"怎么会开始"。日志给出了确定答案：

```
运行段 1 前 5 条事件（时间戳同一秒）:
  2026-10-01 13:26:17 BOOT
  2026-10-01 13:26:17 CONNECT
  2026-10-01 13:26:17 [补传] 开始补传 1 条        ← 进程刚起来就补传了 1 条
  2026-10-01 13:26:17 [缓存] 补传中，数据已入本地队列
  2026-10-01 13:26:17 [补传完成] broker 已确认 1 条
```

运行段 0（03:23:36）的前 5 条事件**形态完全相同**。

- **进入（seed）**：`data/cache.jsonl` 落在**宿主机 bind mount**上，`docker stop`/整栈停机**不会清空它**。
  上一轮运行退出时队列里那 1 行留在盘上 → 下次启动时：`_last_trigger` 初值 0.0 → `trigger_if_due` 第一轮就放行（L420）→ 触发 W 去补那 1 条残留 → 判定点出现 → ③ 入队 → **闭环在启动后 1 秒内建立**。
  同一条路径还有两个触发源：`on_connect` 的无条件触发（L464）、以及任何一次短暂断网/PUBACK 超时留下的 1 行缓存。
- **维持**：§2.3 的正反馈。
- **退出（collapse）**：只有"队列被取空且此后不再有触发"才退出。14:59:23 的演练正是如此——
  `on_connect` 触发的 54 条批次在 ~30 ms 内发完，主循环的下一个判定点在 2 s 之后，没落在 W 的存活窗口内 → 没有入队 → 队列归零 → **此后 `has_backlog()` 恒假，触发链断裂，状态永久退出**（实测 20 min 无补传，§1.3）。

**因此该缺陷的准确画像是"双稳态"**：
- 稳态 D（排空）：队列 0 行 → 不触发 → 永远 0 行；
- 稳态 B（慢路径）：队列 1 行 → 每 30 s 触发+入队 → 永远 1 行。
从 D 进入 B 需要一个种子（最常见的就是**启动残留**，一旦有种子，进入 B 的概率≈1，见 §2.2 的 130 倍裕度）；从 B 回到 D 只能靠"某次补传恰好没被判定点撞上"这种巧合。

### 2.5 与任务描述不一致的两点（以本次核实为准）

1. 描述说"**队列永远有一行**"、"5 个迭代不触发、第 6 个再取空又填回"。方向对，但**它不是无条件稳态**：
   没有种子时系统可以长时间停在 0 %（实测 20 min）。这条修正有实际影响：
   **验证方案必须先播种**，否则修复前后都测不到 16.8 %（§5.2）；同时修复的收益应表述为
   "**让 B 态无法自我维持**"，而不是"少一次入队"。
2. 描述说 ③ 处"补传线程**仍在等 PUBACK** → 本轮数据**必然入队**"。
   "必然"在观测上成立，但机理不是"等 PUBACK"：实测 publish→PUBACK 只要 0.17 ms，
   真正的时间开销是 `_take_over_pending()` 在 bind mount 上的 ~10 ms prologue。
   把它说成"等 PUBACK"会误导修复方向——例如去调 `PUBLISH_ACK_TIMEOUT` 是没用的。

## 3. 候选改法

### 3.1 候选 A（推荐）：判定依据取"本迭代触发**之前**"的在途状态

**怎么改**（示意 diff，不改实现）：

```python
# L520 附近，触发之前先取快照
            # 本迭代"触发之前"是否已有在途补传批次：这才是本轮该不该入队的依据。
            # 必须在这里取——下面的 trigger_if_due 只是启动一个补传线程，
            # 它不该反过来把本轮数据挤进队列（那正是慢路径自我维持的闭环）。
            resend_in_flight = RESEND_WORKER.running
            if mqtt_client.is_connected() and has_backlog():
                RESEND_WORKER.trigger_if_due(mqtt_client, RESEND_RETRY_INTERVAL)

# L544
            if mqtt_client.is_connected() and not resend_in_flight:
                if not publish(mqtt_client, payload, tag=f"第{count}条 在线直发"):
                    save_to_cache(payload, reason="未收到 PUBACK")
            elif not mqtt_client.is_connected():
                save_to_cache(payload, reason="断网")
            else:
                # 确有比本轮更旧的批次正在补传：新数据排队，不越过它
                save_to_cache(payload, reason="补传中")
```

**语义（也就是任务问的"取批/直发的边界怎么定"）**：
> 边界 = **本轮样本是否会越过"比它更旧、且尚未交付"的数据**。
> 可判定的充分条件：**本迭代开始之前已经有在途批次**——那批数据一定比本轮旧，且正在按序发送。
> 由**本轮自己**刚启动的批次不算：它是本轮触发的，不该反过来决定本轮走慢路径。

**为什么能消除"必然入队"**：闭环的两个环节（触发 → 同一迭代内入队）被拆开。
触发仍然发生在迭代开头（保留 L520-522 注释里那个既有修复：设备故障的 `continue` 不会跳过补传），
但本轮样本的取舍只看"我进来之前有没有积压批次"。
进入 B 态后的第 6 轮：`resend_in_flight == False` → 直发 → 队列被 W 取走后**保持 0 行** → 下一轮 `has_backlog()` 为假 → 触发链断裂 → **回到 D 态并停住**。整个退出过程不依赖"哪一方先跑完"（无竞态）。

**失败模式**：
- **丢数据：不会。** A 一行都没动缓存的写入路径：入队仍是 `save_to_cache()`（追加 + `flush` + `fsync`，L181-200），直发失败仍落盘（L546-547），断网仍落盘（L548-550）。改动只决定"某条样本走哪条路"，两条路都自带落盘兜底；一条样本也只会走一条路，不存在丢或重。
- **原本能补上的补不上：不会。** 补传的触发条件、取批、在途窗口、失败回写全部不变；A 不会让任何缓存行失去被补的机会。
- **和原子改名交接冲突：不会。** `_take_over_pending()` / `_finish_resend()` / `CACHE_LOCK` / 单写者所有权一行不改；A 只是把 L544 读的一个布尔量提前到 L523 之前读。
- **顺序语义**：A 允许"本轮样本越过**队列里那些正被 30 s 节流挡着的旧行**"。这**不是新增行为**——现状就是这样：那 5 条直发的样本本来就越过队列里那一行。实测证据：按到达顺序检查 `latency_steady_raw.csv`，**58 条逆序（16.6 %），且 58/58 全部是补传行**（47 条 `resend` + 11 条 `resend+clock-jump`），`direct` 行 **0 条逆序**；逆序深度 25~26 s（≈ 5 × 5.146 s）。也就是说"保证旧数据按序先送达"（L552 注释）**本来只是"每周期一条样本级"的保证，全局顺序早已不成立**。
- **代价**：+1 个局部变量、+3 行注释；无新状态、无新 I/O、无新锁、无新依赖（`running` 本身是无锁读的近似量，性质与现状相同）。可观测性不变（日志四类原因照旧，`补传中` 会显著减少，正好是修复效果的观测点）。

### 3.2 候选 B：直发与补传彻底解耦（在线即直发）

**怎么改**：删掉"补传中"分支——`is_connected()` 为真就一律直发（失败落盘），补传只在后台按自己的节奏排空积压。
即 L544-553 简化为：连接 → 直发（失败入队）；未连接 → 入队。`reason="补传中"` 从此不再出现。

**为什么能消除必然入队**：因果链被切断得更彻底，慢路径永不为 0 以外的稳态（队列只由真实失败填充）。

**失败模式**：
- 丢数据：不会（同 A 的理由）。
- 顺序：**新数据系统性优先于全部积压**。这其实与 **HJ 212-2025 §8.1.2"合理分配带宽、优先新数据"** 一致，
  但与 L552 注释声明的设计意图相反；而现状的"旧数据优先"在全局上早已不成立（§4.4 的 58 条逆序实测）。
- 代价/风险：① 长时间断网恢复期，实时流与积压回放同时占用带宽，没有限流——标准要的"合理分配带宽"反而没人管；
  ② 语义变更与 `task-6`（优先新数据 + RF 补传标志）是同一个决策，**不该在这个缺陷修复里顺手改**。

### 3.3 被否决的改法（含任务描述与性能文档 §7.4 点名的几种）

| 改法 | 判定 | 理由 |
|---|---|---|
| 判定改成"队列为空/无在途批量"（如 `not has_backlog()`） | ❌ **更差** | 队列里那一行要等 30 s 节流才被取走，**这 25~30 s 内每个样本都会看到"队列非空"** → 5 条/周期全部入队 → 慢路径占比反而升到 **~100 %**。"队列非空"和"有批次在补传"必须严格区分 |
| 把 `RESEND_RETRY_INTERVAL` 调小到与 `POLL_INTERVAL` 同量级 | ❌ **更差** | 触发频率≈轮询频率 → 每个样本的判定点都落在"刚启动的批次"窗口内（§2.2 的 130 倍裕度） → 慢路径占比 **~100 %**，只是把滞后从 31 s 缩到 ~5 s。比例指标（本任务的验收线）反而恶化 |
| 把补传触发挪到"读完设备、发完本轮数据"之后 | ❌ 有副作用 | 触发仍在迭代开头是为了让两处 `continue`（设备未连上 / 读失败）不跳过补传——见 L520-522 的注释（那是一次既有缺陷的修复）。挪到末尾会**把那个已修的缺陷放回来**；除非同时在两条 `continue` 前补一次触发（改动更大、可读性更差） |
| 在判定点等待在途批次结束再决定（"③ 处再等一次 running"） | ⚠️ 可行但不推荐 | 逻辑上也能打断闭环（1 条批次只等 ~10 ms），但把**阻塞引入了采集主循环**：遇到慢批次/失败重试时，样本要等整个批次（最坏 `RESEND_WINDOW × PUBLISH_ACK_TIMEOUT = 100 × 5 s`），会拖垮 5 s 采样节拍，还会逼近 healthcheck 的 30 s 心跳窗口。为同样的收益引入阻塞不值得 |
| 只在 `on_connect` 触发处加 `has_backlog()` 判断（L464） | ❌ 治不了 | 它只是减少了"空队列也触发"的一种播种路径，B 态一旦建立仍由 L523 的触发维持 |
| 清空 `data/cache.jsonl` / 重启网关"恢复" | ❌ 不是修复 | 重启后只要队列里还有残留就重新播种（§2.4 两段日志都是这个形态）；且清空缓存等于丢数据 |

## 4. 失败模式分析（逐条回答任务问的四项）

### 4.1 会不会丢数据？（最高优先级）

不会。把"不丢"的三道防线与 A 的关系逐条列出：

| 防线 | 代码 | A 是否触碰 |
|---|---|---|
| 入队即落盘 + `fsync` | `save_to_cache()` L181-200 | 不改 |
| 直发必须等 PUBACK，且用 `is_published()` 复核超时（paho 超时是静默返回） | `_wait_published()` L265-287 | 不改 |
| 直发失败 → 落盘 | L546-547 | 不改（A 保留该分支） |
| 取批靠 `cache.jsonl → .sending` 原子改名，两个写者各写各的文件 | L296-318 | 不改 |
| 补传收尾"回写成功才删 `.sending`" | L321-344 | 不改 |
| 逐窗滚动回写 `.sending`（补传途中被杀只影响在飞的那一窗） | L381-383 | 不改 |
| 进程退出先 `RESEND_WORKER.stop()` 再断开 | L561 / L435-446 | 不改（触发位置不变，退出路径不变） |

A 改变的唯一东西是"某条样本在 L544 走哪条分支"，而两条分支都以下发 PUBACK 确认或落盘收尾。**没有新增"某条样本既没发出也没落盘"的路径。**

### 4.2 会不会让原本能补上的补不上？

不会。补传侧完整不变：触发条件（L523）、节流（L418-422）、取批（L296-318）、
在途窗口（L373-387）、失败回写与重试（L321-344 / L389）全部保留。
A 只会让"本来会被塞进队列、等 30 s"的样本改走直发；直发成功就等于更早送达，直发失败就等价于现状（落盘等补传）。
慢批次场景（broker 退化、逐条等 5 s 超时）下 `resend_in_flight` 连续多个迭代为真 → 仍然像现状一样入队，保守性不丢。

### 4.3 会不会破坏"原子改名交接"？

不会，理由见 §3.1 的失败模式条目（不碰文件、不碰锁、不碰单写者模型）。
A 甚至没有新增对 `cache.jsonl` 的读操作。

### 4.4 顺序语义的实际影响

- 现状：**全局 FIFO 早已不成立**（实测 58 条逆序全部是补传行，`direct` 行 0 条逆序，逆序深度 25~26 s）。
  所谓"旧数据按序先送达"只在"触发那一轮"对**一条**样本成立；后续 5 条直发样本照样越过它。因此 A 造成的顺序松弛与现状同量级甚至更小（A 只影响"与在途批次同窗"的那些样本）。
- A 之后预计的顺序形态：真实断网恢复时，积压批次仍在**先**发（触发发生在本轮决策之前，且批次是成批 `publish` 到同一 socket，paho 单连接按调用序排队），新样本只可能越过"被 30 s 节流挡着、尚未取批"的旧行——这正是现状已有的行为。
- 若下游对顺序有硬要求（例如告警按 ts 判重），应单独提需求；本项目的入库按 `ts` 落库，TDengine 侧不依赖到达顺序（性能文档 §6.5 提到时钟回跳造成的重复 `ts` 才是真正的风险点，与 A 无关）。

### 4.5 与 `task-6` 的关系（需要评审方拍板）

- 候选 A **不改语义**：仍然是"旧数据优先、补传期新数据排队"，只是把"补传期"的判定从"worker 此刻在跑"改成"进本轮之前已有批次在跑"。
- 候选 B / RF 标志 / "优先新数据" 属于 `task-6`（标准对齐）的决策范围。若 `task-6` 最终选择"优先新数据"，那么它落地时应当**顺带用 A 的实现**（A 是 B 的子集：B 只要把 `resend_in_flight` 恒置 False 即可），反之不成立。
  建议：**本任务按 A 实现，`task-6` 立项时复用 A 的改动点**，避免两次改同几行。

## 6. 推荐与不确定项

### 6.1 推荐候选 A，理由

1. **直接打在成因上**：缺陷是"触发与判定在同一迭代内耦合"，A 就是把这个耦合拆掉，闭环失去维持条件；
2. **改动最小**：1 个局部快照 + 1 处判定条件，不新增状态/锁/I-O/依赖，不碰原子改名交接与落盘路径；
3. **退出不依赖竞态**：不像"挪触发位置"或"等待批次结束"那样把结果押在时序上；
4. **保守性只在真需要时保留**：慢批次下仍然入队（与现状一致），只有"本轮自己刚触发的那一批"不再惩罚本轮样本；
5. **风险面清晰**：唯一语义变化是顺序松弛的一小部分，而现状的全局顺序早已不成立（实测 47/47 逆序）；
6. **可观测**：修复效果直接体现在"`补传中` 日志行消失 + `cache.jsonl` 保持 0 字节"，便于事后验证，不依赖延迟测量的精度。

### 6.2 我没验到 / 不确定的部分（诚实清单）

1. **播种配方 R1 我没有实际执行**（会中断 emqx 与网关；本任务只出方案）。
   它的确定性依据是**日志间接证明**：13:26:17 与 03:23:36 两次运行的启动形态与 R1 完全一致（启动后 1 秒内 `开始补传 1 条` + `补传中入队`）。
   实现阶段必须先把 R1 跑通并复现出 B 态，再改代码（§5.3 的门禁）。
2. **探针测的是"同类文件操作 + 同 broker 的 publish/PUBACK"**，不是直接在网关进程里给 `running` 打点
   （那需要改代码，本任务不允许）。不过裕度是 130 倍，量级结论不受影响。
3. **修复后的顺序松弛只做了定性论证**（拿现状"58 条逆序全部是补传行、direct 行 0 条"做参照），没有量化"修复后逆序条数会变成多少"。
   实现阶段应用同一份 `measure_latency.py` 原始 CSV 复算逆序统计，作为附加验收项。
4. **未测多设备/高并发**：全部结论基于单设备 5 s 一条（~700 条/h）。`POLL_INTERVAL` 缩小或多设备下，
   "判定点落在在途窗口内"的概率会变化，本方案未覆盖，不得外推。
5. **R2（`docker pause emqx`）与 paho keepalive 的交互未实测**，只给出"≤60 s"的保守窗口。
6. **`_take_over_pending()` 把整批读进内存**（L304-314 全量 `_read_lines`）、以及 64 MB 缓存裁剪（L203-221）
   在超大积压下都没有验证过——这是既有问题，不在本次范围，但会影响"长时间断网后 A 是否仍保守"的判据。
7. **本次只改网关**：接入层/订阅端不在范围内；`MQTT_TOPIC`/`QoS`/`client_id`（`cems-gateway-plant1` / `cems-subscriber-plant1`）
   在 A 中一行未动。
