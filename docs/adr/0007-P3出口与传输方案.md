## 1. 背景与范围

### 1.1 P3 要动什么

ADR-0006 §6 把 P3 定义为"HJ212 出口 + TCP 传输 + 独立缓存与补传"，并标注它是**唯一碰主链路的阶段**（风险 🟡 中），要求"必须先出方案 + 硬门禁"。

设计上要回答的问题只有五个：**数据从哪来、报文怎么组、缓存怎么隔离、连接怎么管、失败怎么兜**。本 ADR 按这五条组织，外加前置的回归测试规格与门禁清单。

### 1.2 两条硬约束的落地口径（⚠️ 含对 ADR-0006 措辞的一处校正）

**硬约束 1（ADR-0006 §6）：出口必须独立线程 + 独立队列。**
依据是 ADR-0003 的实测：主循环里 `read_device()` p50 仅 **0.08 ms**，而补传取批 prologue p50 要 **10.45 ms**（130 倍）。

⚠️ **校正一处**：那 0.08 ms 是**竞态裕度的量**（判定点是否落在在途窗口内），**不是采集主循环的延迟预算**。主循环本来就含 `publish()`（等 PUBACK，`PUBLISH_ACK_TIMEOUT` 上限 5 s）与 `time.sleep(5.0)`——相对 5 s 轮询周期，几毫秒的本地文件操作是**一阶小量（≤0.1%）**。
→ 所以硬约束 1 的**准确口径**是：**任何依赖对端（网络）的等待都不得出现在采集线程里**；而"采集线程内一次本地落盘"是**容许**的，其开销由门禁 G-M1 用数字定案（判据见 §3.4）。把 0.08 ms 当预算去砍会得出"连 `save_to_cache()` 都得挪走"的过激结论，而地基现状已经在采集线程里做 `flush + fsync`。

**硬约束 2（ADR-0006 §6）：HJ212 出口必须有自己的缓存与补传，不能与 MQTT 分支共用缓存文件。**
落地为：**独立目录 + 独立文件名 + 独立锁 + 独立在途窗口**（§3.3）。理由有两条，第二条是本次探针实测出来的：

1. 两路共用文件 → 一方的取批/回写会动到另一方的数据，且"平台断"会连带影响 MQTT 分支的补传语义。
2. 地基本身的在途批次写法（`os.replace(cache → .sending)` **覆盖**已有的 `.sending`）存在一个**内存独占窗口**（§2.9 D1 实测）；HJ212 分支若照抄，等于把这个窗口复制一份到新分支上，而环保平台最看重的恰恰是"补传不丢"。

### 1.3 本 ADR 明确不做

| # | 不做 | 理由 |
|---|---|---|
| 1 | 不改 `src/`、`docker-compose.yml`、`scripts/` 任何现有文件 | 本阶段只出方案（任务硬约束） |
| 2 | 不改 MQTT 主题/QoS/**固定 client_id**、不动报文体、不动 `cache.jsonl`/`.sending`/`CACHE_LOCK`/`RESEND_WORKER` | 地基冻结 + 任务硬约束 |
| 3 | 不实现"上位机 → 现场机"的下行请求命令（`CN=1000/1011/…`、设置超时/间隔/MN） | P3 只做上行 + 应答解析；下行命令是独立需求 |
| 4 | 不做多平台并发（厂商"一点多发 8 路"） | ADR-0006 §6 原则："只有一个实现时抽象出来的接口一定是错"；先单目标 |

| 6 | 不引入新依赖 | 用标准库 `socket`/`threading`/`queue` + 已有 `gmssl` |

## 2. ① 原子交接回归测试规格（`scripts/verify_atomic_handover.py`）

> 这是 **P3 的前置条件**：P3 要动网关，改之前必须先有这道防线。

### 2.1 被测机制与证据强度现状

被测的是 `src/gateway/gateway.py` 的单写者所有权 + 原子改名交接（当前 md5 `fbd2a9c10528bcf2cf79acf1c78d1adf`，见 `docs/evidence/cache/atomic_handover_probe.json` → `meta.gateway_md5`）：

| 环节 | 代码 | 机制 |
|---|---|---|
| 入队 | `save_to_cache()` L181 | 采集主循环**追加** `cache.jsonl` + `flush` + `fsync` |
| 取批 | `_take_over_pending()` L296 | `os.replace(cache.jsonl → cache.jsonl.sending)` **原子交接**；`leftover + current` |
| 在途 | `resend_cache()` L359 | `RESEND_WINDOW` 一窗先全部 `publish`，再逐条等确认；每窗后**滚动回写** `.sending` |
| 收尾 | `_finish_resend()` L321 | 未确认行放回 `cache.jsonl` **队首**，**写成功才删 `.sending`** |
| 锁 | `CACHE_LOCK` L59 | 保护换手动作 |

**现状证据强度**：只有**间接证据**——故障 2（停 EMQX 11 分钟、缓存 128 条、`[补传完成] broker 已确认 128 条`）与故障 3（改错端口、46/46）都是"整条链路实测补传 100%"，**没有任何一条断言是在直接验证交接本身**。而这两个间接证据**都发生在"没有并发新采集写 cache.jsonl"或"并发量极小"的条件下**，恰好绕开了最危险的时刻。

### 2.2 四条设计约束（缺一不可）

| # | 约束 | 落实方式 |
|---|---|---|
| C1 | **离线** | 不连真 broker；stub MQTT 客户端只实现 `publish` / `wait_for_publish` / `is_published` 三个成员（够 `_publish_async` / `_wait_published` 用） |
| C2 | **确定性** | 失败与注入全部由"第 k 次 publish"下标决定，不用 sleep、不用线程、不用随机；同一输入两次运行输出逐字相同 |
| C3 | **零风险** | 只写 `tempfile.TemporaryDirectory()`；**不碰生产 `data/`**（P7 断言） |
| C4 | **不写大量数据** | 语料 35 行（≈250 B/行）；P7 断言临时目录 **< 1 MB**；遵守故障 4 的教训"凡是会真写宿主机的实验，先写清最多写多少、写在哪、怎么回收" |

### 2.3 沙箱：为什么必须打补丁，而不能只靠环境变量

`gateway.py` 的 `DATA_DIR` 是**推导出来的常量**（`PROJECT_ROOT / "data"`，L55），**没有** `os.getenv` 出口；`CACHE_FILE` / `SENDING_FILE` 同源。因此只设环境变量**无法**把它指到临时目录。

做法（探针已验证 `path_patch_works = true`）：import 之后、调用之前，直接改模块全局属性：

```python
gw.DATA_DIR    = tmp_path
gw.CACHE_FILE  = tmp_path / "cache.jsonl"
gw.SENDING_FILE = tmp_path / "cache.jsonl.sending"
gw.RESEND_WINDOW = 3                    # 造多窗口
gw.PUBLISH_ACK_TIMEOUT = 0.05           # 不真等 5 s
gw.CACHE_MAX_BYTES = 64 * 1024 * 1024   # 保证裁剪路径不触发（裁剪不在本测试范围）
```

⚠️ 三个必须写清的细节：

1. `Final[...]` 只是**类型标注**，运行期不设防；上述函数在调用时才读模块全局，所以补丁生效（探针实测 `A_patch` 三项全 true）。
2. 补丁必须放在**上下文管理器**里：`__enter__` 记录原值并替换，`__exit__` 无论如何都恢复（`try/finally`），避免"测试跑完把模块搞脏"。
3. **安全守卫**：`__enter__` 里做硬检查——`gw.CACHE_FILE.parent == tmp` 且 `gw.SENDING_FILE.parent == tmp` 且 `gw.DATA_DIR == tmp`；**任一不成立就立刻 `SystemExit(3)`，什么都不做**（宁可不测，也不许有污染生产的可能）。

### 2.4 语料与"期间新增"的构造

- **输入语料**：`docs/evidence/drill/resend_snapshot_drill2.txt`，**逐字**读取（35 行真实报文，行首 `YYYY-MM-DD HH:MM:SS` 定长，可按字符串排序）。
- 拆分：`CURRENT = lines[0:33]` 入 `cache.jsonl`；`LEFTOVER = lines[33:35]` 入 `.sending`——这样一次就覆盖了 `leftover + current` 的合并路径（探针实测 `order_is_leftover_plus_current = true`）。
- **"补传期间主循环新采的数据"**：不另造随机报文，而是**复用同一条批内报文的 K=V 段、把时间戳改成明确的后续时刻**（`2026-10-01 15:00:00 …`）。理由：① 报文结构逐字保留真实形态；② 时间戳可排序，排序模式下期望值可计算；③ 与批内 35 行**互不相同**，便于区分"新采"与"未确认"。
- **注入点**：stub `publish()` 内部的 **hook**，在第 `HOOK_PUBLISH_INDEX = 4` 次 publish（= 第 2 窗第 2 条）时调 `gw.save_to_cache(new_line)`——等价于"补传线程正在发第 2 窗时，采集主循环往 `cache.jsonl` 追加了一条"。这是全测试**最关键**的用例。

### 2.5 场景与断言清单

| ID | 场景 | 判据（**必须全部成立**） | 依据 |
|---|---|---|---|
| **P1** | 取批（`.sending` 有 leftover + `cache.jsonl` 有 33 行） | ① `multiset(batch) == multiset(leftover ∪ current)`（**规范化键**：`line.strip()` 后按空白折叠）；② `len(batch) == 35`；③ 批内**无重复**；④ 取批后 `cache.jsonl` **不存在**（`os.replace` 已搬走）；⑤ `.sending` 行数 == 35；⑥ 排序关时**另加**逐元素断言 `batch == leftover + current` | 取批只允许"排列"，不许改内容/丢/重 |
| **P2** | 交接后两写者各写各的 | ① 紧接着 `save_to_cache(x1)`, `save_to_cache(x2)`；② `cache.jsonl` **逐元素** == `[x1, x2]`；③ `.sending` **逐字节**（`read_bytes()`）与写之前相同 | 单写者所有权模型的**核心承诺** |
| **P3** | 补传中主循环同时写（hook） | ① `multiset(cache.jsonl) == multiset(未确认 ∪ 期间新增)`；② `cache.jsonl` 的**前缀**（前 `len(未确认)` 行）逐元素 == 期望未确认序列；③ **后缀**逐元素 == 期间新增行**原序** | "收尾 == 未确认 + 期间新增"，且次序语义可判定 |
| **P4** | 条数守恒 | `len(原始 35) + len(期间新增) == confirmed + len(cache.jsonl)`；且 `confirmed == 35 - len(未确认)` | 一条不多、一条不少 |

### 2.6 关键断言的判据（写清"怎么比"）

**规范化键（canonical key）**——用于所有多重集比较：

```python
def canonical(line: str) -> str:
    """行内容的规范化键：去首尾空白 + 空白折叠。""" 
    return " ".join(line.split())
```

- 只做**空白规范化**，不解析字段、不改大小写、不动时间戳格式 → 任何"内容被改写"都会暴露。
- 多重集比较 = `sorted(map(canonical, xs)) == sorted(map(canonical, ys))`；**同时**断言 `canonical` 序列里无重复（否则"重复 + 丢失"会互相抵消）。

**逐元素比较**——用于 `cache.jsonl` 收尾内容：

- 前缀（未确认部分）用**多重集 + 无重复**（顺序允许是任意排列，见 §2.7）；
- 后缀（期间新增部分）用**逐元素原序**（不变量来自代码事实：`_finish_resend` 写的是 `remaining + _read_lines(CACHE_FILE)`，而 `_read_lines` 保序、`save_to_cache` 是追加）。

**逐字不变**——用于 P2/P5 的 `.sending`：

- 判据是 `read_bytes()` 相等，**不是** `read_text()` 相等（前者连行尾/编码差异一起管）。

**P5 怎么把回写弄失败（真实 OSError，不是打桩）**：

- 在临时目录里把 `cache.jsonl.tmp` **建成目录** → `_write_lines()` 内 `tmp.write_text(...)` 抛 `PermissionError`（`OSError` 子类），走真实异常分支。探针实测的两行关键日志（见 `atomic_handover_probe.json` → `key_log_messages`）：
  ```
  ERROR    [缓存] 写入 cache.jsonl 失败: [Errno 13] Permission denied: '…\cache.jsonl.tmp'
  CRITICAL [补传] 回写 cache.jsonl 失败，保留 cache.jsonl.sending（本批 5 条未确认）等待下次重试
  ```
- **优点**：不 patch `_write_lines`，测的是**真实失败路径**；且解除阻塞（`rmtree` 那个目录）后能验证"保留 `.sending` 确实保住了数据"（探针实测 `B_recovery_after_unblock.confirmed == 5 == batch_len`）。

### 2.7 ⭐ 同一场景跑两遍：排序关 / 排序开

**为什么**：将来若有人给取批加"按时间戳排序"（这是很自然的改动——"补传要按时间序发"），当前的隐式假设（`batch == leftover + current`）会立刻失效。**测试必须在那时仍然证明"交接没坏"**，而不是变成一条假的失败。

**怎么做**：

```python
def permute(batch: list[str], sort_mode: str) -> list[str]:
    """测试自己的排列函数；排序关 = 原序，排序开 = 按行首时间戳稳定排序。"""
    if sort_mode == "off":
        return list(batch)
    return sorted(batch, key=lambda line: line[:19])      # YYYY-MM-DD HH:MM:SS 定长
```

- 沙箱在 `sort_mode == "on"` 时，用一个**只改返回值的包装**替换 `gw._take_over_pending`：内部仍调用原函数（真实文件操作一行不改），只把返回值改成 `permute(...)`。
- **期望值也由同一个 `permute` 算出**（`expected_batch = permute(leftover + current, mode)`）——这样测试断言的是"**交接对排列不敏感**"，而不是"必须保持某个具体顺序"。
- 两遍都必须通过：**P1/P2/P4/P5/P6/P7** 与顺序无关（多重集/字节/条数/逐窗状态），**P3 的后缀断言**也与顺序无关（新增行永远是尾部原序）。排序开时，P3 的**前缀**允许多重集相等（因为 `remaining` 的顺序随排序而变，这是**定义**而不是缺陷）；排序关时，前缀**另加**逐元素断言。
- ⚠️ 注意：排序开/关两遍的**未确认集合本身会不同**（失败是按"批内下标"计划的，排序改变了"哪一条落在第 4 位"）。所以每个模式都按自己的 `expected_batch` 计算期望值——**但 `confirmed` 条数与守恒等式两遍必须相同**，这也是一个可断言的交叉判据。

### 2.8 负向对照（证明测试有鉴别力）

| 对照 | 人为注入的"坏实现" | 应当被哪条断言抓住 |
|---|---|---|
| N1a | `_finish_resend`：回写失败**仍** `unlink` `.sending` | **P5**（`.sending` 不存在 → FAIL） |
| N1b | `_take_over_pending`：用"读完再写一份"代替 `os.replace`（`cache.jsonl` 仍在） | **P1**（第二次取批会产生重复）/ P1④（取批后 `cache.jsonl` 仍存在） |
| N1c | `resend_cache`：不做逐窗滚动回写 | **P6**（观测点与期望不符） |
| N1d | `save_to_cache`：写 .sending 而不是 cache.jsonl | **P2**（`.sending` 字节变了） |

执行方式：在沙箱内用 `monkeypatch`-式替换（只存在于测试进程内），跑对应的检测器，**要求结果必须是 FAIL**；若某个对照竟然 PASS，则脚本以退出码 **2** 报告"检测器无鉴别力"（这是**测试自身的缺陷**，不是被测代码的问题）。四个对照至少实现 N1a 与 N1b。

### 2.9 D1：探针发现的既有窗口（如实登记，不计门禁）

`_take_over_pending()` 的顺序是：先 `leftover = _read_lines(SENDING_FILE)`（进内存）→ 再 `os.replace(CACHE_FILE, SENDING_FILE)`（**覆盖** `.sending`）→ 再 `_write_lines(SENDING_FILE, leftover + current)`。

**在"覆盖完成"与"合并批写完"之间，leftover 只存在于内存里**。此时进程被硬杀（`SIGKILL` / 断电 / 容器被 `kill -9`），`.sending` 上留下的是 `current`，**leftover 永久消失**。探针实测（`C_kill_between_replace_and_writeback`）：2 条 leftover **全丢**，盘上只剩 33 条 `current`。

三点必须说清：

1. **这是既有行为，不是 P3 引入的**，也不在 ADR-0006 的承诺范围内（ADR-0006 只承诺"整文件接管 → 每一行都进本批并排空"）。
2. **窗口宽度未实测**（需真实 kill 计时）；触发还需要"上一轮补传留下了 leftover"这个前提（进程在补传中被杀、或收尾回写失败）。
3. **测试里怎么处理**：D1 作为 `[KNOWN]` 行输出结论与证据，**不计入 PASS/FAIL**（否则套件永远红，反而会被人调松）。但它是**P3 设计决策的输入**——见 §3.3，HJ212 分支换成"唯一段名、永不覆盖"的写法，从结构上消除这个窗口。

### 2.10 磁盘与生产文件保护（P7 的可判定性）

- **硬断言（必过）**：沙箱守卫三项（§2.3）+ 临时目录总字节 < 1 MB + 脚本自身写入集合 ⊆ 临时目录（`__exit__` 时遍历临时目录，断言文件数 ≤ 8 个、总字节 < 1 MB）。
- **哨兵断言（必过，但需要正确解读）**：生产 `data/cache.jsonl` / `.sending` 的 `(exists, size, mtime_ns)` 前后一致。
  ⚠️ **八服务在跑时这条有歧义**：变化既可能是"本脚本越界写了"（严重缺陷），也可能是**并发运行的网关进程**恰好写了它。脚本遇到变化时不猜测，直接 **FAIL 并打印三种可能的解释 + 判定方法**（① 检查沙箱守卫是否失败；② 临时目录是否存在越界迹象；③ 停 `cems-gateway` 后复跑取干净信号）。

  ```powershell
  docker stop cems-gateway
  $env:PYTHONIOENCODING="utf-8"; python scripts\verify_atomic_handover.py
  docker start cems-gateway
  ```
- 本 ADR 的探针就是这么跑的：`D_production_sentinel.unchanged = true`（`data/cache.jsonl` 0 字节、`mtime_ns` 未变）。

### 2.13 局限（本章）

1. **不是并发测试**：hook 注入是**同线程的顺序交错**，它精确复现"取批在途时另一写者追加"的**状态序列**，但**不覆盖**真正的多线程抢占（本测试的设计目标就是确定性，见 C2）。真并发（补传线程 + 采集线程同时跑）只能由故障演练覆盖。
2. **不测裁剪路径**：`CACHE_MAX_BYTES` 被显式放大，64 MB 裁剪（L203）不在范围内（ADR-0003 §6.2 已登记它是既有未验证项）。
3. **不测 `_read_lines` 的读失败分支**（文件被删/权限）——P5 只覆盖**写**失败。
4. **D1 的窗口宽度未测**，只有"窗口存在且致命"这一个定性结论。
5. **P6 用观测点覆盖窗口边界**，靠"每窗第 1 次 publish 时读盘"取得"上一窗回写完成、本窗尚未回写"的稳定瞬间；若有人把回写挪到别的位置，观测点的**语义**会变（但断言仍会报 FAIL，不会静默通过）。
6. **排序模式是测试注入的人为排列**，不是当前代码的行为（当前无排序逻辑）——所以它证明的是"交接对排列不敏感"，**不是**"现在的代码会排序"。

## 3. ② P3 实施方案

### 3.1 数据从哪里取：主循环"一分二"

**决策：网关侧直采（ADR-0006 路线 A），在 `main()` 里采完即分流。**

```python
# ---- src/gateway/gateway.py · main() 内（示意，非实现）----
count += 1
ts = time.strftime(TS_FORMAT)
payload = build_payload(data, ts)      # ← 唯一签名变化：新增带默认值的 ts 参数，行为逐字不变
if HJ212_OUTLET is not None:           # ← 唯一新增语句；默认配置下为 None（出口关闭）
    HJ212_OUTLET.submit(payload=payload, values=data, ts=ts)
# ---- 以下 MQTT 分支原样不动 ----
if mqtt_client.is_connected() and not resend_in_flight:
    ...
```

**为什么放在 `publish()` 之前**：HJ212 不该因为 MQTT 在等 PUBACK（上限 5 s）而晚拿到数据。分流是纯本地动作（§3.4），不依赖 MQTT 状态。

**为什么 `ts` 要显式传**：两条出口必须共享**同一个采样时刻**。若在出口侧再调一次 `time.strftime()`，两次调用可能跨秒（跨秒即两条链路的同一采样点时间戳差 1 s，跨分支对账就失去唯一键）。因此 `build_payload(values, ts=None)`——`ts=None` 时行为与现状**逐字相同**，由门禁 G-B2 断言。

**被否决的做法**：

| 做法 | 否决理由 |
|---|---|
| 让 HJ212 出口订阅 MQTT 再上报 | 违反 §8.1.1 a) "数采仪应直接连接一次仪表"；且把 HJ212 的可用性绑在 MQTT 分支上（MQTT 一断，HJ212 也断）——ADR-0006 §2 已论证路线 A 与 B 不能合并 |
| 从 TDengine 查库再上报 | 路线 B：时延、且**补传能力为 0**（源头没有就是没有） |
| 在 `build_payload()` 内部顺手发送 | 把 IO 混进一个纯函数（可测性被破坏），且 `build_payload` 是两条链路的公共契约 |
| 用全局回调注册表 | 一个实现的场景下是过度抽象（ADR-0006 §6 原则） |

### 3.2 报文体：数据区怎么组（全部有一手出处）

**官方原文（§6.3.4.1，PDF 第 9 页）**：
> 字段与其值使用半角"="连接；在数据区中，**同一项目不同类别的值之间用半角","分隔，不同项目之间用半角";"分隔**。

**官方向量（表 C.18"上传污染物实时数据"，PDF 第 58 页）**：
```
现场机 → QN=…;ST=32;CN=2011;PW=123456;MN=010000A8900016F000169DC0;Flag=9;CP=&&DataTime=20240601085857;
          w19102-Rtd=66;w01001-Rtd=7.1,w01001-Flag=N;w01010-Rtd=2.2;…&&
上位机 → QN=…;ST=91;CN=9014;PW=123456;MN=010000A8900016F000169DC0;Flag=8;CP=&&&&
```
两条证据一致：**项目之间 `;`、同一项目不同类别 `,`**。附录 A.2 的 CN=2051 示例同样如此（`DataTime=…;a01011-Min=…,a01011-Avg=…,a01011-Flag=N;a01012-…`）。

本项目 9 测点实时报文的数据区（示意）：

```
DataTime=20261002143641;a00000-Rtd=33471.0;a34013-Rtd=2.89;a21026-Rtd=19.9;a21002-Rtd=32.3;
a19001-Rtd=5.5;a01011-Rtd=13.2;a01012-Rtd=179.3;a01014-Rtd=45.5;a01013-Rtd=96.9
```

| 字段 | 取值来源与依据 |
|---|---|
| `DataTime` | 采集时刻 `YYYYMMDDhhmmss`。表 5（第 12 页）："在使用实时数据命令 2011、2021 等，时间标签为**数据采集的时刻**" |
| `xxxxxx-Rtd` | 本项目测点值。表 5（第 10 页）："在大气污染源监测时表示**标准状态下干基值**" → 与本链路数值口径一致（`points.py`：本项目数据本身即"标干值"），**直接上报，不做折算、不做单位换算** |
| `xxxxxx-Flag` | 数据标记，取 `N`（表 10，第 19 页："数据有效…默认自动标记"）。⚠️ 本项目目前**没有**仪表状态源，因此固定 `N`；`D/C/M/T/Td` 的自动判定属南向扩项，**不在 P3** |
| 参数编码 | `src/protocol/hj212/factors.py` 的 `FACTORS`（附录 B.2 权威表）——**不得**用 `points.py` 的 `code` 字段（`hj212-协议实现说明.md` §6.2 已登记两处一致性，且现取值已一致；出口侧仍以 `factors` 为真源） |
| 数值格式 | 提取 `build_payload()` 现有的值格式化表达式为一个共享小函数（如 `format_value(v)`），**两条链路共用**，保证同一采样值在两条出口里逐字相同 |

**⚠️ 三处必须在 P3 里显式处理、不许默认掉的地方**：

1. **`DataRegion.from_fields()` 只能拼单项目数据区**（它固定用 `,` 连接全部条目，见 `codec.py` L120-124），且当前**全仓库无消费者**（`grep from_fields` 只命中定义处）。多项目的 9 测点报文**不能**用它拼。
   → 决策：**P3 在出口层自己拼 `raw` 字符串**（`DataRegion(raw=…, fields=DataRegion.parse(raw).fields)`），**不改 P1**；同时把"`from_fields` 只能生成单项目数据区"登记为 P1 的已知局限（`hj212-协议实现说明.md` 的待确认表）。
2. **现有自建参考向量 `tests/protocol/hj212/test_vectors.json → table3_flag9_reference_packet` 用的是 `,` 连接 9 个参数**，与 §6.3.4.1 不符。它的 `kind` 已标注 `derived_reference`（"**不是官方向量**"），所以**不许**把它当组包黄金标准。
   → P3 的组包单测必须以**表 C.18 的结构规则**为判据；并建议在 P1 侧补一条针对该向量的说明（独立变更，不混进 P3）。
3. **`a00000`（Flow）的单位分歧未决**：原文缺省 `m3/s`，本项目 `m3/h`（1 m3/s = 3600 m3/h）。若平台按缺省单位解释，本项目的 `33471` 会被读成 33471 m3/s（相差 3600 倍）。
   → 决策：Profile 增加 `unit_scale: dict[str, float]`（默认**空** = 原样上报）+ 明确要求**"是否除 3600"必须与平台书面确认后才能设值**；默认值必须是"不换算"，避免代码静默改变物理量含义。

```
├── inflight-000001.jsonl                # 在途批次（原子改名而来，唯一名字）
├── inflight-000002.jsonl                # 上次补传未完成残留（更老 → 先发）
└── .outlet_alive                        # 出口线程心跳（可选，P3.6 供健康检查）
```

| 项 | MQTT 分支（地基，不动） | HJ212 分支（P3） |
|---|---|---|
| 待发文件 | `data/cache.jsonl` | `data/hj212/spool.jsonl` |
| 在途文件 | `data/cache.jsonl.sending`（**固定名，每次取批覆盖**） | `data/hj212/inflight-<seq>.jsonl`（**名字唯一，永不被覆盖**） |
| 锁 | `CACHE_LOCK` | `HJ212_CACHE_LOCK`（**独立**） |
| 在途窗口 | `RESEND_WINDOW`（100） | `HJ212_RESEND_WINDOW`（100） |
| 取批 | `os.replace` 覆盖 `.sending` | `os.replace(spool → inflight-<next_seq>)`，`next_seq = max(现有)+1` |
| 收尾 | 未确认回写 `cache.jsonl` 队首 → 删 `.sending` | 未确认留在**本段文件**里 → 全确认后删本段；回写失败保留逐字不变 |

**为什么换成"唯一段名"（这是本 ADR 主动改进地基写法的地方）**：

- 地基的取批要**覆盖**一个固定名文件，于是 leftover 在"覆盖后、合并批写回前"只存在于内存（§2.9 D1 实测：硬杀丢 2 条）。
- 段方案里**没有任何一次改名会覆盖已有文件**：`spool` 改名成一个**新的**段名；已有的旧段原封不动留在盘上、按 `seq` 升序被优先发送。那个内存独占窗口**在结构上不存在**。
- 崩溃恢复不需要额外状态文件：`inflight-*.jsonl` 本身就是"上次没发完的批次"，`next_seq = max(现有段号) + 1` 由文件名即可推导。
- 顺序语义与地基等价：段按 `seq` 升序 = 时间序；段内按行序；`spool` 里的新数据永远排在所有段之后 → "**未确认的比新采的先发**"成立。
- 代价：目录里可能同时存在多个段文件（正常情况下最多 1 个 + 1 个刚改名的）。可接受；`P3.6` 加一条"段文件数 > 3 时记 WARNING"的可观测性。

**取批与发送循环（示意）**：

```
出口线程 loop（被 submit 唤醒，或 HJ212_RESEND_RETRY_INTERVAL 到点）：
  1) 接管：with HJ212_CACHE_LOCK:
         if spool.jsonl 存在:  os.replace(spool.jsonl, inflight-<next_seq>.jsonl)
     失败 → 记 ERROR，本轮不发（数据仍在盘上）
  2) 段列表 = glob("inflight-*.jsonl") 按 seq 升序
  3) for 段 in 段列表:                        # 最老的先发
         逐窗发（HJ212_RESEND_WINDOW 条）：
             每条 publish 到 TCP；等"同 QN 的 CN=9014"（超时/失败 = 未确认）
             窗末：滚动回写**本段文件** = remaining + 本段未发尾部
                   回写失败 → 保留原段文件（逐字不变）并中止本段与后续段（记 CRITICAL）
         本段全部确认 → unlink 本段
         有未确认 → 中止后续段（旧数据优先），记 WARNING
  4) 段文件总数 > 3 → WARNING（可观测性）
```

**每段的报文带 `RF=1`**：表 3 原文"`RF=1`，标志数据报文属于补传报文；**非补传时，无本字段**"。
→ **判定规则必须显式**：**"来自 spool/段文件"**（即不是本轮采集直发）就带 `RF=1`；**刚采集到的那一刻直接发出去的**不带。
（这条同时给 ADR-0006 §4 遗留的 `RF` 语义一个可判定的定义：不是"重发过几次"，而是"是否属于补传批次"。）

**缓存上限与裁剪**：`HJ212_CACHE_MAX_BYTES`（默认 64 MB，与地基同口径）、`HJ212_CACHE_TRIM_RATIO`（0.5），策略沿用"丢最旧、保最新 + CRITICAL 日志"。
⚠️ **差异**：裁剪**只在出口线程做**（采集侧不做整文件重写）；且裁剪只作用于 `spool.jsonl`，**不动在途段**（在途段正在被判"发没发出去"，重写它会破坏"回写失败逐字不变"的不变量）。

**与地基互不干扰的硬保证**（写成断言，见 §3.8 V2）：`cache.jsonl` / `.sending` / `CACHE_LOCK` / `RESEND_WORKER` **一行不改、一句不引用**；`HJ212_OUTLET` 里不 import `cache.jsonl` 相关的任何符号。

### 3.4 线程与队列模型（两条变体 + 一个必须实测的判据）

**共同点**：出口是**一个独立线程**（`daemon=True`，单实例，名为 `hj212-outlet`），在 `main()` 里启动、在 `finally` 里 `stop()`（先落盘再退，仿 `RESEND_WORKER.stop()` 的语义）。所有网络等待（连接、应答、心跳）都只发生在这个线程里。

| | 变体 1（推荐）"磁盘即队列" | 变体 2（备选）"内存队列 + 出口线程落盘" |
|---|---|---|
| `submit()` 做什么 | 追加 `spool.jsonl`（`flush` + `fsync`）→ `EVENT.set()` | `queue.put_nowait(item)` → `EVENT.set()` |
| 采集线程开销 | 一次小文件追加 + fsync | 微秒级 |
| 硬杀（`SIGKILL`/断电） | **不丢**（数据已在盘上） | **丢 ≤ 队列内条数**（须显式声明） |
| 对端断/慢 | 完全不影响采集（追加不依赖网络） | 同 |
| 与地基一致性 | 与 `save_to_cache()` 同类操作（地基已在采集线程里做 flush+fsync） | 引入"数据在 RAM 里"的新状态 |

**决策门禁 G-M1（在容器内实测后才定案）**：

- 测法：在 `cems-gateway` 容器内、对**宿主机 bind mount**（`./data:/app/data`，与生产缓存同盘同挂载）做 n ≥ 30 次"打开追加 250 B + flush + fsync + close"，记录 p50/p95（探针形态同 ADR-0003 附录 A：scratch 子目录、用完 `rmtree`、不写生产缓存）。
- 判据：**p95 ≤ 50 ms 走变体 1**（相对 5 s 轮询周期 ≤ 1%，且不依赖对端）；否则走变体 2，并在验收文档与健康检查里写清"硬杀丢 ≤ N 条（N = 队列深度上限）"。
- 参考量（**不是结论，是量级参照**）：ADR-0003 §2.2 在同类 bind mount 上测到"4 次混合文件操作"的 prologue p50 = 10.45 ms（≈ 2.6 ms/次）。

⚠️ **不要用 0.08 ms 当判据**：那是 `read_device()` 的耗时（竞态裕度量的分子），与"采集循环的延迟预算"不是一回事（§1.2）。

**为什么不用 `queue.Queue` 作为唯一的数据通路（即使选变体 1 也保留一个 `Event`）**：队列只做"唤醒信号"，**不做数据载体**——这样"数据是否已持久化"这个问题只有一个答案（盘上），不会出现"一部分在盘上、一部分在 RAM"的双份真相。

### 3.5 TCP 连接管理

**先给一手取证结论（避免臆造）**：

| 项 | 标准怎么说 | 出处 |
|---|---|---|
| 传输层 | 应用层建构在 **TCP/IP** 上；适用于 GPRS/ADSL/CDMA/…/NB-IoT 等介质 | 第 7 页 |
| 应答模式 | 完整命令 = 请求方发起 + 响应方应答；未收到应答按**超时**处理 | §6.1，第 7 页 |
| 超时与重发 | 超时时间、重发次数**均可自定义**；缺省值见表 1（GPRS/CDMA 10 s / 3 次、ADSL 5 s / 3 次、NB-IoT 30 s / 5 次） | §6.2.1/§6.2.2 + 表 1，第 7–8 页 |
| 心跳 | `CN=9015` **现场机发送心跳包** → 上位机回 `CN=9013` 通知应答；"用于判断网络连接在线状态" | 表 12 第 22 页、表 C.54 第 75 页 |
| 数据应答 | 上位机收到 `CN=2011` 后按 Flag 决定是否回 **`CN=9014`**；`QN` 与请求**相同**、`ST=91`、`Flag=8`、`CP=&&&&` | 表 C.18，第 58 页 |
| 端口 / 谁主动连 / 心跳周期 | ⚠️ **未规定"现场机↔上位机"的连接端口**（全文无 `21215` 等端口号）；**未规定**谁主动连接、心跳周期（心跳只写"非固定污染源系统可自行定义"）。⚠️ 全文唯一出现"端口"的是**附录 E（资料性附录）**：数采仪面向**移动终端**提供 WLAN Socket 服务，示例 `IP:192.168.1.1;Port:3000`——**与上位机连接无关**，不得据此推断环保平台端口 | 第 83 页（附录 E.3 表 E.1）；核对方法见附录 B |

**设计**：

1. **连接方向**：现场机作为 **TCP client** 主动连上位机 —— 这是工程惯例与 §6.8（首次联网前在部里上位机注册）的自然读法，但**标准未明写** → **登记为待确认项**；实现上除"主动连接"这一条外**不假设对端的任何主动行为**（例如不假设对端会反向连回来、不假设对端会先握手）。
2. **所有连接参数走配置，且默认关闭**：
   `HJ212_ENABLED=0`（默认）、`HJ212_HOST`（**无默认值；只有回环场景才允许 `127.0.0.1`**）、`HJ212_PORT`（**无默认值**）、`HJ212_CONNECT_TIMEOUT=5`、`HJ212_ACK_TIMEOUT=10`（表 1 的 GPRS/CDMA 行；有线取 ADSL 行 5 s 亦可，二者皆合规）、`HJ212_RESEND_TIMES=3`（表 1）、`HJ212_HEARTBEAT_INTERVAL=60`（**标准未规定**，本项目取值）、`HJ212_RECONNECT_BACKOFF_MAX=60`。
3. **分帧（必须处理半包/粘包）**：TCP 是字节流，`\r\n` 只是报文内的分隔符。
   - 收：累加缓冲区 → 按 `\r\n` 切分 → 每段先看前 6 字符（`##` + 4 位长度）→ **用长度字段核对 `len(数据段) == declared`** → 再 `decode_packet()` 校验 CRC。
   - 长度不符 / CRC 不符 / 结构异常 → 记 ERROR 并**丢弃该段**（表 2 原文："接收到一条命令，如果 CRC 错误，执行结束"），**不影响后续段的解析**。
   - 发：一条报文一次 `sendall()`（含 `\r\n`），单连接串行，不做流水线。
4. **确认语义**：`CN=2011`（Flag=9 → D=1 → 需应答）→ **必须等到同 `QN` 的 `CN=9014`**；`ST=91` 作为辅助校验（表 C.18 的两条报文 `QN` 相同、应答方 `ST=91`）。
   - 匹配键 = `QN`（17 位毫秒时间戳，唯一标识一次命令交互）；实现上维护"在途 QN 集合"。
   - 超时（`HJ212_ACK_TIMEOUT`）内未收到 → 该条**未确认** → 保留在段文件里；按 §6.2.1 b) "超时后重发"，重发次数用尽则判"通信不可用"，**关闭连接走重连退避**（而不是继续堆在途请求）。
   - 确认判据**可配置**（`HJ212_ACK_CN=9014`、`HJ212_ACK_REQUIRED=1`）——因为地方平台可能不回应答；但一旦设 `ACK_REQUIRED=0`，等于"TCP 写成功即视为送达"，**补传保证会被削弱**，必须在文档与验收里显式降级说明（门禁 G-M4）。
5. **心跳**：连接空闲超过 `HJ212_HEARTBEAT_INTERVAL` 时发 `CN=9015`（`CP=&&&&`、Flag=9），等 `CN=9013`；心跳失败 → 判连接不可用 → 关闭 + 退避重连。心跳同时兼作 NAT/防火墙的静默断链探测（TCP 层没有 keepalive 的情况下，这是唯一能在"物理断链但对端未发 RST"时发现故障的手段）。
6. **重连退避**：指数退避 1 → 2 → 4 → 8 … 上限 `HJ212_RECONNECT_BACKOFF_MAX`（60 s）+ 抖动；连不上/断开期间**不做任何删除动作**，样本继续进 `spool.jsonl`；恢复后按段序补传（`RF=1`）。
   - 参照量：地基 paho 的重连实测最坏 **84 s**（故障 1 记录）——退避上限 60 s 与之同量级，避免"平台刚恢复、本地还在睡"。
7. **加密**：`HJ212_ENCRYPT=1` 时用 `HJ212_SM4_KEY`（32 位十六进制，16 字节）；§6.4.1 是"互联网**应**加密、专网**宜**加密" → 由 Profile 决定。**代码里不得出现任何密钥默认值**（安全红线）；`encrypt=1` 且未配密钥时 `Hj212Profile` 会在构造期直接报错（P1 已实现），出口启动即失败——**fail fast，不静默降级为明文**。
8. **不做多连接并发**：一个目标一个连接、一个发送线程串行发（同 paho 单连接模型），保证 `QN` 与应答的一一对应和顺序语义。

### 3.6 失败模式逐条论证

| # | 问题 | 结论 | 论证 |
|---|---|---|---|
| 1 | **会不会丢数据？** | 出口侧**不会**（在其能力范围内）；**采集侧的上游断链仍会真丢** | ① 采集侧：`submit` 落盘（变体 1 无内存驻留；变体 2 的残留被显式声明）；② 出口侧：**只有收到确认才删除**，段文件滚动回写、回写失败逐字保留（由 §2 的 P5 回归覆盖）；③ 崩溃后段文件按 `seq` 恢复；④ ⚠️ **上游（网关↔设备）断链真丢**——这是 `RELEASE-v2.0.0` §2.5 边界 2 与故障 1 的实测（净损失 ≈34 条），**HJ212 分支改变不了它**（源头没有就是没有）。任何"一条不丢"的表述都必须限定在"已进入网关的数据" |
| 2 | **会不会拖慢主循环？** | 不会（数字由 G-M1/G-M2 定案） | ① `submit` **不做任何网络等待**；② 不在采集侧做接管（那段 10.45 ms 的 prologue 只在出口线程发生）；③ 不在采集侧做裁剪（可能整文件重写）；④ 独立锁 → 不会与补传线程的 `CACHE_LOCK` 互等；⑤ 变体 1 的开销是一次追加+fsync，相对 5 s 周期是一阶小量（§1.2 的口径校正） |
| 3 | **会不会影响现有 MQTT 分支？** | 不会 | ① 不同文件、不同目录、不同锁、不同线程、不同在途窗口；② `cache.jsonl`/`.sending`/`CACHE_LOCK`/`RESEND_WORKER` **一行不改、一句不引用**；③ 主题/QoS/`MQTT_CLIENT_ID` 不变；④ 唯一共享面是 `build_payload`（加默认参数，门禁 G-B2 逐位回归）与只读的 `data` dict；⑤ 出口默认关闭（`HJ212_ENABLED=0` 时主循环只多一次 `is not None` 判断） |
| 4 | **顺序会不会变？** | 分支内近似时序；跨分支不保证 | 段按 `seq` 升序 + 段内行序 + 新数据永远在段之后 → "未确认先于新采"成立（与地基现有语义一致）。**两个分支之间不保证先后**（各自独立线程），必须显式声明，避免下游按到达序做跨分支判重 |
| 5 | **缓存会不会涨爆盘？** | 有上限 + 裁剪，但**会丢最旧** | 沿用"丢最旧保最新 + CRITICAL"，上限 64 MB；裁剪只在出口线程、只作用 `spool.jsonl`。⚠️ 长期不可用 = 必然丢最旧数据，这是"宁可丢最早的，也别把盘写满"的既有决策（地基 L61-64 的注释），**必须在验收与运维文档里写清**，并建议加健康检查项 |
| 6 | **平台不按标准应答怎么办？** | 可配置降级，但**补传保证同时降级** | `HJ212_ACK_REQUIRED=0` → 只能"发送成功即视为送达"；TCP 写成功 ≠ 对端业务处理成功。**必须拿到平台书面口径**（门禁 G-M4），否则不许悄悄关掉应答要求 |
| 7 | **出口线程自己挂了怎么办？** | 不静默死 | 线程入口 `except Exception: LOGGER.exception(...)`（沿用 `ResendWorker._run` 的写法），心跳文件 `.outlet_alive` 供健康检查；**死掉不影响 MQTT 分支与采集** |
| 8 | **磁盘满？** | 该条丢失并 CRITICAL | 与地基同级的物理边界（`save_to_cache` 已有同样的处理）；出口侧追加失败会记 CRITICAL 并保留已有数据 |

**配置纪律**：

2. **不把任何平台地址/口令/密钥写进代码或 `docker-compose.yml` 的默认值**（安全红线）。P3 落地时若要在 compose 里加变量，只加**键名与注释**，值留给部署方。
3. **一个进程只跑一个目标**（§1.3 第 4 条），但类设计成 `Hj212Outlet(profile, data_dir)` 形式——多目标留到有第二个真实实现之后（到时"每目标一份实例 + 独立 data_dir"就是自然的扩展点）。

#### V2（离线，stub transport）`scripts/verify_hj212_outlet.py`（P3 新增）

用**stub transport**（`send(bytes) -> None` 记录 + 可注入"断链/超时/不回应答/回错 QN"）+ **stub 应答器**（按收到的 QN 自动回一条 `CN=9014`），断言：

| # | 断言 | 判据 |
|---|---|---|
| H1 | 组包结构 | 与手工构造的期望报文**逐字符**相等；`decode_packet()` 往返一致；`;`/`,` 规则与表 C.18 一致；长度字段 == 数据段字符数（不含 CRC） |
| H2 | `RF` 只出现在补传 | 实时直发报文**不含** `RF`；段文件里的报文含 `RF=1`（`decode_packet` 的 `packet.resend`） |
| H3 | 只删确认过的 | 注入"第 k 条不回应答"→ 段文件里恰好剩该条（多重集比较）；`confirmed == 总数 - 未确认` |
| H4 | ⭐ **"平台断 5 分钟"等价场景** | 造 N 条 spool → stub 拒绝发送 N 分钟量级 → 恢复 → **100% 排空 + 条数守恒**（复用故障 2/3 的 128/46 条形态；语料同 `resend_snapshot_drill2.txt`） |
| H5 | 段回写失败 | 与 §2 的 P5 同型：段文件字节不变、一条不丢、解除阻塞后可恢复 |
| H6 | 多窗口滚动 | 与 §2 的 P6 同型（`HJ212_RESEND_WINDOW=3`），观测点读真实盘 |
| H7 | 分帧正确性 | 半包（一次只喂 7 字节）、粘包（两条报文一次喂入）、坏 CRC、长度不符 → 全部按 §3.5.3 处理且**不误判为送达** |
| H8 | 提交路径不阻塞 | `submit()` 的 p50/p95 断言（阈值取 G-M1 定案值），且在 stub 完全不响应时 `submit()` 耗时**不变** |

## 4. 有意偏离与"我认为更好的做法"

| # | 偏离/改进 | 论证 |
|---|---|---|
| 1 | **HJ212 在途批次用"唯一段名"（`inflight-<seq>.jsonl`），不照抄固定名 `.sending`** | 地基的固定名要求"用新批**覆盖**旧在途文件"，产生一个 leftover 只存在于内存的窗口（探针实测硬杀丢 2 条）。段名唯一 → 结构上不存在覆盖动作 → 该窗口消失；且崩溃恢复只需文件名（按 `seq` 升序），不需要额外状态文件。代价是目录里可能出现多个段文件（正常 ≤ 2，> 3 记 WARNING） |
| 2 | **不把内存 `queue` 当数据通路（即使选变体 2 也要显式声明残留）** | "数据是否已持久化"必须只有一个答案。地基的强项恰恰是"入队即落盘 + fsync"；新分支若把可靠性寄托在 RAM 上，等于把地基最有价值的性质降级 |
| 3 | **"独立队列"落地为"独立缓存文件 + 独立锁"，而不是一个 `Queue` 对象** | ADR-0006 的意图是"两路互不干扰、且不依赖对端"。文件级隔离同时满足两点；用同一个 `CACHE_LOCK` 反而会让出口的文件操作阻塞采集线程（地基取批的 prologue 就在锁里，p50 10.45 ms） |
| 4 | **校正"0.08 ms 是主循环预算"的读法** | 0.08 ms 是竞态裕度的分子，不是延迟预算；用它去否决"采集线程内一次本地落盘"会与地基现状自相矛盾（地基已在采集线程里做 flush+fsync）。真正该守的是"**采集线程不做任何依赖对端的等待**" |
| 5 | **`RF` 的判定规则显式化为"是否来自 spool/段文件"** | ADR-0006 §4 把 `RF`/优先新数据留给后续拍板；P3 必须给一个**可判定**的定义，否则实现者会各自发明（"重发过就带 RF"是错的：补传批次里第一次发出去的也必须是 `RF=1`） |
| 6 | **组包黄金标准取表 C.18 的结构规则，而不是仓库里那条自建参考向量** | 那条向量 `kind = derived_reference`（自己声明"不是官方向量"），且用 `,` 连接 9 个参数，与 §6.3.4.1 定的 `;`/`,` 规则不符 |

⚠️ **我没有找到"P3 会不可避免地破坏不丢数据"的证据**：出口侧可以完整复制地基的三道防线（入队即落盘、只在确认后删除、回写失败保留唯一副本），且能在结构上修掉地基那个内存独占窗口。**唯一无法消除的丢数据边界在采集侧上游**（网关↔设备断链，`RELEASE-v2.0.0` §2.5 边界 2 / 故障 1 的 ≈34 条），它与 P3 无关，但**必须写进 P3 的结论**，不许用"补传 100%"去覆盖它。
