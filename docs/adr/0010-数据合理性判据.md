# ADR-0010 · 数据合理性判据（跳变 / 冻结）与「可疑 ≠ 无效」的区分

- 状态：已实现并标定（2026-10-11，提交 `a026831` + 标定修订；W1~W6 全部实测，见 §12）
- 关联：`docs/adr/0009-接入层逐点质量位.md`（本 ADR 复用它的事件表与逐点机制）；
  `docs/架构与可维护性说明.md` §四 第 2 档
- 影响文件：`src/platform/subscriber_to_td.py`、`src/common/errors.py`（新增 `kind` 取值）、`docker-compose.yml`

---

## 1. 背景

ADR-0009 建立了逐点质量位机制，能表达"这个测点不可信"。但判据只有量程：

| 判据 | 现状 |
|---|---|
| 有限性（`NaN` / `inf`） | 有 |
| 量程（物理上不可能） | 有 |
| 跳变率（相邻样本突变） | 没有 |
| 冻结（值长期不动） | 没有 |

这两类在真机上观测不到（真机是正常工作的），但可以在仿真测点上注入。
而用户的目标是「把真机故障实验的效果映射到其他仿真数据上，其他层一律按真实数据处理」——
所以判据必须在其他层（接入层）实现，且不区分真机 / 仿真。

---

## 2. 最大的风险：误报（本 ADR 首先要处理的问题）

CEMS 稳态运行时，物理量本来就很稳。实测：`Temp` 在 `26.0 ~ 26.2 degC` 之间波动了 40 分钟。

若判据写成"值不变就报警"，会把正常运行判成故障 ——
而误报比漏报更糟：运维会直接关掉它，于是这个能力等于不存在。

**所以判据必须是「容差 + 持续」，不是「相等」**：

| 判据 | 定义 |
|---|---|
| 跳变 | `\|Δ\| > 量程宽度 × JUMP_RATIO` |
| 冻结 | 连续 `N` 个样本都落在 `[v0 − 容差, v0 + 容差]` 内，`容差 = 量程宽度 × TOLERANCE_RATIO` |

**都用"量程百分比"表达** → 不需要逐点配置
（9 个测点量纲差 4 个数量级：`Flow ≈ 34000` vs `O2 ≈ 6.8`）。

---

## 3. 核心决策：「可疑」≠「无效」

| 判据 | 语义 | 处置 |
|---|---|---|
| 超量程 / `NaN` / `inf` | 物理上不可能 | 不写该列（丢） |
| 跳变大 | 可疑，但可能是真实工况突变 | 照常入库 + 留痕标为可疑 |
| 冻结 | 可疑，但可能是真实稳态 / 检修恒值 | 照常入库 + 留痕标为可疑 |

**为什么"可疑"不能丢**：
- 跳变可能是真实的（设备启停、工况切换）—— 丢掉等于掩盖真实事件
- 冻结可能是真实的（停机、检修期间恒值）
- 而"超量程"不一样：物理上不可能，丢掉是安全的

**这是 ADR-0009 同一原则的延伸**：
ADR-0009 说"无效与缺失必须可区分"；本 ADR 说"可疑与无效也必须可区分"。

---

## 4. 落点：复用 ADR-0009 的事件表，新增 `stored` 列

显式表达处置，让"丢了什么"和"标了什么但留着"各是一句 SQL。

**`kind` 取值**（受 `NCHAR(10)` 限制，见 §6）：

| `kind` | `stored` | 含义 |
|---|---|---|
| `invalid` | `0` | 超量程 / `NaN` / `inf` |
| `missing` | `0` | 报文里没有这个测点 |
| `jump` | `1` | 相邻样本突变（可疑，值已入库） |
| `frozen` | `1` | 长期不变（可疑，值已入库） |

**加了 `stored` 之后**：
- 「丢了什么」→ `WHERE stored = 0`
- 「标了什么但留着」→ `WHERE stored = 1`

## 5. 配置

| env | 含义 | 默认（2026-10-11 已标定，见 §12.4） |
|---|---|---|
| `QUALITY_CHECK_ENABLE` | 总开关 | `1`（见 §7 的取舍） |
| `QUALITY_JUMP_RATIO` | 跳变阈值 = 量程宽度 × 该比例 | `0.25`（量程的 25%） |
| `QUALITY_FREEZE_SAMPLES` | 连续多少个样本在容差带内算冻结 | `1200`（≈ 100 分钟 @5 s） |
| `QUALITY_FREEZE_TOLERANCE_RATIO` | 冻结容差 = 量程宽度 × 该比例 | `0.0001`（≈ 寄存器分辨率量级） |

**上表是标定后的值，不是最初拍的值** ——
最初写的 `12 / 0.005` 被 W4 实测否掉（真机数据在线 10.4 分钟误报 39 条 `frozen`）。
标定方法与全部证据见 §12.3 / §12.4；两条测试已按新语义有意识地改写（见 §12.5）。

## 6. 两个已实测的约束（都改变了本 ADR 的写法）

### ① `ALTER STABLE ADD COLUMN` 可用（TDengine 3.3.6.13，实测）

```sql
ALTER STABLE probe ADD COLUMN stored TINYINT;   -- Query OK
DESCRIBE probe;                                 -- stored TINYINT 出现
SELECT ... FROM p1;                             -- 旧行 stored = NULL（向后兼容）
```

但 `CREATE STABLE IF NOT EXISTS` 不会加列（项目既有结论）——
升级已存在的表必须显式 `ALTER`，不能只靠建表语句。

### ② `kind` 列是 `NCHAR(10)`，新取值必须 ≤ 10 字符（实测踩到）

```
INSERT ... kind='suspect_jump'  ->  DB error: Value too long for column/tag: kind
```

这就是为什么取值定成 `jump` / `frozen` 这种短名，而不是 `suspect_jump`；
人可读的解释放 `reason` 列（它是 `NCHAR(200)`，够用）。

## 7. 待定的取舍：判据默认开还是关？

| 选项 | 利 | 弊 |
|---|---|---|
| 默认开 | 实验能直接用；真机真出异常也能抓到 | 误报会污染事件表（虽然只留痕不丢数）；调参前可能有噪声 |
| 默认关 | 零风险 | "最终版本"里它是关的 → 实验证明不了它存在 |

**倾向：默认开，但阈值保守**（宁可漏报也不要误报），
且因为只留痕不丢数，"开着"的代价远小于"把真实数据丢掉"。

## 8. 验证判据（机制断言，不依赖具体数值）

| # | 判据 |
|---|---|
| **W1** | 注入单点阶跃 → 该点照常入库，事件表 `1` 条 `kind=jump / stored=1` |
| **W2** | 注入持续不变（超过门限样本数）→ 该点照常入库，事件表 `kind=frozen / stored=1` |
| **W3** | 注入超量程 → 该点不入库，事件表 `stored=0 / kind=invalid`（= ADR-0009 的 V1/V2，回归） |
| **W4** | 误报对照：真机正常数据（稳态抖动 `26.0~26.2`）跑 ≥ 10 分钟 → 事件表零新增 |
| **W5** | 判据关闭时，行为与"不实现本 ADR"完全一致 |
| **W6** | 被标为可疑的点仍然出现在报表/曲线里（因为 `stored=1`） |

**W4 是本 ADR 最重要的一条** —— 它防的正是 §2 那个风险："把正常运行判成故障"。

## 9. 局限与不做（单列）

- 传感器缓慢漂移（硬件腐蚀）—— 本 ADR 不覆盖：漂移是缓慢的，跳变与冻结都抓不到；
  需要趋势检测或独立参照（`docs/runbooks/真机接入.md` S3 的 ±0.5 degC 判据一直未做）
- 多测点交叉验证（如 `O2` 与 `NOx` 的相关性）—— 不做
- 阈值没有标定 —— §5 的默认值是估计值，必须用 W4 在真实数据上校准
- 判据是"每设备的进程内状态" —— 接入层重启后前 N 个样本无法判冻结（有冷启动窗口）
- 本 ADR 尚未实现，§8 判据全部未经实测

## 12. 实施记录与标定（2026-10-11 · 提交 `a026831` + 标定修订）

**状态：已实现且判据可用；但 §5 的默认值被 W4 实测否掉，已按标定改写。**

### 12.1 实现（提交 `a026831`）

| 步 | 做了什么 |
|---|---|
| `QualityConfig` / `QualityChecker` | 跳变 + 冻结判据，每设备实例一份进程内状态 |
| 事件表 | 新增 `stored TINYINT`；已存在的表靠 `ALTER STABLE ADD COLUMN` 补列（`CREATE ... IF NOT EXISTS` 不加列，实测）；旧行 `stored IS NULL` |
| `errors.py` | `PointInvalidKind.JUMP/FROZEN` + `kind.stored` / `DROPPED_KINDS` |
| `on_message` | 串接判据；`STATS["suspect_points"]` |
| compose | 4 个 `QUALITY_*` env 加在 `x-subscriber-env` 锚点（两实例都有） |

### 12.2 W1~W6 结果

| 判据 | 结果 |
|---|---|
| **W1 跳变** | 注入 `Dust 2.5→60`（57.5% 量程）→ 主表 `dust=60` 照常入库；事件 `jump / stored=1 / raw=60` ✅ |
| **W2 冻结** | 注入 20 条恒定 → 主表 20 行全在；事件 `frozen / stored=1` ✅ |
| **W3 回归** | 超量程 → 主表 `NULL`；事件 `invalid / stored=0`（= ADR-0009 的 V1/V2）✅ |
| **W4 误报** | 原默认值不合格 —— 见 §12.3 |
| **W5 关闭** | `QUALITY_CHECK_ENABLE=0` → 事件表 `count(*)=0`，主表照常入库 ✅ |
| **W6 可见性** | 被标 `jump`/`frozen` 的点主表可查（非 NULL）✅ |
| 鉴别力 | 故意把可疑点从 `values` 里 `pop` 掉（违反"可疑照常入库"）→ 3 条接线用例 FAIL（含 `KeyError`）→ 改回 → 全绿 ✅ |

### 12.3 W4 把 §5 的默认值否掉了（实测，不是估计）

| 配置 | 在线误报 | 3.2 小时离线连续重放 |
|---|---|---|
| `(容差 0.005, N=12)` = 原默认 | 39 条 / 10.4 分钟 | 238 条 |
| `(0.005, N=180)` | 3 条 / 20.5 分钟 | 12 条 |
| `(1e-4, N=360)` | 0 条 / 13.7 分钟 | 0 条 |

**根因**：0.5% 的容差会把"跨十几分钟的慢漂移段"整段吃进同一条游程 ——
而真机数据本来就含这种段（§2 自己观测的"`Temp` 在 26.0~26.2 稳了 40 分钟"正是它）。
**实测结论：在这个容差下"加大 N"到不了零误报，必须同时收紧容差。**

### 12.4 标定（负责人独立复算，10 天全量）

**方法**：把 10 天全部真机数据（`cems.plant1_device1`，25093 个样本，
2026-10-01 00:28 ~ 10-11 17:42）按"游程内每个值都在 `基准 ± 1e-4 × 量程` 内"求最长自然平台期：

| 测点 | 最长自然平台期 | 时长 | 发生时间 |
|---|---|---|---|
| `flow` | 5 | 0.4 min | 10-01 01:01 |
| `dust` | 404 | 33.7 min | 10-02 22:07:15 ~ 22:41:00 |
| `so2` | 120 | 10.0 min | 10-01 02:34 |
| `nox` | 186 | 15.5 min | 10-03 15:21 |
| `o2` | 71 | 5.9 min | 10-01 00:53 |
| `velocity` | 63 | 5.2 min | 10-01 00:54 |
| `temp` | 173 | 14.4 min | 10-11 15:29（真机期间） |
| `humidity` | 62 | 5.2 min | 10-11 15:27 |
| `pressure` | 75 | 6.2 min | 10-01 00:52 |

**取 `N = 1200 = 404 × 3`（≈100 分钟 @5s）**，容差 `1e-4 × 量程`。

**为什么不取 360**：10-02 那个 `dust` 平台期实测 404 > 360，会被误报。

**改后实测**：新默认值上线（subscriber 于 `17:43:37` 重建）后 → `frozen` 零新增 ✅

### 12.5 标定带来的语义变化（必须记住）

§2 最初的理由是"用容差吸收稳态抖动，否则会误报"。
**实测把这个理由推翻了**：真正防误报的是长 N，不是宽容差；
宽容差反而制造误报（把慢漂移段整段算成冻结）。

**所以容差的角色变了**：从"吸收稳态抖动" → "只吸收浮点/量化噪声"。
后果：`Temp` 容差从 1.5 degC 缩到 0.03 degC，于是 `26.0 → 26.1` 就跨出带外、游程重起算。
（两条测试已按新语义有意识地改写，并新增一条专门钉住这个变化。）

### 12.6 `jump` 是好的 —— 但要知道它会响在哪

实测：仿真器设计上就会产生尖峰（`SIM_SPIKE_PROB`），尖峰使 `dust` 从约 `3` 跳到 `30~55`
—— 超过 `25% 量程 = 25` 的门限。10 天内 `dust > 25` 出现 298 次（≈ 30 次/天）。

**这不是误报**：值确实跳了。
按 §3 的处置，`jump` 是 `stored=1`（照常入库 + 留痕），所以：
- 数据不丢；
- 事件表留下约 30 条/天的跳变痕迹 —— 可以被后续统计利用（这正是"可疑"该有的样子）。

### 12.7 实施中发现的两个真问题（都已修）

| # | 问题 | 后果 |
|---|---|---|
| 1 | 默认值被抄了两份（dataclass 字段 + `from_env` 字面量） | 改标定值时只改了一份 → `from_env()` 与 `QualityConfig()` 悄悄不一致（12 vs 1200）。已改为从 `dataclasses.fields()` 取唯一真源；被一致性测试抓到 |
