# ADR-0008 · 多设备（第二台设备 / 多实例路线）

- 状态：**已实现并实测**（2026-10-02）
- 关联：`docs/evidence/drill/multi_device_two_instances_20261002.txt`（原始输出）、
  `docs/runbooks/故障台账.md` 故障 7（两台设备共因断网演练）
- 影响文件：`src/device/modbus_server.py`、`src/device/simulator.py`、`src/gateway/gateway.py`、
  `src/platform/subscriber_to_td.py`、`docker-compose.yml`、`.env.example`

---

## 1. 背景：数据层已经是多设备，采集侧还是"一实例一台"

- 数据层从设计上就是多设备的：超级表 `cems.cems_data` 的 TAG 是 `(plant, device)`，
  子表名 `{plant}_{device}`（`src/platform/subscriber_to_td.py` 的 `CHILD_TABLE`）。
- 采集侧三处**硬依赖**让第二台设备起不来（都不是"设计上不支持"，而是"没留出口"）：

| # | 位置 | 问题 | 本轮处置 |
|---|---|---|---|
| 1 | `src/gateway/gateway.py` 的 `DATA_DIR` | 缓存/续传状态全部落在 `PROJECT_ROOT/data` 下的固定文件名上，**没有 env 出口** → 两个网关实例会共用 `cache.jsonl`、`inflight-*.jsonl`、`.gateway_alive` | 新增 `GATEWAY_DATA_DIR`，默认值仍是 `PROJECT_ROOT/data` |
| 2 | `docker-compose.yml` | `container_name` 固定（`cems-gateway` / `cems-subscriber`）→ 起不了第二套 | 第二套用独立容器名（`cems-gateway-plant2` / `cems-subscriber-plant2`） |
| 3 | `gateway.py` | `MQTT_CLIENT_ID` 默认 `cems-gateway-plant1`、`MQTT_TOPIC` 默认 `cems/plant1/data` → 两个实例撞 client_id 会互相踢下线 | 第二套由 compose 注入不同的 `MQTT_TOPIC` / `MQTT_CLIENT_ID` |

> **一处事实更正**：`MQTT_TOPIC`（`gateway.py:42`、`subscriber_to_td.py:61`）与
> `TD_PLANT` / `TD_DEVICE`（`subscriber_to_td.py:79-80`）**本来就是 `os.getenv(...)` 可覆盖的**，
> 不是写死的常量。它们"固定"只是因为 compose 里给第一套实例注入的是字面量。
> 所以这两项不是代码阻塞点，而是编排阻塞点。

## 2. 决策一：设备层用**多从站**（一个 TCP 服务端、多个 unit id），不另开端口/容器

**备选**
- (a) 一个 TCP 服务端提供多个从站（`SLAVE_IDS=1,2`），每个从站独立数据块 + 独立仿真器
- (b) 起两个设备实例（`5020` / `5021`），各一个从站

**决策：选 (a)**，理由：
1. **更像现场的接线形态**：一条链路（一个 IP:端口）后面挂多台仪表，数采侧按 unit id 分别读取
   （多台仪表挂同一条 RS-485 总线、再由串口服务器转 TCP 即此形态）。
2. **省掉一整套编排面**：不用第二个端口、第二份端口映射、第二个 healthcheck、第二个 service 定义；
   任务书里"端口不要撞"这条约束在这个方案下**自然消失**（只有 5020 一个端口）。
3. **网关侧本来就按 unit 参数化**：`MODBUS_UNIT` 已是 env，第二套网关只需把它设成 2。
4. 单设备形态**逐值不变**：`SLAVE_IDS=1` 时仍走 `ModbusServerContext(..., single=True)` 的原有调用路径。

**代价**
- 两台设备在同一个进程里：设备层重启/崩溃是**共因故障**（同时影响两台）。
  这恰好与本轮"同时影响两台的断法"演练一致；要单独注入"只断某台"的故障，需要 unit 级
  （或第二个进程）的注入手段 —— 当前没有，列入局限。
- 从站数 > 2 时仍是一个进程，CPU 随从站数线性增长（本仿真每从站每 2 秒一次采样，量级可忽略）。

**数据可区分性**（否则多设备演示没有意义）：第 n 台的种子 = `SIM_SEED + (n-1)`，
相位偏移 = `(n-1) × SLAVE_PHASE_OFFSET`（默认 3 小时）。
第 1 台 = `SIM_SEED` + 相位 0 ⇒ 与改造前**逐值一致**（实测：从站 1 的 `sample_all()` 与改造前
模块级 `SIMULATOR` 完全相同）。两台实测差异见 §5。

## 3. 决策二：编排用"两份 service 定义 + `x-` 锚点复用 + profiles 门控"

**备选**
- (a) 两份完整 service 定义（复制粘贴）
- (b) 一份定义 + 锚点展开成两个服务
- (c) `docker compose up --scale` 派生同构副本
- (d) 独立 overlay 文件（`-f docker-compose.yml -f docker-compose.plant2.yml`）

**决策：两份定义 + 锚点复用 + profiles**，理由：
1. YAML 锚点只能把一份定义**合并进**某个服务，**无法把一份定义展开成两个服务**
   （服务名/容器名/从站号/主题/缓存目录都不同）⇒ (b) 在 YAML 语义上不成立，(a) 是必然。
2. 但"哪些键共用、哪些键每实例不同"必须一眼可见，所以共用部分抽成
   `x-gateway-env` / `x-gateway-healthcheck` / `x-gateway-depends` /
   `x-subscriber-env` / `x-subscriber-healthcheck` / `x-subscriber-depends`
   （沿用项目既有的 `x-app: &app` / `*logging` 风格），第二套只写差异键。
3. (c) 不成立：本链路的实例**不是同构副本**（从站号、主题、client_id、缓存目录、容器名各不同），
   且 `container_name` / `ports` 与 `--scale` 冲突。
4. 用 **profiles** 而不是"默认把两套都起来"：默认启动面（8 个服务）是现状与验收基线；
   第二套是"能力已具备、按需开启"。若默认起两套，两台设备的数据会同时进 `cems.cems_data`，
   任何不带设备过滤的查询都会把两条曲线混在一起（`scripts/verify_pipeline_live.py` 正是
   因为这一点在并行改动里补上了设备 TAG 过滤）。
5. 不用 (d)：需要新增一个 compose 文件（本轮的改动面已约定只碰 `docker-compose.yml`），
   而且 `-f` 同样有"不带 `-f` 的 `down` 停不掉第二套"的问题。

**代价 / 已知坑**
- 不带 `--profile plant2` 的 `docker compose stop/down/ps` **管不到**第二套实例
  （`ps` 在它们运行时仍会列出，但 `down` 不会停）。关闭第二套要显式：
  `docker compose --profile plant2 stop gateway2 subscriber2`。这一条已写进 README。
- 第二套的启用是**两个开关**：`.env` 里 `SLAVE_IDS=1,2`（设备层真的提供从站 2）
  ＋ `docker compose --profile plant2 up -d`。只做后者时第二个网关读不到从站 2，
  日志会持续报 Modbus 读失败（不会静默）。**没有把 `SLAVE_IDS` 默认写成 `1,2`**，
  就是为了守住"默认 env 不变"。
- 加第三台设备目前是"照着 `gateway2` / `subscriber2` 再复制一份"（N=2 时最省事）。
  N≥3 或设备需要动态增减时，应该换成"单实例订阅通配 + 从主题解析设备号"（见 §4 的代价）。

## 4. 决策三：接入层**每台设备一个实例**，不用"单实例订阅通配 + 从主题解析设备号"

**决策：每台设备一个接入实例**，理由：
1. 本模块带状态的东西**天然是每设备一份**：判据滑窗（`AlarmJudge`）、最近折算值快照
   （`LAST_REFERENCE`）、持久会话 `client_id`，以及"一个实例只写一张子表"这个前提 ——
   `_check_tags()` 的子表标签一致性校验正是建立在这个前提上。
2. 多实例让这些状态各归各的：**单设备代码路径零改动**（只加了一处主题↔标签一致性告警）。
   通配方案要把写入器/告警表/判据状态全部按设备字典化重写，属于把已经正确的路径重写一遍，
   与"不许让单设备现状回归"直接冲突。
3. N=2 时代价只是多一个容器（内存量级几十 MB）。

**代价 / 边界**
- N 较大或设备需要动态增减时，每台一个容器不划算：那时应改成单实例订阅通配，
  但**必须同时**把 `TdWriter`、`AlarmTables`、`AlarmJudge`、`LAST_REFERENCE` 全部按设备字典化，
  并把标签校验改成"按 topic 解析出的 (plant, device) 逐个子表校验"。
- 主题命名沿用既有契约 `cems/<plant>/data`（**不改主题形状**）：第二套用 `plant2` / `device2`。
  同厂区两台设备要有不同主题，就得给主题加一层（如 `cems/plant1/device2/data`）——
  那属于主题契约变更，本轮不做；启动时的"主题厂区段 vs `TD_PLANT`"告警正好能抓出配错的组合。

## 5. 网关缓存目录：`GATEWAY_DATA_DIR`（多实例的正确性前提）

两个网关共用一个缓存目录**不是"慢一点"**，而是**数据张冠李戴**：
- 段号由目录内文件名推导（`_next_segment_path`），A 实例会接着 B 实例的段号往下写；
- 补传是"整目录接手"（`_take_over_pending` 扫 `inflight-*.jsonl` glob），
  A 会把 B 缓存的报文**发到 A 自己的主题上**，两边都以为发成功了；
- `.gateway_alive` 心跳互相覆盖，healthcheck 判断的不再是本实例的采集循环。

因此第二套实例显式给 `GATEWAY_DATA_DIR=/app/data-plant2`（宿主 `./data/plant2`）。
默认（不设该变量）= `PROJECT_ROOT/data`，与改造前**逐字节一致**；相对路径按**项目根**解析。

## 6. 实测（原始输出见 `docs/evidence/drill/multi_device_two_instances_20261002.txt`）

| 项 | 结果 |
|---|---|
| 两台设备同时出数 | `SELECT DISTINCT device FROM cems.cems_data` → `device1` / `device2`（2 个） |
| 两条曲线可区分（同一时间窗） | device1: SO2 均值 31.47、O2 6.4~6.5%、NOx 32.70；device2: SO2 21.10、O2 7.4~7.5%、NOx 34.81 |
| 单设备回归 | `pytest -q` 194 passed；`scripts/verify_pipeline_live.py --minutes 2` 全通过（退出码 0，默认按 `device1` 过滤） |
| 第二台自己的全链路自检 | `scripts/verify_pipeline_live.py --minutes 2 --device device2` 全通过（退出码 0） |
| 共因断网（断 EMQX 链路 75 秒） | 两台各自缓存并补传：device1 **10 条**、device2 **10 条**（分两批 8+2 / 6+4，均为 `broker 已确认`） |
| 逐条对账 | 网关"已入本地队列"的每一条时间戳都在库中对应设备下 → **零丢失** |
| 缓存/查询按设备隔离 | 报表接口逐分钟条数 == 本实例设备在库里的条数（不是两台之和）；同一时间窗在两个设备维度上产生**两个独立 Redis 条目**（各 +1，重复查询 +0） |

## 7. 局限与"没做到"（必须单列）

1. **停 EMQX 容器（重启 broker）会丢离线队列**：EMQX 的会话是内存态
   （实测 `emqx ctl conf show durable_sessions` → `enable = false`），重启后两个订阅端的
   `session_present` 都是 `False`。此时网关补传拿到的是 **broker 级 PUBACK**，
   而订阅端可能还没重订阅 → 报文在 broker 侧被丢弃、网关却已从缓存删除。
   本轮停 EMQX 的那次演练实测到这一现象（两台各补传 29 条，device1 全部落库、device2 的 29 条未落库，
   原因即"订阅端重订阅与网关补传的竞态 + 会话未持久化"）。
   **要扛 broker 重启必须开 EMQX `durable_sessions`（或让订阅端先于网关恢复）**，本轮未改 broker 配置。
2. **"只断其中一台"的故障注入没有**：设备层是多从站单进程，无法只让从站 2 消失（除改 `SLAVE_IDS` 重启）。
3. **加第三台设备仍是手工复制** compose 定义；未做参数化生成。
4. **同厂区两台设备**（`plant1/device1` + `plant1/device2`）的主题命名未落地，需要主题加一层（契约变更）。
5. 展示层的设备维度（缓存键 + 读路径 tag 过滤）由并行改动落地
   （`src/web/cache.py`、`src/web/report.py`、`ca06af1`/`58c4ce8`/`d9e599d`）；
   **每台设备一个 web 实例**是展示层的部署形态，本轮未在 compose 里加第二套 web。
