# ADR-0011 · 上游直读（只读 Modbus TCP 服务）、心跳状态快照与契约指纹

- 状态：已实现并单测（2026-10-14；含 1 个真 socket 端到端测试与 1 处 pymodbus 地址语义实测）
- 关联：`docs/adr/0006-HJ212出口与北向适配.md`（同样是"新增对外接口"的定位与边界口径）、
  `docs/adr/0009-接入层逐点质量位.md`（证据表与"要把状态说清"的同一条纪律）
- 影响文件：`src/gateway/upstream_modbus.py`（新增）、`src/gateway/gateway.py`、
  `src/common/points.py`、`src/platform/subscriber_to_td.py`、`.env.example`、`docker-compose.yml`

---

## 1. 背景：三个空位

起因是一次"对标商业网关"的复盘。把展会上的产品能力逐条对到本项目，发现三处空位，
共同点是**都不影响现有功能，但都让系统在某种情形下"说不出话"**：

| # | 空位 | 现状 | 后果 |
|---|---|---|---|
| 1 | 上游直读 | 网关是**纯客户端**（`ModbusTcpClient`），对外零服务 | 现场 SCADA / DCS 想拿实时值，只能订阅 MQTT（要求它懂报文格式）或查时序库（拿到的是入库后的历史，有延迟） |
| 2 | 心跳只有时间戳 | `.gateway_alive` 内容 = `str(time.time())` | "循环在转但每条都读失败"与"一切正常"在文件里长得一样，healthcheck 判不出区别 |
| 3 | 数据不知道自己是哪版契约采的 | 链路可追溯数据从哪来，但样本不带规则标识 | 改了 scale/量程后回查历史，分不出改前改后；网关与接入层各自构建时"一边改了契约"**两边都不报错** |

第 1 条不是我发明的需求：工业网关的通行形态就是**两个角色并存**——
Moxa AIG-501 规格写的是 `Modbus RTU/ASCII/TCP **master**` **加上** `Modbus TCP **server**`；
MGate 写的是"主动轮询并缓存设备数据，**SCADA 直读**"。

---

## 2. 决策

| # | 决策 |
|---|---|
| 1 | 网关新增一个**只读 Modbus TCP 从站**，暴露"最近一次成功采集的快照" + 状态区；**默认关闭** |
| 2 | `.gateway_alive` 内容从"一行时间戳"改为**一份 JSON 状态快照**；保活语义不变 |
| 3 | 网关在每条报文末尾附加 `Cfg=<契约指纹>`；接入层取出来比对，不一致打 ERROR 并计数 |

三件事都刻意做成"**新增，不改既有语义**"：默认关、只加字段、只加文件内容。

---

## 3. 决策一：上游直读服务

### 3.1 「角色」和「协议」是两件事（这是本决策最重要的部分）

"被上游直读"是一个**角色**，不是某个协议。Modbus TCP server 和 OPC UA server 是
同一个角色的两种协议实现。所以选 Modbus 不等于"放弃 OPC UA 这条路"，而是
**先把角色补上，协议可以后换**。

**为什么先做 Modbus 而不是 OPC UA**：

| 理由 | 说明 |
|---|---|
| 地址与编码**与设备层完全同构** | 同一套 `points.py` 契约与 `scale`，上游读到的数与"直接读设备"**逐值可比**（有测试断言） |
| 依赖现成 | `pymodbus` 已在依赖里，设备层已有 `StartTcpServer` / `ModbusSlaveContext` 的完整用法 |
| OPC UA 是另一个量级的工程 | 要维护地址空间、会话、订阅、证书；资源约束（128 MiB）下要么挤掉余量，要么放宽约束 —— 而"128 MiB 有意义"是边缘定位的核心论据 |

**并且有外部证据支持"先不做 OPC UA"**：对 20 条可读的真实招聘 JD 的取证显示，
OPC UA 在 JD 里是"南向采集协议清单里的一员"，期待的能力是**会用**不是**会实现**——
`Kepware` / `UaExpert` / `地址空间` / `证书` 这几个词在所有 JD 里的出现次数都是 **0**。
真正要求"实现协议栈"的只有 2 条，且都是 30k+ 的 C/C++ 岗（见
`_opcua_jobmarket.md`，本决策引用其结论但不把它当唯一依据）。

### 3.2 寄存器地图（本项目自定，没有行业标准约束）

```
0..8        9 个测点，与设备层同布局同编码（uint16 大端，值 = round(真实值 × scale)）
9..99       保留（恒 0；留给以后扩展，这样不动 0..8 就永远兼容）
100-101     最近一次成功采集的时间戳（uint32 秒，高字在前；0 = 从未采到）
102-103     成功采集计数（uint32）
104         状态位 bit0=采集链路正常 bit1=MQTT在线 bit2=快照已陈旧
105         轮询周期 ×10       106 契约指纹低 16 位       107 陈旧门限 ×10
```

状态区放 100 起而不是紧接着 9：**给"以后要加测点"留出连续的 0..99 段**，
不必因为加一个测点就改变状态区的偏移（那会让所有上游配置失效）。

单点编码越界（设备回了脏数据）时写 `65535`（`REG_INVALID_MARKER`）。本项目所有测点
合法上限里的最大值是 Flow 的 65000（`scale=1`），所以 65535 一定撞不上真值 ——
有测试专门盯这条。**绝不回绕**：回绕出来的数看起来完全合法，是最难查的一类故障。

### 3.3 只读是真的只读

靠**数据块拒绝写入**实现（`_ReadOnlyBlock.setValues` 抛错 → pymodbus 转成 Modbus
异常响应），不是靠文档约定。本进程自己的刷新线程走另一个方法 `refresh()` ——
"谁能写"在代码结构上就写死了，不靠调用方自觉。

端到端测试会**真的发一个写请求并断言它失败**，而且写失败后要确认值没被改动。

### 3.4 陈旧语义：宁可标脏，不可装作正常

读设备失败时**不清零、也不回落**，而是保留上一次的成功值并把 `stale` 位置起
（与设备层 `RealDeviceReader` 的处置一致）。用 0 表达故障是本项目明令禁止的做法 ——
0 落在量程内，看不出错。

快照的时间戳**只在成功采集后**更新。这条听起来显然，但反过来做（每次循环都刷时间）
会让 `stale` 位永远不亮，等于把"读不到设备"伪装成"数据是新的"。有测试盯这条。

### 3.5 一个 pymodbus 地址语义的坑（实测记录）

`pymodbus 3.6` 的 `ModbusSlaveContext` 默认 `zero_mode=False`，`getValues`/`setValues`
都会把请求地址 **+1** 再落到数据块上（源码见 `getValues` 的 `if not self.zero_mode: address += 1`）。

- 设备层取 `zero_mode=False`，但它**写也走同一个上下文**
  （`context[slave].setValues(3, REG_BASE, values)`），读写同路 → +1 抵消 → 正确。
- 本模块的刷新线程直接落到**裸数据块**，只有"读"这一侧被 +1 → 实测客户端读到
  `[第2点, 第3点, …, 第9点, 0]`（整体错位一位，末位恒 0）。

实测矩阵（真起服务、真连、真读）：

| `zero_mode` | 刷新走哪条路 | 客户端读地址 0..8 |
|---|---|---|
| `False` | `context[slave].setValues()`（设备层走法） | 正确 |
| `False` | 裸块 `block.setValues()`（本模块原写法） | **`IllegalAddress`** |
| `True` | `context[slave].setValues()` | 正确 |
| `True` | 裸块 `block.setValues()` | 正确 |

结论：本模块用 `zero_mode=True`（请求地址与数据块下标一一对应）。
设备层**不需要改** —— 它的取法同样是正确的，只是机制不同。这一点在代码注释里写明了，
免得后来者看到两处不一致就"统一"掉其中一个。

### 3.6 默认关闭，且每实例一个端口

与 HJ212 北向出口同一条纪律：**新增对外接口不随默认部署一起打开**。
`UPSTREAM_MODBUS_ENABLE=0` 是默认值。

默认绑 `127.0.0.1`（与项目其余对外接口口径一致）；默认端口 5022
（设备层 5020、串口桥 5021，避开）。多实例部署时每个实例必须给不同端口 ——
`start()` 会先探端口，被占时返回 `False` 并打 CRITICAL，**不让网关退出**：
上游读不到是可降级能力，采集主链路不该被它拖死。

## 4. 决策二：心跳状态快照

**向后兼容是硬约束**：容器 healthcheck 判的是 `.gateway_alive` 的 **mtime**
（`time.time() - p.stat().st_mtime < 30`），与文件内容无关。所以内容从
`str(time.time())` 换成 JSON 不会破坏任何现有编排，有测试专门断言"换格式后 mtime 仍然新鲜"。

新增的内容（每次都写，文件很小）：

```
{"ts":…, "pid":…, "cfg":"<指纹>", "modbus_ok":…, "mqtt_ok":…,
 "backlog_bytes":…, "samples":…, "published":…, "cached":…,
 "read_failures":…, "modbus_reconnects":…}
```

**原子写**（临时文件 + `os.replace`）：读的人永远不会撞见写了一半的 JSON。
这条纪律与缓存文件的"原子改名交接"同源，有测试断言不留 `.tmp` 残留文件。

它解决的是原来那个洞：`mtime` 新鲜只证明"循环在转"，
`modbus_ok=false` 或 `cached` 持续增长才说明"在转但不出数"。

## 5. 决策三：契约指纹

### 5.1 指纹含什么、不含什么

参与指纹的字段：`name` / `address` / `column` / `low` / `high` / `scale` / `dtype` / `endian`
——即**决定"这个数字是什么"**的那些。

**故意不含** `unit` / `code` / `limit`：它们不改变数值含义，改它们不该让全部历史数据
变成"另一版契约"。（`limit` 变化影响的是**告警口径**，而告警事件表已经单独存了
`judge_version`，两者各管各的。）三条性质都有测试盯着。

用 `sha256` 而不是内置 `hash()`：内置 `hash` 对 `str` 带进程级随机盐，
跨进程、跨容器不可比 —— 那恰好毁掉本函数唯一的用途。

### 5.2 接入层只记不拦

指纹不一致时打一条 ERROR + `STATS["cfg_mismatch"] += 1`，**但不拒收数据**。理由：

- 不一致不等于这条数据不能用（比如只改了 `unit`）；
- 拦掉会把"配置没对齐"升级成"数据断了"——**那比漂移本身更糟**。

告警只打第一次，之后靠计数体现规模，免得一次部署错刷满日志。
报文里没有 `Cfg=`（老网关未升级）时也提示一次，否则"没人发指纹"会被误读成"契约一致"。

字段放在报文**末尾**：前两个字段是时间戳、位置固定；附加字段一律后缀，
这样按位置切分的既有调用方（`scripts/loadgen_devices.py` 用 `build_payload(values)[20:]`）
不受影响。

## 6. 代价与边界（要主动说出来的部分）

| 代价 / 边界 | 说明 |
|---|---|
| **多了一个监听端口** | 默认关闭 + 默认绑 127.0.0.1 已把暴露面压到最小，但它确实是一个新的对外服务 |
| **内存增量未实测** | 新增一个服务线程 + 数据块。网关原占用 22~27 MiB，128 MiB 额度下大概率有余量，但**本 ADR 没有实测数据**（Docker 未运行）——见 §7 |
| **直读没有补传语义** | 上游读的是"当前快照"。它错过了某个值就拿不到了 —— 这**与 HJ212 路线 A 的"有补传"本质不同**。想要一条不丢仍然只能走 MQTT 入库 + 对账那条路 |
| **直读没有历史** | 只有"最近一次成功采集"。要历史/统计必须查库（那是 ADR-0006 路线 B 的地盘） |
| **状态区地图是本项目自定** | 100 起、uint32 高字在前、位定义，都没有行业标准依据；它是"本项目与上游之间的约定"，换上游要重新对齐 |
| **报文变长** | 每条多 ` Cfg=xxxxxxxx`（14 字节），对 5 秒一条的量级无影响 |
| **没做 OPC UA** | 见 §3.1。角色已补，协议可后换 |

## 7. 诚实清单（没做 / 没验的）

1. **内存增量没有实测**。测试证明了功能正确，但"起了这个服务后网关内存涨多少"
   没有数字。要在 Docker 起来后补一次 `docker stats` 对照。
2. **没有真 SCADA 对读**。端到端测试用的是 `pymodbus` 客户端，不是 UaExpert /
   Kepware / 真实 SCADA。协议层正确性有保证，"现场系统能不能配通"没有验证。
3. **只读拒绝的实测边界**：测的是 FC06（写单个保持寄存器）。FC05 / FC15 / FC16
   走的是别的数据块（co / hr），行为是否一致**未逐条验证**。
4. **上游直读没有纳入验收脚本**。`scripts/acceptance_min.py` 的 25 项判据不含它
   （默认关闭的能力不进默认验收）。
5. **契约指纹只覆盖测点契约**，不覆盖库表结构、告警阈值、协议参数 —— 那几类各自
   有别的版本标识（如 `judge_version`）。
6. **`Cfg` 没有落库**。它目前只用于"网关 ↔ 接入层"的实时比对与日志，
   **没有写进时序库的列**。也就是说：事后想查"这段历史数据是哪版契约采的"仍然查不到，
   只能在采的时候发现不一致。要做到可事后追溯需要加列 + schema 迁移，本次没做。

## 8. 备选方案与为什么没选

| 方案 | 为什么不选 |
|---|---|
| 直接做 OPC UA server | 角色对但代价大（地址空间/会话/订阅/证书）；且外部取证显示 JD 期待的是"会用"不是"会实现"。先把角色用最便宜的协议补上 |
| 让上游订阅 MQTT | 要求上游懂 MQTT + 本项目报文体，耦合方向反了（上游被要求适配我的格式） |
| 给网关加一个 HTTP/JSON 只读接口 | 更简单，但 HTTP 不是现场 SCADA 的通行取数方式；且项目已有一个 HTTP 出口（北向 HTTP-JSON），职责会混 |
| 心跳继续只写时间戳，状态另开一个文件 | 多一个文件就多一处"要么一起写要么不一致"的可能；content 换成 JSON 零成本且向后兼容 |
| 契约不一致时拒收数据 | 把配置问题升级成数据中断，比漂移本身更糟（见 §5.2） |
| 用内置 `hash()` 算指纹 | 带进程级随机盐，跨容器不可比，等于没有 |

| 项 | 结果 |
|---|---|
| 新增单测 | `tests/gateway/test_upstream_and_heartbeat.py`，**24 条**（含 2 条真 socket 端到端） |

## 10. 影响面

- **不改**：采集主链路、MQTT 报文的既有字段、入库路径、告警判据、既有 583 条测试的行为。
- **新增**：1 个模块、3 个配置项（+1 可选）、`Cfg=` 后缀字段、心跳文件内容格式、1 个统计项
  `STATS["cfg_mismatch"]`。
- **默认关**：上游直读不改变任何默认部署的行为。
