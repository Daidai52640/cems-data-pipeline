## 1. 背景：现状是"一处不合格 → 整条拒收"

`src/platform/subscriber_to_td.py` 的 `parse_payload` docstring 原文：

> 每个测点都要过两关：先 `math.isfinite`（挡 NaN/inf），再比量程白名单（挡负数、超量程）。
> 任一测点不合格就整条拒收 —— 因为 NaN/inf 会让 TDengine 报 syntax error，
> 整行连其余正常测点一起丢，不如提前拦下。

**这条规则当初是对的** —— 因为它要挡的是两种不同的"坏"，而其中只有一种真的写不进去：

| 坏法 | 例子 | 能不能只丢它一个？ |
|---|---|---|
| 语法坏 | `NaN` / `inf` → TDengine 直接报语法错误 | 不能 —— 整行写不进去 |
| 语义坏 | `Temp=301.0` 超量程 —— 它是个合法的数，只是不可信 | 能 —— 其余列照常写 |

而这条 docstring 把两个理由写在同一句里：
"语法坏必须整条拒收"这个正确的理由，顺带把"语义坏"也拉进了整条拒收。

## 2. 问题：真机接入让它从"简化"变成"缺陷"

### 2.1 事实：这是一个有名字的已知工程问题

**故障不隔离 / 单点故障扩散**。工业网关厂商 HMS（Ewon）把它写进了官方文档：

> "a single tag in error (truly bad) can cause a number of other (good) tags to appear in error as well
> because, for communication optimization purposes, tag requests and responses are grouped in one single exchange.
> The whole group is then affected with the same error status."
> —— <https://support.hms-networks.com/hc/en-us/articles/7502870918418-How-to-isolate-truly-bad-Tags-from-the-others>

**根因与本项目一致**：为了效率把多个测点打包成一次交换，于是一个坏点污染整组。

### 2.2 事实：成熟体系都是"逐点"

| 体系 | 机制 |
|---|---|
| **OPC UA** | 每个值自带 `StatusCode`（Good / Bad / Uncertain + 子状态）—— <https://reference.opcfoundation.org/Core/Part4/v104/docs/7.34> |
| **西门子 WinCC** | 质量码逐 Tag 映射到 OPC UA StatusCode |
| **《排污单位自动监测数据标记规则》**（生态环境部） | 每个参数一个数据标记：`N` 正常运行 / `D` 故障 / `C` 校准 / `M` 维护 / `T` 调试 |
| **HMS Ewon** | 坏点自动停止轮询 → 不再进组 → 不影响其他点；并写事件日志留痕（"Polling disabled for this tag"） |
| **时序库侧** | <https://vaex.io/docs/guides/missing_or_invalid_data.html> 明确要求区分 missing 与 invalid |

### 2.3 本项目的暴露面

| # | 事实 |
|---|---|
| 1 | `gateway.py` 的 `build_payload` 硬编码 `Flag=N` —— 整条一个标记，与 HJ 212 的"每参数一个"不同构 |
| 2 | `points.py` 明确写"本项目不是 HJ 212 报文"（内部简化格式） |
| 3 | ADR-0007 把"数据标记 `D/C/M/T` 的判定源（本项目无仪表状态源）"登记为南向扩项 |
| 4 | 仿真器里从没有"某一点可能是坏的"这个需求 —— 真机接进来才第一次产生它 |

## 3. 决策一：按"坏法"分两条路

| 坏法 | 判定 | 处理 |
|---|---|---|
| 语法坏 | 时间戳不可解析 / 报文长度不足 / 一个测点都没有 | 整条拒收（保持现状）—— 真的写不进去 |
| 语义坏 | 单点 `NaN` / `inf` / 超量程 | 只丢该点，其余照常入库 |

**备选**
- (a) 保持整条拒收，只把坏点写进日志 → 日志不可查、不可统计，且其他点仍然丢
- (b) 主表加一列 `invalid_points`（逗号分隔点名）→ 可行但不好查（要 `LIKE`），且丢掉"原因"与"原始值"
- **(c) 独立无效点事件表** → 选它
- (d) 把无效点写成哨兵值 `9999.99` 入库 → 哨兵是传输语义（HJ 212-2025 §8.1.1 d），
  塞进入库列会让项目既有的"算归算、传归传"失守

---

## 4. 决策二："无效"必须与"缺失"可区分

**这是本 ADR 最关键的一条。**

逐点丢之后，那一列在库里是 `NULL` —— 而"这一分钟没采到"也是 `NULL`。
若到此为止，就是把整条静默换成了单点静默：

| 后果 | 说明 |
|---|---|
| 故障归因做不了 | 分不清"网络断"、"设备死"、"数据被判无效" |
| 覆盖率失真 | 无效被丢后看起来就是"缺数"，与真断线无区别 |
| 达标判定被误导 | 超标数据因"超量程"被丢掉 = 把超标藏起来 |

**所以必须同时提供"逐点留痕"。**

### 4.1 新增无效点事件表

| 列 | 含义 |
|---|---|
| `ts` | 报文时间戳 |
| `plant` / `device` | 标签（同主表口径） |
| `kind` | `invalid`（有值但不可信）/ `missing`（报文里根本没这个点）—— 见 §10 |
| `point` | 测点名 |
| `reason` | 原因（例：`超出量程 [0.0, 300.0]: 301.0` / `报文未提供`） |
| `raw` | 原始值（保留证据；`missing` 时为 `NULL`） |

- 表名由 env 覆盖，默认 `cems_point_invalid`（照 `ALARM_EVENT_STABLE` 的既有写法）
- 它不参与达标判定，只是证据层
- 它不进主表，也不加列到主表 —— 主表列布局保持不动（既有报表/导出不受影响）

### 4.2 与达标判定 / 覆盖率的关系

- **覆盖率**：无效样本计入"不可用"（它确实不能用于判定）
- **但归因可区分**：查 `cems_point_invalid` 就能说出"哪一分钟、哪个点、为什么"
- **小时结算的"样本不足"门限**是既有机制，不改

## 5. 决策三：`Flag` 字段不动

- `Flag=N` 保持硬编码（本项目 `Flag` 本来无语义）
- 逐点质量信息落在事件表，不塞进 `Flag`
- 若将来接 HJ 212 北向出口，`Flag` 的逐参数语义需另有 ADR（属 ADR-0006 的 P3 范围）

## 6. 落点设计（实现层面）

### 6.1 `parse_payload` 返回值

```
parse_payload(text) -> (timestamp, values, invalid)
#                      ^时间戳   ^有效测点(名→值)  ^无效测点(名→原因)
```

- 语义坏不再 raise；只有语法坏才 raise
  → 调用方原有的"整条拒收"分支只服务语法坏，语义因此变窄但不消失
- `reason` 是给人看的字符串（进日志与事件表）

### 6.2 入库：按有效测点动态构造列

```sql
INSERT INTO {child} USING {stable} TAGS(...) (ts, c1, c3, ...) VALUES (...)
```

前置检查已实测通过（2026-10-11，TDengine 3.3.6.13）：

```sql
CREATE STABLE probe (ts TIMESTAMP, a FLOAT, b FLOAT, c FLOAT) TAGS (plant NCHAR(16), device NCHAR(16));
INSERT INTO pt1 USING probe TAGS ('p1','d1') VALUES (NOW, 1.1, 2.2, 3.3);              -- 全列
INSERT INTO pt1 USING probe TAGS ('p1','d1') (ts, a, c) VALUES (NOW+1s, 4.4, 6.6);     -- 部分列
```

读回结果：
```
           ts            |   a  |   b  |   c
 2026-10-11 15:53:35.759 |  1.1 |  2.2 |  3.3
 2026-10-11 15:53:37.067 |  4.4 | NULL |  6.6     ← 省略的列真的是 NULL
```

这次实测同时坐实了 §4 的担忧：省略的列就是 `NULL`，与"这一分钟没采到"完全不可区分 ——
所以 §4 的无效点事件表不是可选增强，是本方案能成立的前提。

## 9. 局限与不做（单列）

- **传感器漂移失准**、**超量程的真实物理量**、**MQTT 伪造报文**、**时钟错乱** —— 本 ADR 不覆盖
- **`Flag` 的逐参数语义** —— 不做（需与 ADR-0006 的 P3 出口一起考虑）
- **无效点的重传 / 补救** —— 不做：无效就是无效，不补
- **事件表在高频无效场景下的写入放大** —— 未实测；若某台设备长期无效，需要限流或聚合。本期不做，登记为已知边界
- TDengine 部分列 INSERT 与 `USING/TAGS` 共存 —— 已实测通过（见 §6.2）
- 本 ADR 尚未实现，因此 §8 的判据全部未经实测

## 10. 评审补充（2026-10-11 · 补测试时实测到的现状）

**背景**：实施本 ADR 之前，先给 `src/platform/subscriber_to_td.py` 的纯函数补了单元测试
（116 条，提交 `bd80a51`；依据见 `docs/架构与可维护性说明.md` §四 2-1）。
测试把现状钉桩的过程中，实测到 6 处与原判断不符的行为 ——
其中 2 处（#3、#6）改变了本 ADR 的实现步骤。

| # | 实测现状 | 对本 ADR 的影响 |
|---|---|---|
| **1** | 缺测点也走整条拒收，且该检查在最后 —— 坏点与缺点并存时只报一个原因（一条报文只报一个） | 需明确归类：§3 只写了"一个测点都没有 = 语法坏"，没写"缺其中几个"。→ 决策见 §10.1 |
| **2** | `parse_timestamp` 接受非补零格式（`2026-9-1 1:00:00`） | 无害的宽容，保持；已钉进测试 |
| **3** | `TdWriter._insert` 假设整行齐全 —— 缺点即 `KeyError` | 实现必须从它开始，见 §10.2。原 §6.2 只写了 SQL 形状，漏了这一步 |
| **4** | 重复测点静默"后者覆盖" | 报文自相矛盾 → 决策见 §10.1 |
| **5** | 非测点字段的值完全不校验（如 `Flag=XYZ`） | 无害（本来就忽略），保持 |
| **6** | `STATS["rejected"]` 按"条"计数 | 逐点化后该指标失真（1 个坏点算 1 条拒收，9 个坏点也算 1 条）→ 必须拆，见 §10.3 |

### 10.1 决策补充：报文里"点的有无"与"重复"怎么归类

| 情况 | 归类 | 理由 |
|---|---|---|
| 一个测点都没有 | 语法坏 → 整条拒收 | 没有可写的列，报文无意义（§3 原有） |
| 缺其中几个测点 | 语义坏 → 该点记 `kind='missing'`，其余照常入库 | 与"超量程"一样是单点问题；若判整条坏，就把单点问题又放大成整条 |
| 同一个点出现两次 | 语法坏 → 整条拒收 | 不是数据质量问题，是报文格式问题 —— 同一个点有两个值，采信哪个都是猜 |

`kind='missing'` 与 `kind='invalid'` 必须分开：
前者是"网关没给"，后者是"给了但不可信" —— 两者的处置可能不同
（前者可能是网关读不到该寄存器，根因在采集侧；后者在数据侧）。

### 10.2 实现顺序修订：先改 `_insert`，再改 `parse_payload`

原 §6.2 只写了"按有效测点动态构造列"。实测发现 `TdWriter._insert` 目前假设整行齐全
（缺列直接 `KeyError`）—— 所以实现步骤修订为：

1. **先改 `_insert`**：支持"传入哪几列就写哪几列"（TDengine 部分列已实测可行，见 §6.2）
2. **再改 `parse_payload`**：返回 `(ts, values, invalid)`
3. **再加事件表**（建表 + 写入 + `kind` 列）
4. **最后改 `on_message`**：串起来 + 计数拆分（§10.3）

**顺序不能反**：先改 `parse_payload` 而 `_insert` 仍要求整行齐全 → 运行时 `KeyError`。

### 10.3 计数修订：`rejected` 必须拆成两个

| 原 | 修订后 | 含义 |
|---|---|---|
| `STATS["rejected"]` | `STATS["rejected_messages"]` | 语法坏丢掉的报文条数 |
| — | `STATS["invalid_points"]` | 语义坏丢掉的测点个数 |

**理由**：逐点化之后，"拒收"有两个粒度。
若继续只有一个按"条"计的指标，看不出一台设备是"整条不通"还是"偶尔一个点坏" —— 又是一种静默。

### 10.4 测试衔接

`tests/platform/test_subscriber_pure.py` 里所有 `current_behavior_*` 用例
（含 `test_current_behavior_one_bad_point_rejects_whole_payload`、`test_on_message_current_behavior_*`）
钉的正是本 ADR 要改掉的行为 —— 实现时必须逐个有意识地改写或删除，
不许为了让测试变绿而绕过它们。

### 11.3 实现时补做的 4 处裁决（ADR 原文未规定）

| # | 问题 | 裁决 | 理由 |
|---|---|---|---|
| **1** | 测点值不是数（`SO2=abc`） | 语法坏 → 整条拒收 | 契约是「`名字=数值`」。`abc` 不是"合法但不可信的数值"，而是不符合报文格式；且 `PointInvalid.raw: float \| None` 表达不了它 |
| **2** | 9 个测点全无效 | 只留痕、不写主表、不落盘 | 没有可写的列；落盘会永久堵塞队列 —— 一条永远写不进库的报文会被反复重试 |
| **3** | `point` 未做成 TAG → 改用按点子表 | 采纳，见 §11.4 | 见下 |
| **4** | 帧不齐（缺 `O2` 或任一污染物） | 跳过折算与告警，但该条仍入库 | 缺了折算必需的输入就没法算；但其余测点的数据不该因此丢 —— 与本 ADR 同一精神 |

### 11.4 对 §4.1 的唯一偏离：事件表按测点分子表

**原写法**：`TAGS = (plant, device)`，`point` 作普通列。
**实现**：`point` 参与子表命名（`plant1_device1_invalid_dust`），同时保留 `point` 列。

**为什么必须偏离**：TDengine 的子表主键是 `(子表, ts)`。
若 `point` 只是普通列，同一条报文里两个测点同时无效 → 两行 `ts` 相同 → 互相覆盖，丢掉一条证据。
而"同一报文多点无效"恰恰是本 ADR 要覆盖的常见场景（例如整帧被干扰）。

**效果等价于"把 `point` 做成 TAG"**（TDengine 里 tag 组合就是子表划分），
只是显式落在子表名上；`WHERE point='Dust'` 仍然可用。
**代价**：每个 (设备, 测点) 一张子表 → 9 个测点 × N 台设备 = 9N 张 —— 已登记为取舍，未做压力测试。
