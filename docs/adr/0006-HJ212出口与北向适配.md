# ADR-0006：HJ212 出口与北向适配层（定位、边界与分期）

- **状态**：已定（方案阶段；实现分 P1~P5）
- **日期**：2026-10-02
- **关联**：`docs/RELEASE-v2.0.0-地基冻结.md`（地基已冻结）、`docs/adr/0003-补传入队判定修正.md`（网关补传）

---

## 0. 结论速览

| 决策 | 内容 |
|---|---|
| **做什么** | 在地基之外**新增 HJ212 出口**：`网关 → [HJ212 适配] → 环保平台`（实时分支） |
| **不做什么** | 不改主链路；不做 SM4 密钥管理闭环；**不做**补传优先级重排（§8.1.2） |
| **分期** | P1 编解码 → P2 SM4 → P3 出口与传输 → P4 本地回环 → P5 第二协议与抽象接口 |
| **定位** | ⚠️ **预留能力 / 可对接**，**不是"已对接环保平台"** |
| **依据** | HJ 212-2025 官方 PDF 一手取证（见 §5，含 SHA256 与页号） |

## 1. 背景与问题

### 1.1 现状（地基 v2.0.0 的事实）

```
【南向·已有】设备 ──Modbus──► 网关 ──MQTT──► 入库 ──► Web
【北向·已有】只有 MQTT 内部格式 + CSV/Excel 导出
```

- 实际报文体是**内部简化格式**：`"2026-10-02 14:36:41 Flow=33471.0 … Flag=N"`（走 MQTT）
- ⚠️ **不是 HJ 212 通信包**；`Flag=N` 既不是标准的 `Flag`（整数 0-255 位标志）也不是 `RF`

### 1.2 要解决的问题

**项目不该是一个封闭的私人玩具**：真实 CEMS 现场，数采仪必须能**对接环保平台**。
现状缺失的不是"数据"，而是**对上报的协议出口**。

**⭐ 而且这条能力在真实产品里是标配**——两家厂商资料原文：
- "支持 HJ212-2025 等国标协议…能同时对接 **8 路平台**，国发平台和省市区各级环保平台都能同步上传"
- "独有的**「一点多发」**功能，可同时向 **8 个不同标准**的监控平台发送数据，让部、省、市、县各级监管同步无忧"

---

## 2. 定位：两条路线的区别（**先分清，否则边界说不清**）

| | **路线 A：网关侧实时分支**（本 ADR 做） | **路线 B：库侧统计出口**（后续） |
|---|---|---|
| 图 | `网关 ──► [HJ212 适配] ──► 环保平台` | `库 ──► [OPC UA / HTTP 适配] ──► DCS/MES、上层系统` |
| 数据源 | 网关**直采**（`read_device()`） | **已入库**的数据 |
| 时延 | 秒级 | 入库后（本机端到端 P50 约 0.58 s，相对上报周期可接受） |
| **补传能力** | ✅ **有**（复用网关缓存 + 原子交接） | ❌ **无**（源头没有就是没有） |
| 适合 | **实时数据上报**（`CN=2011`） | **统计/历史/报表类**（分钟、小时、日数据） |
| 现实对应 | 数采仪「一点多发」 | 平台定时任务查库后上报 |

**⭐ 为什么 HJ212 必须走 A：**
1. 标准把上报主体定义为**"现场机"**（§8.1.1 a 要求现场机**直接连接一次仪表**）——走 B 不是标准形态
2. **`RF` 补传标志、断点续传**这些语义只在采集中间段才有意义（B 侧无从判断"这条是不是补传"）
3. 环保平台最看重"**数据一条不丢**"，而这正是网关缓存已经证明能做到的（实测补传 100%）

**⭐ 为什么 B 仍然值得做**：统计类数据本来就是"从库里算出来的"，`report.py` 的聚合与覆盖率标记可直接复用。

### 2.1 分层结论（**分层的依据是"数据源"，不是"协议"**）

```
A 实时源（网关 read_device + 缓存）──► [HJ212 适配 + SM4] ──► 环保平台
B 历史源（TDengine 查询 + 聚合）  ──► [OPC UA 适配] ──► DCS/MES
                                  ──► [HTTP/REST 适配] ──► 上层系统
                                  ──► [CSV/Excel] ──► 人工报表      ← 已有，不重做
```

**⚠️ A 与 B 不合并**：两者**可用性语义不同**（一个能补传、一个不能），强行统一会掩盖这个差别。

## 3. ⚠️ 边界：明确不做什么（防止过度声明，这是本 ADR 最重要的部分）

| # | 不做 | 理由 |
|---|---|---|
| **1** | ❌ **不改主链路** | 地基 v2.0.0 已冻结。MQTT + 内部简化报文体**照跑**，HJ212 是**并列的第二出口** |
| **2** | ❌ **不实现 SM4 密钥管理闭环** | §6.4.3 要求"初始密钥**在生态环境部的上位机注册**、90 日轮换、向前获取新密钥" → **必须有部里上位机配合，客观不具备条件**。**做到"加解密 + 用国标公开示例验证"，密钥管理只做设计说明** |
| **3** | ❌ **不声称"已对接环保平台"** | 没有真实接收方。定位是**"能生成、能自校验、能本地回环"**的接口层 |
| **4** | ❌ **不实现分包（`PNUM`/`PNO`）闭环** | 本项目 9 测点报文约 150~300 字符，远低于 `CP` 上限 950 → **只预留结构** |
| **5** | ❌ **不做补传优先级重排（§8.1.2）** | 见 §4，**评估后决定不做** |
| **6** | ❌ **不做多仪器仪表规约库** | 那是**南向（对下采集）**的事（厂商"千种规约"指这个）；本项目只有 Modbus 仿真设备，**没有真实仪表协议可适配** |

## 4. 有意偏离：§8.1.2「优先保障新采集的数据上传」**不做**

**条文原文**（PDF 第 25 页）：
> "数据上传失败时，现场机应自动补传，数据补传时应合理分配网络带宽，**优先保障新采集的数据上传**，数据段超 1 024 个字符时应分包传输。"

**评估结论：本项目【实质满足】，不为此改代码。** 理由（三条，均为实测或代码事实）：

| # | 理由 |
|---|---|
| **1** | **主循环在线时本来就走直发**：`gateway.py` L551-564，仅"补传批次在途"那一轮才入队 → **新采集的数据本身就是优先的** |
| **2** | **不存在带宽竞争**：故障 2 实测——停 EMQX **11 分钟积压 128 条**，恢复后 `[补传完成] broker 已确认 128 条`，**排空耗时 < 1 秒** |
| **3** | **不可能饿死**：`_take_over_pending()` 是**整文件接管**（`os.replace`），每一行都进本批并排空 → 没有任何行被永久延后 |

**⚠️ 反过来，真去实现"优先新数据"会引入风险**：要满足它必须让积压**延后**，
于是才产生"老数据饿死"的可能，才需要再写公平算法/带宽预算去防——**为不存在的问题引入复杂度。**

**→ 决策：不改。** 若将来在大积压（数十万行）场景下实测出问题，再单独评估。

**取证件**：生态环境部官网正式电子版 PDF
`https://www.mee.gov.cn/ywgz/fgbz/bz/bzwb/jcffbz/202507/W020250711505311328432.pdf`

| 项 | 值 |
|---|---|
| 页数 | **92 页** |
| 大小 | 5.57 MB |
| **PDF SHA256** | `ED5E46FC1CF5DC99ACE6878A5D347F4C0269B818052F3774C9708CF60A74E506` |

### 5.1 通信包结构（§6.3.3 表 3，PDF 第 9 页）
```
##0255QN=20240601085857223;ST=32;CN=2011;PW=123456;MN=010000A8900016F000169DC0;
Flag=9;CP=&&&&2200\r\n
```
| 字段 | 规定 |
|---|---|
| 包头/包尾 | `##` … `\r\n` |
| 数据段长度 | **十进制整数 4 位**（长 255 写作 `0255`） |
| `QN` `ST` `CN` `PW` `MN` | 请求编码(20) / 系统编码(5) / 命令编码(7) / 密码(9) / 数采仪入网编码(24) |
| **`Flag`** | **整数（0-255）**：V5~V0 标准版本号；A 是否含包号总包数；D 命令是否应答。<br>示例：`Flag=9` = `00001001` → 本次修订版 + 需应答 + 不拆包 |
| `PNUM` `PNO` | 总包数(6) / 包号(5)，**不分包时无本字段** |
| **`RF`** | **字符 4**：`RF=1` 标志该报文属于补传报文；**非补传时，无本字段** |
| `CP` | 指令参数，**字符 [0, 950]**，`CP=&&数据区&&` |

### 5.2 加密（§6.4，PDF 第 13 页）
> §6.4.1："使用**互联网**传输数据时，**应**加密传输；使用各类**专网**传输数据时，**宜**加密传输…"
> §6.4.2："采用 **SM4** 加密算法，16 字节（128 位）密钥，工作模式 **ECB**，填充 **Nopadding**，对数据段 `CP=&&` 到 `&&CRC校验码` 之间的字符加密"
> §6.4.4："现场机向上位机发送的数据命令应加密（**命令编码 2000～2999**）…其他命令无须加密"
> 附录 A.2："数据段加密时，每 16 个字符为一组加密…**先完成 CRC 校验并组包，再对数据段加密**"

**⭐ 提取三条实现约束**：
1. **加密顺序不可反**：**先算 CRC、再加密**
2. **`CN=2011` 落在 2000~2999 → 实时数据上传需加密**
3. **加密可按传输介质开关**（专网"宜"、公网"应"）→ 正好对应"不同平台不同要求"

### 5.3 CRC（附录 A，PDF 第 31 页）
> "本标准采用 **ANSI CRC16**"

## 6. 分期规划

### 原则：**先有实现，再抽象接口**
⚠️ 最忌讳"先设计通用协议适配框架再往里填"——**只有一个实现时抽象出来的接口一定是错的**。
**→ 先做 HJ212，再做第二个（HTTP/REST），然后从两个真实实现里提炼公共接口。**

| 阶段 | 内容 | 依赖 | 工作量 | 风险 | 可验证性 |
|---|---|---|---|---|---|
| **P1** | **HJ212 编解码**（包头/长度/数据段/ANSI CRC16/`Flag` 位掩码）+ **官方向量单测** | 无 | 半天 | 🟢 **零**（纯新增） | ⭐ **有官方示例当黄金向量** |
| **P2** | **SM4 加解密层**（用 `gmssl`；**附录 A.2 的 4 组公开向量**，密钥公开 `16 个 0x30`） | P1 | 1~2 h | 🟢 零 | ⭐ 官方向量 |
| **P3** | **HJ212 出口 + TCP 传输 + 独立缓存与补传** | P1、P2 | 半天~1 天 | 🟡 **中**（唯一碰主链路的阶段）→ **必须先出方案 + 硬门禁** | 复用故障 2/3 的积压场景 |
| **P4** | **本地回环上位机**（生成↔解析端到端） | P3 | 2~3 h | 🟢 零 | 端到端跑通 = "有对接方" |
| **P5** | **第二个协议（HTTP/REST）+ 提炼北向适配接口** | P4 | 半天 | 🟢 低 | 抽象有依据（两个实现） |

### ⚠️ P3 的两条硬约束（**从地基的实测教训来**）
1. **出口必须独立线程 + 独立队列**——主循环里 `read_device` 只有 0.08 ms，而取批 prologue 要 10.45 ms
   （ADR-0003 实测：判定点必然落在在途窗口内）。**同步阻塞发送会让平台慢/断时拖住采集。**
2. **HJ212 出口必须有自己的缓存与补传**——**否则一旦平台断，这一路数据就丢**，
   **而"补传"恰恰是环保平台最看重的**（比不做这个接口更糟）。
   ⚠️ **不能与 MQTT 分支共用缓存文件**（两路会互相干扰），**需独立一套**（复用同一模式）。

### ⭐ 附带产出：原子交接回归测试（**与标准无关，但价值高**）
**背景**：网关那套防丢数据的**原子改名交接**（`cache.jsonl` ↔ `.sending`）目前**只有间接证据**
（故障 2/3 的补传 100%），**没有独立回归测试**。而 P3 会动到网关，**改之前必须先有这道防线**。

**测试设计要点**（离线、确定性、零风险）：
- **不变量**：取批只是排列 / 两文件并存且新数据只进 `cache.jsonl` / 收尾后期间新采数据一条不少 /
  条数守恒 / **回写失败仍保留 `.sending`** / 多窗滚动回写正确
- **做法**：import 网关模块 + 路径指向 `TemporaryDirectory` + **stub MQTT 客户端**（无网络无 broker）；
  `RESEND_WINDOW=3` 造多窗；**在第 k 次 publish 的 hook 里调 `save_to_cache()`**，
  确定性复现"补传中主循环同时写 `cache.jsonl`"
- **重点断言**：**P1「排序只是排列」**（规范化键做多重集相等）、P5 回写失败→`.sending` 逐字不变、
  **P6 每窗后 `.sending` == `remaining` + 未发尾部**、P7 临时目录 < 1 MB 且断言生产文件 size/mtime 未变
  （**遵守故障 4 的教训：不在宿主机写大量数据**）
- **输入**：报文取 `docs/evidence/drill/resend_snapshot_drill2.txt`（与真实报文逐字一致）

## 8. 已知局限 / 待确认

| # | 项 |
|---|---|
| 1 | ⚠️ **无真实接收方**：P1~P4 的验证靠"官方向量 + 本地回环 + 开源实现对拍"，**不等于现场验证** |
| 2 | ⚠️ **省/市/企业的具体差异无法逐条查证**：各厂商扩展字段、地方补充要求不在国标里 → Profile 只能做"结构上支持配置"，**不能声称"适配了某省"** |

| 4 | ⚠️ **SM4 用第三方库**（`gmssl`）：库的维护状态、与 ECB/Nopadding 的兼容性**未实测** |
| 5 | ⚠️ **"南向多仪器规约"不在本 ADR 范围**（厂商"千种规约"指这个方向） |
