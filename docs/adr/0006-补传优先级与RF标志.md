### 1.2 §8.1.2 大气污染源自动监测数据上传要求（PDF 第 25 页，页眉页码 22）

**原文（表 15 前的段落，逐字摘录）**：

**要点拆成三条可验收的要求**：

| # | 要求 | 本项目现状 | 判定 |
|---|---|---|---|
| R1 | 上传失败时**自动补传** | 断网缓存 + 重连触发补传；两次演练成功率 **100 %（35/35）**（[性能与可靠性指标](../reference/性能与可靠性指标.md) §5.2/§5.4） | **满足** |
| R2 | 补传时**合理分配网络带宽**、**优先保障新采集的数据上传** | 补传批次在途时，主循环把本轮实时样本**直接写缓存**（`gateway.py` L551-564 的 `else: save_to_cache(reason="补传中")`）→ "新采集的数据"在补传期间**不进入发送路径** | **不一致**（缺口 1） |
| R3 | 数据段超 1024 字符**应分包传输** | 实测单条报文 **127 字符**（35 行演练快照全部为 127；网关入队日志样本最大 146，**测量命令见附录 A**），加 `RF=1` 后仍远低于 1024 | **不触发**（需在文档中记录阈值与实测值，避免以后报文变长后无人发现） |

**同一条要求在水污染源一节重复出现**：`§8.2.2 水污染源自动监测数据上传要求`（PDF 第 28 页）原文为
"水污染源监测数据上传要求见表 17。数据上传失败时，**现场端**应自动补传，数据补传时应合理分配网络带宽，

说明这是**通用**要求而非废气专条。

### 1.3 §6.3.3 表 3 数据段结构组成表（PDF 第 9 页，页眉页码 6）

**表 3 中 `RF` 行原文（逐字摘录）**：

> 补传标志　RF　字符　4　`RF=1`，标志数据报文属于补传报文；非补传时，无本字段。

**同一张表里的上下文（同一页）**：

| 名称 | 类型 | 长度 | 描述（原文要点） |
|---|---|---|---|
| `Flag` | 整数（0-255） | [6, 8] | "标志位包含标准版本号、是否拆分包、数据是否应答。包括 V5、V4、V3、V2、V1、V0、A、D"。示例："`Flag=9` 的二进制编码 00001001，表示版本号为本次修订，需要应答且数据段不包含拆分包" |
| `PNUM` / `PNO` | 字符 | 6 / 5 | 总包数 / 包号；不分包时无本字段 |
| `RF` | 字符 | 4 | 见上 |
| `CP` | 字符 | [0, 950] | `CP=&&数据区&&`，数据区定义见 6.3.4 |

同页还有两条与本设计直接相关的结构约束：

- 6.3.3 引言："数据段结构组成见表 3，表 3 中'长度'包含字段名称、半角'='、字段内容三部分内容"
  → `RF` 的"长度 4"即字符串 `RF=1`；**标准只定义了 `RF=1` 一个取值**。
- 表 2（通信包结构组成）："数据段｜字符｜[0, 1024]｜变长的数据"；包头固定 `##`、CRC 4 位、包尾固定 `<CR><LF>`。
- 图 4（通信协议数据结构示意图）把"总包数、包号、**补传标志**"画在**非必要内容**（虚线框）区，且顺序为
  `… 包号 PNO → 补传标志 RF → 指令参数 CP`。

**从条文推出的三条设计约束**：

| # | 条文 | 对本项目的约束 |
|---|---|---|
| C1 | "非补传时，无本字段" | 实时报文**不得**出现 `RF=0`；解析端必须把"缺字段"当**非补传**，而不是当错误 |
| C2 | 只有 `RF=1` 一个取值 | 解析端遇到 `RF=` 其他值时**不得拒收整条报文**（拒收会丢一条真实监测数据），按非补传处理并告警即可 |
| C3 | RF 位于"包号之后、`CP` 之前"，且属非必要字段 | 本项目 MQTT 报文体**不是**标准通信包（见 §1.4），因此 RF 在报文里的**字节位置**只是"尽量贴近相对次序"的工程映射；解析端按 `key=value` 取值，位置无关。**若将来实现真正的 HJ 212 通信包，RF 必须落在数据段中 `CP` 之前** |

### 1.4 顺带核实：本项目的"报文"与标准的"通信包"不是一回事

| 维度 | 标准（HJ 212-2025 §6.3） | 本项目（MQTT payload） |
|---|---|---|
| 形态 | `##` + 数据段长度 + 数据段 + CRC + `<CR><LF>`，ASCII | 单行文本：`时间戳 + 9 个 key=value + Flag=N` |
| 字段 | `QN/ST/CN/PW/MN/Flag/PNUM/PNO/RF/CP` | 时间戳 + 9 个测点（`points.NAMES`）+ `Flag=N` |
| 传输 | 现场机 ↔ 上位机（TCP/串口等） | 网关 → EMQX → 订阅端（MQTT，QoS 1） |
| 与标准的关系 | 标准本身 | **本项目自定义的"报文体"**，测点顺序对齐 HJ 212 上传值序（`README.md` L21、`AGENTS.md` §1），但不是字节级实现 |

推论：本文所说的"加 RF 字段"是**在本项目自定义报文体里按标准语义加一个 `RF=1` 标记**，
不是"实现了 HJ 212 的补传标志字段"。这个区分必须写清，否则会把"语义对齐"误当成"协议合规"。

### 1.5 ⚠️ 顺带发现：现有 `Flag=N` 既不是标准的 `Flag`，也不是 `RF`

- 标准表 3 的 `Flag` 是**整数 0-255 的位标志**（版本号/拆分包/应答），长度 [6,8]，形如 `Flag=9`。
  本项目写的 `Flag=N` **不符合该字段的类型定义**。
- 我在全仓库检索确认：`Flag` **没有任何消费方**——`subscriber_to_td.parse_payload()` 明确跳过非测点字段
  （L168-169：`if not sep or key not in names: continue  # 跳过 Flag 等非测点字段`），
  除网关 `build_payload()`（L489）与 `scripts/probe_o2_unavailable_publish.py`（L73）**写出**它之外，
  没有任何代码**读取**它。项目文档里也没有对 `Flag=N` 语义的定义。

**结论与处置**：`Flag=N` 是一个**语义未定义、无消费方的装饰字段**（不是契约字段，改动它不会破坏任何现有行为）。
但本方案**仍然不动它**，理由是：把 `RF` 语义塞进一个名字已被标准占用、且本项目又用错了类型的字段，
会让"字段名 → 语义"的对应关系更难解释（改了以后 `Flag=N` 到底是标准的 Flag 还是本项目的补传标志？）。
**新增独立字段 `RF`，`Flag=N` 原样保留**。这一条作为"既有偏差"记录在案，**本次不处理**（改它属于报文契约变更，需单独评审）。

### 2.2 缺口 1 的准确画像（不是"排序错了"，是"实时流在补传期间不发送"）

按 §1.2 的 R2，"优先保障**新采集的数据**上传"里的"新采集的数据"= **主循环正在采的实时样本**，不是"积压里较新的那些"。

现状下，一批补传在途时（`RESEND_WORKER.running == True`，且该状态在主循环取快照时已成立）：

```
主循环（每 5.146 s 一圈）                    补传线程（一次 pass 处理整批）
────────────────────────────                ──────────────────────────────
resend_in_flight = True   ← 快照
read_device() → build_payload()
if connected and not resend_in_flight:  ← 假
elif not connected:                      ← 假
else: save_to_cache(reason="补传中")      ← ★ 实时样本只落盘，不发
                                            for 窗口 in 整批: 一次入队 ≤100 条 → 逐条等 PUBACK
```

**因此**：补传 pass 期间产生的实时样本**全部不进入发送路径**，只能等这个 pass 结束、下一轮
`_take_over_pending()` 把它们取走时才被发出。也就是说：

- broker 健康时影响可忽略：实测单条 QoS1 `publish→PUBACK` P50 **0.17 ms**（ADR-0003 §2.2 的容器内探针），
  且演练日志里 128 条批次的"开始补传"与"确认完成"**落在同一秒**（[故障台账](../runbooks/故障台账.md) 故障 2；
  性能文档 §5.3 的 54 条同形）——**这正是本项目"优先新数据"缺口的收益难以观测的原因**；
  ⚠️ 不要把"排空耗时"混进来：ADR-0003 §7.5 实测的 **109.9 s** 是"断开 → 队列归零"的**端到端**耗时，
  其中绝大部分是 paho 重连退避，**不是补传发送吞吐**（性能文档 §5.3 已做时间分解）；
- broker"连接在但变慢/挂死"时，pass 时长 = `条数 × PUBLISH_ACK_TIMEOUT`（100 条 = 500 s），
  这段时间里**所有实时样本都在排队**，"新采集的数据"被整批积压挡住——这是条文要禁止的情形。

> ⚠️ 顺手纠正任务描述里的一个假设：**"补传行会污染『当前浓度』"在当前代码里不成立**。
> `web_dashboard.query_recent()`（L149-153）是 `WHERE ts >= now - Nm AND ts <= now ORDER BY ts DESC LIMIT n`，
> 末尾那条就是 **最大 ts**；补传行携带的是**更旧的 ts**，不可能成为"当前值"。
> 补传行真正影响的是：① **窗口统计/曲线**（旧 ts 落进最近窗口，把该窗口的样本变密、均值偏移）；
> ② **按到达顺序的快照** `LAST_REFERENCE`（L391-401，注释写明是"最近一条**已成功入库**数据"，
> 补传批晚到会把快照**回退成更旧的值**）。这两条才是 RF 落地后值得处理的污染面，见 §4.5。

|---|---|
| 样本 | 349 条 = 直发 **291** + 补传 **58** |
| 按到达顺序检查 ts 单调性 | **逆序 58 条（16.6 %）**，**58/58 全部是补传行**（47 条 `resend` + 11 条 `resend+clock-jump`），`direct` 行 **0 条逆序** |
| 逆序深度 | 25 ~ 26 s ≈ 5 × 5.146 s（= `RESEND_RETRY_INTERVAL` 节流窗口内直发的 5 条越过了队列里的旧行，见 ADR-0003 §2.3） |

**结论**：全局严格 FIFO 早已不成立；"旧数据按序先送达"只在"触发那一轮"对**一条**样本成立。
因此本方案的排序改动**不是**在一个"严格有序"的系统上搞乱它，而是在一个**本来就近似时序**的系统上
把"优先方向"从"旧优先"翻成"新优先"。这一点决定了验收线怎么写（§6.1 第 4 项）。

## 3. 缺口 1：候选方案

### 3.0 条文到实现的映射（先说清判据，否则候选没法比）

| 条文要点 | 本项目可落地的等价物 | 判据 |
|---|---|---|
| 优先保障**新采集的数据**上传 | 主循环采到的样本**优先进入 paho 发送路径**，不因补传批次在途而排队 | 补传在途期间产生的实时样本，**不存在**"只落盘、不尝试发送"的轮次 |
| **合理分配**网络带宽 | 不让补传一次性独占 paho 出站队列（同一 client、同一 TCP 连接、出站队列 FIFO） | 实时样本在出站队列里的排队深度有上界，而非"整个在途窗口" |
| 补传本身不得停 | 补传 pass 仍然覆盖整批；未确认的数据仍能重试 | 补传成功率不下降；最老的数据仍能被尝试 |

⚠️ 本项目的"带宽"**不是**物理带宽瓶颈：`EMQX + 单机 Docker` 下单条 PUBACK P50 **0.17 ms**（ADR-0003 §2.2），
128 条批次的发送在**同一秒内**完成（[故障台账](../runbooks/故障台账.md) 故障 2 的日志形态）。
**唯一的"带宽竞争"是 paho 单连接的出站队列顺序**。
把"合理分配带宽"理解成"给补传限速"在本项目是**过度实现**（且有害，见候选 3）。

### 3.1 候选 1：批内重排（newest-first）

**怎么改**（示意，不改实现）：

```python
# _take_over_pending()，L314 附近
batch = leftover + current
# 批内新数据优先：按报文行首的 19 字符时间戳降序。
# 排序键只取行首定长前缀（"%Y-%m-%d %H:%M:%S" 字典序 == 时间序），不解析 datetime：
# 既避免异常行把整批带崩，也不引入任何新依赖。Python sort 稳定，同 ts 行保持相对次序（可复现）。
batch.sort(key=lambda line: line[:19], reverse=True)
```

**为什么（部分）满足条文**：补传批次内部，**最新的先发**——"补什么"这件事上，
"新采集的那部分"确实更早到达平台。但**它不改变 §2.2 的机制**：
实时流在补传期间仍然只落盘、不发送。所以候选 1 只能算**部分满足**，
若单独实施，**不得声称"已对齐 §8.1.2"**。

**失败模式：老数据会不会饿死？→ 不会（可证明）**

`resend_cache()`（L373）是 `for offset in range(0, len(batch), RESEND_WINDOW)`，
**没有任何条数/时间预算**，因此每个 pass 都会**尝试整批每一条**；未确认的行在
`_finish_resend()` 里放回 `cache.jsonl` 队首，下一 pass 再排一次。
排序只是把"最老的一条"从队首挪到队尾，**它仍会被尝试**。

**代价与风险（如实列）**：

| # | 代价 | 量化 |
|---|---|---|
| 1 | 尾部延迟 | 最老一条的等待从"第一条"变成"第 N 条"。健康 broker（0.17 ms/条）下 N=128 → **< 25 ms，可忽略**；broker 挂死（每条等满 5 s）下 → **(N-1)×5 s**，128 条 = **635 s**。⚠️ 这一格是"新数据优先"的固有代价：**考核用的历史数据被推到最晚** |
| 2 | 全局顺序更乱 | 补传行内部从"升序到达"变成"降序到达"，逆序条数会从 58 涨到"补传条数"量级（128 条积压 → 最多 128 个逆序对）。**这是设计目标，不是回归**，必须在验收线里预先声明（§6.1 第 4 项），否则会被误判 |
| 3 | 实现/可观测 | +1 行排序 +3 行注释；建议日志补一行"本批 N 条，最新 ts → 最旧 ts"，用于断言；无新状态、无新 I/O、无新锁、无新依赖 |
| 4 | 对补传成功率 | 不影响（pass 覆盖不变，实测成功率 100 %，性能文档 §5.2/§5.4） |

### 3.2 候选 2（推荐）：在线即直发 + 批内 newest-first

**怎么改**：

```python
# L551-564：取消"补传在途 → 新样本入队"这一分支（ADR-0003 里被显式留给 task-6 的"候选 B"）
if mqtt_client.is_connected():
    # ★ 在线即直发：新采集的数据不因网关正在补传而排队（HJ 212-2025 §8.1.2）
    #   直发失败仍然落盘（下一轮补传接手），不丢数据
    if not publish(mqtt_client, payload, tag=f"第{count}条 在线直发"):
        save_to_cache(payload, reason="未收到 PUBACK")
else:
    save_to_cache(payload, reason="断网")
# 同时：删掉 resend_in_flight 快照（L525）——它不再参与判定；触发位置（L519-522）保持不动
# 同时采纳候选 1 的 batch 排序
```

**为什么满足条文**：这两句合起来才是"优先保障新采集的数据上传"的完整含义——

1. **新采集的数据永远第一时间进入发送路径**（在线即直发，不再因为"有批次在途"而只落盘）；
2. 补传批次内部**最新的先补**（候选 1），使"当前值"尽快回到最新；
3. 补传 pass 仍覆盖整批、未确认仍回写队首 → R1（自动补传）不受影响。

**失败模式：老数据会不会饿死？→ 不会**

补传侧（触发条件、节流、取批、分窗、滚动回写、收尾回写）**一行不改**，pass 仍是"整批一次走完"。
候选 2 只把**实时样本**从"入队等下一 pass"改成"立刻发一次，失败再入队"——
失败样本仍进 `cache.jsonl`，仍被下一 pass 取走。**没有新增"某条样本既不发送也不落盘"的路径**。

**代价与风险（如实列，这是本候选最需要评审的地方）**：

| # | 代价 | 机制与量级 |
|---|---|---|
| 1 | ⚠️ **主循环可能被补传窗口拖慢** | 补传线程会一次性把 ≤ `RESEND_WINDOW`=100 条塞进同一个 paho 出站队列；候选 2 之后，实时样本也开始走 `publish()`，在"连接在但 ACK 极慢"的区间里，它可能排在**已入队的整窗补传之后**，`_wait_published()` 最多等满 `PUBLISH_ACK_TIMEOUT=5 s` → 该轮采集周期从 5.1 s 变成 ~10.1 s（read+publish 超时+sleep），**这段时间里少采约一半样本**（采不到的数据 = 永久缺失，故障台账故障 1 的教训） |
| 2 | 劣化窗口有界 | paho `keepalive=60`：挂死的 broker 会在约 90 s 内被判连接断开，此后 `is_connected()` 为假 → 实时样本直接落盘、节拍恢复 5.1 s。所以**每次挂死事件的最坏影响 ≈ 90 s 内少采 ~8 条**（估算，**必须实测标定**，见 §7.1 门禁） |
| 3 | 语义变更 | `reason="补传中"` 永久消失。稳态下它本来就是 0（ADR-0003 §7.4/§7.6 已修掉），残留只有"每次网关重启 1 条"（ADR-0003 §7.6）→ 收益 = 去掉这 1 条 + 去掉长补传期间的全部排队 |
| 4 | 观测口径 | 逆序条数会进一步上升（直发行越过积压行，这**正是**"优先新数据"的定义）→ 需与候选 1 一起写进验收线的"预期变化" |

### 3.3 候选 2 的可选加固：补传在途期间用**更短的 ACK 超时**（待标定，不进本次推荐的必要条件）

针对 §3.2 风险 1：实时样本在补传在途时用 `LIVE_ACK_TIMEOUT_DURING_RESEND`（例如 1.0 s，**数值需实测标定**），
超时即落盘。效果：最坏采集周期 5.1 → ~6.1 s（少采比例 ~16 % 而不是 ~50 %）。
代价：把"1~5 s 内其实会确认"的数据也判为失败并落盘 → 这些条会以 `RF=1` 补发一次
（TDengine 同 ts 覆盖，不会重复计数，但会**抬高"补传条数"统计**，需在报告里说明）。
⚠️ **本机无法标定**：本环境只有"健康 broker（0.17 ms）"与"完全断/挂死（不透）"两种极端，
**没有"慢而可用"的中间态**注入手段（容器无 `CAP_SYS_ADMIN`，不能加 netem 延迟；`docker pause` 是冻结不是变慢）。
→ 因此该加固**记录为待条件具备时评估**，不作为本次推荐的必要项。

### 3.4 候选 3（不推荐）：候选 2 + 补传"每轮条数预算/限速"

**怎么改**：给 `resend_cache()` 加预算（每轮最多发 M 条，剩余留在 `.sending` 等下一轮），
`RESEND_WINDOW` 退回"入队粒度"语义。

**为什么会被提出来**：这是对"合理分配网络带宽"最字面的一种实现——用限速给实时流让出带宽。

**失败模式：老数据饿死 → 会，而且不可逆**

若"每轮预算 M / 轮间隔 T"的吞吐 `M/T` **低于**上游产生速率（正常 12 条/min），
积压将**单调增长**，只能靠 `CACHE_MAX_BYTES=64 MB` 的"丢最旧、保最新"裁剪兜底（L203-221）——
**被裁掉的历史 = 永久缺失**。本项目对这类失败模式的既有结论很明确：
故障台账故障 1 已证"上游压根没采到的数据，缓存再大也救不回来"；补传丢的历史同样是考核数据，同样不可逆。

要让它可接受，必须同时具备（都属于新增状态与运维负担）：
① 积压**年龄看门狗**（队首最老一条的 age 超阈值 → 提升预算 + 告警）；
② 预算**自适应**（积压越大，补传配额越大，最终退化为不限速）；
③ 把 64 MB 裁剪路径纳入监控与演练。
而收益侧：本项目**没有**"补传吞吐影响到实时性"的实测证据（正常态一个 pass 在亚秒级完成，见 §2.2）。
→ **收益无证据、风险不可逆，不推荐**。

### 3.5 被否决的做法

| 改法 | 判定 | 理由 |
|---|---|---|
| 把多条数据**合并**成一个大报文再传（"省带宽"） | ❌ | ① 标准要求的是"数据段超 1024 字符应**分包**传输"，**没有**要求合并；② 合并会改报文契约（一报文多条）+ 订阅端解析改造；③ 与"逐条 PUBACK 确认"的可靠性模型冲突（一条失败整批重发） |
| 给补传再加一个 MQTT client / 独立连接（实时与补传分通道） | ❌ | 需新增固定 `client_id`（触碰硬约束的精神）、同主题双发布者、EMQX 会话/ACL 面变大；乱序程度更高，收益与候选 2 重叠 |
| 直发改成"异步不等 PUBACK + 回调里失败再落盘" | ❌ **禁止** | 破坏"不丢数据"底线：`publish()` 后进程被杀时该条**既没确认也没落盘**。除非改成"先落盘再发"的 WAL 式模型（见下行） |
| WAL 式"先落盘、发送成功后再删" | 🔶 演进方向，**本次不做** | 逻辑更干净（无静默丢窗口），但等于重做"入队/取批/收尾"整条链路与原子交接模型；违背"不破坏原子交接"的本次约束 |
| 只调 `RESEND_WINDOW`（100 → 5~10） | ⚠️ 有收益也有代价 | 能压缩 §3.2 风险 1 的队头阻塞上界，但 `_write_lines(SENDING_FILE, …)` 的**整文件回写次数 ×10~20**（滚动回写是每窗一次，L381-383），大积压下 I/O 放大。若要做，必须把**入队粒度与回写粒度解耦**（每 K 步才回写一次）→ 改动量上升。**收益依赖"慢而可用"的 broker，本环境无法标定**，见 §3.3 |
| 把补传触发挪到"读完设备之后" | ❌ | ADR-0003 §3.3 已否决：会把"设备故障的 `continue` 跳过补传"这个既有缺陷放回来 |
| 只改判定而不动顺序（即现状 + RF 标记） | ⚠️ 部分满足 | 缺口 1 未解决，仅缺口 2 落地；可作为"分两步走"的第一步（§7.3） |

### 3.6 候选对比表

| 维度 | 候选 1 批内重排 | **候选 2 在线即直发 + 批内重排（推荐）** | 候选 3 = 候选 2 + 限速预算 |
|---|---|---|---|

| 满足 §8.1.2 R2 | **部分**（只做到"补传里新的先发"） | **满足**（实时流永不排队） | 满足（形式上更贴"合理分配带宽"） |
| 老数据饿死 | 不会（pass 全量覆盖，有证明） | 不会（补传侧一行不改） | ⚠️ **会**（预算 < 到达率 → 积压单调增长 → 64 MB 裁剪丢最旧 = 永久缺失） |

| 可观测性 | +1 行批次范围日志 | 同上；`补传中` 日志消失 | 同上 + 预算/积压年龄指标 |
| 对补传成功率 | 不变 | 不变 | 需持续监控（否则悄悄退化） |
| 结论 | 可做，但**不足以**声称合规 | **推荐**（配 §7.1 硬门禁） | **不推荐** |

## 4. 缺口 2：`RF` 标志设计

### 4.1 取值定义（按 §1.3 的条文，不是按任务描述的预设）

| 报文类型 | `RF` 字段 | 依据 |
|---|---|---|
| **补传报文**（本条由补传线程发出） | 出现 `RF=1` | 表 3："`RF=1`，标志数据报文属于补传报文" |
| **实时报文**（本条由主循环直发成功） | **不出现 `RF` 字段** | 表 3："**非补传时，无本字段**" |
| `RF=` 其他值 / 空值 | 按**非补传**处理 + 记 warning，**不拒收** | 表 3 只定义 `RF=1`；拒收 = 丢一条真实监测数据（§1.3 约束 C2） |
| 无 `RF` 字段 | 非补传（兼容升级前的报文与旧缓存文件） | §1.3 约束 C1 |

> ⚠️ **明确不采纳**："`RF=0` 表示实时数据"。发布 `RF=0` 与条文"非补传时，无本字段"直接冲突，
> 且会给解析端制造一个"字段存在但值为 0"的第三态。**任务描述里的这一条不应照做**。

### 4.2 打在报文的哪个字段（位置）

| 项 | 决定 |
|---|---|
| 字段名 | `RF`（与标准同名同大小写） |
| 值 | `1`（唯一取值） |
| 位置 | 报文体**末尾追加**：`<ts> <9 个测点> Flag=N RF=1`。解析端按 `key=value` 取值，位置不影响解析 |
| 与标准相对次序 | 表 3 的次序是 `… PNO → RF → CP`；本项目 payload 整体相当于 `CP/数据区`，做不到字节级对应，故只做"追加在尾部"的工程映射。**若将来实现真正的 HJ 212 通信包，RF 必须落在数据段中 `CP` 之前**（§1.3 约束 C3） |
| 长度影响 | +4 字符（含分隔符 +5）；实测报文 127 字符 → 132 字符，**仍远低于数据段 1024 上限**，不触发分包（§1.2 R3） |

### 4.3 在哪一步写入（★ 这一步与原子交接直接相关）

| 方案 | 做法 | 评价 |
|---|---|---|
| **R-1（推荐）入队即标记** | `save_to_cache()` 写入前给报文追加 ` RF=1`（幂等：行内已有 `RF=` 则不改写） | ★ **唯一正确的位置**：`save_to_cache()` 是"将来必被补传"的**唯一入口**（L554/557/564 三个调用点全部经过它），且**唯一写者是采集主循环**。标志**随数据一起落盘**，因此进程被杀/重启后 `.sending` 里的行**仍带正确标志**——若标志只存在补传线程的内存里，重启后会以"实时"身份重发，标志语义当场失效 |
| R-2 补传时临时改写 | 补传线程 publish 前把行改成带 `RF=1` | ❌ 线上报文与 `.sending` / 日志 / 对账快照**不再是同一份内容**，事后无法用缓存文件复核"线上到底发了什么"（`measure_resend_success.py` 正是用快照原文做证据） |
| R-3 升级遗留行 | `_take_over_pending()` 取批时，对**没有 `RF=` 的行**补 `RF=1` 后再写入 `.sending` | ✅ 需要：升级瞬间 `.sending` / `cache.jsonl` 里可能有旧代码写下的、不带 RF 的行。补标记发生在补传线程**独占 `.sending` 的所有权窗口内**（`CACHE_LOCK` 内），不碰 `cache.jsonl` 的单写者模型。⚠️ 它会让"取批前后多重集相等"这条测试断言失效 → 回归测试的守恒断言必须用**规范化键**（§5.2 P1） |

### 4.4 契约影响评估

| 受影响对象 | 影响 | 处置 |
|---|---|---|
| `src/common/points.py` | **不是测点**：无寄存器、无量程、无单位、无限值、不进 `POINTS`/`COLUMNS`/`RANGES`/`REG_COUNT`/溢出自检 | 建议**新增一小节常量**作为报文契约的单一真源：`RF_FIELD="RF"`、`RF_RESEND_TOKEN="RF=1"`、`RF_COLUMN="rf"`、`FLAG_COLUMNS=("rf",)`。⚠️ **绝不加入 `COLUMNS`**——`COLUMNS` 被 `report.py` L249 用作 `", ".join(f"AVG({column})" …)`、被 `query_tool.py` L104/122 当测点列遍历、被 `web_dashboard.py` L148 用 `POINTS` 拼列名；把 `rf` 混进去会凭空多出 `AVG(rf)` 之类的"测点"语义 |
| `subscriber_to_td.parse_payload()` | 返回值从 `(ts, values)` 变 `(ts, values, is_resend)`；**调用点只有 `on_message`（L478）** | 属**内部函数契约变更**，改动面 1 处 + 可能的脚本；`probe_o2_unavailable_publish.py` 构造的报文不带 RF → 按条文属"非补传"，**继续有效**（这正是"缺字段=实时"的兼容价值） |
| 老报文/老缓存 | `parse_payload` 现在**跳过所有非测点字段**（L168-169），因此带 `RF=1` 的报文**不会被老订阅端拒收** | ✅ 向后兼容，且**升级顺序无强依赖**：先升网关（订阅端自动忽略新字段）或先升订阅端（缺字段按非补传处理）都成立。前提是解析端**必须容忍缺字段**，不得把"没有 RF"当错误 |
| 入库表 `cems.cems_data` | **建议加列** `rf`（`TINYINT`，历史行 NULL）。不加列则"平台侧能区分"只存在于 `on_message` 那一刻，事后无法回答"这段历史里补传占多少""在线补传成功率" → 缺口 2 只解决一半 | 建表语句 + `_ensure_columns`（L234-245，`ALTER STABLE … ADD COLUMN`，既有幂等升级路径）扩展为"测点列 + 标记列"两张清单。⚠️ **待实测**：`ADD COLUMN rf TINYINT` 在 TDengine 3.3.6.13 上是否可行、NULL 在 REST 返回里的表现（既有代码只加过 `FLOAT`）；若 `TINYINT` 有问题则退 `FLOAT` 或 `INT` |
| 既有查询/报表 | **加列不影响任何现有查询**：已核实全仓库**没有 `SELECT *`**——`web_dashboard.query_recent`（`SELECT ts, {POINTS}`）、`query_tool.show_latest`（`TD_COLUMNS`）、`report.query_aggregate`（`AVG(COLUMNS)` + `COUNT(*)`）全部显式列名；`/api/data`、`/api/report` 的响应结构不变 | 要让曲线/报表**区分**补传点，属于展示层改动，需**显式**加字段/加参数，建议单独排期（§4.5） |
| 覆盖率口径 | `report.py` 的 `coverage` 是 `COUNT(*)` **到达条数**口径（其文件头 L47-48 已声明与告警层的"有效样本"口径的区别） | **不改**：补传行本来就应该计入（它把历史窗口的缺口补上）。改口径会让历史报表与新报表不可比 |
| ⚠️ **NULL 陷阱（红线）** | 历史行的 `rf` 是 NULL。TDengine 里 `WHERE rf = 0` **不会**返回 NULL 行 | **默认查询一律不得加 `rf` 过滤**；确需过滤必须写 `WHERE rf IS NULL OR rf = 0`（即"历史未知按实时处理"），并把这条写进代码注释与评审清单。这属"静默丢数据"型事故（报告里有、过滤后没了） |
| 依赖 | 解析只用 `key=value` 的既有 `partition("=")` 循环 | **不引入新依赖** ✅ |

### 4.5 平台侧（订阅端）需不需要同步改？怎么区分处理

**需要，但可分批**（§4.4 已证向后兼容）：

1. **第一批（必需）**：网关加 `RF=1` + 订阅端**只要不改就会被忽略** → 先上这一批，链路行为零变化；
2. **第二批（必需，才叫"能区分"）**：订阅端解析 RF → 打日志/计数 → 落库 `rf` 列；
3. **第三批（按需）**：消费侧使用 `rf`（下面的口径）。

**区分处理的三条口径（必须显式声明）**：

| 场景 | 口径 |
|---|---|
| **入库** | `RF=1` 的行**照常入库**。RF 只做标记，**绝不用于丢弃**——补传数据是考核数据，丢它等于历史永久缺失 |
| **统计** | ① 在线补传成功率 = 平台侧"`rf=1` 到达条数" ÷ 网关侧"入队条数"（网关日志计数）；两侧对不上即说明链路有损。② "实时样本"统计：`rf` 为空或 0 的行（注意 NULL 陷阱） |
| **展示** | `/api/data`、`/api/report` **默认口径不动**。若要让操作员看出"这个点是补上来的"，做法是**新增**（响应里多带 `rf`，或新增查询参数 `rf=0/1`），而不是静默改变现有曲线内容——本项目已有"口径变更必须显式"的固定做法（`report.py` 文件头即为此而写） |
| **`LAST_REFERENCE` 快照** | 现状按**到达顺序**覆盖（L391-401）。补传批晚到会把"最近一条"回退成更旧的值。建议改为"只在 `ts` 更新（严格更大）或 `rf` 非补传时更新"，并在注释里写明新语义（属可选小改，列入实施清单） |

**场景构造（确定性插桩，不是竞态）**：


**断言清单（每条对应一个不变量，且必须与「是否排序」无关）**：

| # | 断言 | 说明 |
|---|---|---|
| P1 | `Counter(去RF后的 batch) == Counter(去RF后的 取批前两文件内容)` | **排序只是排列**——排序改动最容易犯的错是"顺手过滤掉了某类行"。用**规范化键**（剥掉 ` RF=1`）以容纳 §4.3 的 R-3 补标记 |
| P2 | 插桩时刻：`CACHE_FILE.exists() and SENDING_FILE.exists()` 且两者非空 | I2 |
| P3 | 收尾后 `CACHE_FILE` 的行 == `未确认行 + 期间新增行`（**逐元素相等**，不只是集合相等） | I3（覆盖顺序，不只是条数） |
| P4 | `len(取批前的两文件) == confirmed + len(remaining)` 且 `len(收尾后 cache) == len(remaining) + len(新增)` | I4 |
| P5 | monkeypatch `gw._write_lines` 只对 `CACHE_FILE` 返回 False → 断言 `SENDING_FILE` 仍存在且内容与失败前逐字相同 | I5（这是"不丢数据的底线"，与排序无关但必须一起守） |
| P6 | 多窗路径：每个窗之后读 `.sending`，断言内容 == `remaining + 该窗之后未发的尾部` | I6（**排序改动直接影响 chunk 边界**，这是本测试的重点） |
| P7 | 资源与副作用：临时目录内总字节数 < 1 MB；断言测试前后**生产 `data/cache.jsonl` 的 size 与 mtime 未变** | 硬约束：不许在宿主机写大量数据（故障台账故障 4 的处置），不许污染在跑的服务 |
| P8 | **同一序列跑两遍**：一遍用"当前实现"、一遍用"打开排序后的实现"（脚本内用一个开关驱动排序函数），两遍的 P1~P6 **都必须成立** | ★ 这才是"**改了排序之后原子交接仍然不丢数据**"的直接判据 |

| A3 | **补传期间没有"实时样本只落盘"的轮次**（候选 2 的直接证据）——⚠️ 判据必须选对场景：健康 broker 下一个 pass 在亚秒级发完（小于一个 `POLL_INTERVAL`），**两种实现在这类演练里表现可能完全一样**。可区分的两个场景：① **网关重启的残留**：改动前每次重启必出现 1 条 `[缓存] … 补传中`（ADR-0003 §7.6 实测），改动后应为 **0 条**；② **挂死 broker**（`docker pause emqx`，§7.1 门禁场景）：改动前 `[缓存]` 行紧跟在 `[补传] 开始补传` 之后，改动后 `[补传] 开始补传` 与 `[补传完成]` 之间**不出现** `[缓存]` 行 | 网关日志逐行判别（`[缓存]` 行里的原因字段）；①用 §6.1 的演练顺带做（重启网关前先留 ≥2 条积压），②用 §7.1 的门禁顺手记录 |
| A4 | **不饿死**：快照里**最早**的一条（最老）在库内存在；补传成功率仍 **100 %** | 快照逐条核对（ADR-0003 §5.4）+ `measure_resend_success.py` 的 `success_rate` 字段 |
| A5 | ⚠️ **逆序条数是预期上升，不是回归**：只做候选 1 时，逆序集中在补传行内部（≈ 补传条数），`direct` 行仍 0 条；**采纳候选 2 后 `direct` 行也会参与逆序**（直发行越过更旧的积压行 = "优先新数据"的定义本身） | 用 §2.4 的同一口径复算（`measure_latency.py` 原始 CSV 的逆序统计）。**必须把"预期逆序"写进验收线**，否则会被误判为顺序退化；同时要说明：本项目所有消费方都按 `ts` 处理（§4.4 已核实无 `SELECT *`、无按到达顺序取当前值的查询），到达顺序不影响正确性 |
| A6 | 环境复核：六服务 healthy；`cache.jsonl` 归零后观察 ≥ 6 min 不回"长期非空"态 | 同 ADR-0003 §5.4 第 6 项 |

## 7. 推荐、实施顺序与硬门禁

### 7.1 推荐

**候选 2（在线即直发）+ 候选 1（批内 newest-first）**，RF 按 §4 落地。理由：

1. **打在条文的语义主体上**：§8.1.2 要优先保障的是"**新采集的数据上传**"，
   而现状恰恰是"补传期间新采集的数据不进入发送路径"。只做批内排序（候选 1）**不解决**这一点，
   只做在线即直发（不排序）则会丢掉"补传里最新先到"这个廉价收益。两者是互补的，不是二选一。
2. **不引入新的失败模式**：候选 2 不动补传侧任何一行（触发/节流/取批/分窗/回写/收尾），
   因此**不存在"老数据饿死"**；直发失败仍落盘，**不存在"既不发送也不落盘"**的路径。
   反面例子是候选 3（限速预算）——它把"老数据补不上"变成结构性风险，而收益在本项目**没有实测证据**。
3. **改动量与风险可控**：净改动 ≈ 删一段分支 + 1 行排序 + 注释；不碰文件所有权、不碰锁、不引入依赖。
4. **可观测、可回归**：顺序方向、`[缓存]` 行是否出现在补传窗口内、`rf` 分布，都是**可直接断言的量**；
   并且 §5 的原子交接回归测试给出了"排序不改变任何守恒断言"的判据。
5. **诚实标注代价**：候选 2 让主循环在"连接在但 ACK 极慢"的区间里可能被整窗拖慢（每次事件 ≤ ~90 s，
   估算少采 ~8 条）。这个代价**必须实测标定**，见下面的硬门禁。

**⚠️ 硬门禁（照 ADR-0003 §5.3 的做法：结论必须有实测支撑，不许拿推算当验收线）**：

```
场景（"连接在但 ACK 不透"，ADR-0003 §5.2 R2 的成熟配方）：
  docker stop emqx → 攒积压（≥ 20 条）→ docker start emqx → docker pause emqx → 观察 90 s
测三件事：① 主循环两圈之间的实际间隔（网关日志时间戳即可，单时钟）
          ② 日志里 `[缓存]` 行的出现频率与原因字段
          ③ 该窗口内库内新增条数（`SELECT COUNT(*)`，只读）

步骤：
  S1 改动前：先跑一次（这就是"现状基线"）。预期：补传线程在等 PUBACK，
             但主循环把实时样本直接落盘 → 节拍仍接近 5.146 s、库内不增长。
  S2 改动后（实施顺序第 3 步之后）：同一场景复测。
  S3 判据：若 节拍/漏采 相对 S1 的劣化 ≤ 3 条 → 保留候选 2；
           若 > 3 条（或节拍劣化超过 1 个 POLL_INTERVAL 的量级）→ 二选一：
             ① 追加 §3.3 的"补传在途期间短 ACK 超时"加固（阈值实测标定）；或
             ② 回滚第 3 步，退回"只做候选 1 + 登记有意偏离"（见下）。
```

**备选（若门禁判定不可接受）**：只做候选 1，并把"实时流在补传期间仍排队"作为**有意偏离**登记在案，
理由写成"正常态补传一个 pass 在亚秒级完成（§2.2），条文收益不可测；而候选 2 存在可推导的漏采代价"。
**这个备选同样成立了"不硬凑方案"的要求**——但必须在评审记录里写清它**不满足** R2，
不得在对外材料里声称"已对齐 §8.1.2"。

## 8. 没做到 / 不确定的部分（诚实清单）

1. **"挂死 broker 下主循环少采 ~8 条"是推算，不是实测**。它由"`_wait_published` 最多 5 s +
   `sleep(5)` → 周期 ~10.1 s"与"paho keepalive=60 → 约 90 s 判定断连"两项机制推出，
   **本轮没有跑这一场景**（本任务只出方案，且该场景会中断服务）。
   §7.1 的门禁就是为补齐它而设。
2. **"慢而可用"的中间态无法在本环境注入**：容器无 `CAP_SYS_ADMIN`（不能加 netem 延迟，
   见故障台账故障 4 的附带事实），`docker pause` 是**冻结**不是变慢。
   因此 §3.3 的短 ACK 超时加固**无法标定阈值**，只能记录待评估。
3. **`ADD COLUMN rf` 的 TDengine 行为未实测**：既有 `_ensure_columns`（L234-245）只加过 `FLOAT`；
   `TINYINT` 是否可用、老行 NULL 在 REST 返回里的类型、`GROUP BY rf` 对 NULL 的分组表现，
   **均需在实现阶段先做一次只读+一次性 ALTER 的验证**（我不会在没有验证前把它写成"确定可行"）。
4. **"paho 出站队列的严格 FIFO 顺序"是从 paho 行为与 `_out_messages` 的语义推出，
   没有用探针直接观测过**（观测需要 hook paho 内部结构，属改代码）。§3.2 风险 1 的量级因此带不确定性。
5. **在线演练只覆盖"broker 容器停/起"**：未覆盖网络分区、EMQX 队列溢出
   （`max_mqueue_len=20000` ≈ 27 h）、64 MB 缓存裁剪、会话过期 24 h ——
   这些与本文结论的交互未验证（既有文档同款局限：性能文档 §10 第 4 条、§5.5 第 3 条）。
6. **大积压下 `_take_over_pending()` 全量读入内存 + 排序**未验证：排序本身是 O(n log n)、
   128 条无感，但 64 MB 缓存上限（约 50 万行）下，排序与全量读入的内存/耗时**未测**（既有问题，本次不改）。
7. **报文字符长度的实测口径有限**：127 字符来自 35 行演练快照（全部 127），146 来自日志抽样的最大长度；
   两者都远低于 1024，但**没有对"极端值"（如 Flow 由 5 位变 6 位、以后加测点）做余量分析**。
8. **`RF` 的"重复投递"口径只在设计层面处理**：同一 ts 若既被实时投递过、又被补传投递过，
   TDengine 按 ts 覆盖，**最终行里的 `rf` 取决于写入顺序**（可能从 0 变 1，反之亦然）。
   本文给的口径是"`rf` 表示该 ts **最后一次写入**时的传输属性"，**没有做端到端的实测验证**；
   若要严格，需在入库端做"`rf` 取或（1 优先）"的合并逻辑——那属于额外改动，本文只记录。
9. **`Flag=N` 的既有偏差只记录、未修正**（§1.5）：它不符合表 3 对 `Flag` 的类型定义。
   是否要把它改成标准形态（或直接删掉）需要单独评审（属报文契约变更）。
10. **本文未验证"批次内 newest-first 对 `measure_latency.py` 分类结果的影响"**：
    该脚本按"观测延迟是否显著大于直发基线"给行打 `direct` / `resend` 标签，
    排序改变后**补传行的延迟量级不变**（仍是 31 s 级），但**序号与 ts 的对应关系变了**，
    复算脚本是否需要同步调整（例如 A5 的逆序统计）**要在实现阶段实测确认**。
