## 1. 为什么要加这两层（不是"计划里写了"）

### 1.1 Nginx：后端并发模型与静态资源都不适合直接对外

| 问题 | 现状（加反代之前） | 反代之后 |
|---|---|---|
| **并发模型** | waitress 是 `WEB_THREADS=8` 的**进程内线程池**。第 9 个并发请求在内核 accept 队列排队；慢客户端（手机弱网、大屏机器休眠唤醒）会一直占住一个线程 | nginx 事件驱动，用极小内存挂住慢连接，只在后端真能处理时才转发过去 |
| **静态资源** | `/static/echarts.min.js` 有 **1 024 740 B**，每个字节都要过一次 Python WSGI 循环 | nginx 用 `sendfile` 由内核页缓存直送 socket，并加 1 年不可变缓存（304） |
| **TLS 终结位置** | 后端直接对外，将来上 HTTPS 必须把证书装进业务镜像 | 证书只装在**这一层**，后端继续明文 HTTP；轮换证书不需要重建业务镜像 |
| **对外契约** | 外部要知道"后端端口 5001"（Windows 上还因为 5000 被占用而特意改过） | 对外只有 80；后端地址/端口从对外契约里消失 |

### 1.2 Redis：报表类聚合查询被反复重算

`/api/report/*` 与 `/api/curve`（聚合粒度）把 `INTERVAL + AVG` 全推给 TDengine 算，
但**同一个时间窗**在前端每 5 秒刷新一次、或一次会话内反复查询时，
库侧会一遍遍重算完全相同的聚合。实测一次 30 天 1 小时粒度曲线的 p50 是 **16.0 ms**，
是实时接口（7.0 ms）的两倍多 —— 这就是被重复支付的固定成本。

⚠️ **不是所有查询都适合缓存**，这一条是本次改造最关键的判断：

- `/api/data`（大屏实时曲线）**按定义包含"当前秒"**，缓存它等于把当前数据冻住 → **明确不缓存**；
- 报表默认口径的上界是 `now`（`minute_report` 默认最近 1 小时、`day_report` 默认今天），
  **窗口没闭合** → **按设计不缓存**，实测这 30 次请求的查库次数在开关前后完全一样（§5.3）。

### 4.2 nginx 的四个关键决定

1. **上游用变量 + Docker DNS，不用 `upstream` 块**
   ```nginx
   resolver 127.0.0.11 valid=10s ipv6=off;
   set $cems_web "http://web:5000";
   proxy_pass $cems_web;
   ```
   `upstream` 块只在 nginx 启动时解析一次服务名并永久缓存 IP；web 容器重建
   （改代码后的常规操作）IP 会变，nginx 不重启就 502。
   代价是丢掉 upstream 的 keepalive 连接池 —— 单机个位数 QPS 场景不值得为它牺牲可运维性。
   **实测**：整场测量里 web 容器被 `--force-recreate` 重建了 6 次，nginx 全程未重启，
   重建后立即访问 `/api/health` 正常返回。

2. **转发头用"连接的真实对端"重写，不信任客户端自带值**
   ```nginx
   proxy_set_header Host              $host;          # 原样透传，否则后端绝对链接指向 web:5000
   proxy_set_header X-Real-IP         $remote_addr;
   proxy_set_header X-Forwarded-For   $remote_addr;   # 边缘节点，前面没有可信代理
   proxy_set_header X-Forwarded-Proto $scheme;
   ```
   本层是边缘，前面没有可信代理 → 直接取 TCP 对端，客户端自带的 `X-Forwarded-*` 一律被覆盖。
   将来再加一层代理，这里要改成信任那一层的 XFF 链（配置里写了这条注释）。
   另外 `proxy_redirect off`：不让 nginx 把重定向里的端口从 80 改写成 5000（那会泄漏内部拓扑）。

3. **超时与前端对齐**：前端 `FETCH_TIMEOUT_MS = 15000`，
   所以 `proxy_read_timeout / proxy_send_timeout = 15s`、`proxy_connect_timeout = 5s`。
   nginx 侧必须 ≥ 15 s，否则浏览器看到的是 nginx 的 504 而不是自己的超时文案。

4. **`proxy_buffering on` 是有意保留的**：本项目没有 SSE/WebSocket/流式接口
   （大屏是 5 s 轮询的普通 JSON），缓冲区能把后端响应先收进 nginx，
   让 waitress 线程尽快释放。若以后加 SSE，这里必须改 `off`。

### 4.3 缓存层（`src/web/cache.py`）的正确性设计

**核心不变量：只缓存"已闭合、且能证明其内容没再变过"的时间窗。**

一条查询要进缓存必须同时满足：

| # | 条件 | 为什么 |
|---|---|---|
| ① | 查询上界 ≤ `data_ts − 60 s`（`data_ts` = 观测到的**最新数据时间戳**） | 窗口"写完了"。用数据时间戳而不是容器墙钟：时间戳与数据同源，无跨时钟误差 |
| ② | 查询上界 < 现在（`align_range` 已保证） | **当前秒/当前分钟永不进缓存** |
| ③ | 读侧复核"窗口指纹"未变 | 迟到写入/回填会让窗口内容变化，必须作废 |

**安全边界 60 s 的取值依据**：网关补传慢路径实测滞后 P50 31 s / max 32.1 s
（[性能与可靠性指标](../reference/性能与可靠性指标.md) §4.2）。边界必须严格大于补传滞后，
取 60 s 有 1.9 倍余量。

**指纹设计**（踩了五个版本才定下来，过程见 §8）：

- `/api/data`（**无缓存**接口）每次读库后，把"每个分钟里观测到的最晚一条"写进 Redis hash
  `cems:v1:meta:minmax`（只保留最近 `CACHE_MINMAX_KEEP=3000` 分钟 ≈ 50 h）。
- 缓存条目里连同结果一起存下**当时窗口内被观测到的分钟指纹**。
- 读侧重算指纹比对：**不一致就作废回源**。

**为什么缓存返回旧数据不会让报表/告警判错**：

1. 被缓存的只有**已闭合窗口**，而"闭合"由库内真实时间戳判定，不是估计；
2. 任何让窗口内容变化的写入，只要被 `/api/data` 观测到，就会改变指纹并立刻作废该条目；
3. 残留风险（不掩盖）：一次发生在**观测覆盖之外**、且**该分钟原本就未被观测**的写入
   不会改变指纹，要等 `CACHE_TTL_SECONDS=300 s` 兜底。此时该窗口最多偏旧 300 s，
   且影响面是**分钟/小时级均值**（窗口内少 1 条 = 1/12 ~ 1/60 权重），
   远小于 `ROUND_DIGITS=2` 的分辨力；告警判据是连续窗口越限（见 [ADR-0002 告警判据选型](0002-告警判据选型.md)），
   不依赖单点。**不会把"达标"判成"超标"。**

**降级**：Redis 不可用时整层退化为空操作（所有查询直连 TDengine，结果与加缓存前逐字节一致）；
`CACHE_ENABLED=0` 时同样旁路 —— 后者正是本此 A/B 的对照手段。

**启动自检**：连接成功后跑一遍命令自检（`set/get/incr/hset/hgetall/scan/delete` + 分钟最大值读写），
失败打 WARN。这一步不是洁癖：连接层的容错会把"代码/C 端 API 用错"伪装成"Redis 挂了"，
表现为"缓存看着开着、其实一次不命中"（实测踩过，见 §8）。

## 5. 验收 3：缓存前后对比数字

### 5.1 测法

- **两侧都走 nginx**（唯一变量是 `CACHE_ENABLED`）：如果一侧走 5001、一侧走 80，
  差异里会混进反代开销（§5.4 已单独量），归因就不干净。
- 每组开始前 `POST /api/cache/clear` 清空条目，并打两次 `/api/data` **预热水位**
  （等价于大屏已经在刷新）。⚠️ 不预热会让展示层不知道"库里到哪一刻了"，
  全部请求被判"窗口未闭合" → 看起来像"缓存完全没用"（实测踩过）。

### 5.4 反代层自身开销

同一接口、同次数（40 次）、先直连 5001 再走 80：

| 路由 | 直连 p50 | nginx p50 | Δp50 | 直连 p95 | nginx p95 | 响应体 |
|---|---|---|---|---|---|---|
| `/` | 1.66 ms | 2.62 ms | **+0.96 ms** | 19.17 ms | 21.50 ms | 逐字节相同 |
| `/api/data` | 7.01 ms | 6.78 ms | **−0.23 ms** | 31.13 ms | 27.77 ms | 逐字节相同 |

**不能用这组数字宣称"nginx 静态资源更快"** —— 本机测不出 sendfile 的优势，
要证明得换到 Linux 宿主或容器内对容器测。

### 5.5 误差来源

| # | 来源 | 量级 | 说明 |
|---|---|---|---|
| 1 | 样本量小 | 60/30/20 次 | 分位数只到 p95；max 受单次抖动支配 |
| 2 | Windows 端口转发抖动 | 偶发 +20~30 ms | p95 明显高于 p50 的主因；与缓存/反代无关 |
| 3 | 单机、无并发 | — | **不得外推到多用户、高并发场景**（与 [性能与可靠性指标](../reference/性能与可靠性指标.md) 同一限制） |

| 5 | 缓存命中率与"请求节奏"相关 | — | 同一窗口被连续请求越多，命中率越高（本项目场景是 5 s 一轮的持续刷新） |

## 6. 验收 4：失效策略实测（数据更新后多久刷新）

### 6.1 两条失效路径

| 路径 | 触发条件 | 生效时延 |
|---|---|---|
| **写后失效（主路径）** | 某窗口内出现新的、更晚的数据 → 该分钟的最大值变化 → 指纹变化 → 条目作废 | **秒级**（下一次报表请求即回源） |
| **TTL 兜底** | 条目到 `CACHE_TTL_SECONDS=300 s` | 300 s |
| （第三条）写侧不写不可验证项 | 结果集超过 `CACHE_MAX_VALUE_BYTES=1 MiB` | 该次不写缓存 |

TTL 为什么是 300 s：它只兜"指纹机制盖不到"的三种情况
（水位丢失 / 外部直接改库 / 超出观测覆盖的写入），不是主失效手段。
调小它会让命中率下降但更安全，调大反之；300 s 是本场景下"命中率与最坏偏旧时长"的折中。

### 6.2 演练方法（`scripts/measure_cache_invalidation.py`）

1. 选一个**已闭合**的分钟窗口（`now - 5 min` 起，实测数据连续、无空分钟）；
2. 读走该窗口全部原始行 → 记下基线均值与行内容（用于还原）；
3. 预热缓存，**自检必须有命中**（否则缓存没生效，演练无效），并验证基线可重复；
4. 向该窗口插 1 行哨兵（`so2=123.456`，秒位取该分钟现有最大值之后，保证"该分钟最大值"真的前进）；
5. 立刻开始轮询 `/api/report/minute`，同时后台按大屏节奏持续打 `/api/data` 推水位；
6. 观测到窗口均值变化即停，记录时延；
7. `try/finally`：**DELETE 该窗口 + 逐行写回原始行**，并核对"行数一致、逐行逐值一致"。

### 6.3 实测结果（3 次独立演练）

| 次 | 目标窗口 | 哨兵 ts | 基线（n / so2） | 更新后（n / so2） | **刷新时延** | 还原核对 |
|---|---|---|---|---|---|---|
| 1 | 18:43:00 | 18:43:57 | 11 / 28.98 | 12 / 39.61 | **0.208 s** | 11 行，逐行一致 ✅ |
| 2 | 18:43:00 | 18:43:57 | 11 / 28.98 | — | **0.208 s** | 11 行，逐行一致 ✅ |
| 3 | 18:43:00 | 18:43:57 | 11 / 28.98 | — | **0.004 s** | 11 行，逐行一致 ✅ |

- 三次都命中了写后失效路径，**没有一次需要等 TTL**。
- 时延由两段构成：① 大屏下一次打 `/api/data` 的等待（实测后台线程 1 s 一轮，
  生产 `REFRESH_SECONDS=5`）；② 报表请求发现指纹变化并回源（实测 **0.004 s**，即第 3 次的读数）。
- 原始数据：[cache_invalidation_drill.json](../evidence/cache/cache_invalidation_drill.json)
  （含逐次观测、基线指针、还原核对、缓存计数增量）
- 重复性：三次结果一致（0.208 / 0.208 / 0.004 s），均 **< 0.25 s**。

## 8. 取舍与踩坑记录（为什么这么写）

### 8.1 取舍

| 取舍 | 选择 | 代价 |
|---|---|---|
| 上游解析方式 | 变量 + Docker DNS（可运维） | 丢 keepalive 连接池；单机低 QPS 可接受 |
| 静态资源 | nginx 直接落盘仓库里的 `src/web/static` | 需要把该目录挂进容器（不复制副本，避免两份不同步） |
| 缓存粒度 | 整个查询窗口（起止时间进键） | 窗口上界一变就换键；换来的是"键即语义、不需要额外失效" |
| 安全边界 | 60 s（补传 max 32.1 s 的 1.9 倍） | 最近 60 s 的窗口一律不缓存（利用率换正确性） |
| 观测表覆盖 | 3000 min ≈ 50 h | 比它更早的窗口不写缓存（直连查库），换来"绝不返回无法验证的旧数据" |
| redis 持久化 | 不开 AOF/RDB | 重启后缓存为空是**正确的**（水位也一起没了，缓存会先停用直到重新观测到数据） |
| redis 淘汰 | `allkeys-lru` + `maxmemory 128mb` | 只存可重建的查询结果，淘汰最旧的即可，绝不能让 Redis 因 OOM 拒写 |

### 8.2 踩到的坑（都已修，记下来避免重犯）

1. **失效判据用"最新数据时间戳"→ 永不触发**。它永远比历史窗口新，
   判据 `窗口上界 ≥ 水位 − 边界` 对历史窗口恒不成立。实测向已缓存窗口插一行，
   轮询 1431 次（≈300 s 直到 TTL）都没刷新。
2. **改成"可缓存区间的最大时间戳"→ 仍不触发**。哨兵的时间戳比它旧，判据失效。
3. **改成"逐行时间戳集合"→ 误杀**。`/api/data` 每次都会重新看到最近 10 分钟的全部行，
   把它们全当"新写入"登记，于是最近 10 分钟的窗口每次请求都判脏、命中率掉到 0
   （实测 `dirty` 计数 = `miss` 计数）。
4. **改成"分钟最大值"→ 只比较整个窗口的最大值，漏判**。
   窗口 `[18:36, 18:41)` 里 18:40 分钟的最大值更大，往 18:38 插一条更晚的行，
   窗口最大值不变 → 判据毫无反应。
5. **改成"逐分钟明细整体比对"→ 又要求"每个分钟都观测过"**，
   结果一小时前/昨天的窗口永远无法验证、缓存命中率恒为 0。
6. **最终：只哈希"窗口内被观测到的分钟"**（观测集合 + 取值都要一致）。
   还顺手修了一个性能坑：曾把"未观测的分钟"也逐个哈希进指纹，
   30 天曲线窗口有 43200 个分钟 → 实测 p50 从 16 ms 涨到 **63 ms**（比不加缓存还慢）。
   现在代价与"被观测的分钟数"（约 10 条）成正比。

7. **`redis-py` 5.3.1 的降序封装会静默返回空**：
   `zrevrangebyscore(...)` / `zrange(..., byscore=True, desc=True)` 都不报错、只返回 `[]`。
   这类"静默空"是缓存里最难查的一类故障（接口全正常，只是永不刷新）。
   现在一律用 `execute_command` 走命令字面量，并把它写进启动自检。
8. **连接层容错会把"用法错误"伪装成"Redis 挂了"**：一个 `TypeError` 让整层缓存降级成直连，
   表现为"插了数据立刻就刷新"，看着像功能正常。→ 启动自检必须覆盖真实用到的命令形状。
9. **测量脚本自身的两个坑**（都已在脚本里写注释）：A/B 前不预热水位 → 全部请求判"未闭合"；
   报表窗口对齐上界会随当前分钟滚动 → 缓存键自己变，脚本一直盯着一条从没被预热过的新键。
10. **演练脚本的时区坑（造成过真实数据错位，已修并已复原）**：
    taosAdapter REST 返回的 `ts` 是 **UTC**（`2026-10-01T10:43:04.000Z`），
    而"本地 18:43"就是同一个物理时刻。脚本一度把它当本地时间直接回写，
    把 11 行写到了 10:43。已用
    [`_incident_20261001_timestamp_shift_repair.py`](../evidence/cache/_incident_20261001_timestamp_shift_repair.py)
    逐行还原并核对（行数、时间戳序列、逐值一致），该脚本作为事件留档保留在
    `docs/evidence/cache/` 下。
    **这是本次改造中唯一一次对库内真实数据造成影响的操作，已完全复原，记录在此不掩盖。**
    根因与正确写法已写进 `scripts/measure_cache_invalidation.py` 的
    `read_rows` / `restore_rows` 注释。

## 10. 没做到 / 测不准的部分（诚实清单）

1. **反代层"静态资源更快"没测出来**：本机是 Windows Docker Desktop，
   宿主→容器的端口转发开销把 1 MB 传输的差异放大了，实测 nginx 比直连慢 3.44 ms。
   sendfile/内核零拷贝的优势**在本机测不出来**，需要 Linux 宿主或容器内对容器测。
2. **反代层优势没有真实负载证据**：本机是单客户端、个位数 QPS，
   没有制造"慢客户端占住 waitress 线程"的场景，因此"反代提升并发能力"这条
   **只有机理分析，没有实测数字**。要有说服力需要慢客户端 + 并发压测（本轮未做）。
3. **缓存命中率是针对"重复查询同一窗口"这一节奏测的**：
   若用户的查询窗口每次都不同（每次换时间范围），命中率会显著低于 96.88 %。
   本文给出的 96.88 % 对应"大屏/报表停在固定窗口上反复刷新"这个真实场景。
4. **写后失效依赖 `/api/data` 被调用**：水位由它喂。若某个部署从不调 `/api/data`
   （例如只调报表接口的脚本），水位不前进 → 缓存不写入（退化直连，不会返回旧数据）。
   代价是那种用法下缓存不生效。
5. **观测覆盖 50 h 是硬边界**：比它更早的窗口不写缓存。
   若要让"上月月报"也吃缓存，需要把 `CACHE_MINMAX_KEEP` 提到 45000+，
   代价是 Redis 内存与 hash 读取量上升 —— 本轮没做，也没测那个量级下的表现。
6. **残留风险只在理论上界过，没有构造出来**：§4.3 说的
   "发生在观测覆盖之外、且该分钟原本未被观测的写入"，本轮没有构造真实场景去触发它，
   因此 300 s TTL 兜底的实际效果**没有实测数字**。
7. **未做并发/多客户端压测**：所有数字都是单客户端串行请求。
   多客户端并发下的命中率、Redis 连接表现、nginx 限流是否合理，均**未测**。
8. **未测 Redis 不可用时的降级效果**：代码里实现了整层旁路，但本轮没有
   `docker stop cems-redis` 去实测"web 仍正常服务、只是变慢"这件事。
9. **TTL 取值未做敏感性分析**：300 s 是折中值，没有测 60 s / 600 s 下的
   命中率与最坏偏旧时长的曲线。
