# 架构与可维护性说明

> **本文档的目的：主动记录现状与技术债，而不是等别人发现。**
> 面试官看到"项目主动列出自己的问题 + 改进优先级"，比看到"看起来完美的代码"更信任你 ——
> 能识别并承认技术债，是工程判断力的一部分。

- **审计日期**：2026-10-07
- **审计方法**：AST 静态扫描（65 个 Python 文件 / 26607 行）+ 与两个成熟开源项目对照
- **对照对象**：EMQX Neuron v2.15.0（开源工业协议网关）、Fledge（开源工业数采平台）
- **一句话结论**：**可维护性处于个人项目上游水平，但有两个系统性缺口 —— ① 点位模型缺"线格式"字段；② 最大的几个模块没有单元测试。**

## 三、与同类开源项目对照

### 3.1 ⭐ 比它们做得好的地方

| # | 本项目 | 对照 |
|---|---|---|
| **1** | **完整业务语义**：`limit`（排放限值）、HJ 212-2025 参数编码、折算公式出处（HJ 75-2017 式 C8）、基准氧 6%、哨兵值 9999.99 的法条依据（HJ 212-2025 §8.1.1 d） | Neuron 是**通用网关，设计上就放弃业务语义**；Fledge 也没有环保口径 |
| **2** | ⭐ **"算归算、传归传"分离**：`to_reference_o2()` 返回 `nan`（分母≤0，折算不存在）；`to_transmit_value()` 返回 `9999.99`（协议要求传最大值）。注释明令"严禁把哨兵值塞回计算函数，否则'算不出来'会被判成'严重超标'" | Neuron **用 NaN 承载"值失效"语义**（错误码 3008 = `isnan()` 转换而来）。这是把协议语义塞进数值本身，不如本项目干净 |
| **3** | **契约自检在导入期**（`points.py` 顶部 raise） | Neuron 的 4 层校验里，数据库 CHECK 是**运行期**才拦 |
| **4** | **全链路唯一真源**：`points.py` 一处定义，设备/网关/接入/展示共用，注释写明"以前散在 5 个文件各抄一遍，加/改测点必然漏改" | Fledge/Neuron 是运行时配置，不存在这个问题，但也没有"编译期契约"的概念 |
| **5** | **两套重试层的成功判据不同且写明**：网关侧 = broker PUBACK；接入层 = DB INSERT 成功 | Neuron 的 store&forward **只做在 MQTT 北向上**，其他北向协议无等价缓存；Fledge 有缓冲但判据是"发给北向目的地" |

### 3.2 ⚠️ 不如它们的地方（按"会不会真的害你"排序）

| # | 缺口 | 它们怎么做 | 影响 |
|---|---|---|---|
| **1** | ⭐⭐ **点位模型没有"线格式"字段** | Neuron：**14 种字节序** + 位偏移 + 字符串排布，做成**点位一等属性**，并编码进地址语法（`1!400004#BL`），用每驱动一份 JSON 的 `tag_regex` 按数据类型正则校验 | 🔴 **真机到货立刻撞** —— 变送器手册明写"16bits 数据高字节在前"，而本项目代码里**无处表达字节序** |
| **2** | ⭐⭐ **点位是"代码"不是"数据"** | Neuron：SQLite + Excel 批量导入导出 + 协议元数据自动发现（OPC UA 点位发现）；Fledge：运行时配置 + REST API | 🔴 加一台设备 = 改代码 + 重新部署。**这正是"配置驱动"要解决的问题** |
| **3** | ⭐ **地址基准（0 基/1 基）是全局常量** | Neuron 的 Modbus FAQ **坑 #1** 就是这个，且按设备配 | 🟡 多设备（有的从 40001 起）时会撞。本项目 `REG_BASE=0` 是全局的 |
| **4** | **无指标暴露** | Neuron：`/metrics` Prometheus 文本 + 每节点 `last_rtt_ms`/`tag_reads_total`/`tag_read_errors_total`/`group_last_timer_ms` + **驱动可注册自有指标**；Fledge：Health 页看服务响应与**数据进出计数** | 🟡 只能靠日志，无法做趋势与阈值告警 |
| **5** | **日志无"三件套"** | Neuron：**每节点一个独立日志文件** + 节点级 DEBUG 开关（**带自动回落**）+ **一键导出日志包** | 🟡 现场排障效率 |
| **6** | ⚠️ **无"保留策略"作为一等概念** | ⭐ Fledge：purge 任务的 **`Retain Unsent Data`** 有三个明确选项 —— `purge unsent` / `retain unsent to any destination` / `retain unsent to all destinations`（**按目的地逐个跟踪投递状态**） | 🟡 本项目是"PUBACK/INSERT 后即删"（隐含）。**若将来增加第二个下游，会导致其中一个下游丢数** |
| **7** | **无配置版本迁移机制** | Neuron：`persistence/` 下 **23 个顺序编号 SQL 迁移脚本**，约束下沉到 `CHECK`/`UNIQUE`/外键级联，改约束走"建新表→INSERT SELECT→DROP→RENAME" | 🟡 本项目 `points.py` 有"改版说明"注释（写得很细），但没有自动化迁移 |
| **8** | **无审计日志 / 无一键诊断包** | Fledge：**Audit Logging** 是 Core 功能；**Support bundle** 含系统诊断报告 | 🟢 个人项目优先级低 |
| **9** | **无"过滤管道"概念** | Fledge：Filters 分 ingress（转换/富化）与 egress（压缩/削减），可组合成 **pipeline 并复用到多个服务**；内置 **Delta**（死区，只发变化量）、**Rate**（缓存不发的数据、故障时补发）等 | 🟢 本项目换算/校验散在网关内联逻辑里 |
| **10** | **存储引擎不可选、取舍未文档化** | Fledge：SQLite / SQLiteLB / PostgreSQL / SQLiteMemory 四选，并**明确写出 in-memory 的代价"停机或断电会丢失缓冲数据"** | 🟢 本项目是文件型 JSONL，无替代方案 |

### 3.3 两个值得学的"坦诚"

- **Fledge**：改存储插件时明确写"**不会迁移旧存储里的数据，未发送的数据可能丢失**"。
- **Neuron**：主备文档明确写"**15 秒检测窗口内两侧都不运行会丢数据**""**主节点恢复瞬间两节点同时运行会重复数据**"，并直言完整 HA"成本极高且现场 PLC/网络往往不支持"。

> 这两家的共同点：**把"我们做不到什么"写进文档**。
> 本项目的 ADR 已有类似习惯（如 ADR-0007 标注"方案（待评审）"），可以再进一步 —— 把未验证项与失败模式单独汇总一节。
