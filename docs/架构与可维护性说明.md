#### 债 14：接入层"一处不合格 → 整条报文拒收" = 故障不隔离（2026-10-11 真机接入时暴露，原审计未发现）

**现象**：`parse_payload` 对任一测点不合格（`NaN` / `inf` / 超量程）都 `raise ValueError`
→ 调用方整条报文丢弃。

**为什么当初是对的、现在成了缺陷** —— 它把两种"坏"用一条规则处理：

| 坏法 | 例子 | 能不能只丢它一个 |
|---|---|---|
| 语法坏 | `NaN` / `inf` → TDengine 报语法错误 | ❌ 不能 —— 整行写不进去 |
| 语义坏 | `Temp=301.0` 超量程 —— 数值合法，只是不可信 | ✅ 能 |

而 `parse_payload` 的 docstring 把两个理由写在同一句里：
"语法坏必须整条拒收"这个正确的理由，顺带把"语义坏"也拉进了整条拒收。

**工业口径**：这叫「故障不隔离 / 单点故障扩散」。成熟体系都是逐点质量位 ——
OPC UA 的 `StatusCode`、西门子 WinCC 的质量码、《排污单位自动监测数据标记规则》的逐参数标记。
工业网关厂商 HMS（Ewon）甚至把它写成官方已知问题并给出规避做法
（隔离坏点 + 写事件日志）。本项目 `Flag` 是整条一个，与上述"逐点"不同构。

**影响**：真机那 2 个测点与 7 个仿真测点在同一张表、同一列布局里
→ 2 个点故障，9 个点一起断档。且故障期间 `docker ps` 全绿（见债 15）。

**处置**：已实现并实测（2026-10-11，提交 `e64563a`）——
`docs/adr/0009-接入层逐点质量位.md`。V1/V2/V6 由负责人独立重跑：
注入 1 个超量程测点 → 该点 `NULL` + 事件表 1 条留痕，其余 8 点非空列计数 = 8（全部入库）。

#### 债 15："全绿零数据" —— 网关心跳在"读设备"之前刷新（2026-10-11 真机接入时暴露，原审计未发现）

**现象**：`src/gateway/gateway.py` 的心跳先于读设备动作刷新；设备层未就绪时只进入无限重试。
**后果**：9 个测点全停，而 `docker ps` 全部 healthy、零告警 —— 比"数据错"更难发现。
**处置**：分两半，**检测侧已修**、根因侧待办。
- 检测侧（已修）：数据新鲜度三件套 —— `FRESHNESS_WARN_SECONDS`（大屏标红）、`/api/health` 按数据新鲜度判 200/503、
  `STALE_ALERT_SECONDS`（连续不健康打 CRITICAL）。即"心跳还在刷、但数据已停"这种情况现在会被判不健康并告警，
  不再是"全绿零数据"。见 `docs/runbooks/真机接入-基线冻结v2.md` §5.2。
- 根因侧（待办）：`gateway.py` 的心跳刷新仍在读设备之前（`touch_heartbeat()`）；原计划 2-2 指标暴露覆盖此场景。

| **2** | "算归算、传归传"分离：`to_reference_o2()` 返回 `nan`（分母≤0，折算不存在）；`to_transmit_value()` 返回 `9999.99`（协议要求传最大值）。注释明令"严禁把哨兵值塞回计算函数，否则'算不出来'会被判成'严重超标'" | Neuron 用 NaN 承载"值失效"语义（错误码 3008 = `isnan()` 转换而来）。这是把协议语义塞进数值本身，不如本项目干净 |
| **3** | 契约自检在导入期（`points.py` 顶部 raise） | Neuron 的 4 层校验里，数据库 CHECK 是运行期才拦 |
| **4** | 全链路单一真源：`points.py` 一处定义，设备/网关/接入/展示共用，注释写明"以前散在 5 个文件各抄一遍，加/改测点必然漏改" | Fledge/Neuron 是运行时配置，不存在这个问题，但也没有"编译期契约"的概念 |
| **5** | 两套重试层的成功判据不同且写明：网关侧 = broker PUBACK；接入层 = DB INSERT 成功 | Neuron 的 store&forward 只做在 MQTT 北向上，其他北向协议无等价缓存；Fledge 有缓冲但判据是"发给北向目的地" |

### 3.2 不如它们的地方（按"会不会真的害你"排序）

| # | 缺口 | 它们怎么做 | 影响 |
|---|---|---|---|
| **1** | 点位模型没有"线格式"字段 | Neuron：14 种字节序 + 位偏移 + 字符串排布，做成点位一等属性，并编码进地址语法（`1!400004#BL`），用每驱动一份 JSON 的 `tag_regex` 按数据类型正则校验 | 真机到货立刻撞 —— 变送器手册明写"16bits 数据高字节在前"，而本项目代码里无处表达字节序 |
| **2** | 点位是"代码"不是"数据" | Neuron：SQLite + Excel 批量导入导出 + 协议元数据自动发现（OPC UA 点位发现）；Fledge：运行时配置 + REST API | 加一台设备 = 改代码 + 重新部署。这正是"配置驱动"要解决的问题 |
| **3** | 地址基准（0 基/1 基）是全局常量 | Neuron 的 Modbus FAQ 坑 #1 就是这个，且按设备配 | 多设备（有的从 40001 起）时会撞。本项目 `REG_BASE=0` 是全局的 |
| **4** | 无指标暴露 | Neuron：`/metrics` Prometheus 文本 + 每节点 `last_rtt_ms`/`tag_reads_total`/`tag_read_errors_total`/`group_last_timer_ms` + 驱动可注册自有指标；Fledge：Health 页看服务响应与数据进出计数 | 只能靠日志，无法做趋势与阈值告警 |
| **5** | 日志无"三件套" | Neuron：每节点一个独立日志文件 + 节点级 DEBUG 开关（带自动回落）+ 一键导出日志包 | 现场排障效率 |
| **6** | 无"保留策略"作为一等概念 | Fledge：purge 任务的 `Retain Unsent Data` 有三个明确选项 —— `purge unsent` / `retain unsent to any destination` / `retain unsent to all destinations`（按目的地逐个跟踪投递状态） | 本项目是"PUBACK/INSERT 后即删"（隐含）。若将来增加第二个下游，会导致其中一个下游丢数 |
| **7** | 无配置版本迁移机制 | Neuron：`persistence/` 下 23 个顺序编号 SQL 迁移脚本，约束下沉到 `CHECK`/`UNIQUE`/外键级联，改约束走"建新表→INSERT SELECT→DROP→RENAME" | 本项目 `points.py` 有"改版说明"注释（写得很细），但没有自动化迁移 |
| **8** | 无审计日志 / 无一键诊断包 | Fledge：Audit Logging 是 Core 功能；Support bundle 含系统诊断报告 | 本项目优先级低 |
| **9** | 无"过滤管道"概念 | Fledge：Filters 分 ingress（转换/富化）与 egress（压缩/削减），可组合成 pipeline 并复用到多个服务；内置 Delta（死区，只发变化量）、Rate（缓存不发的数据、故障时补发）等 | 本项目换算/校验散在网关内联逻辑里 |
| **10** | 存储引擎不可选、取舍未文档化 | Fledge：SQLite / SQLiteLB / PostgreSQL / SQLiteMemory 四选，并明确写出 in-memory 的代价"停机或断电会丢失缓冲数据" | 本项目是文件型 JSONL，无替代方案 |

### 3.3 两个值得学的"坦诚"

- **Fledge**：改存储插件时明确写"不会迁移旧存储里的数据，未发送的数据可能丢失"。
- **Neuron**：主备文档明确写"15 秒检测窗口内两侧都不运行会丢数据""主节点恢复瞬间两节点同时运行会重复数据"，并直言完整 HA"成本极高且现场 PLC/网络往往不支持"。

> 这两家的共同点：把"我们做不到什么"写进文档。
> 本项目的 ADR 已有类似习惯（如 ADR-0007 标注"方案（待评审）"），可以再进一步 —— 把未验证项与失败模式单独汇总一节。

### 复核（2026-10-11）：真机接入的实际结果与原预期不同

**原预期**（2026-10-07 审计时）："真机接入会改动网关/接入层，先有测试再改更安全"（见 2-1 的原"为什么等"）。

**实际结果**：真机接入了，只动"设备接入侧"：

| 改了什么 | 文件 |
|---|---|
| 新增 RS485 → Modbus TCP 桥（扮演现场那台"串口服务器"，跑在 Windows 宿主） | `scripts/serial_bridge.py` |

| 新增变送器点位契约（2 个测点，`int16` / `AB`） | `src/common/points_transmitter.py` |

**未改动**：网关、接入层、库表、大屏 —— 一行未改。

**为什么能不改**：设备层本身就是一个"9 寄存器的 Modbus 从站"。把真机数据喂进它的 2 个寄存器后，
下游看到的仍是同一套接口 → 下游无感。
（现场对应形态：CEMS 里的数采仪把多路仪表聚合成一个寄存器块，上位机只读它。）

**一处必须说清的额外成果**：「点位集可配置」（`POINT_SET`，对应 §3.2 缺口 #2「点位是代码不是数据」）
已实现但移到独立分支 `feat/point-set-config`（已推 origin 与 gitee），主线未启用。
→ 所以主线相对上一个基线的改动，确实只有设备接入侧（另含更早的日志重构与线格式契约）。

**证据**：`docs/runbooks/真机接入-基线冻结v1.md`（版本标识 / 运行时 / 配置 / 两套链路 / 实测数据）。
