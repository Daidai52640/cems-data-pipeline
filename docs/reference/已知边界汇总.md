# 已知边界汇总（全项目）

> **这份文档解决什么**：本项目的局限散在**每一份文档各自的「局限 / 诚实清单」章节**里 ——
> `runbooks/离线部署验证.md` 的"没验到的 5 条"、`reference/并发与负载指标.md` 的"局限性 7 条"、
> `runbooks/最终验收报告.md` 的"诚实边界 7 条"、各 ADR 的"后果 / 代价 / 诚实清单"……
> **没有一处能看到全貌**。本文把它们收拢成一张表。
>
> - **收拢范围**：`docs/` 下全部 `.md`（含 `adr/` `runbooks/` `reference/` `test-reports/` `evidence/`
>   `legacy/`）+ 仓库根 `ACCEPTANCE.md`、`README.md`。
> - **提取口径**：只取作者**显式写出来的**"局限 / 未验证 / 不保证 / 已知缺陷 / 代价 / 环境依赖 / 风险 / 误差来源"。
>   **严格只汇总已有内容，不新编边界**；**本表不产生任何新事实**，也没有重跑任何验证。
> - **合并规则**（否则同一件事会在表里出现 5 次）：同一条约束在多份文档里重复出现时，合并为一行，
>   `来源文档` 列**列全**。合并判据是"指的是同一个约束"，不是"措辞像"。
> - **不做的事**：不收"已作废文档里的数字类结论"（旧 RTO 6.33~9.86 s 之类），只收边界；
>   `legacy/` 的作废清单单列在 §5。
> - 配套文档：`docs/reference/术语表.md`（叫法对齐）｜`docs/README.md`（文档导航）

## 1. 结论先行

**表内共 143 条**（不含 §5 的 8 条已作废清单；口径见文末「未确认项」第 1、2 条），按类别分布：

| 类别 | 条数 | 一句话读法 |
|---|---|---|
| **未验证** | **44** | 没测过。既不能说行，也不能说不行 |
| **不保证** | **17** | 测过，但**不能承诺**这条性质成立 |
| **已知缺陷** | **32** | 已确认的实现弱点或已定性的失效模式（含"已修，留痕"） |
| **设计代价** | **36** | **主动取舍**换来的损失（通常已论证过成本收益） |
| **环境依赖** | **14** | 只在特定环境下成立（单机 / Docker Desktop / 本机编码约定 / 镜像搬运方式） |

**全项目最要紧的 3 条**（详见 §3）：

1. **没有真实现场联调** —— 数据是合成的、负载是合成的、没有接过真实仪表与环保平台。这一条**框住了其余几乎所有结论的适用域**。
2. **单机部署 + 库无副本（`REPLICA 1`）+ 备份未挂定时调度** —— 机器一关系统就停；整层可靠性压在**人工执行**的备份上。
3. **"一条不丢"只能限定在"已进入网关的数据"** —— 上游断链真丢（实测净损失 ≈34 条）；broker 重启仍会整台设备丢积压（TC-E2E-002 判定**不通过**，107/272 = 39.3%）；接入层落盘队列还有两种会丢的情形。

> 表内行按**类别**排列，顺序：未验证 → 不保证 → 已知缺陷 → 设计代价 → 环境依赖。
> 每条都能按 `来源文档` 列逐字指回原文。

## 3. 全项目共同的最大边界（只挑 3 条）

**第 1 条 · 没有真实现场联调（它框住了其余所有结论的适用域）**

数据是合成波形、负载是合成的、没有接过一次真实仪表与真实环保平台。这一条同时出现在
`README.md` §已知边界1、`ACCEPTANCE.md` §三-1、`docs/runbooks/全链路验收设计.md` §6、
`docs/runbooks/最终验收报告.md` §4-1、`docs/adr/0006-*` §3 边界3 / §8-1、
`docs/adr/0007-*` §5.1-1、`docs/reference/HJ212协议层独立验证记录.md` §5-1。
读数：**协议层已验证到"官方向量 + 开源实现对拍 + 本地回环"，再往上一步（换真实对端）没有数据。**

**第 2 条 · 单机 + 库无副本 + 备份靠人跑（可靠性预算全压在人工上）**

单台 Windows 宿主、10 个容器、`REPLICA 1`、`SHOW DNODES` 只有 1 个；多机/集群/HA 全未验证；
**备份脚本未挂定时调度**（`docs/runbooks/恢复演练与对账口径.md` §7-1 自称"当前最大的缺口"，
`docs/runbooks/运维手册.md:151` 重复了这条）。读数：**机器一关系统就停；库这一层没有任何副本兜底。**

**第 3 条 · "一条不丢"只能限定在"已进入网关的数据"（唯一会让甲方真丢数据的边界）**

三个实测在同一个方向上：
① 上游（网关↔设备）断链**真丢**，源头没有就是没有（`docs/runbooks/故障台账.md` 故障1，净损失 ≈34 条）；
② **broker 重启零丢失判定不通过** —— 3 次执行 2 次整台设备积压全丢，缺失 **107/272 = 39.3%**，
且根因未定位（`docs/test-reports/TC-E2E-002-*` §十）；
③ 接入层落盘队列**还有两种会丢的情形**（落盘失败 / 超 256 MB 丢最旧），掉电场景未演练
（`docs/runbooks/最终验收报告.md` §4-7）。
读数：**任何"零丢失"的表述都必须带上限定语。**

> **差一档的第 4 名**（值得一提但不进前 3）：**吞吐与采集容量** —— 单网关实例节拍硬上限 ≈1.05 条/秒，
> 52.6 条/秒是"50 个实例编排下测到的点、不是链路容量"（`README.md` §已知边界5、`docs/reference/并发与负载指标.md` §7.3）。
> 它限制的是"能跑多大"，不是"会不会丢"。

## 4. 这些边界是诚实还是风险？

**先说结论：绝大多数是主动取舍（可接受），少数几个是待补的洞；两类混在同一张表里，必须分开读。**

### 4.1 属"主动取舍"（可接受，但**不能把"我们选择不做"说成"验证过不需要"**）

判据是**文档里有没有给出取舍依据或量化触发条件**。符合的：

| 取舍 | 依据出处 |
|---|---|
| 静压用 kPa、温度写 `degC`（偏离国标） | `docs/adr/0001-*` §4（写明真项目怎么办） |
| 折算值不落库、事件表存判定快照 | `docs/adr/0001-*` §3.2、`docs/adr/0002-*` §2.2-4 |
| 不做 SM4 密钥管理闭环 / 不做分包 / 不做补传优先级重排 / 不做规约库 | `docs/adr/0006-*` §3 边界 2/4/5/6、§4（逐条论证） |
| 不做主从复制（"按成本收益判断不做"，且给了触发改动的量化判据） | `docs/adr/0005-*` §1.2、§5.3 |
| 每设备一个接入实例、主题形状不改、缓存目录每实例一份 | `docs/adr/0008-*` §4、§5 |
| Redis 不持久化 / 60 s 安全边界 / 观测覆盖 50 h / 丢 keepalive | `docs/adr/0004-*` §8.1 |
| 只有一个构建入口、`pull_policy: never`、profiles 管不到第二套 | `docs/runbooks/容器重建与代码生效.md`、`docs/runbooks/双设备启用与验证.md` §1 |
| 磁盘写满实验主动不做（先算速率：384 MB/天 → 约 2500 天后才写满） | `docs/runbooks/故障台账.md` 故障4 |
| 验证据点故意放仓库外、A6-4 换机器判 SKIP | `ACCEPTANCE.md` §A6-4、§五-4 |

> 这一类的共同点：**代价被写清了，而且写了"什么条件下应该改回来"**。
> 唯一要避免的表达是把它们说成"验证过不需要"——`docs/adr/0005-*` §5.3 与
> `docs/runbooks/恢复演练与对账口径.md` §7-6 都专门点了这一句。

### 4.2 属"待补的洞"（真风险，按严重度排序）

| # | 风险 | 为什么是洞而不是取舍 |
|---|---|---|
| 1 | **broker 重启仍会丢整台设备的积压**（`TC-E2E-002` 判定**不通过**；107/272 = 39.3% 缺失，库里有永久缺口） | 它不是"选择不做"，是**必测项失败且根因未定位**（没做 EMQX 侧 trace）。这是唯一一条会让甲方真丢数据、且没有关闭时间的项 |
| 2 | **备份未挂定时调度** | 国标 HJ 75 H.4 明确"**应**自动备份"；文档自己称"当前最大的缺口"。属"该做没做"，不是取舍 |
| 3 | **点位模型没有"线格式/字节序"字段** | 文档判据是"真机到货**立刻撞**"（变送器手册明写高字节在前）。已列入第 1 档改进计划（`docs/架构与可维护性说明.md` §四 1-1），属**有硬时限的待补项** |
| 4 | **没有做定时对账** | 后果是"静默丢行在下一次人工对账前不会被发现"——与第 2 条同源（人工依赖） |
| 5 | **5 个大模块约 5100 行没有单元测试** | 文档自评"**这是最严重的一条**"：改它们的唯一保护是分钟级的端到端验收，**结果是"不敢改"** |
| 6 | **验收判据有两处失效 + 一处历史残渣未处置** | 已定性、已登记，但**需要口径决策**；文档明确"不为全绿去改判据"，也就意味着它还挂着 |
| 7 | **无指标暴露（没有 `/metrics`）** | 只能靠日志，无法做趋势与阈值告警；真机接入后是第一批要补的 |
| 8 | **EMQX 4 次自行 `terminate`，根因未定位，且卡住不自愈** | 触发方不在项目控制范围内，只能人工 `docker start`；它直接关系到第 1 条那个失效模式的现场环境 |
| 9 | **消息总线无认证（1883 匿名可读写）** | 默认只绑 `127.0.0.1` 是安全的，但这是**部署约束**而不是能力；要对外必须先做代码改动 |
| 10 | **P3 的回归测试规格尚未实现、9 项待确认全需外部输入** | 属"能力已就绪、只差对接"的正常前置，但在补齐前**P3 不能算验收通过** |

### 4.3 读这张表要守住的三条

1. **"未验证"不等于"有缺陷"**，也不等于"没问题"。它只说明**没有证据**。
   表里 2.1 节的条目**既不能拿来说行，也不能拿来说不行**。
2. **"设计代价"可以对外说，但必须连着代价一起说**。
   例如"我们不做多副本"要接着说"因为单机上多副本与整机故障同一个故障域，收益趋近 0，而且我们**没有验证过**不需要"。
3. **"不保证"是能力边界，"已知缺陷"是要修的东西**。
   两者在对外表述里最容易混：可以说"上游断链时我们保护不了"（不保证），
   但不能把"broker 重启会丢积压"说成"那是边界"——那是**判定不通过的缺陷**。
