## 1. 配置文件在哪、谁注入了什么

| 位置 | 作用 | 说明 |
|---|---|---|
| **环境变量** | **唯一真源** | 4 个服务进程（device / gateway / subscriber / web）启动时读取 |
| `docker-compose.yml` | 容器部署的注入点 | 用 YAML 锚点复用：`x-app`（4 服务共用）、`x-gateway-env`、`x-subscriber-env` |
| `.env.example` → `.env` | 本机/局域网演示的覆盖入口 | compose **自动读取** `.env`；`.env` 已在 `.gitignore` 中，**不要提交** |
| 代码里的默认值 | 兜底 | 与"本机直接 `python src/…` 运行"一致；容器部署时基本都会被 compose 覆盖 |

### 1.1 `docker-compose.yml` 按服务注入的变量（共 7 个服务块有 `environment`）

| 服务块 | 注入的变量 |
|---|---|

**compose 里用 `${VAR:-默认}` 从宿主机 `.env` 取值**（即 `.env` 的取值会再覆盖进容器的 `environment`），
只有这一条链：`.env` / shell → `docker compose` 插值 → 容器 `environment` → `os.getenv`。
⚠️ `docker compose` 的插值发生在 **YAML 解析阶段**，`docker compose up` 之后改 `.env` 必须
`docker compose up -d` 重建容器才生效（见 `docs/runbooks/容器重建与代码生效.md`）。

### 1.2 配置优先级

```
进程环境 / docker-compose environment（最高）
        ↑ 由 .env 插值而来
        ↑
代码里的 os.getenv(NAME, default) 第二个参数（最低：进程环境里没有该变量时才生效）
```

- **没有**配置文件、没有 `.ini/.yaml` 解析、没有命令行参数与环境的合并逻辑（少数脚本另有 `--` 参数，见 §8）。
- `os.getenv(NAME)` **不带默认值**的 7 处，环境缺失即抛 `KeyError`（属**故意失败**，见 §4）。

### 1.3 ⚠️ 密钥类变量：只列名，不列值

下表把 `TD_PASS`、`TD_USER`、`MQTT_*` 凭据相关项的"默认值"一律标为
**「由环境注入（`.env` 的 `TD_USER` / `TD_PASS`）」**，**不复制 `.env` / `.env.example` 里的任何口令**。
代码里确实写有"本机演示用"的回落口令（`src/platform/subscriber_to_td.py:81-82` 等处），
**它只在完全未配置时生效，属演示值，不适用于任何真实部署**；本文不复述其字面值。

## 2. 全表

> **列含义**：**默认值** = 代码第二个参数（"（无默认值）"= 不带第二参数，未设置即 `KeyError`）；
> **用途** = 从代码上下文/就近注释读出，读不出写"用途待确认"；
> **取值范围/单位** = 代码里有校验的以校验为准，否则写代码可读出的量纲；
> **改了会怎样** = **只写能从代码确定的**，代码确定不了的留空（`—`）。

## 3. 怎么自查"一个都没漏"（本次扫描的口径与结果）

| 口径 | 数量 | 说明 |
|---|---|---|
| 被扫描的 `.py` 文件 | **59** | `src/` 25 个 + `scripts/` 34 个（不含 `__pycache__`） |
| **实际读点（AST 调用点）** | **190** | `os.getenv(...)` / `os.environ.get(...)` / `os.environ[...]` |
| **去重后的变量名** | **120** | = 本表 §2.1–§2.7 的全部条目（含 §5 的 **3** 个包装函数间接读取）；**已机器复核：AST 集合与表内条目集合双向零差** |
| 里含 `os.environ[...]` 硬赋值（**不是读**） | 7 | 全部在演练脚本里，见 §4 |
| 正则粗扫 `os.getenv` 或 `os.environ` 的命中数 | 179 | 比 AST 多 3 处：**注释与文档字符串里提到的** `os.getenv("TD_DEVICE", …)`（`_device_scope.py:68`）、`os.getenv(...)`（`verify_alarm_rate.py:38` 注释）、`dict(os.environ)`（`verify_sim_reproducible.py:68`） |

**复算方法**（AST，不依赖正则，排除注释干扰）：

```powershell
# 逐文件统计"真实读点"，与本表条目数对照
python -c "import ast,os;t=0;f=0
for top in ('src','scripts'):
  for dp,dn,fn in os.walk(top):
    if '__pycache__' in dp: continue
    for x in fn:
      if not x.endswith('.py'): continue
      p=os.path.join(dp,x); s=open(p,encoding='utf-8').read(); n=0
      for node in ast.walk(ast.parse(s)):
        if isinstance(node,ast.Call) and isinstance(node.func,ast.Attribute) and node.func.attr=='getenv': n+=1
        if isinstance(node,ast.Subscript) and 'environ' in ast.dump(node.value): n+=1
      if n: f+=1; t+=n; print(p,n)
print('files',f,'reads',t)"
```

**本次的机器自查**：把上表的"变量名"集合与 AST 扫描结果集合做**双向差集**，双向均为 0 ——
即"扫描出的每一个变量都在表里、表里的每一个变量都真的在代码里被读"。同类变量跨服务重复出现时
（`MQTT_TOPIC`/`MQTT_CLIENT_ID` 在网关与接入各一行；`TD_DB` 等 5 个在接入与展示各一行；
`CACHE_MAX_BYTES` 在网关正文与展示层引用各一行；`CACHE_MARGIN_SECONDS` 在展示层正文与校验脚本各一行），
**按所属服务分行列出、来源列把两处行号都给出**，去重后合计 120 个变量名。

⭐ **2026-10-11 的补齐与对账**（真机接入 + 逐点质量位 + 判据 + 停流告警落地后，本表曾**整整少收 13 个变量**——
其中就包括**真机接入的全部 `REAL_DEVICE_*`**：表自称配置的唯一真源，却没收最值钱那一段的配置）。现补齐并逐项对账：

```
表内条目      106
+ 补齐         13   （REAL_DEVICE_* ×7、QUALITY_* ×4、POINT_INVALID_STABLE、STALE_ALERT_SECONDS）
− 包装函数间接读 3   （ALARM_ENABLE、ALARM_HOURLY_ENABLE、QUALITY_CHECK_ENABLE —— 不走 ast.getenv）
= AST 实算     120  ✅ 双向零差
```

**"用途待确认"的条数 = 0**：120 个变量的"实际用途"都能从代码上下文或就近注释读出，
因此 §2 各行的"实际用途"列**没有一条**写"用途待确认"。
读得出用途、但**细节**仍需复核的 8 项，统一列在 §7「未确认项」（不占用该列，以免与"用途未知"混淆）。

## 5. 扫描口径的两个例外（必须写清，否则复算对不上）

1. **包装函数间接读取**：`src/common/alarm_judge.py:169-170` 与 `src/platform/subscriber_to_td.py`（`QualityConfig.from_env` 的 `flag()`）
   都用了 `def flag(key, default): return os.getenv(key, default)…` 这种包装，把变量名当参数传入 →
   AST 在 `os.getenv` 处看到的是形参 `key`，**不是**变量名。
   本表通过"以字符串常量形式传给 `os.getenv` 包装函数的变量名"补齐了 **`ALARM_ENABLE`、`ALARM_HOURLY_ENABLE`、`QUALITY_CHECK_ENABLE`** 三个。
   （⚠️ `QUALITY_JUMP_RATIO` / `QUALITY_FREEZE_SAMPLES` / `QUALITY_FREEZE_TOLERANCE_RATIO` **不**属于这一类 ——
   它们直接写在 `os.getenv(...)` 里，AST 能看见。）
2. **动态变量名**：`scripts/_td_ops.py:381` 的 `env_path()` 支持调用方运行时传入任意变量名，
   静态扫描**列举不全**（当前仓库内未见其带新变量名的调用点）。

## 6. 读取方式小结（同一变量的"多读点"为什么是好事）

- 同名变量在多处被读，**唯一真源的做法是"定义一处、其余引用"**，本仓库已对两处明确这么做了：
  - `CACHE_ENABLED`：唯一真源在 `src/web/cache.py:119`（`CACHE_FLAG`），`report.py` 引用它
  - `TD_PLANT` / `TD_DEVICE`：唯一真源在 `src/web/cache.py:152-153`（`DEVICE_SCOPE`），`report.py` 引用它
- 反之，`TD_URL`/`TD_USER`/`TD_PASS`/`TD_DB`/`TD_STABLE` 在接入层与展示层**各自解析一遍**（§2.2/§2.3），
  `POLL_INTERVAL` 在网关/web/脚本三处各自解析 —— 这类"多点解析"意味着**改一处必须成套改**。
