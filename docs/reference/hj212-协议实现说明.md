# HJ 212—2025 协议实现说明（P1 编解码 + P2 SM4 加解密）

> **定位**：本模块是**能生成、能自校验、能本地回环**的接口层，
> **不是"已对接环保平台"**（ADR-0006 §3 第 3 条）。
> **范围**：只做 ADR-0006 §6 的 **P1（编解码）** 与 **P2（SM4）**。
> P3（出口/传输/补传）与 P5（第二协议与抽象）**不在本模块**。

**标准取证件**：生态环境部官网正式电子版 PDF（92 页，SHA256
`ED5E46FC1CF5DC99ACE6878A5D347F4C0269B818052F3774C9708CF60A74E506`）。
本说明中所有"第 N 页"均指 **PDF 物理页**（不是页脚印刷页码）。

## 3. 官方向量测试的实际输出

`tests/protocol/hj212/test_vectors.json` 里的报文都是**从 PDF 逐字提取**的，
提取脚本会对每条向量重新校验（声明长度 + ANSI CRC16 + SM4 往返）后才写入，
因此 JSON 不可能与原文漂移。

### 3.1 附录 A.1 的 CRC 示例（第 32 页）

原文（分两行印出，`\r\n` 是字面 4 个字符）：

```
##0087QN=20240601085857223;ST=32;CN=1011;PW=123456;MN=010000A8900016F000169DC0;Flag=9;CP=
&&&&2200
```

| 断言 | 实测 |
|---|---|
| 报文总长 | 97 = 2(包头) + 4(长度) + 87(数据段) + 4(CRC) |
| 长度字段 | `0087` → 87（**不含** CRC 的 4 个字符） |
| `CRC16(数据段)` | `2200`，与原文一致 ✅ |
| 头部字段 | QN/ST/CN/PW/MN 逐字一致，`Flag=9` |
| 数据区 | `&&2200`（占位符，与 CRC 同形） |

### 3.2 §6.3.3 表 3 的 `Flag=9` 示例（第 9 页）

原文自述：`Flag= 9的二进制编码00001001，表示版本号为本次修订，需要应答且数据段不包含拆分包。`

| 位 (7..0) | 1 1 1 1 1 1 | 1 | 1 |
|---|---|---|---|
| 二进制 | `00001001` | | |
| 本模块解析 | 版本号 `0010`（=2，本次修订版） | A=0（不拆包） | D=1（需应答） |

另用**本项目 9 个测点**组了一条参考报文做端到端往返（**非官方向量**，原文该处数据区是占位符）：

```
##0258QN=20240601085857223;ST=31;CN=2011;PW=123456;MN=010000A8900016F000169DC0;
Flag=9;CP=&&DataTime=20240601085857;a00000-Rtd=33471.0,a34013-Rtd=12.34,
a21026-Rtd=18.5,a21002-Rtd=42.1,a19001-Rtd=6.8,a01011-Rtd=11.2,a01012-Rtd=138.5,
a01014-Rtd=8.6,a01013-Rtd=101.3&&8801
```

（上面为便于阅读做了折行，实际是**单行 268 字符**。）
`解码 → 再编码` 逐字符一致，`CRC16 == 8801` ✅。

### 3.3 附录 A.2 的四组加密示例（第 32–33 页）

密钥：原文"**密钥使用16个0x30**"→ `bytes([0x30]*16)`（48 个 ASCII `'0'`）。

| # | 场景 | 明文数据区长度 | 官方密文 | 本模块实测 |
|---|---|---|---|---|
| 1 | 非加密，无不足 16 字符部分 | 208 | — | 明文组包，CRC `2200` ✅ |
| 2 | **加密**，无不足 16 字符部分 | 208（=13 整块） | 208 字节 | **逐字节完全相同** ✅ |
| 3 | 非加密，**有**不足 16 字符部分 | 147（=9 整块+3） | — | 明文组包，CRC `B541` ✅ |
| 4 | **加密**，有不足 16 字符部分 | 147 | 144 字节 | **前 144 字节完全相同** ✅，余下 3 字符 `g=N` 保持明文 |

**示例 2 的实测密文（前 2 块，与原文逐字节核对）：**

```
E43E159ACFAB242CB53155FB8B9281A1  A242577ABFAED881BE88B72D69FC55ED
```

**示例 4 的"不足 16 字符"部分**：原文第 33 页把密文印到 `0x03,0xA4}` 就
转入 `g=N&&B541`。实测该 144 字节解密回
`DataTime=…a01014-Fla`，而明文数据区是 147 字符
（`…a01014-Flag=N`）——**余下的 3 个字符 `g=N` 正是原文按附录 A.2
"不足 16 个字符的部分使用明文"规则留在明文的尾部**。
原文的 PDF 文本层把这段明文尾部与收尾的 `}&&` 叠印成了 `}g=N&&`，
属于排版/文本层现象，不是标准内容矛盾。

## 4. `Flag` 位掩码的取值依据（⚠️ 与常见实现不同，务必读）

### 4.1 原文的两句话

表 3 原文：`包括V5、V4、V3、V2、V1、V0、A、D`，并给出示例
`Flag= 9的二进制编码00001001，表示版本号为本次修订`。

**把这两句放在一起读**：`00001001` 里，版本号 `000010` 占的是
**bit5~bit2**，最低两位留给 A 和 D。据此本模块采用：

```
bit:  7  6  5  4  3  2  1  0
      -  -  V5 V4 V3 V2 A  D
```

* `bit5..bit2` = 版本号（4 位）：`0000`=HJ/T 212—2005、`0001`=HJ 212—2017、
  **`0010`=HJ 212—2025（本次修订）**
* `bit1` = A（是否含 `PNUM`/`PNO`）
* `bit0` = D（命令是否应答）

按此布局 `Flag=9` = `00001001` → 版本 `0010`（本次修订）、A=0、D=1，
**与原文自述完全一致**。

### 4.2 用标准正文的所有报文示例反向验证

对标准附录 C（第 52–80 页）的**全部 193 条报文示例**做统计：

| `Flag` 取值 | 二进制 | bits5..2 | 出现次数 | 其中带 `PNUM`/`PNO` |
|---|---|---|---|---|
| 8 | `00001000` | `0010` | 119 | 0 |
| 9 | `00001001` | `0010` | 70 | 0 |
| 10 | `00001010` | `0010` | 2 | **2** |
| 11 | `00001011` | `0010` | 2 | **2** |

两条独立的结构性证据：

1. **`bits5..2` 恒为 `0010`**——正好等于原文自述的"本次修订版本号"。
2. **A 位与 `PNUM`/`PNO` 的有无一一对应（2/2）**：第 77 页的分包示例
   用 `Flag=10/11` 且都带 `PNUM`/`PNO`；其余 189 条用 `Flag=8/9` 且都不带。

同时 `Flag=9/11` 出现在**发出**的命令、`Flag=8/10` 出现在**应答**上，
与" D=命令是否应答"的语义相符。

这组数据被固化成测试 `test_flag_bit_layout_backed_by_appendix_c_histogram`
与 `test_flag_pagination_pair_from_appendix_c_page77`，
以及 `flags.spec_example_consistency()`（把"原文自述与示例一致"变成可断言事实）。

### 4.3 ⚠️ 与 ADR-0006 描述的差异

ADR-0006 §5.1 写"示例：`Flag=9` = `00001001` → 本次修订版 + 需应答 + 不拆包"，
**结论正确**；但它没有写清位宽，若按"V5~V0 占最低 6 位"去实现
（`9 & 0b111111 = 9` → 版本号解析成 `001001`）就会**解错**。
本模块以原文正文的 193 条示例为准，采用 §4.1 的布局。

## 5. SM4 加解密层（P2）

### 5.1 参数（§6.4.2 原文）

SM4、16 字节（128 位）密钥、**ECB**、**Nopadding**；
加密范围是数据段里 `CP=&&` 到 `&&CRC校验码` 之间的字符。

### 5.2 ⚠️ 实现中发现的两个必须写清的坑

#### 坑 1：`gmssl` 的 `crypt_ecb` 会补齐分组，不能直接用

实测 `gmssl==3.2.2`（`CryptSM4`）：无论 `padding_mode` 取 `PKCS7`（默认）还是
`ZERO`，**加密方向都会补齐到下一个分组**——16 字节明文进去、32 字节密文出来。
这与附录 A.2"不足 16 字符的部分使用明文"**直接冲突**。

**处理**：本模块仍然用 gmssl 做 SM4 分组运算，但**只调用它的单分组原语**
（`CryptSM4.one_round`），自己按 16 字符切块循环，把分组模式的控制权拿回来。
算法 100% 来自 gmssl，只是绕开了它的补齐包装。

该行为被固化成回归测试 `test_gmssl_crypt_ecb_padding_trap_is_documented`：
若将来 gmssl 修好这个行为，测试会失败并提示重新评估实现方式。

**SM4 算法本体正确性**由 GB/T 32907 标准测试向量锚定：
密钥 `0123456789abcdeffedcba9876543210`、明文同值 → 密文
`681edf34d206965e86b3e94f536e4246`（`test_sm4_matches_official_standard_vector`）✅

#### 坑 2：加密顺序不可反（附录 A.2）

原文："**先完成 CRC 校验并组包，再对数据段加密**"。
因此**CRC 是对明文数据段算的那一份，加密之后不再重算**。

由此推出一个容易写错的推论：**带密文的报文，其 CRC 无法直接拿收到的数据段复算**，
必须先解密还原明文数据段再校验。实现见 `codec._plaintext_segment` 与
`test_official_a2_packet_roundtrip`（两个加密示例的 CRC 都是 `2200`/`B541`，
与明文示例完全相同）。

### 5.3 加密后长度字段的口径（与 ADR 描述有出入，已按原文修正）

原文两条示例**互相印证**同一个口径：**长度字段 = 数据段的字符数，不含 CRC 的 4 个字符**。

* 附录 A.1：报文 97 = 2 + 4 + **87** + 4，长度字段写 `0087`；
* 附录 A.2 示例 2：长度字段写 `0295` = 80(头部) + 5(`CP=&&`) + 208(密文写法) + 2(`&&`)。

因此：

* **不加密**时，长度字段 = 明文数据段长度；
* **加密**时，长度字段 = **密文字符数**（`{0xNN,…}` 写法下每字节 5 个字符）
  + 头部与 `CP=&&`/`&&` 的长度——即**实际要传出去的字符数**。

⚠️ 附录 A.2 的加密示例里，长度字段填的是 **295 / 234（明文长度）**，
但它实际传输的字符数是 **1128 / 802**。若按原文印刷值解读，接收方无法
按表 2 的定义定位数据段边界。本模块取"与实际传输一致"的口径，
并在测试 `test_encrypted_packet_length_semantics` 中登记该差异。

### 6.3 单位差异（不做换算）

原文缺省单位与本项目工程单位不完全一致，例如
`a00000` 原文 `m3/s`、本项目 `m3/h`（1 m3/s = 3600 m3/h）。
**本模块不做单位换算**——换算是出口层的业务决策，不是编解码层的职责。
差异已在 `factors.Factor.note` 与上表登记。

| # | 不做 | 说明 |
|---|---|---|
| 1 | **SM4 密钥管理闭环** | §6.4.3 要求初始密钥在生态环境部上位机注册、90 日轮换 → **客观不具备条件**。本模块只做"加解密"，密钥一律由调用方传入，**不做任何持久化、传输或轮换**。 |
| 2 | **分包（`PNUM`/`PNO`）闭环** | 只校验结构（成对出现、与 A 位一致），**不做拆包/组包**。本项目 9 测点报文约 262 字符，远低于 `CP` 上限 950。 |
| 3 | **真实网络发送** | 本模块只产出字符串，不碰 socket。 |
| 4 | **补传优先级重排（§8.1.2）** | ADR-0006 §4 已论证本项目实质满足、且真做会引入风险。**`RF=1` 的组装能力已支持**，但"什么时候补传"不在本模块。 |
| 5 | **通用协议适配框架** | 只有一个实现时抽象必错（ADR-0006 §6 原则）。`src/protocol/__init__.py` 刻意不定义任何接口。 |
| 6 | **参数编码表全量录入** | 附录 B 有 80+ 页，只收录本项目用到的 9 个；未收录的一律 `UnknownFactorError`，**绝不臆造**。 |
| 7 | **省/市级平台差异** | ADR-0006 §8 第 2 条已限定：Profile 只做"结构上支持配置"，**不声称适配了某省**。`BUILTIN_PROFILES` 里的两份只用于本地回环与测试。 |

### 7.3 与 ADR-0006 描述不一致之处（**以原文为准**）

| # | ADR-0006 原文 | 标准原文 | 本模块采用 |
|---|---|---|---|
| 1 | §5.1 注"`CP` 指令参数，字符 [0, 950]"（作为唯一上限） | 表 2：**数据段**字符 `[0, 1024]`；表 3：`CP` 字符 `[0, 950]` | 两者都实现：`MAX_DATA_SEGMENT_LENGTH=1024`（§8.1.2）、`MAX_CP_LENGTH=950` |
| 2 | §5.1 示例报文 `##0255…` | 附录 A.1 的官方示例是 `##0087…`（数据段 87 字符） | 用 `0087` 作为官方向量。`0255` 未在 PDF 中定位到对应示例（表 2 只在**举例** "长255，则写为0255"），**不作为向量** |
| 3 | §5.1 示例写 `ST=32` | 表 7：`32` = 地表水体环境污染源；大气污染源是 `31`。原文附录 A.1/A.2 的示例确实是 `32` | Profile 默认 `ST=31`（本项目是烟气），测试向量按原文录 `32` |
| 4 | §5.2 只引用附录 A.2 的"先 CRC 后加密" | 附录 A.2 还规定"**不足 16 个字符的部分使用明文**"（ADR 未引用） | 实现为 Nopadding 的真实语义；并由官方示例 4 验证 |
| 5 | §5.3 CRC 只写"ANSI CRC16" | 附录 A.1 的 C 代码规定了初值/多项式/**异或到高字节**的具体做法 | 按 C 代码逐行实现；注意它**不是**常见的 CRC-16/ARC（后者 check 值 0xBB3D） |
