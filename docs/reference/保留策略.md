# 保留策略（缓冲满了怎么办、什么时候可以删）

> ⭐ **一句话结论**：
> **本项目的策略是「丢最旧、保最新」+ `PUBACK`/`INSERT` 成功即删**。
> ⚠️ 但真正要讲清的是两件事：**① 为什么选它不选另两种；② 它在什么条件下会变成 bug。**

- **状态**：✅ **已实现**（两处缓冲都按同一口径）｜ ⚠️ **裁剪路径未实测**（见 §5）
- **对标**：Fledge 的 purge 任务 `Retain Unsent Data`（三选项，见 §3）

---

## 1. 缓冲在哪两处（参数不同、口径相同）

| | **网关断网缓存** | **接入层落盘队列** |
|---|---|---|
| 文件 | `data/cache.jsonl`（单文件） | `data/subscriber/spool.jsonl`（**分段**） |
| 上限 env | `CACHE_MAX_BYTES` = **64 MiB** | `SUBSCRIBER_SPOOL_MAX_BYTES` = **256 MiB** |
| 裁剪比例 env | `CACHE_TRIM_RATIO` = **0.5** | `SUBSCRIBER_SPOOL_TRIM_RATIO` = **0.5** |
| **策略** | ⭐ **丢最旧、保最新** | ⭐ **丢最旧、保最新** |
| 日志级别 | ⭐ **`CRITICAL`**（喊得响） | 同级（已积压 / 超限 / 丢了多少条 / 保留多少条） |
| 挡的是什么 | 网关 ↔ broker 中断 | 接入层 ↔ 库（写库失败 / 库不可用） |
| 何时删条目 | **收到 MQTT `PUBACK` 后** | **`INSERT` 成功后** |
| 代码 | `gateway.py` `_trim_cache_if_oversize()` | `ingest_spool.py` `_trim_if_oversize()` |

⭐ **为什么两处上限差 4 倍（64 vs 256 MiB）**：
网关侧缓存的是**已在内存里、等 broker 确认**的报文，规模受 broker 短暂中断约束；
接入层落盘的是**已经过了 broker、等库**的报文，要扛的是"库长时间不可用"（运维窗口更长）。
⚠️ 说明：这个理由是**推断的工程口径，不是原文记录** —— 本文把它补成明文。

## 2. 策略：**丢最旧、保最新**（不是"丢最新"、也不是"不丢"）

```
超过上限 ⇒ 读全部行 ⇒ 保留最新 50%（CACHE_TRIM_RATIO = 0.5）⇒ 丢掉最旧的 50%
并且 ⭐ 升 CRITICAL：已积压 X MB 超过上限 Y MB，丢弃最旧的 N 条（保留最新 M 条）
```

**为什么不"不丢"（涨爆盘）**：磁盘写满会让**整条链路**（含日志、库、其它容器）一起崩 ——
用"丢一部分数据"换"系统还活着"，是**有意识的取舍**，不是疏忽。

**为什么不"丢最新"**：⭐ **最新数据是最值钱的** ——
CEMS 的核心用途是**当前排放是否超标**，5 分钟前的数据比 5 小时前的有用得多。
且新数据才可能赶得上"恢复后立刻补传"；丢新的等于**恢复后发的是过时值**。

**为什么保留 50%、而不是"每来一条丢一条"**：
攒够一半再裁，避免**高频小裁剪**（每条都重写整个文件）；代价是**裁剪时会临时超限约 2 倍**
（64 MiB 上限 ⇒ 最坏写到 ~128 MiB 才裁）。⚠️ 这一条是取舍，不是最优。

## 3. ⭐ 对标 Fledge 的 `Retain Unsent Data` 三选项

| Fledge 的选项 | 含义 | 本项目 |
|---|---|---|
| `purge unsent` | 丢未发送的 | ❌ 不采用（等于放弃缓存的意义） |
| `retain unsent to any destination` | 只要**任一**目的地投递成功就能删 | ⭐ **本项目实际等价于这个**（"PUBACK 后即删"） |
| `retain unsent to all destinations` | **必须所有**目的地都投递成功才能删（**按目的地逐个跟踪投递状态**） | ❌ 未实现 —— **因为现在只有一个下游** |

### ⚠️ 3.1 这就是它将来会变成 bug 的地方（架构文档已登记）

> 架构文档 §三 3.2-6 原文：*"本项目是'PUBACK/INSERT 后即删'（**隐含**）。
> ⭐ **若将来增加第二个下游，会导致其中一个下游丢数**。"*

**机制**：现在"删除判据"是**一个**确认（broker 收了 / 库写了）。
一旦北向增加**第二个目的地**（比如同时上送两个平台），仍然"第一个成功就删" ——
⭐ **第二个目的地永远收不到那条数据，而且没有任何报错**（因为第一个成功了）。

**修法**（记录备用，**现在不做**）：改成**按目的地逐个跟踪投递状态**，全部确认后才删 ——
即 Fledge 的第三个选项。代价是**每条报文要记一个投递位图**。

## 4. ⭐ "什么时候可以删缓冲"（2-4 的原问题，真机跑通后才敢回答）

**现有判据：下一跳确认即删**
```
网关缓存   →  收到 MQTT PUBACK                  →  删
接入层落盘 →  TDengine INSERT 成功               →  删
```

⭐ **关键要讲清的一句**：**"下一跳确认"不等于"端到端到达"**。

| 判据 | 证明了什么 | **没**证明什么 |
|---|---|---|
| `PUBACK` | broker **收到了** | ⚠️ 接入层**写进库了**吗？没有 |
| `INSERT 成功` | 库**接受了写入** | ⚠️ 查询**真能查到**吗？异步落盘、副本/保留期都还可能有变数 |

⇒ ⭐ **所以本项目的端到端确认不靠这两个判据，靠"对账"**：
`scripts/verify_data_lineage.py`（逐条追一条数据从设备到库）、
`scripts/verify_pipeline_live.py`（活链路对账）。
**这才是"可以删了"的最终依据。**

## 5. ⚠️ 未实测的部分（如实登记）

| # | 未验证 | 为什么没做 | 登记处 |
|---|---|---|---|
| 1 | ⭐ **64 MiB 裁剪路径从未真正触发过** | 要造 **约 50 万条**积压（超"单次 ≤3 分钟"的度量约束） | `adr/0003` §6.2、`adr/0007` §5.2-7、`reference/并发与负载指标.md` §7.4 |
| 2 | `_take_over_pending()` **全量读入内存** | 大积压下内存峰值未测 | 同上 |
| 3 | 分段方案在 **> 100 段**时的行为 | 未造到那个规模 | `adr/0007` §6-7 |
| 4 | 256 MiB（接入层）裁剪路径 | 同上，同样未触发 | 本文首次登记 |

⇒ ⭐ **诚实结论**：**策略是设计好并写进代码的，但"真到上限时会发生什么"没有实测数据**。
所以对外只能说"**有上限、有裁剪、会喊 CRITICAL**"，**不能说"裁剪经过验证"**。
