# CEMS 并发与负载指标

本文给出 **v3.0.0「高并发」能力**的量化数字：① 横向 N 台设备并发上报（吞吐 vs N、并发下的延迟分位）
② 纵向背压（网关在什么条件下积压、能不能追上、会不会丢）③ 资源余量。
每个数字都带**测法、原始数据位置、误差来源**，并单列一节写**边界与局限性** ——
最容易误读的一处是"负载发生器直发 EMQX、绕过了网关"，见 §7.1。

- 测量时间：2026-10-02 21:30 — 22:25（本地时间，`Asia/Shanghai`）
- 被测拓扑：`loadgen` → EMQX(QoS 1) → 接入层(`subscriber_to_td`) → TDengine；
  纵向背压另起**隔离网关实例**（同镜像 + 环境变量覆盖），见 §5.1
- 机器：15.53 GiB 内存的 Windows 主机 + Docker Desktop；被测期间**生产链路 10 个容器全程 healthy**
- 被测代码：`scripts/loadgen_devices.py`（本版本新增），容器内代码与工作区通过 md5 比对，无差异

## 3. 测法

### 3.1 延迟：三条时间线，全部落在宿主机时钟上

```
t_publish   交给 paho 发布的那一刻        （宿主机 monotonic）
t_arrival   旁听探针收到该报文的时刻      （宿主机 monotonic）
t_seen      REST 轮询首次查到该 ts 的时刻 （宿主机 monotonic）

lat_gen    = t_publish − 计划发布时刻    ← 本机发送侧排队
lat_broker = t_arrival − t_publish       ← 发布 → broker 投回
lat_store  = t_seen − t_arrival          ← broker → 库内可查
lat_e2e    = t_seen − t_publish          ← 端到端
```

四条延迟**全部由宿主机时钟相减**，因此**不含跨容器时钟漂移**。
这一条很重要：容器虚拟时钟存在 823 ms 级锯齿（见 [性能与可靠性指标.md](性能与可靠性指标.md) §3），
是该链路上最大的时钟误差源；本文口径刻意避开它，代价是**放弃使用报文自身的 `ts`** ——
报文 ts 与真实网关一样是**秒级**的（未改契约），用它当起点会叠加 `U(0,1) s` 量化偏差。
报文 `ts` 只用于对账。

### 3.2 对账：逐条，不是抽样

```
发布集合 P = {(设备, ts)}      ← 运行期台账（实际发出去的那些，不按算法重算）
库内集合 D = 该设备子表里的全部 ts
missing  = |P − D|   >0 就是真丢数
extra    = |D − P|   库内落在本次发布集合之外的行（历史残留 / 上一轮遗留）
duplicate_ts = 库内同一 ts 出现多行
```

⚠️ TDengine 子表主键是 `(子表, ts)`，**同 ts 是覆盖而非追加**，所以"库内行数 < 发布条数"
既可能是丢数、也可能是同秒覆盖。本文用两条判据区分：① `missing` 必须为 0；
② 造数保证**同一台设备同一秒只有一条**（见 §4.1 的构造约束）。

### 3.3 收尾判据

高并发下 broker 队列 + 接入层单线程会让"入库"明显滞后于"发布结束"（实测滞后可达 40 s）。
因此收尾判据是"**库内可见条数 = 已发布条数**"，而不是等固定秒数 ——
否则汇总里的"库内可见"会小于"已发布"，看起来像丢数，其实只是还没查完。
汇总里的 `throughput.drain_complete` 就是这个判据的结果，引用数字前请先看它。

## 4. 横向：吞吐 vs N

### 4.1 被测负载

| 运行 | N | 周期 | 时长 | 接入实例数 k | 发布线程 | 发布条数 | 排空完成 |
|---|---|---|---|---|---|---|---|
| n2 | 2 | 1 s | 30 s | 2 | 2 | 60 | ☑ |
| n10 | 10 | 1 s | 40 s | 10 | 10 | 400 | ☑ |
| n50 | 50 | 1 s | 20 s | 50 | 50 | 1000 | ☑ |

- **每台曲线不同**：每台一个派生种子（`seed + (i-1)×7919`）+ 一个相位偏移；
  汇总里为每台记了 `curve_digest`（9 个测点值的 sha256 前 12 位），50 台两两不同。
- **报文格式逐字复用** `src/gateway/gateway.py` 的 `build_payload()`：
  `"YYYY-MM-DD HH:MM:SS Flow=… Dust=… … Pressure=… Flag=N"`（9 个测点，顺序取 `points.POINTS`），
  数值全部收在量程内（超量程会被接入层**整条拒收**，负载发生器不造非法数据）。
- **构造约束（必须知道）**：接入层子表主键是 `(子表, ts)`，所以**同一张子表里的多台设备必须落在不同整秒**。
  `--ingest-channels k < N` 时负载发生器给通道内第 j 台加 j 秒整数偏移并在
  `每通道台数 > 周期` 时告警；**本文三组运行都是 k=N（一台一张表），偏移恒为 0，数字不含该构造**。

### 4.2 结果

| N | 发布速率（条/秒） | 端到端吞吐（条/秒） | 发布成功 | 旁听到达 | 库内可见 | 缺失 | 重复 ts |
|---|---|---|---|---|---|---|---|
| 2 | 2.069 | 2.069 | 120 | 120 | 120 | **0** | 0 |
| 10 | 10.256 | 10.256 | 400 | 400 | 400 | **0** | 0 |
| 50 | 52.587 | 52.032 | 1000 | 1000 | 1000 | **0** | 0 |

- 名义速率（N ÷ 周期）= 2 / 10 / 50 条/秒；实测 2.07 / 10.26 / 52.59 条/秒。
  偏差来自"发布窗口按首末两条之间的实际时长计"，不是丢数。
- **吞吐随 N 线性**：单台始终 ~1 条/秒，N 从 2 到 50 未出现饱和迹象。
- 表中 `库内可见` 是**排空之后**的数字：三组 `drain_complete=true`，
  即发布出去的每一条都真的在库里（逐条对账 `missing=0`）。

### 4.3 并发下的延迟分位（毫秒）

| N | publish→broker P95 | broker→库内可查 P50 / P95 | **端到端 P50 / P95 / max** |
|---|---|---|---|
| 2 | 16.0 | 172.0 / 328.0 | **172.0 / 329.0 / 344.0** |
| 10 | 16.0 | 203.5 / 344.8 | **204.0 / 359.1 / 391.0** |
| 50 | 16.0 | 157.0 / 297.0 | **172.0 / 297.0 / 360.0** |

读数：

- 三组端到端 P50 都在 **0.17 ~ 0.21 s**、P95 都在 **0.30 ~ 0.36 s**，**没有随 N 单调恶化**
  （N=50 反而略低于 N=10，差 32 ms —— 那是单次 20 s 窗口的抖动，不能读成"越大越快"）。
- 延迟几乎全部落在 `broker → 库内可查`（P50 157~204 ms）；`publish → broker` 的 P95 只有 16 ms。
- 这 150~200 ms 里含**轮询量化**：`t_seen` 是 0.3 s 一次的 REST 轮询得到的，
  所以 `lat_store`/`lat_e2e` 天然带 `U(0, 300 ms)` 均匀偏差（P50≈150 ms 正好是它的一半）。
  → **真实入库延迟是几十毫秒量级**；本文 P50/P95 是**观测上界**。
  独立佐证：裸 REST 单行 INSERT 实测 **6.0 ms/行（167 行/秒）**，见 §5.4。

## 5. 纵向：背压

### 5.1 为什么要另起一个"隔离网关实例"

要压的是**网关采集层**，但生产网关（`cems-gateway`、`cems-gateway-plant2`）的 `POLL_INTERVAL=5.0`
写在 `docker-compose.yml` 里，而本次任务的硬约束是**不改任何既有文件**。
因此用**同一个镜像 + 环境变量覆盖**另起一个一次性实例（`POLL_INTERVAL`/`PUBLISH_ACK_TIMEOUT`/
`RESEND_WINDOW`/`RESEND_RETRY_INTERVAL` 本来就是环境变量，没有改一行代码）：

```powershell
docker run -d --name cems-loadgen-gw-<tag> --network cems-net `
  -v "<临时目录>:/app/data-loadgen" `
  -e POLL_INTERVAL=0.2 -e MQTT_TOPIC=cems/loadtest/gw/device1/data `
  -e MQTT_CLIENT_ID=cems-loadgen-gw-<tag> -e GATEWAY_DATA_DIR=/app/data-loadgen `
  -e MODBUS_HOST=device -e MODBUS_PORT=5020 -e MODBUS_UNIT=1 `
  cems-pipeline:latest python src/gateway/gateway.py
```

主题前缀独立、缓存目录挂临时目录、`client_id` 独立 → 生产两台设备的数据/主题/缓存都不受影响（§8 有复核）。
数据源仍是真的 Modbus 仿真设备（`cems-device:5020` 从站 1）。

### 5.2 结论①：网关采集循环有 ≈1 条/秒/实例 的硬上限

把同一个网关实例的轮询周期从 5 s 一路压到 0.05 s（**100 倍**）：

| `POLL_INTERVAL` | 运行时长 | 实际发布速率 | 缓存峰值 | 补传次数 |
|---|---|---|---|---|
| 5.0 s | 40 s | 0.23 条/秒 | 0 行 | 0 |
| 1.0 s | 45 s | 1.09 条/秒 | 0 行 | 1（见下） |
| 0.2 s | 60 s | 1.09 条/秒 | 0 行 | 0 |
| 0.05 s | 100 s | 1.05 条/秒 | 0 行 | 0 |

（速率由旁听器按**唯一 ts** 统计：`backpressure_<tag>_published.json`。）

**压不动**：0.2 s 与 0.05 s 的相对速率差 < 4 %。原因在采集主循环的形状：

```
每轮 = 读 Modbus（本地 ~1 ms） + 等 PUBACK（本地往返 ~1 ms） + sleep(POLL_INTERVAL)
```

`POLL_INTERVAL` 只能缩到 0，而循环体自身占用（paho 的 `wait_for_publish` + `time.sleep` 实际唤醒粒度）
叠起来约 **0.9 s**，于是单实例节拍停在 **~1.1 轮/秒**。这是**本机 + 本部署下的实测常数**，
换机器/换 broker 距离都会变，不可外推（§7.3）。

> ⚠️ 这正是"提高频率打爆"在本部署下**打不爆**的原因：网关还没开始丢数据，它自己先慢下来了。
> 想压出积压必须让 `publish()` **失败**（断网 / broker 慢），而不是提高频率 —— 见 §5.3。

`POLL_INTERVAL=1.0` 那唯一 1 条缓存，日志原文是 `[缓存] 断网，数据已入本地队列`
（换实例重启的瞬间 paho 还没连上），随后 `[补传] 开始补传 1 条` → `[补传完成] 已确认 1 条`。
它顺带证明**断网缓存 + 补传这条路径是活的**。

### 5.3 结论②：缓存与补传的追赶能力（人工播种积压）

既然自然压不出积压，就**人工播种**：在隔离网关的缓存目录里预写 120 行报文
（格式与网关自己写的完全一致，时间戳分布在过去 120 s，模拟"断了 2 分钟"），再启动网关观察它怎么追。

| 项 | 值 |
|---|---|
| 播种条数 | **120**（`21:56:28` → `21:58:27`，1 s 间隔） |
| 网关启动瞬间 | `[补传] 开始补传 120 条，在途窗口 100 条` |
| **同一秒内** | `[补传完成] broker 已确认 120 条` |
| 旁听器统计（整段，按唯一 ts） | **226** 条已发布（= 120 播种 + 106 新采集） |
| TDengine 表 `loadtest_lt6` 行数 | **226** |
| 逐条对账 | **缺失 0**、重复 ts 0 |
| 结束时候选缓存目录 | `cache.jsonl` **0 行**、`inflight-*` **0 个** |

**结论：120 条积压在同一秒内全部补发并被 broker 确认，一条不丢，缓存归零。**
单条 PUBACK 本地往返是毫秒级，所以补传吞吐约等于采集循环的节拍上限（§5.2），120 条远未触及上限。

> **没测到的**：更大积压（数千条以上）的**排空耗时曲线**。
> 采样口径决定了它抓不到：补传期间 `cache.jsonl` 是 0 行（数据已被原子改名进
> `inflight-<seq>.jsonl`，并在补传窗口内被滚动压缩回写），1.5 s 一次的目录采样全是 0
> （[backpressure_catchup_cache.csv](../evidence/perf/backpressure_catchup_cache.csv) 68 个采样点均为 0）。
> 要画出排空曲线得让补传慢下来（例如 `RESEND_WINDOW=1` 强制每轮只发 1 条），列入 §7.4 后续。

### 5.4 旁证：存储层不是瓶颈

裸 REST 直插（不经 MQTT/接入层，只测 taosAdapter 的写入能力；两次独立运行，取较慢的一次）：

| 方式 | 实测 |
|---|---|
| 单行 INSERT × 200 | **6.0 ms/行 → 166.8 行/秒**（第二次 4.2 ms / 235.5 行/秒） |
| 一批 100 行 | 38 473 行/秒（第二次 64 468） |
| 一批 1000 行 | 171 567 行/秒（第二次 177 432） |

原始数据：[raw_insert_bench.json](../evidence/perf/raw_insert_bench.json)。

即：本文 52.6 条/秒的峰值离存储层单行写入上限（167 行/秒）还有 **3 倍余量**；
而接入层是**单线程同步 INSERT**（`on_message` 内直接执行 SQL 并等返回），
所以接入层的理论上限 ≈ 167 条/秒/实例。

## 6. 资源余量

用 cgroup v2 的 `cpu.stat: usage_usec` 与 `memory.current` **前后两次采样相减**，
得到负载期间的**真实占用**（比 `docker stats` 的"容器生命周期均值"准；
`docker stats --no-stream` 快照另存在 `loadgen_stats_<tag>_post.csv` 作为内存口径对照）。

| 容器 | N=2 | N=10 | N=50（1000 条） |
|---|---|---|---|
| emqx | 19.9 % × 1 核 / +27.1 MB | 20.4 % / −2.8 MB | **24.1 % / +43.3 MB** |
| tdengine | 4.9 % / −19.2 MB | 6.5 % / +20.4 MB | **11.1 % / +32.2 MB** |
| cems-subscriber（生产） | 0.6 % | 0.3 % | 0.3 % |
| cems-gateway（生产） | ~0.7 % | 0.6 % | 0.6 % |
| cems-device | 1.4 % | 1.5 % | 1.5 % |

（`% × 1 核` = 该时段 CPU 秒数 ÷ 墙钟秒数；宿主 15.53 GiB 内存。）

- **CPU 大头在 broker**（20~24 %×1 核），不在接入层。部分原因是本文给每台设备起了
  一个**持久会话**的接入实例（N=50 → 50 个连接），连接数本身要花 broker 的 CPU。
- **存储层**从 5 % 涨到 11 %×1 核，是唯一随 N 明显变化的被测组件。
- **内存增量都很小**（最大 +43 MB，来自 emqx 的会话/队列）；15.53 GiB 里 emqx 占 0.53 GiB、
  tdengine 占 0.47 GiB，余量充足。
- ⚠️ 不要把这里读成"容量上限只有 52 条/秒"：瓶颈是**测试机的编排方式**
  （一台一实例 = 一台一个连接 + 一个进程），不是链路本身，见 §7.3。

## 7. 局限性（引用本文数字前必须读）

### 7.1 ⭐ 负载发生器直发 EMQX，**绕过了网关**

报文虽然与真实网关**逐字一致**，但 `scripts/loadgen_devices.py` 是**直接 publish 到 EMQX** 的：

| 本文测到了 | 本文**没有**测到 |
|---|---|
| 接入层（`subscriber_to_td`）的解析 / 量程白名单 / 建子表 / INSERT | 网关的 Modbus 轮询、寄存器换算、`build_payload` 的采集节奏 |
| EMQX 的 QoS 1 投递与持久会话排队 | 网关的**断网缓存**与**补传**在真实负载下的行为（只测了播种追赶，§5.3） |
| TDengine 的写入 | 告警判定 / 小时结算链路（本文接入实例全部 `ALARM_ENABLE=0`） |

**所以 §4 的"吞吐 vs N"是「接入 + 存储层」的容量，不是「网关采集层」的容量。**
网关侧容量在 §5 单独测，其上限（~1.05 条/秒/实例）比 §4 的 52.6 条/秒低两个数量级 ——
**两者不可互换引用。**

### 7.2 延迟数字带 300 ms 级量化上界

`t_seen` 由 0.3 s 一次轮询得到，故 `lat_store`/`lat_e2e` 逐条误差是 `U(0, 300 ms)`。
本文 P50（~0.18 s）几乎正好是该分布中位数，**说明观测值主要反映轮询相位而非链路**。
严格可引用的只有两条：① 分段相对大小（入库段远大于 broker 段）；
② 上界 —— **端到端真值 ≤ 观测 P50 − 150 ms ≈ 30 ms 量级**，与 §5.4 的 6 ms/行自洽。

### 7.3 N 的上限是测试机的容器数，不是链路容量

本文按"一台设备一个接入实例"测（与生产同构），N=50 就要 50 个 Python 进程 + 50 个 MQTT 连接。
再往上加，先撞到的是**本机进程数/内存**（每实例约 27 MB 常驻），不是 EMQX 或 TDengine。
所以 **52.6 条/秒是"50 个实例编排下测到的点"，不是链路容量上限**。
接入层的**架构**上限只能从代码推：单实例单线程同步 INSERT ≈ 167 条/秒（§5.4）。
要多实例聚合吞吐，正确方向是改接入层为"单实例订阅通配 + 按主题解析设备号"（契约外改动，见 ADR-0008）。

### 7.4 未做的实验

| # | 没做 | 为什么 |
|---|---|---|
| 1 | 真实断网 + 大积压 + 排空曲线 | 需停 `emqx`，会影响生产两条设备链路；改用"人工播种积压"替代（§5.3），只测了 120 条 |
| 2 | `cache.jsonl` 64 MB 上限裁剪（`CACHE_MAX_BYTES`） | 要造 64 MB 积压（约 50 万条），超出"单次 ≤3 分钟"约束 |
| 3 | 接入层多实例**共享同一子表**（多对一） | 表结构决定的不可用组合（同秒覆盖），已作为构造约束标注（§4.1） |
| 4 | 跨天/长稳（内存增长、时间戳漂移） | 本次窗口 < 1 小时 |
| 5 | 用 `RESEND_WINDOW=1` 强制慢补传以画出排空曲线 | 需要 20 min 级窗口，与"单次 ≤3 分钟"冲突 |

### 7.5 采样口径造成的盲区

1. **缓存目录采样抓不到补传过程**：补传期间数据在 `inflight-<seq>.jsonl` 里且被滚动压缩，
   1.5 s 一次的目录采样恒为 0（§5.3）。
2. **`--settle` 语义**：收尾判据是"库内可见 = 已发布"（见 §3.3）。
   早期一版实现按"固定等 N 秒"收工，会把"还没查完"误判成丢数 —— 该口径缺陷已在脚本内注释记录。

### 7.6 EMQX 队列深度：**能查到，但本文没有把它当证据**

`docker exec emqx emqx ctl clients list` 的每个客户端带 `enqueued_msgs` / `dropped_msgs` / `inflight`
字段，理论上可直接读队列深度。本文没把它当依据，原因：
① 本次运行中**没有取到可信、可复现的增量口径**（数量级与 §4 结果不匹配）；
② 丢数判据用**逐条对账**（发布集合 vs 库内集合）更直接、更强。
另：`max_mqueue_len=20000`（约 27 h @5 s）与 `session_expiry_interval=24h` 在本次负载下**远未触及**。

### 7.7 其他

- 主机是 Windows + Docker Desktop（WSL2 后端），容器共享同一内核；容器虚拟时钟有 823 ms 级锯齿。
  本文用宿主时钟规避了跨时钟误差，但**发布节拍抖动**（Windows `time.sleep` ~15 ms 粒度）会进
  `lat_gen`（实测 P50 0 ms / P95 16 ms）。
- **`extra` 不为 0 的运行**：那是**上一轮运行遗留在 EMQX 持久会话队列里的行**在本次被投递进来
  （用 `client_id` 区分运行可避免）。它**不影响**"缺失=0"这条结论（`missing` 只看发布集合），
  但会让"库内总行数"变大。汇总里 `reconciliation.window` 给出了本次发布 ts 的时间窗，
  可据此判断 `extra` 是不是别的运行留下的。
- **同一秒的采样上限**：接入层子表主键 `(子表, ts)` 决定了**单台设备每秒最多一条**。
  真实网关是 5 s/条，不会碰到；但做更高频压测时，负载发生器必须让同一台设备跨秒
  （`interval < 1 s` 时脚本会自动切成"每秒发一台"的轮询，代价是每台有效采样周期被拉长到 N 秒）。

## 8. 不污染真实链路的证据与清理

- **主题隔离**：负载发生器只发 `cems/loadtest/...`；生产网关只发 `cems/plant1/data`、`cems/plant2/data`。
  接入实例按**精确主题**订阅，不存在"通配订阅把 loadtest 数据吸进生产子表"的路径。
- **标签隔离**：入库标签固定 `plant=loadtest`、`device=lt<i>` → 子表 `loadtest_lt<i>`；
  生产子表是 `plant1_device1` / `plant2_device2`，**不共用子表**。
- **运行期间生产链路复核**（压测结束后立即查）：
  - `device IN ('device1','device2')` 的最近数据**正常递增**（`device1` 21:16:28/21:16:33，`device2` 21:16:24/21:16:29）；
  - 10 个容器全部 `healthy`；
  - 隔离网关实例用独立 `client_id` 与独立缓存目录，用完 `docker rm -f` 删除。
- **清理**（已执行）：`& $py scripts/loadgen_devices.py --devices 60 --cleanup` →
  `dropped` 60 张表；复查 `SELECT COUNT(*) FROM cems.cems_data WHERE tbname LIKE 'loadtest%'` = **0**。

## 9. 没做到 / 不确定（诚实清单）

1. **没造出"自然积压"**：单台网关轮询压到 0.05 s（100 倍）后缓存仍恒为 0 行 ——
   因为采集循环自身有 ~1.05 条/秒硬上限（§5.2）。要积压必须让 broker 侧失败，
   而本次约束不允许停生产 `emqx`。所以纵向背压的"积压增长曲线"实际是**一条 0 值平线**，
   照实报，没有编造上升段。
2. **大积压的排空耗时未测**：只测了 120 条（同秒补完）；数千条以上的排空曲线与 64 MB 裁剪阈值都没跨过（§7.4）。
3. **延迟真值给不出**：秒级 ts + 0.3 s 轮询量化，只能给观测上界（§7.2）。
4. **52.6 条/秒不代表链路容量**：同时受"50 个容器 + 50 个连接"的测试机编排限制（§7.3）。
5. **告警/折算链路未纳入**：接入实例全部 `ALARM_ENABLE=0`，
   没有测"并发 + 告警判定 + 小时结算"叠加时的表现。
6. **EMQX 队列深度未作为证据**：命令查得到，但没取到可信可复现的增量口径（§7.6）。
7. **接入层"多对一"能力是空的**：一个实例只能订阅一个主题、只能写一张子表，
   N 台设备必须 N 个实例，且同一子表里多台设备必须错开整秒。
   这不是本次引入的问题，但它是横向扩展的真实约束，写在这里备查。
8. **测量期间有并发干扰**：本次测量与另一个执行体在同一仓库/同一台机器上并行跑过压测，
   出现过进程互相清理、持久会话队列把上一轮数据投递进来的现象（表现为 `extra` 偏大）。
   本文引用的三组吞吐与四档背压数字都对账 `missing=0`；受干扰的运行未收入本文。
   复测时请**独占机器**，并给每轮不同的 `--tag`（`client_id` 随之不同）。
