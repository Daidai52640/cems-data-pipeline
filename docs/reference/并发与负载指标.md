# CEMS 并发与负载指标

本文给出 **v3.0.0「高并发」能力** 的量化数字：① 横向 N 台设备并发上报（吞吐 vs N、并发下的延迟分位）
② 纵向背压（网关在什么条件下积压、能不能追上、会不会丢）③ 资源余量。
每个数字都带**测法、原始数据位置、误差来源**，并单列一节写**边界与局限性** ——
本文最容易误读的地方是"负载发生器直发 EMQX、绕过了网关"，见 §7.1。

- 测量时间：2026-10-02 21:30 — 22:25（本地时间，`Asia/Shanghai`）
- 被测拓扑：EMQX(QoS 1) → 接入层（`subscriber_to_td`）→ TDengine；另有**隔离网关实例**用于纵向背压
- 机器：15.53 GiB 内存的 Windows 主机 + Docker Desktop；被测期间**生产链路的 10 个容器全程 healthy**

## 3. 测法（延迟三条时间线，全部落在宿主机时钟上）

负载发生器在发布每条报文时记下三个宿主时刻，再用 REST 轮询补齐第四个：

```
t_publish   交给 paho 发布的那一刻            （宿主机 monotonic）
t_arrival   旁听探针收到该报文的时刻          （宿主机 monotonic）
t_seen      REST 轮询首次查到该 ts 的时刻     （宿主机 monotonic）

lat_gen    = t_publish − 计划发布时刻        ← 本机发送侧排队（纯宿主时钟）
lat_broker = t_arrival − t_publish           ← 发布 → broker 投回（纯宿主时钟）
lat_store  = t_seen − t_arrival              ← broker → 库内可查（纯宿主时钟）
lat_e2e    = t_seen − t_publish              ← 端到端（纯宿主时钟）
```

四条延迟**全部由宿主机时钟相减**，因此**不含**跨容器时钟漂移
（容器虚拟时钟的锯齿漂移见 [性能与可靠性指标.md](性能与可靠性指标.md) §3，极差可达 823 ms ——
本项目既有文档已经证明它是这条链路上最大的时钟误差源，本文口径刻意避开它）。

为什么不能直接用报文里的 `ts` 当起点：报文 ts 是**秒级**的（与真实网关一致，未改契约），
用它算延迟会叠加 `U(0,1) s` 的量化偏差。本文的入站侧一律用 `t_publish`，`ts` 只用于对账。

对账口径（逐条，不是抽样）：

```
发布集合 P = {(设备, ts)}                    ← 运行期台账，不是按算法重算
库内集合 D = 该设备子表里的全部 ts
missing = |P − D|   （>0 就是真丢数）
extra   = |D − P|   （历史残留 / 别的运行留下的行，不计入丢数）
重复ts  = 库内同 ts 出现多行
```

⚠️ 第 4 条：TDengine 子表主键是 `(子表, ts)`，**同 ts 是覆盖而不是追加**，
所以"库内行数 < 发布条数"既可能是丢数、也可能是**同秒覆盖**。本文靠两点区分：
① `missing` 必须为 0；② 造数时保证**同一台设备同一秒只有一条**（见 §4.1）。

## 4. 横向：吞吐 vs N

### 4.1 被测负载

三次运行都是"**每台设备 1 s 一条、各一条独立曲线**"，唯一变量是 N：

| 运行 | N | 周期 | 时长 | 接入实例数 k | 发布线程 | 发布条数 |
|---|---|---|---|---|---|---|
| n2 | 2 | 1 s | 60 s | 2 | 2 | 120 |
| n10 | 10 | 1 s | 60 s | 10 | 10 | 600 |
| n50 | 50 | 1 s | 20 s | 50 | 50 | 1000 |

**每台的曲线确实不同**：每台一个派生种子（`seed + (i-1)×7919`）+ 一个相位偏移，
汇总里为每台记了 `curve_digest`（9 个测点值的 sha256 前 12 位），50 台两两不同。
报文格式**逐字复用** `src/gateway/gateway.py` 的 `build_payload()`：
`"YYYY-MM-DD HH:MM:SS Flow=… Dust=… … Pressure=… Flag=N"`（9 个测点，顺序取 `points.POINTS`）。

> **一处必须说明的构造**：`--ingest-channels k < N`（多台共用一张子表）时，
> 同一子表内多台设备必须落在**不同的整秒**上，否则 `(子表, ts)` 同秒覆盖会让"N 台"塌成"1 台"
> （实测：10 台共用一张表时 300 条只留 39 行）。负载发生器因此给第 j 台加 j 秒的整数偏移，
> 并在 `每通道台数 > 周期` 时告警。本文的三次吞吐运行 **k=N**（一台一张表），
> 此偏移恒为 0 —— 也就是说**本文数字不含这个构造**。

### 4.2 结果

| N | 发布速率（条/秒） | 端到端吞吐（条/秒） | 发布成功 | 旁听到达 | 库内可见 | 缺失 | 重复 ts |
|---|---|---|---|---|---|---|---|
| 2 | 2.034 | 2.034 | 120 | 120 | 120 | **0** | 0 |
| 10 | 10.169 | 10.169 | 600 | 600 | 600 | **0** | 0 |
| 50 | 52.587 | 52.587 | 1000 | 1000 | 1000 | **0** | 0 |

- "端到端吞吐" = 库内可见条数 ÷（发布第一条 → 最后一条可见）的总时长，**含排空时间**，
  因此它是"链路真正吞下去的速率"，而不是"发出去多快"。N=2/10/50 三组都 `drain_complete=True`。
- 名义速率（N ÷ 周期）分别是 2 / 10 / 50 条/秒；实测 2.03 / 10.17 / 52.59，
  偏差来自"发布窗口按首末条之间的实际时长计"，不是丢数。
- **吞吐随 N 线性**：2 → 10 → 50 台，速率 2.03 → 10.17 → 52.59 条/秒，单台仍是 ~1 条/秒。
  即在本机（EMQX + TDengine + 10 个生产容器同时在跑）环境下，**接入+存储层没有出现饱和迹象**。

### 4.3 并发下的延迟分位（毫秒）

| N | publish→broker P95 | broker→库内可见 P50 / P95 | **端到端 P50 / P95 / max** |
|---|---|---|---|
| 2 | 16.0 | 179.5 / 312.0 | **179.5 / 312.0 / 344.0** |
| 10 | 16.0 | 203.5 / 344.8 | **204.0 / 359.1 / 391.0** |
| 50 | 16.0 | 157.0 / 297.0 | **172.0 / 297.0 / 360.0** |

读数：

- 三组的端到端 P50 都在 **0.17 ~ 0.21 s**、P95 都在 **0.30 ~ 0.36 s**，**没有随 N 单调恶化**
  （N=50 反而比 N=10 略低，差 32 ms —— 这是单次 20 s 窗口的抖动，不能读成"越快越稳"）。
- 延迟几乎全部落在 `broker → 库内可查` 这一段（P50 157~204 ms），
  而 `publish → broker` 的 P95 只有 16 ms。
- 这 150~200 ms 里含**轮询量化**：`t_seen` 是 0.3 s 一次的 REST 轮询查到的，
  所以 `lat_store`/`lat_e2e` 天然带 `U(0, 300 ms)` 的均匀偏差（P50≈150 ms 正是它的一半）。
  → **真实入库延迟的量级是几十毫秒**；本文的 P50/P95 是"观测上界"。
  独立佐证：裸 REST 单行 INSERT 实测 **6.0 ms/行（167 行/秒）**（§5.4）。

## 5. 纵向：背压

### 5.1 为什么要另起一个"隔离网关实例"

要压的是**网关采集层**，但生产网关（`cems-gateway`、`cems-gateway-plant2`）的
`POLL_INTERVAL=5.0` 写在 `docker-compose.yml` 里，而本次任务的硬约束是**不改任何既有文件**。
所以纵向背压用**同一个镜像 + 环境变量覆盖**另起一个一次性实例：

```powershell
docker run -d --name cems-loadgen-gw-<tag> --network cems-net `
  -v "<临时目录>:/app/data-loadgen" `
  -e POLL_INTERVAL=0.2 -e MQTT_TOPIC=cems/loadtest/gw/device1/data `
  -e MQTT_CLIENT_ID=cems-loadgen-gw-<tag> -e GATEWAY_DATA_DIR=/app/data-loadgen `
  -e MODBUS_HOST=device -e MODBUS_PORT=5020 -e MODBUS_UNIT=1 `
  cems-pipeline:latest python src/gateway/gateway.py
```

- 主题前缀 `cems/loadtest/gw/...`、缓存目录挂临时目录、`client_id` 独立
  → **生产两台设备的数据、主题、缓存文件都不受影响**（§8 有复核）。
- `POLL_INTERVAL` / `PUBLISH_ACK_TIMEOUT` / `RESEND_WINDOW` / `RESEND_RETRY_INTERVAL`
  全部本来就是环境变量（见 `src/gateway/gateway.py` 配置区），**没有改一行代码**。
- 数据源仍是真的 Modbus 仿真设备（`cems-device:5020`，从站 1）。

### 5.2 结论①：网关采集循环存在 ≈1 条/秒/实例的硬上限

把同一个网关实例的轮询周期从 5 s 一路压到 0.05 s（100 倍），实测发布速率：

| `POLL_INTERVAL` | 运行时长 | 实际发布速率 | 缓存峰值 | 补传次数 |
|---|---|---|---|---|
| 5.0 s | 40 s | 0.23 条/秒 | 0 行 | 0 |
| 1.0 s | 45 s | 1.09 条/秒 | 0 行 | 1（1 条，见下） |
| 0.2 s | 60 s | 1.09 条/秒 | 0 行 | 0 |
| 0.05 s | 100 s | 1.05 条/秒 | 0 行 | 0 |

（速率由旁听器按**唯一 ts** 统计，见 `backpressure_<tag>_published.json`。）

**压不动**：0.2 s 与 0.05 s 的相对发布速率差别 < 4 %。原因在采集主循环的形状：

```
每轮 = 读 Modbus（本地，~1 ms） + 等 PUBACK（本地往返，~1 ms） + sleep(POLL_INTERVAL)
```

`POLL_INTERVAL` 只能缩到 0，而循环体自身占用的时间（含 paho 的 `wait_for_publish` 与
`time.sleep` 的实际唤醒粒度）叠起来约 **0.9 s** —— 于是无论周期设得多小，
单实例的采集节拍都停在 **~1.1 轮/秒**。这是**本机 + 本部署下的实测常数**，
换机器/换 broker 距离都会变，不能外推（§7.3）。

> ⚠️ 这也是"提高频率打爆"这个实验在本部署下**打不爆**的原因：
> 网关还没开始丢数据，它自己就已经先慢下来了。
> 想真正压出积压，得让 `publish()` 失败（断网/broker 慢），而不是提高频率 —— 见 §5.3。

`POLL_INTERVAL=1.0` 那次出现的唯一 1 条缓存：日志原文是 `[缓存] 断网，数据已入本地队列`
（网关换实例重启的瞬间 paho 还没连上），随后 `[补传] 开始补传 1 条` → `[补传完成] 已确认 1 条`。
它顺带证明**断网缓存 + 补传这条路径是活的**。

### 5.3 结论②：缓存与补传的追赶能力（人工播种积压）

由于 §5.2 的硬上限，"自然"压不出积压，于是改用**人工播种**：在隔离网关的缓存目录里
预写 120 行报文（格式与网关自己写的一模一样，时间戳分布在过去 120 s，模拟"断了 2 分钟"），
再启动网关观察它怎么追。

| 项 | 值 |
|---|---|
| 播种条数 | **120**（`2026-10-02 21:56:28` → `21:58:27`，1 s 间隔） |
| 网关启动瞬间 | `[补传] 开始补传 120 条，在途窗口 100 条` |
| 同 1 秒内 | `[补传完成] broker 已确认 120 条` |
| 旁听器统计（整段运行，按唯一 ts） | **226** 条已发布（= 120 播种 + 106 新采集） |
| TDengine 表 `loadtest_lt6` 行数 | **226** |
| 逐条对账 | **缺失 0**、重复 ts 0 |
| 结束时候选缓存目录 | `cache.jsonl` **0 行**、`inflight-*` **0 个** |

**结论：120 条积压在同一秒内被全部补发并被 broker 确认，一条不丢，缓存归零。**
单条 PUBACK 的本地往返是毫秒级，所以补传吞吐 ≈ 采集循环的节拍上限（§5.2），
这批 120 条远没有触及上限。

> **没测到的**：更大的积压（数千条以上）的**排空耗时曲线**。
> 原因是采样口径：缓存目录在补传期间是 **0 行**（数据已被原子改名进 `inflight-<seq>.jsonl`，
> 而那段在补传窗口内会被滚动压缩回写），1.5 s 一次的目录采样抓不到这个过程
> （实测 68 个采样点全是 0，见 `backpressure_catchup_cache.csv`）。
> 要画出排空曲线，得让补传慢下来（例如 `RESEND_WINDOW=1` 强制每轮只发 1 条）——
> 这条留作后续，见 §7.5。

### 5.4 旁证：存储层不是瓶颈

裸 REST 直插（不经 MQTT/接入层，仅测 taosAdapter 的写入能力）：

| 方式 | 实测 |
|---|---|
| 单行 INSERT × 200 | **6.0 ms/行 → 166.8 行/秒** |
| 一批 100 行 | 38 473 行/秒 |
| 一批 1000 行 | 171 567 行/秒 |

即：本文 52.6 条/秒的峰值负载，**离存储层的单行写入上限（167 行/秒）还有 3 倍余量**；
而接入层是**单线程同步 INSERT**（`on_message` 里直接执行 SQL 并等返回），
所以接入层的理论上限就是 ~167 条/秒/实例。（脚本：[`raw_insert_bench`](../evidence/perf/) 输出见本节表格。）

## 6. 资源余量

用 cgroup v2 的 `cpu.stat: usage_usec` / `memory.current` **前后两次采样相减**得到负载期间的
真实占用（比 `docker stats` 的"容器生命周期均值"准；`docker stats --no-stream` 快照另存在
`loadgen_stats_<tag>_post.csv`，作为内存口径的对照）。

| 容器 | N=2（120 条） | N=10（600 条） | N=50（1000 条） |
|---|---|---|---|
| emqx | 19.9 % × 1 核 / −0.4 MB | 20.4 % / −2.8 MB | **24.1 % / +43.3 MB** |
| tdengine | 5.0 % / +5.4 MB | 6.5 % / +20.4 MB | **11.1 % / +32.2 MB** |
| cems-subscriber（生产） | 0.5 % | 0.3 % | 0.3 % |
| cems-gateway（生产） | ~0.7 % | 0.6 % | 0.6 % |
| cems-device | 1.4 % | 1.5 % | 1.5 % |

（`% × 1 核` = 该时段 CPU 秒数 ÷ 墙钟秒数；宿主 15.53 GiB 内存。）

读数：

- **CPU 大头在 broker**（20~24 %×1 核），不在接入层。原因之一是本文的测法给每台设备
  起了一个**持久会话**的接入实例（N=50 → 50 个连接），连接数本身要花 broker 的 CPU。
- **存储层**随负载从 5 % 涨到 11 %×1 核，是唯一随 N 明显变化的被测组件。
- **内存增量都很小**（最大 +43 MB，来自 emqx 的会话/队列）。
  机器总余量：15.53 GiB 中 emqx 占用 0.53 GiB、tdengine 0.47 GiB，属于"还很空"。
- ⚠️ 不要把这组数字读成"容量上限只有 52 条/秒"：瓶颈是**测试机的容器编排方式**
  （一台一实例 = 一台一个连接 + 一个进程），不是链路本身。见 §7.3。

## 7. 局限性（引用本文数字前必须读这一节）

### 7.1 ⭐ 负载发生器直发 EMQX，**绕过了网关**

`scripts/loadgen_devices.py` 的报文虽然与真实网关**逐字一致**，但它是**直接 publish 到 EMQX** 的：

| 本文测到 | 本文**没有**测到 |
|---|---|
| 接入层（`subscriber_to_td`）的解析/量程白名单/建子表/INSERT | 网关的 Modbus 轮询、寄存器换算、`build_payload` 的采集节奏 |
| EMQX 的 QoS 1 投递与持久会话排队 | 网关的**断网缓存**与**补传**在真实负载下的行为 |
| TDengine 的写入与查询 | 网关与平台的**告警判定/小时结算**链路（本文 `ALARM_ENABLE=0`） |

换句话说：**§4 的"吞吐 vs N"是「接入 + 存储层」的容量，不是「网关采集层」的容量。**
网关侧的容量在 §5 单独测，且它的上限（~1.05 条/秒/实例）比 §4 的 52.6 条/秒低两个数量级 ——
**两者不可互换引用。**

### 7.2 延迟数字带 300 ms 级的量化上界

`t_seen` 由 0.3 s 一次的 REST 轮询得到，所以 `lat_store` / `lat_e2e` 的逐条误差是 `U(0, 300 ms)`。
本文报的 P50（~0.18 s）几乎正好等于该分布的中位数，**说明观测值主要反映的是轮询相位，不是链路**。
可引用的严格结论只有两条：① 三段延迟的相对大小（入库段远大于 broker 段）；
② 上界 —— **端到端真值 ≤ 观测 P50 − 150 ms ≈ 30 ms 量级**，与 §5.4 的 6 ms/行 INSERT 自洽。

### 7.3 N 的上限是测试机的容器数，不是链路的容量

本文按"一台设备一个接入实例"测（与生产同构），N=50 就要 50 个 Python 进程 + 50 个 MQTT 连接。
再往上加 N，先撞到的是**本机进程数/内存**（每个实例 ~27 MB 常驻），不是 EMQX 或 TDengine。
所以 **52.6 条/秒 是"在 50 个实例的编排下测到的点"，不是链路容量上限**。
接入层的**架构**上限只能从代码推出：单实例单线程同步 INSERT ≈ 167 条/秒（§5.4）。
要多实例聚合吞吐，正确做法是改接入层为"单实例订阅通配 + 按主题解析设备号"（属契约外改动，见 ADR-0008）。

### 7.4 未做的实验

| # | 没做 | 为什么 |
|---|---|---|
| 1 | **真实断网 + 大积压 + 排空曲线** | 需要停 `emqx` 容器，会影响生产两条设备链路；改用"人工播种积压"替代（§5.3），但只测了 120 条 |
| 2 | **`cache.jsonl` 64 MB 上限裁剪**（`CACHE_MAX_BYTES`） | 要造 64 MB 积压（约 50 万条），超出"单次 ≤3 分钟"的约束 |
| 3 | **EMQX 队列深度** | 见 §7.6 —— 查得到，但与本文关心的"丢没丢"无关，且 `max_mqueue_len=20000` 未触及 |
| 4 | **接入层多实例共享同一子表**（多对一） | 表结构决定的不可用组合（同秒覆盖），已在 §4.1 标注为构造约束 |
| 5 | **跨天/长稳（内存增长、时间戳漂移）** | 本次运行窗口 < 1 小时 |

### 7.5 采样口径造成的两个盲区

1. **缓存目录采样抓不到补传过程**：补传期间数据在 `inflight-<seq>.jsonl` 里、且被滚动压缩，
   1.5 s 一次的目录采样恒为 0（§5.3 的"没测到"）。
2. **`--settle` 语义**：收尾判据是"**本轮无新行入库**持续 `--settle` 秒"或"库内可见 = 已发布"。
   高并发下 broker 队列 + 接入层单线程会让"入库"明显滞后于"发布结束"，
   因此**必须**等到 `库内可见 = 已发布` 才能收工（脚本已按此实现）；
   早期一次口径缺陷（提前收工）会把"还没查完"误判成丢数，已在脚本注释中记录。

### 7.6 EMQX 队列深度：**能查到，但本文没有把它当证据**

`docker exec emqx emqx ctl clients list` 每个客户端带 `enqueued_msgs` / `dropped_msgs` / `inflight`
字段，理论上可以直接读队列深度。本文没有用它，原因：
① 该输出在本次运行中**没有随负载给出可信的增量**（数量级与 §4 结果不匹配，未复现出稳定口径）；
② 本文的丢数判据是**逐条对账**（发布集合 vs 库内集合），它比"队列深度"更直接、更强。
`max_mqueue_len=20000`（约 27 小时 @5 s）与 `session_expiry_interval=24h` 在本次负载下**远未触及**。

### 7.7 其他

- 主机是 Windows + Docker Desktop（WSL2 后端），容器共享同一内核；
  容器虚拟时钟存在 823 ms 级锯齿（见 [性能与可靠性指标.md](性能与可靠性指标.md) §3）。
  本文虽用宿主时钟规避了它，但**发布节拍的抖动**（`time.sleep` 在 Windows 上的 ~15 ms 粒度）
  会进 `lat_gen`（实测 P50 0 ms、P95 16 ms）。
- 一次运行里 N=2/N=10 的 `extra` 不为 0（418/3815 行）：那是**前一次运行遗留在
  持久会话队列里的行**在本次被投递进来。它不影响"缺失=0"这条结论（`missing` 只看发布集合），
  但说明**复用同一 `client_id` 的会话会跨运行携带数据** —— 本文每轮用不同的 `client_id`（带 tag），
  正式复现时也请如此。

## 8. 不污染真实链路的证据与清理

- **主题隔离**：负载发生器只发 `cems/loadtest/...`；生产网关只发 `cems/plant1/data`、`cems/plant2/data`。
  接入实例按**精确主题**订阅，不存在通配订阅把 loadtest 数据吸进生产子表的路径。
- **标签隔离**：入库标签固定为 `plant=loadtest`、`device=lt<i>` → 子表 `loadtest_lt<i>`。
  生产子表是 `plant1_device1` / `plant2_device2`，两者**不共用子表**。
- **运行期间生产链路复核**（压测结束后立即查）：
  - `cems.cems_data` 里 `device IN ('device1','device2')` 的**最近 4 条正常递增**
    （`device1` 21:16:28 / 21:16:33，`device2` 21:16:24 / 21:16:29，本地时间）；
  - 10 个容器全部 `healthy`（emqx / tdengine / device / gateway / gateway2 / subscriber / subscriber2 / web / nginx / redis）；
  - 隔离网关实例用独立 `client_id`、独立缓存目录，用完 `docker rm -f` 删除。
- **清理命令**（已执行，见 §9 清理确认）：

```powershell
# 删掉本次造出的全部 loadtest 子表（只删 plant=loadtest 的 lt*，不碰 device1/device2）
& $py scripts/loadgen_devices.py --devices 50 --cleanup
# 确认没有残留
"SELECT tbname FROM cems.cems_data WHERE tbname LIKE 'loadtest%'" | <REST 查询>
```

## 9. 没做到 / 不确定（诚实清单）

1. **没造出"自然积压"**：把单台网关的轮询压到 0.05 s（100 倍），缓存仍然恒为 0 行 ——
   因为采集循环自身有 ~1.05 条/秒的硬上限（§5.2）。想要积压必须让 broker 侧失败，
   而本次约束不允许停生产 `emqx`。所以纵向背压的"积压增长曲线"实际上是**一条 0 值平线**，
   我照实报，没有编造上升段。
2. **大积压的排空耗时未测**：只测了 120 条（同秒补完）；数千条以上的排空曲线、以及
   64 MB 裁剪阈值，都没跨过（§7.4）。
3. **M=1 条/秒 的延迟是观测上界**：不是真值，真值给不出（秒级 ts + 0.3 s 轮询量化，§7.2）。
4. **N=50 的 52.6 条/秒不代表链路容量**：它同时受"50 个容器 + 50 个连接"的
   测试机编排方式限制（§7.3）。
5. **告警/折算链路未纳入**：本文所有接入实例都设 `ALARM_ENABLE=0`，
   没有测"并发 + 告警判定 + 小时结算"叠加时的表现。
6. **EMQX 队列深度未作为证据**：命令查得到（`emqx ctl clients list` 带 `enqueued_msgs`/`dropped_msgs`），
   但本次没有取到可信、可复现的增量口径，因此不作为结论依据（§7.6）。
7. **接入层的"多对一"能力是空的**：一个接入实例只能订阅一个主题、只能写一张子表，
   N 台设备必须 N 个实例，且同一子表里多台设备必须错开整秒（否则 `(子表, ts)` 同秒覆盖）。
   这不是本次引入的问题，但它是横向扩展的真实约束，写在这里备查。
