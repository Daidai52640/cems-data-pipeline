# 长跑时长取舍：为什么 12.93 小时就够了，不必补到 24 小时

> **结论**：本项目**不需要**为了"跑满一整天"再占用一天机器。
> 对"**边缘侧资源约束**"这个结论，**12.93 小时与 24 小时无本质差别** —— 下面是实测依据，不是感觉。

- **决策日期**：2026-10-12
- **实际时长**：`2026-10-11 18:58:44 → 10-12 07:54:45` = **12.934 小时**（目标曾设 24 h）
- **收尾原因**：操作方有峰谷电约束，**08:00 前必须跑完、09:00 前必须全断** —— 这是**外部约束**，不是能力限制

---

## 1. 24 小时本来是为了抓什么

长跑（soak test）之所以是 24 h/72 h，是因为**只有长时间才暴露**三类问题：

| # | 只有长跑才暴露的 | 本项目实测（12.93 h） | 判断 |
|---|---|---|---|
| 1 | **内存泄漏** | `gateway` 第 1 小时均 vs 最后 1 小时均：**+0.0 MiB**；`gateway-plant2` **−0.0 MiB**；`device` +1.3 MiB（**小于自身波动 17.7 MiB，在噪声里**） | ✅ **平** |
| 2 | **连接 / FD 泄漏** | 跑满后 FD 数：`device 9 / gateway 7 / gateway-plant2 7 / subscriber 4` —— **贴地板**（裸 Python 进程约 3~4） | ✅ **平** |
| 3 | **缓存 / 队列无限增长** | `cache.jsonl`、`spool.jsonl` 全程 **0 字节** | ✅ **平** |

⇒ ⭐ **24 小时唯一要抓的三类，12.93 小时已经全部是干净的。**

## 2. 就算那 +1.3 MiB 是真泄漏，也无关紧要

```
1.3 MiB / 12.93 h ≈ 0.10 MiB/小时
推到 24 h：24.3 + 2.4 ≈ 26.7 MiB   ≪   128 MiB 上限
```

## 3. ⭐ 资源占用与"昼夜 / 工况"无关（这条最容易被想当然）

仿真器确有**日变化相位**（污染物白天高、夜里低），直觉上"跑过白天才完整"。
**但 CPU 与内存取决于"每 5 秒一条"这个数据速率，不取决于数值大小** ——
速率恒定 ⇒ **跑过白天不会让资源峰更高**。

实测佐证：跨夜窗口内 CPU 峰 **10.95%**、内存峰 **39.7 MiB**，与白天时段（§运行手册的 25 分钟窗口）
同一量级，**没有"白天更高"的现象**。

⇒ ⭐ **"覆盖完整昼夜"只对告警/数据语义有意义，对资源结论无关。**

## 4. 那 24 小时到底买到了什么

**只剩一句话**："我连续跑满了一整天" —— ⭐ **叙事价值，不是技术价值**。

⭐ **而且有更便宜的等价说法**（信息量更大）：
> "边缘侧资源约束下**跨夜连续运行 12.93 小时**：内存零漂移、FD 贴地板、队列零积压、
> 每容器 1451 个采样点**零缺采**、**零触顶**。"

## 5. 成本侧

| | |
|---|---|
| 收益 | 一个说法 |
| 成本 | **额外约 11 小时占用机器 + 电费**（操作方明确在意峰谷电价） |

⇒ **性价比不划算。**

## 6. 什么情况下值得补到 24 h

⭐ 只有一种：**机器本来就开着干别的** —— 那时"顺手继续跑"是零成本，补到 24 h 无所谓。
**但不应"专门为它"多留一天机器。**

## 复现这段分析

```powershell
# 逐容器统计内存趋势（首小时均 vs 末小时均、min/max）
python scripts\measure_edge_resource_summary.py --csv docs\evidence\edge\resource-24h.csv

# FD 数（连接泄漏的经典指标）
foreach ($c in 'cems-device','cems-gateway','cems-gateway-plant2','cems-subscriber') {
  docker exec $c sh -c 'ls /proc/1/fd | wc -l'
}
```
