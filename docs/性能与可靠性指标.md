## 3. 测量前的时钟基准（不先做这步，延迟数字没有意义）

端到端延迟 = **库内可见时刻（宿主机时钟）** − **报文时间戳（网关容器时钟）**。
这是两个时钟相减，所以先证明"这两个时钟是什么关系"。

### 3.1 三条时间线

| 时间 | 谁产生 | 用途 |
|---|---|---|
| 报文 `ts` | 网关 `time.strftime()`，**容器**墙钟，**秒级** | 迟延起点 |
| `t_arrival` | MQTT 旁听探针收到报文的**宿主机**墙钟 | 分段点 |
| `t_first_seen` | REST 轮询首次查到该 `ts` 的**宿主机**墙钟 | 迟延终点 |

### 3.2 A 部分：容器之间是否同一时钟

`docker exec <容器> date +%s.%N`，每个样本自带"执行前/执行后"宿主时间括号，取中点：

| 容器 | 容器时钟 − 宿主机（10 轮，min / P50 / max） |
|---|---|
| tdengine | −318.6 / −9.2 / +461.3 ms |
| cems-gateway | −321.5 / −8.0 / +458.5 ms |
| cems-device | −322.8 / −12.8 / +455.7 ms |
| cems-subscriber | −325.0 / −16.7 / +452.6 ms |
| emqx | −327.3 / −15.9 / +453.6 ms |

两两差 P50 只有 **0.5 ~ 8.6 ms**（波动 7 ~ 20 ms，来自 exec 抖动）。结论：
**五个容器共享同一个 `CLOCK_REALTIME`**（同一 VM 内核），且它们**一起漂**。

### 3.3 B 部分：容器时钟 vs 宿主机时钟（锯齿波）

用 `SELECT NOW()` 对齐（REST 往返 P50 2.2 ms → 偏移测量精度约 ±1.1 ms），45 s 采样：

- 偏移范围 **−352.4 ms ~ +471.0 ms（极差 823.4 ms）**
- 连续段斜率 **−25.9 / −26.6 / −26.4 ms/s**（≈ **−26 000 ppm**，即容器时钟比宿主机慢约 2.6 %）
- 周期性**向前跳变** **+823.4 / +299.4 / +466.5 ms**

即：容器虚拟时钟"慢跑 + 周期补跳"，在宿主机时钟上是一把锯齿。

### 3.4 C 部分：谁相对真值在跑偏（NTP 外部基准）

stdio 无第三方依赖的 NTP 四时戳查询（`ntp.aliyun.com` / `cn.pool.ntp.org` / `time.cloudflare.com` 取中位）：

| 时钟 | 相对真值 | 45 s 内极差 |
|---|---|---|
| 宿主机时钟 | +498 ~ +516 ms（稳定落后约 0.5 s） | **18 ms** |
| 容器时钟 | +221 ~ +1007 ms | **787 ms** |

**结论：漂的是容器虚拟时钟**（宿主机时钟速率稳定，容器时钟速率偏慢 2.6 % 并被周期补偿）。

### 3.5 因此对延迟数字做了什么处理

1. 每次轮询都用同一条 SQL 取回库端（=容器）时钟：`SELECT NOW() AS t_now, ts …`，
   算出**同期**偏移 `δ = 库端时钟 − 宿主机时钟`，校正 `lat_visible_corr = lat_visible + δ`。
   30 分钟运行内 δ 覆盖 **−420 ms ~ +537 ms**（7185 个采样点）。
2. 时钟**跳变**落在两次轮询之间时，该窗口内新出现的行无法判断是"跳变前"还是"跳变后"入库
   → 打标剔除。30 分钟运行触发 **116 次跳变事件，剔除 11 行**（349 条里占 3.2 %）。
3. 逐样本仍有报文时间戳的**秒级量化**偏差（见 §4.4）。

> ⚠️ 不要在本文档以外的场合引用"未做时钟校正"的毫秒级数字。原始锯齿也可从
> [clock_consistency.json](measurements/clock_consistency.json) 的逐秒序列复算。

## 4. 指标① 端到端延迟

### 4.1 测法（为什么不用"两个进程各记时间相减"）

跨容器各记时间相减，结果里混的是 §3 的时钟偏移（最大 823 ms 锯齿），不是延迟。
本文用**两条独立观测 + 单时钟分段**：

```
MQTT 旁听探针（宿主机线程）  收到报文 → t_arrival   （宿主机时钟）
REST 轮询（宿主机线程）      该 ts 首次可查 → t_first_seen（宿主机时钟）

lat_visible  = t_first_seen − ts          ← 端到端（含跨时钟，已做 δ 校正）
lat_arrival  = t_arrival    − ts          ← 设备读数 → broker（含跨时钟，已校正）
delta2       = t_first_seen − t_arrival   ← broker → 库内可查（**纯宿主机时钟，无跨时钟问题**）
```

- 旁听探针是**额外的一个订阅端**（`client_id=cems-metrics-probe-<pid>`，干净会话），
  不修改网关/接入层的 `client_id`、主题、QoS，也不发消息、不写库。
- 轮询用 `SELECT NOW(), ts … ORDER BY ts DESC LIMIT 600`（0.25 s 一次），
  这样**晚到的旧 ts（补传行）也能被发现**——只盯 `MAX(ts)` 会把补传行漏掉。
- 有效性自检：探针收到 **349 条**、库内新增 **349 条**、`no-probe` **0 条**
  → 旁听与入库一一对应，没有"探针收到但库内没有"的丢数据。

### 4.2 结果（30 分钟稳态，349 条；负载见 §2.1）

| 分组 | n | min | P50 | P95 | max | mean |
|---|---|---|---|---|---|---|
| 全样本 | 349 | 0.057 s | **0.699 s** | **31.804 s** | **32.293 s** | 5.764 s |
| 直发 direct | 291 | 0.057 s | **0.582 s** | **1.069 s** | 1.232 s | 0.613 s |
| 补传 resend | 47 | 31.026 s | **31.521 s** | 31.980 s | 32.085 s | 31.535 s |

分段（仅直发）：

| 分段 | n | min | P50 | P95 | max |
|---|---|---|---|---|---|
| 设备读数 → broker（含秒级量化） | 291 | 0.008 s | 0.475 s | 0.938 s | 0.988 s |
| broker → 库内可查（纯宿主机时钟） | 291 | −0.001 s | 0.123 s | 0.236 s | 0.257 s |
| 上一条扣掉轮询探测延迟（−0.125 s） | 291 | −0.126 s | 0.000 s | 0.110 s | 0.132 s |

分布是**双峰**的：291 条在 1 s 级（直发），58 条在 31 s 级（补传）。这不是链路抖动，
而是 §7 的稳态特征。**全样本 P95 = 31.8 s 完全由补传路径决定。**

### 4.3 独立复核（单时钟，只看网关自己的日志）

网关每次补传都先取走上一周期入队的积压，再把本轮新采数据入队，因此
"第 i 条入缓存的行 = 第 i+1 个补传周期发出去的"——**两边都是网关时钟，不涉及跨容器**：

- 105 个样本：min **30 s**、P50 **31 s**、P95 **31 s**、max **32 s**、mean 30.8 s
- 与 §4.2 的跨时钟结果 31.52 s 吻合（差 0.5 s 来自时钟校正残差）
- 证据：[gateway_resend_lag_current_run.csv](measurements/gateway_resend_lag_current_run.csv)

### 4.4 误差来源（延迟）

| # | 来源 | 量级 | 处理 |
|---|---|---|---|
| 1 | 报文时间戳**秒级量化**：`lat_visible_corr = 真值 + u`，`u ~ U(0,1)` | 逐样本 **±0.5 s** | 用"上界法"给真值上界（§4.5）；观测 P50/P95 直接引用时偏保守 0.5 s |
| 2 | 容器虚拟时钟锯齿（§3.3） | **±0.8 s**（不校正时） | 每轮同期 `SELECT NOW()` 校正；跳变窗口剔除 11/360 行 |
| 3 | REST 轮询探测延迟 `U(0, 0.25 s)` + 往返 2.5~31 ms | 均值 125 ms | 对 `delta2` 减去 0.125 s；对端到端用上界法规避 |
| 4 | 旁听探针与实际订阅端投递时刻不同 | 毫秒 ~ 百毫秒（实测 `delta2` 从 −1 ms 到 257 ms） | 只影响分段，不影响端到端 |
| 5 | 校正量采样间隔 × 时钟漂移率 | 0.25 s × 26 ms/s ≈ **7 ms** | 已含在残差里 |
| 6 | 负载单一（1 台设备 / 700 条每小时） | — | **不得外推到多设备、高并发场景** |

**量化相位冻结（重要）**：容器时钟速率偏慢 2.6 %，与 5 s 轮询近似同步，
导致单次运行内 `u` 几乎不动（连续多行的 `u` 只差 0.02 s）。后果：
用"min/max 中点法"估计固定段时，两次运行分别得到 **−2 ms** 与 **+138 ms**，
差 140 ms——**该方法的逐次误差是 ±150 ms 量级，不能当作精确值**。
这正是下面改用上界法的原因。

### 4.5 结论（怎么引用这个数字）

- 真实延迟 `= 观测值(corrected) − u`，而 `u ≥ 0` → **`min(观测值)` 就是真值的一个合法上界**：
  **端到端（设备读数 → 库内可查）真值 ≤ 57 ms**（30 分钟样本的最小观测值 0.057 s）。
- 分段上界：设备读数 → broker ≤ **8 ms**（291 条最小观测值 0.008 s）；
  broker → 库内可查扣掉探测延迟后中位 **0 ms**、P95 **110 ms**
  → 可读作"入库在接收入口后几十毫秒内完成"。
- 所以直发路径可以下的结论是：**< 0.1 s 量级，秒级时间戳无法分辨更细**；
  再精细的分辨需要把报文时间戳精度提到毫秒级（属契约变更，本次未做）。
- 补传路径：**31.0 ~ 32.1 s**，由 `RESEND_RETRY_INTERVAL=30 s` 决定，见 §7。

- 第二轮（演练清空积压后的 12 min，140 条，**0 条补传**）复核：
  P50 0.819 s / P95 1.113 s / max 1.204 s，上界 ≤ 0.368 s。
  观测 P50 比第一轮高 237 ms，**全部来自量化相位不同**（第一轮相位先到 0.05，第二轮只到 0.37），
  不是链路变慢——这正是 §4.4 第 1、6 条要提醒的读法。
  原始数据：[latency_direct_raw.csv](measurements/latency_direct_raw.csv)

## 5. 指标② 补传成功率

### 5.1 测法与定时

`docker stop emqx` 静置 181 s（网关进断网缓存）→ 静置结束**立即快照**
`data/cache.jsonl`（这就是"该补的条数"的证据）→ `docker start emqx` → 等网关排空队列
→ 回查库内是否每一条都在。脚本 `scripts/measure_resend_success.py`，
`try/finally` 保证无论中途是否报错都会把 emqx 起回来并等 healthy。

### 5.2 对账台账（第二次演练，全程）

| 项 | 值 |
|---|---|
| 断开前库内基线 | **3388 条**（`MAX(ts)=2026-10-01 14:54:42`） |
| 断开时长 | **181.0 s** |
| 断开期间理论产生（时长 ÷ 5.0） | 36.2 条 |
| 断开期间**实际产生 = 该补条数 N** | **35 条**（快照 35 行、去重后 35 条；≤ 基线的 0 条） |
| 恢复后队列剩余 | **0 行** |
| 恢复后补上 **M** | **35 条** |
| 快照之后新产生并最终入库 | 20 条（网关还没察觉恢复时产生的行，和积压在同一批补出去） |
| 库内新增 | 3388 → 3443，**+55 条** |
| 恒等式校验 `基线 + N + 新产生 − 剩余 == 新增` | **成立**（3388+35+20−0 = 3443） |
| **补传成功率 M/N** | **100.00 %** |

快照明细（35 行报文原文）在 [resend_snapshot_drill2.txt](measurements/resend_snapshot_drill2.txt)，
时间跨度 14:54:47 → 14:57:41；完整台账在 [resend_reconciliation_drill2.json](measurements/resend_reconciliation_drill2.json)。

### 5.3 恢复过程时间分解（这才是"5 min 内重连"要看的）

| 时刻 | 事件 |
|---|---|
| 14:54:45 | 网关记录 `MQTT 连接断开` |
| 14:54:46 | `docker stop emqx` |
| 14:57:46 | 快照，得 N=35（静置 181 s 结束） |
| 14:57:47 | `docker start emqx` |
| 14:57:59 | emqx healthy（**+13 s**） |
| 14:59:23 | 网关 `MQTT 已连接`，`[补传] 开始补传 54 条` → 同一秒内 `[补传完成] broker 已确认 54 条`（**+84 s**） |
| 14:59:23 | 队列排空，drain 耗时 **96.9 s** |

**从断开到数据补齐 278 s（4 min 38 s）**。其中：emqx 起回 13 s、**paho 重连退避 84 s**、
补传 54 条 < 1 s。也就是说恢复时长几乎全被**重连退避**吃掉，而不是补传吞吐。

### 5.4 重复性

两次独立演练（14:49 与 14:54）结果一致：**N=35、M=35、100 %、drain 96.9 s**。
（第一次演练的台账脚本里"快照之后新产生的行"取数窗口有缺陷，已修正；
第一次的 N/M 与排空时间不受影响。修正记录见第 9 节。）

### 5.5 误差来源（补传成功率）

| # | 来源 | 说明 |
|---|---|---|
| 1 | 分母口径依赖"快照时刻" | 快照之后到网关重连之间还产生 20 条，它们不在 N 里，但和积压一起补出去。若把它们并入分母：54/54 仍是 100 %。**分母定为"断网期间该补的条数"，不是缓存文件行数** |
| 2 | 样本量小 | 两次都是 N=35，只能说"两次都 100 %"，给不出置信区间 |
| 3 | 断的是 broker 容器，不是真实链路 | 未覆盖网络分区、broker 队列溢出（EMQX `max_mqueue_len=20000` ≈ 27 h）、缓存裁剪（64 MB） |
| 4 | 未做故障注入 | 没有制造"补传途中杀网关进程"这类中途故障去打 `_finish_resend` 的回写路径 |
| 5 | 排空判据是"缓存文件归零" | 归零后又等了 5 s 才回查，最后 1 条理论上仍在途（实测恒等式成立，说明它已入库） |

### 5.6 恢复后的环境复核（lead 要求的确认项）

- 六服务：emqx / tdengine / device / gateway / subscriber / web **全部 running healthy**
- 库内条数连续两次采样**递增**：3388 → 3442 → 3443
- 恢复瞬间 `cems-subscriber` 有约 1 min 的 `unhealthy`（它的 healthcheck 是探 1883 端口，
  重连前后短暂探不通，属预期），随后恢复 healthy

## 6. 指标③ 数据完整率

### 6.1 窗口选取及理由

| 时段 | 是否采用 | 理由 |
|---|---|---|
| 04:00 — 13:25 | **排除** | Docker 整栈停机约 9.3 h（对比 §6.3 的断档检测：单处 34374 s）。这段时间**没有采集器在跑**，不是数据链路丢数据，算进去只会得到一个没有意义的分母 |
| 00:28 — 03:53（上一轮运行） | 作为**参照窗口** | 同样连续、0 断档，205.2 min，样本更长 |
| **13:26:17 — 15:10:26（本轮运行）** | **主窗口** | 从本轮第一条入库 ts 到测量结束、104.2 min 连续在线；期间唯一的接入层容器重建（13:59:25，约 4 s）由 EMQX 持久会话补投、未造成 ts 断档；两次计划演练断开由缓存补齐。**断档检测为 0**（最大间隔 6 s） |

### 6.2 测法

- 取窗口内全部 `ts`，算相邻间隔，**断档判据 = `max(3 × 中位间隔, 中位间隔 + 10 s)` = 15 s**。
- 三个口径同时给：**名义完整率**（对 720 条/h）、**实测节奏完整率**、**有效完整率**
  （实际条数 ÷ (实际条数 + 断档推断缺失条数)）。
- 扫描窗口右端留出补传滞后（本轮取 `now − 120 s`）。**否则在途的那 1 条会被误判成缺口**——
  实测在 14:19 的一次扫描里就出现过 1 处 11 s 间隔，重扫即消失。

## 7. 当前部署的稳态特征：约 1/6 的数据走 31 s 补传路径

这是本轮最有价值的发现，**它是当前部署的稳态行为，不是本次测量引入的**。

### 7.1 现象与比例（实测，不是估算）

- **比例**：30 分钟延迟测量里 349 条中 58 条走补传（**16.6 %**）；
  网关日志窗口内 **106 / 631 = 16.8 %**（[gateway_resend_summary_current_run.json](measurements/gateway_resend_summary_current_run.json)）。
  与"约 1/6"一致，**是实测比例**。
- **滞后**：网关单时钟口径 105 个样本，P50 **31 s**（min 30 / max 32）。
- 106 次入缓存的原因**全部是"补传中"**（`{'补传中': 106}`）——没有一次是"断网"或"未收到 PUBACK"。

### 7.2 队首为什么长期不空（机理）

`src/gateway/gateway.py` 主循环顺序是：

```
① 若已连接且 has_backlog()  → 触发补传线程（受 RESEND_RETRY_INTERVAL=30 s 节流）
② 读设备 → 生成报文（ts 在这里产生）
③ 若已连接且 not RESEND_WORKER.running → 直发；否则 save_to_cache()
```

同一个迭代里，①刚取走队列（`cache.jsonl` 被改名成 `.sending`），③把本轮新采的行又写回队列；
而 `RESEND_WORKER.running` 在 ③ 判断时通常仍为真（补传线程在等 PUBACK），于是本轮数据**必然入队**。
之后 5 个迭代因为 30 s 节流不会触发补传，新数据走直发；第 6 个迭代再次触发——
**队列被取空又立刻填回，永远有一行在队列里**。这解释了：

- 每 ~31 s 一次补传周期，每次恰好 1 条；
- 入队原因 100 % 是"补传中"；
- **演练把积压清空后该特征消失**：14:59:23 排空后缓存保持 0 行，随后 12 min 的测量
  里补传行为 **0 条**（[latency_direct_raw.csv](measurements/latency_direct_raw.csv)）。

### 7.3 对延迟分布的影响

| 分位 | 含该特征（实测） | 清空积压后（实测，12 min） |
|---|---|---|
| P50 | 0.699 s | 0.819 s（差异来自量化相位，§4.4） |
| **P95** | **31.804 s** | 1.113 s |
| max | 32.293 s | 1.204 s |
| 补传占比 | 16.6 % | 0 % |

**该特征把全样本 P95 从 1 s 级抬到 31.8 s**，对"5 min 内重连"仍合规（§8），
但它让 ~1/6 的数据稳定晚 31 s 到达，对实时性敏感的下游（告警、报表窗口）是要注意的。

### 7.4 可选的改法（**本轮未实施**，仅记录）

1. 把补传触发放在"读完设备、发完本轮数据"**之后**（现在放在循环开头）；
2. 触发条件加上"积压条数 > 在途窗口"或"队列中最早一条已等待超过 T"；
3. 同迭代内先判断补传线程是否已结束再决定入队（③ 处再等一次 `running` 状态）；
4. 把 `RESEND_RETRY_INTERVAL` 调到与 `POLL_INTERVAL` 同量级。

以上任一都会改变 `gateway.py` 的现有行为，**属契约外改动，需另行评审**。本轮只测量、不修改。

## 10. 没做到 / 测不准的部分（诚实清单）

1. **亚 0.1 s 的端到端分辨做不到**：报文时间戳只有秒级，容器虚拟时钟又带 ±0.8 s 锯齿。
   本文只能给出"真值 ≤ 57 ms"这样的**上界**，给不出"P50 = xx ms"的精确值。
   要更细必须改报文时间戳精度（契约变更，本轮未做）。
2. **没有真实负载发生器**：全部数字来自单台设备、5 s 一条、约 700 条/h。
   多设备、高并发、1 s 级上报下的延迟与吞吐**未测**，不得外推。
3. **"设备读数 → broker"分段的精确值不可测**：只能给 ≤8 ms 的上界，
   原因是量化相位在单次运行内冻结（§4.4），中点法在两次运行间差 140 ms。
4. **长断网路径未验证**：EMQX `max_mqueue_len=20000`（约 27 h）、网关缓存 64 MB 裁剪、
   会话有效期 24 h —— 都没有跨过阈值做验证。
5. **未做中途故障注入**：没测"补传进行中杀网关进程"对 `.sending` 回写路径的影响。
6. **HJ 75-2017 §9.4.5 表 3 原文未取证**：表内前三条用任务给定口径；"系统响应时间 ≤200 s"
   是二手来源。检索到的公开资料只到验收报告层面（见下），不足以引用条文原文。
7. **告警/折算链路未纳入性能测量**：告警判定尚未落地，折算值不入库，所以本轮只测了
   采集 → 入库这一段。
8. **无 24 h 长稳数据**：未测内存/磁盘增长、未测跨天的时间戳漂移累计。
9. **量化相位冻结这一现象本身未深挖**：只测到"单次运行内相位近似不动、跨运行差 140 ms"，
   没有做相位与轮询周期的同步机制分析。
10. **第一次演练的台账脚本有缺陷**：`快照之后新产生的行`取数窗口取错（用快照 max(ts) 当右端），
    已修正为"快照时刻 → 回查时刻"；第一次的 N/M=35/35、drain 96.9 s 不受影响。
