## 二、测试目标

验证"故障期间已经进入网关的数据"在恢复后**逐条**补齐，覆盖两条承诺：

1. **broker 重启零丢失**：停止/重启 EMQX 容器，离线期间的数据不丢（在 `durable_sessions=true` 下重新验证，且必须做**逐条对账**而非只比总数）；
2. **断网续传**：两台设备同时断链后，恢复时数据补齐、零丢失；并确认新引入的**网关启动预检**没有误伤这条恢复路径（设备先起/网关后起、设备未起/网关重启两类场景）。

### 4.3 对账口径（关键）

* **来源**：网关每次入队都打一条 `[缓存] <原因>，数据已入本地队列: <YYYY-MM-DD HH:MM:SS> …`。本报告取该日志行的时间戳集合为"应补传集合"，并按窗口用 `docker logs --since/--until` 抓取（不用人工转录）。
* **落库集合**：`SELECT to_char(ts,'yyyy-mm-dd hh24:mi:ss') FROM cems.cems_data WHERE plant='plantX' AND device='deviceX' AND ts BETWEEN …`。**必须同时按 plant + device 两个 tag 过滤**：同机并行还有别的演练线复用 `device1` 作为设备 tag。
* **缺失判定**：`应补传集合 − 落库集合`；缺失 = 0 才算通过。
* **重复口径**：同一子表同一 `ts` 是主键、重复写入是覆盖而非新增，因此"是否重复"在库层由时间戳唯一性保证；本报告以"集合去重后条数 = 原始条数"（实测 0 重复）表述，不宣称做过重复注入。
* 原始输出全部留档：`docs/evidence/drill/`。

**失效边界（本轮能确定的部分）**：

2. 丢失的**不是**"订阅端没重连"：两台订阅端每次都在重连后打印 `会话恢复=True`（durable session 生效），且同一次故障里**同版本的 plant2 订阅端 100% 收全**。

4. 三次执行中两次失败的**都是 device1**；run3 的毫秒级次序显示 device1 的网关(0ms)先于其订阅端(+49ms)连上，而 device2 的订阅端(+21ms)先于其网关(+29ms)。run1 中 plant2 的次序与之相反却仍投递成功，因此**次序只能解释方向、不足以定论**，EMQX 内部为何在该窗口丢弃这些报文**未做 trace、根因未最终定位**（见 §9.1）。
5. 不排除与设备相关性（两次都命中 device1），但样本量仅 3 次，**不足以判定是设备相关还是偶发**。

### 场景二【测试1 专项】durable_sessions 持久队列跨 broker 重启（订阅端离线窗口完全覆盖故障窗口）

**设计意图**：把"补传"与"订阅端会话恢复"在时间上**彻底错开**——先把两个订阅端停掉，再重启 broker，让网关把离线积压**补进 broker 的持久队列**，最后才把订阅端拉起来消费队列。这样能单独验证 `durable_sessions=true` 的核心承诺（离线队列跨 broker 重启存活），并与场景一形成对照。

#### TC-E2E-002-02-1：持久队列跨 broker 重启投递

| 项 | 内容 |
|---|---|
| 用例ID | TC-E2E-002-02-1 |
| 前置条件 | 10 容器 healthy；两台缓存 0 行 |
| 执行命令 | `docker stop cems-subscriber cems-subscriber-plant2` → `docker stop emqx` → 停机 120 秒 → `docker start emqx` → 等网关补传完成 → `docker start cems-subscriber cems-subscriber-plant2` |
| 时间线 | 停订阅端 00:41:59 → 停 emqx 00:42:01（listener stopped 00:41:59）→ **外部进程于 00:43:33 将 broker 拉起**（broker 不可用 92 秒）→ 网关重连 00:44:27 → 补传完成 00:44:42 → 起订阅端 00:44:43 → 全部入库 00:44:53 |
| 订阅端离线窗口 | **164 秒**（00:41:59 ~ 00:44:43） |
| 网关补传 | 两台各 `[补传] 开始补传 29 条` → `[补传完成] broker 已确认 29 条`（订阅端当时仍离线） |
| 订阅端恢复 | 两台均 `MQTT 已连接（会话恢复=True）` |
| 实际结果（对账） | `device1`：缓存 29 条 → 落库 **29 条，缺失 0**；`device2`：缓存 29 条 → 落库 **29 条，缺失 0** |
| 队列投递耗时 | 订阅端起后 **≤10 秒**内 58 条全部落库（连续探测：缺失 58 → 0） |
| 缓存残留 | 两台均 0 行 |
| 判定 | **PASS** |
| 原始输出 | `docs/evidence/drill/emqx_restart_1b_durable_reconcile_20261003.{json,txt}` |

**结论**：`durable_sessions=true` 的离线队列**确实能跨 broker 进程重启存活并投递**——只要补传发生在订阅端会话恢复**之前**（本例错开 16 秒）。这反证了场景一的丢失并非"持久化没开"或"队列不能跨重启"，而是被限制在**恢复时刻的重叠窗口**内。

### 场景三【测试2】双设备同时断链续传

**故障原理**：`docker network disconnect cems-net emqx` —— broker 进程不退出，只断链路。两台网关各自 `publish` 拿不到 PUBACK → 落缓存；链路连通后各自重连、各自补传。

#### TC-E2E-002-03-1：断链 120 秒 → 恢复后逐条对账

## 九、观察项 / 未覆盖与不确定项

### 9.1 观察项（影响结论解释，但不改变判定）

1. **1A 失败的最终根因未定位**。已确定的事实边界是"broker 确认（PUBACK）后未投递、且只在网关补传与订阅端会话恢复同秒发生时出现"，但 EMQX 内部为何在该窗口丢弃报文**没有做 EMQX 侧 trace**，故不给出根因结论，只给现象与边界。
2. **两次失败都落在 device1**（plant1）。3 次样本无法区分"设备/实例相关"与"偶发"，需要扩大样本或对 EMQX 加 trace 才能定论。
3. **同机并行有另一条验收线**：非 compose 容器 `cems-tzdrill-*`、`tmp-lineage-*`、`cems-lgsub-acc_*` 等使用隔离 topic（`cems/tzdrill/data`、`cems/trace/data`）与隔离 tag，但**共用同一个 EMQX 与 TDengine**。演练期间观测到 EMQX 被外部动作重启 3 次（00:39:56 / 00:43:33 / 00:48:11），已在对应用例中标注。run1 的故障与恢复窗口（00:31:57~00:36:37）内 EMQX 只有两次生命周期事件——我方 `docker stop`（listener stopped 00:31:57）与我方 `docker start`（listener started 00:34:27）——**不存在**外部重启；且该窗口内该线的 `cems-lgsub-*` 订阅端尚未上线（恢复时刻的 clients list 只有本链路 4 个会话 + `cems-tzdrill-*` 2 个）→ **run1 的丢失结论不受外部负载影响**。
4. **`emqx ctl subscriptions list` 返回 `No subscriptions.`**，与 `clients list` 的 `subscriptions=1` 不一致（本版 EMQX 的 CLI 行为），会话证据一律以 `clients list` 为准。
5. **`docker logs --since` 只接受 RFC3339**：`--since "2026-10-03 00:31:00"` 会被拒（`invalid value for "since"`）并只回显错误行，工装已改为 `YYYY-MM-DDTHH:MM:SS`（若直接照抄会得到"空日志"从而误判为"没有入队记录"）。
