## 二、测试目标

验证系统在不同层级故障场景下，恢复后数据零丢失，确保：
1. **平台侧故障**（subscriber重启）：EMQX持久会话排队消息，恢复后补投，零丢失
2. **网关侧故障**（gateway重启）：网关快速恢复，数据采集无中断
3. **消息层故障**（emqx重启）：gateway断网缓存刷盘，恢复后补传，零丢失

## 三、通过标准

每个场景满足以下全部条件才算通过：
1. 故障恢复后等待足够时间，数据补传完成
2. 故障期间预期数据条数 = 故障时长（秒）/ 5秒（网关轮询间隔）
3. 实际入库条数 ≥ 预期条数 × 95%（允许故障切换瞬间丢≤2条）
4. 数据时序正确（时间戳连续，无乱序）
5. 无重复数据（同一时间戳无重复记录）

## 五、测试场景执行结果

### 场景A：subscriber 容器重启（平台侧故障）✅ 通过

**故障原理**：subscriber 是 MQTT 消费者，使用持久会话（clean_session=0）。subscriber 离线期间，EMQX 会为其排队 QoS≥1 的消息。恢复后 EMQX 将排队消息补投给 subscriber，subscriber 写入 TDengine。

| 步骤 | 操作 | 预期结果 | 实际结果 | 状态 |
|---|---|---|---|---|
| A1 | 记录故障前 TDengine 最新时间戳和总量 | 获得基线数据 | 总量8632条，最新时间戳20:47:13 | ✅ |
| A2 | docker restart cems-subscriber | 容器重启，状态从 healthy→starting→healthy | 重启成功，状态starting | ✅ |
| A3 | 等待 30 秒（故障持续时间） | subscriber 离线 30 秒，EMQX 排队消息 | 离线约30秒 | ✅ |
| A4 | 确认 subscriber 恢复 healthy | 容器状态 healthy | Up About a minute (healthy) | ✅ |
| A5 | 等待 60 秒让补传完成 | EMQX 将排队消息补投，subscriber 写入 TDengine | 补传完成 | ✅ |
| A6 | 查询故障期间时间范围内的数据条数 | ≥ 预期条数 × 95%（≥6条） | 故障期间6条数据全部补传成功 | ✅ |
| A7 | 检查数据时序和重复性 | 时间戳连续，无重复记录 | 20:47:18~20:47:43连续6条，5秒间隔，无重复 | ✅ |

**场景A数据明细**：
```
故障前：20:47:03, 20:47:08, 20:47:13（正常）
故障期间（subscriber离线）：20:47:18, 20:47:23, 20:47:28, 20:47:33, 20:47:38, 20:47:43 ← 6条全部补传成功！
故障恢复后：20:47:48, 20:47:53...（正常）
```

**场景A结论**：EMQX 持久会话 + subscriber 补传机制工作正常，**零丢失**。

### 场景B：gateway 容器重启（网关侧故障）✅ 通过

**故障原理**：gateway 是数据采集和 MQTT 发布者。gateway 重启期间，设备数据无人采集（device 还在跑但没人读）。gateway 恢复后重新开始采集。

**注意**：gateway 重启期间设备数据本身就没人采集，所以这部分数据"本来就不存在"，不算丢失。验证重点是：gateway 重启后数据恢复正常，5秒/条，时序连续。

|---|---|---|---|---|

| B3 | 等待 30 秒（故障持续时间） | gateway 离线 30 秒，无新数据采集 | 实际重启仅约5秒即恢复 | ✅ |
| B4 | 确认 gateway 恢复 healthy | 容器状态 healthy | Up 37 seconds (healthy) | ✅ |
| B5 | 等待 60 秒让恢复和补传完成 | gateway 重新采集，如有缓存则补传 | 恢复稳定 | ✅ |
| B6 | 查询故障前后的数据连续性 | 重启前最后一条和重启后第一条之间有间隔（正常），恢复后数据连续 | 20:50:53→20:50:58仅5秒间隔，数据完全连续 | ✅ |

**场景B结论**：gateway 容器重启（docker restart）仅需约 5 秒，Python 进程启动快，数据采集**几乎无中断**。

### 场景C：emqx 容器重启（消息层故障）✅ 通过

**故障原理**：EMQX 是 MQTT Broker。EMQX 重启期间，gateway 无法发布消息（会触发断网缓存，写 cache.jsonl），subscriber 无法接收消息。EMQX 恢复后，gateway 重连并补传缓存数据，subscriber 重连并接收持久会话排队消息。

| 步骤 | 操作 | 预期结果 | 实际结果 | 状态 |
|---|---|---|---|---|
| C1 | 记录故障前 TDengine 最新时间戳和总量 | 获得基线数据 | 总量8730条，最新时间戳20:55:18 | ✅ |

| C3 | 等待 30 秒（故障持续时间） | EMQX 离线 30 秒，gateway 触发断网缓存 | 离线约30秒，gateway缓存数据 | ✅ |
| C4 | 确认 emqx 恢复 healthy | 容器状态 healthy | Up About a minute (healthy) | ✅ |
| C5 | 等待 90 秒让重连和补传完成 | gateway 重连补传缓存，subscriber 重连接收排队消息 | 重连和补传完成 | ✅ |
| C6 | 查询故障期间时间范围内的数据条数 | ≥ 预期条数 × 90%（≥5.4条） | 故障期间6条数据全部补传成功 | ✅ |
| C7 | 检查数据时序和重复性 | 时间戳连续，无重复记录 | 20:55:23~20:55:48连续6条，5秒间隔，无重复 | ✅ |

**场景C数据明细**：
```
故障前：20:55:03, 20:55:08, 20:55:13, 20:55:18（正常）
故障期间（emqx离线）：20:55:23, 20:55:28, 20:55:33, 20:55:38, 20:55:43, 20:55:48 ← 6条全部补传成功！
故障恢复后：20:55:53, 20:55:58...（正常）
```

**场景C结论**：gateway 断网缓存（双文件模型）+ emqx 恢复后补传机制工作正常，**零丢失**。
