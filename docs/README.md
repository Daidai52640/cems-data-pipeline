# 项目文档导航

> 这一页只解决一件事：不管是谁，先看哪一套、从哪进。
> 同一事实只写一份，另一套只做链接，不重复写两遍。
>
> 当前形态：双设备（`plant1/device1` + `plant2/device2`），
> 部署为 8 个基础容器 + 2 个双设备容器（`--profile plant2`）= 10。
>
> 版本号有两个体系，别混用（2026-10-12 定义）：
>
> | 体系 | 含义 | 当前值 | 出处 |
> |---|---|---|---|
> | 架构 / 部署版本（`X.Y` / `X.Y.Z`） | 系统形态：几台设备、几个容器、哪些容器 | `3.0`（双设备）；`v2.x` = 单设备 6 容器 / 8 测点 | 本页 + `legacy/` 的 RELEASE 文档 |
> | 验收里程碑（`vX.0`） | 一次验收动作的结论，与系统形态不是一回事 | `v4.0` = 2026-10-03 验收口径 25 项收官验收 | `runbooks/最终验收报告.md` |
>
> "当前版本 3.0"与"v4.0 验收"不矛盾：前者说系统长什么样，后者说验收做到第几轮。
> `reference/并发与负载指标.md` 里的 `v3.0.0` 指架构版本的精确写法（等同于 `3.0`）。
>
> 历史版本（v2.x 单设备、6 容器 / 8 测点）的已失效报告见 `legacy/`。

## 一、角色 → 走哪条

| 角色 | 入口顺序 |
|---|---|
| 新接手的开发 | 本页（导航）→ `adr/`（为什么这么设计）→ `reference/`（约束与数字）→ `scripts/`（怎么复现）→ `evidence/`（原始数据） |
| 接手维护的人 / 代码评审人 / 使用方 | 仓库根 `README.md`（项目是什么、怎么跑）→ 本页 → 按下面"我想知道 X"取用 |
| 运维 / 排障 | `runbooks/`（怎么做、出过什么事）→ `reference/`（阈值与数字） |
| 只想看结论 | `reference/性能与可靠性指标.md` + `runbooks/故障台账.md` |
| 要验收 / 要复现 | `runbooks/全链路验收设计.md`（19 条契约 + 判据）→ `test-reports/`（实跑报告） |

## 二、我想知道 X → 去哪

| 我想知道 | 去哪 |
|---|---|
| 这个项目是干什么的、怎么跑起来 | 仓库根 `README.md` |
| 为什么测点是这样设计的 / 为什么加 nginx / 为什么补传这样改 | `adr/`（每份一个决策：背景 → 决策 → 后果） |
| 数字是多少（延迟、完整率、RTO、覆盖率、吞吐） | `reference/性能与可靠性指标.md` + `reference/并发与负载指标.md` |
| 遇到过的坑 / 边界在哪（丢数据的边界、时钟漂移、broker 重启） | `reference/` + `runbooks/故障台账.md` |
| 怎么做（备份、恢复、对账、巡检、容器重建） | `runbooks/` |
| 怎么验收（这条链路该怎么测、通过标准是什么） | `runbooks/全链路验收设计.md`（设计）→ `test-reports/`（报告） |
| 数据可信度依据（原始数据在哪） | `evidence/`（每次测量的原始 json / csv） |
| 架构图和链路图 | `diagrams/` |
| 哪些文档已经失效了 | `legacy/`（含 `DEPRECATED.md` 写明作废原因） |

## 四、写文档的硬规矩

> 标题故意不带条数 —— 带条数的标题本身就是一处会烂掉的引用（它原本写"三条"，实际已有四条）。

1. **结论必须能追溯到证据**
   每个数字后面要么给命令，要么给 `evidence/` 里的文件名。不许出现"约为""大概"这类无法核对的数字。

2. **区分"决策"与"事实"（最常见的错误）**
   - "我们选了全量备份，因为…" → 决策 → `adr/`
   - "实测恢复耗时 6.63~14.92 秒" → 实测 → `reference/` 或 `evidence/`
   - "容器时钟会漂" → 约束（事实）→ `reference/`
   把事实写进 ADR、或把决策写进 reference，都会让人找不到东西。

3. **局限与"没做到"必须单列一节**
   凡有实测，必有局限（样本量、负载条件、未验证的分支）。
   不写局限的数字不可信 —— 这在本项目的多份文档里已是固定写法（见各文档的 §8/§10）。

4. **判据要跟着数据走，不能钉死历史时刻**
   本轮验收实跑暴露的教训：多条判据写死了"某个历史小时"或"绝对事件数"，
   库一重建/基线一调就必然误报（甚至出现在空数据源上恒真）。
   写判据时优先用"与数据无关的机制型断言"（相对值、集合相等、逐条对账），少用绝对值。

5. **引用位置时不要写行号**（跨文档、跨代码都适用）
   教训：`架构与可维护性说明.md` 前部插入一段内容后行号整体下移，另一份文档里
   6 处 `文件:行号` 引用全部指错 —— 而 `check_doc_links.py` 查不出来，因为它是纯文本、不是链接。
   要写"文件 + 小节标题"或"文件 + 符号名"（稳定锚点）：
   - ✅ `docs/架构与可维护性说明.md`（§三·2「不如它们的地方」）
   - ✅ `src/common/points.py` 的 `to_transmit_value()`
   - ❌ `docs/架构与可维护性说明.md:96-97`、`src/common/points.py:233`
   例外：引用工具输出 / 原始日志时行号可以写（那是一次性的、不会再变）。

## 五、证据归档约定（`evidence/`）

**命名**：保留生成时的原始文件名（便于与脚本输出对照）；不要为了好看重命名。

**只留数据，不留运行时日志**：容器 stderr 与旁听端的逐行确认属于运行时日志，
体积小但数量极大（曾占 `perf/` 的 84%），不入库；入库的是
逐条对账的 csv / 汇总 json / 原始基准（数字可复现即可）。

**一次性脚本与事故留档**：允许放到 `evidence/`，但必须在文件名或首行注明用途与"是否为一次性"。
（例：一次真实数据损坏与还原的修复脚本，属于该留档的证据，不是垃圾。）
